Honesty: When Assembly Is the Better Choice

Chapter 3 said when C89 wins, and chapter 4 said when C++98 wins. This is the third and last of those chapters, and it is the deepest step down the machine. Below C89 there is one more language, and it is the only one the processor actually understands. There are places where it is the better choice, and the honest move is to say which ones and then show how to drop into it and come back.

This is not a retreat, and it is not a claim that Z98's output is bad. It is the same tradeoff the whole volume is written in, moved one rung down. Z98 emits C89; a C89 compiler turns that into assembly; and the assembly is a language you can write by hand where the generated sequence is not the sequence you need. The question, as in the previous two chapters, is per routine: does this one function need an instruction sequence the compiler will not give it? Sometimes the answer is yes, and assembly is the right tool. Most of the time it is no, and the first thing to do is not write assembly at all.

Era framing. Statements here about the era's machines, assemblers, and interrupt hardware are era context, and where a statement is an opinion the text says so. Statements about Z98 are checked against docs/reference/Language_Spec_Z98.md, the compiler source, and the compiler built from the committed seed. The assembly on this page was produced on this host with gcc -m32 -S and the seed-built compiler, and the hand-written source is GNU assembler input. The era's assemblers — MASM/TASM on DOS or Windows, or OpenWatcom's wasm — do not run on this host, and nothing here claims they were run. The instruction set is the same 32-bit x86; the syntax and the assembler are not.

What you expect

A reader arriving from a modern toolchain expects one of two things, and both are wrong for this machine. The first is that you can drop a small inline assembly block into a function the way modern C compilers allow, and let the compiler schedule around it. Z98 offers no such thing, and the reason is not an oversight. The second is the opposite: that a language which emits readable C89 has made assembly unnecessary, so the chapter is only a formality. That is also wrong. Emitted C runs through a C compiler, and a C compiler produces the sequence its own costs and rules lead it to — not the sequence a specific routine needs.

The right frame is the one the volume keeps using. There is no rivalry between Z98 and the layers under it; there is a stack, and you are allowed to stand on whatever rung the job needs. Z98 is a checked language that emits C89; C89 is a portable language that a compiler turns into assembly; assembly is what the processor runs. Each rung gives up checking and portability and gains control. The question this chapter answers is which routines earn that trade, and how to make the step down and back without leaving the type checker everywhere else.

There is one expectation worth setting aside before the evidence, because it is where readers most often waste a day. Assembly on this target is not a way to make a whole program faster. A hand-written loop beats the compiler on a short, hot, well-understood routine; across a program, the compiler usually wins, because it sees the whole function and the register allocator is better at book keeping than a person. The chapter says plainly that for a hot inner loop or an interrupt handler, assembly is sometimes the better choice, and it says just as plainly that for almost everything else it is not.

What you get

Four things, in the order you meet them. First, the C89 emission itself, so you can see exactly what the compiler produces for a trivial function and what the default run-time checks cost. Second, the honest fact that inline assembly is not a Z98 feature, and what to use instead. Third, the two ways to reach assembly anyway: drop to the emitted C, or write a routine by hand. Fourth, the cases where that step is the better choice — an inner loop, an interrupt handler — and the case where Z98 already has the feature and no assembly is needed at all.

The case Why assembly is the better choice
A hot inner loop the compiler will not tighten a measured leaf routine beats the emitted C when the instruction sequence, not the algorithm, is the cost
An interrupt handler (ISR) the hardware and the OS fix the entry convention, and the entry sequence is assembly by definition
An instruction the C compiler will not emit port I/O, rdtsc, lock prefixes, and MMX/SSE are reachable only through an assembler
Memory-mapped I/O this one is not a reason to use assembly: Z98 has *volatile T and @volatileCast for it, below

The emission is not assembly

Start with what the compiler actually produces. This Z98 function returns its argument doubled, and it is deliberately trivial so the generated code is easy to read: 

fn twice(x: i32) i32 {
    return x + x;
}

Compiled with the default safety mode, -fsafe, the emitted C is not a single expression. It carries the compiler's run-time checks, because integer overflow is one of the six checks that are on by default. The six are the checked integer cast, division or modulo by zero, the shift count, the null unwrap, an out-of-bounds index, and integer overflow: 

/* twice */
int zF_B4A7D5F3_twice(int x) {
    int zT_1;
    unsigned int zT_2;
    unsigned char zT_4;
    zT_1 = zig_wrap_add_s(((long long)(x)), ((long long)(x)), 32u);
    zT_2 = zig_overflow_flag_add_s(((long long)(x)), ((long long)(x)), 32u);
    zT_4 = zT_2 == (unsigned int)(0);
    if (!(zT_4)) { pal_trap(); }
    return zT_1;
}

That is a faithful translation of a checked add, and it is not what a hand-written leaf looks like. The same function emitted with -ffast, which disables the six run-time checks, is the expression you wrote: 

/* twice */
int zF_B4A7D5F3_twice(int x) {
    return (int)(x + x);
}

This contrast is the first and most important fact of the chapter. The checks are a real cost, they are on by default, and the first thing to reach for when a routine is too slow is -ffast, not an assembler. The compiler's own self-build uses -ffast; a user program defaults to -fsafe. The trade is the one chapter 2 described: the checks are why you chose Z98, and -ffast is how you tell the compiler you will accept the C semantics for a whole build when that is what the program needs. Only after -ffast has been measured is assembly the next question.

The other thing to notice is the name. The function you wrote as twice is emitted as zF_B4A7D5F3_twice. Z98 mangles its identifiers, so the symbol in the object file is not the name in your source. That matters later, when a hand-written routine has to carry a name the linker can see, and it is the same mangling chapter 3 used to show that a Z98 module and a C89 module can each define an ordinary name without colliding.

There is no inline assembly

Z98 has no inline assembly, and this is a language fact, not a policy. There is no asm keyword and no assembly builtin; a probe that writes the C and C++ form is rejected before any code is emitted: 

$ /tmp/manual_seed/zig1_5_clean -o out inline_asm.z98
inline_asm.z98:4:8: error[2000]: expected ';' but found token
    asm volatile ("nop");
        ^^^^^^^^
inline_asm.z98:4:8: error[2000]: unexpected token
    asm volatile ("nop");
        ^^^^^^^^
inline_asm.z98:5:0: error[2000]: expected expression
}
^
inline_asm.z98:5:0: error[2000]: unexpected token
}
^

The token asm is not recognized, so the parser stops at it. The only assembly in the tree lives in the fixed platform layer — the trap sequence in zig_pal.c and bytes inside the seed runtime — and that is not part of the language. The parser has no asm token and the semantic pass has no assembly builtin, so this is not something a future chapter can promise; the feature does not exist.

The way over is the one the previous chapters already established: an assembly routine is a separately compiled object, and Z98 calls it through an ordinary extern declaration and the C ABI. You do not inline assembly into Z98; you write it beside Z98 and link it, exactly as chapter 3 linked a C function.

Dropping to the emitted C

The first path down is to start from the C the compiler already emitted and turn it into assembly with the host compiler. The emitted main translation unit contains the call to the hand-written symbol, and compiling that unit with gcc -m32 -S produces the assembly the C compiler would have assembled: 

$ mkdir -p out && /tmp/manual_seed/zig1_5_clean -o out asm.z98
$ cd out && cp ../asm_forty_two.h ../asm_forty_two.s .
$ gcc -m32 -S -I . asm_FF935E89.c -o asm.s
$ grep asm_forty_two asm.s
	call	asm_forty_two@PLT

The assembly for the checked twice is the second thing worth reading, because it makes the run-time-check cost concrete. This is the emitted C compiled to assembly, with the CFA directives removed for length: 

zF_B4A7D5F3_twice:
	pushl	%ebp
	movl	%esp, %ebp
	pushl	%esi
	pushl	%ebx
	subl	$16, %esp
	call	__x86.get_pc_thunk.si
	addl	$_GLOBAL_OFFSET_TABLE_, %esi
	movl	8(%ebp), %eax
	movl	%eax, %ecx
	movl	%eax, %ebx
	sarl	$31, %ebx
	movl	8(%ebp), %eax
	cltd
	subl	$4, %esp
	pushl	$32
	pushl	%ebx
	pushl	%ecx
	pushl	%edx
	pushl	%eax
	call	zig_wrap_add_s
	addl	$24, %esp
	movl	%eax, -12(%ebp)
	movl	8(%ebp), %eax
	movl	%eax, %ecx
	movl	%eax, %ebx
	sarl	$31, %ebx
	movl	8(%ebp), %eax
	cltd
	subl	$4, %esp
	pushl	$32
	pushl	%ebx
	pushl	%ecx
	pushl	%edx
	pushl	%eax
	call	zig_overflow_flag_add_s
	addl	$24, %esp
	movl	%eax, -16(%ebp)
	cmpl	$0, -16(%ebp)
	sete	%al
	movb	%al, -17(%ebp)
	cmpb	$0, -17(%ebp)
	jne	.L181
	movl	%esi, %ebx
	call	pal_trap@PLT

	movl	-12(%ebp), %eax
	leal	-8(%ebp), %esp
	popl	%ebx
	popl	%esi
	popl	%ebp
	ret

Read it against the four lines -ffast produces. The checked version sets up a frame, calls a wrap helper, calls an overflow-flag helper, branches on the flag, and calls a trap. The unchecked version is a load, an add, and a return. Neither is wrong: the first is the semantics you asked for, and the second is the semantics you accepted. The point for this chapter is that the generated assembly is a starting point you can read and, if a routine genuinely needs it, take over. The __x86.get_pc_thunk and GOT setup are a modern position-independent Linux artifact of this host; the era's non-PIC flat target does not carry them.

Dropping to the emitted C means this: take the emitted .c, compile it with gcc -m32 -S, keep the resulting .s beside your source, hand-edit the routine whose sequence you need to change, assemble it, and put it on the link line in place of the compiler's object for that unit. You are not editing the compiler and you are not forking the emitter; you are taking one translation unit down a rung.

Hand-written assembly, linked back

The second path is to write the routine by hand and call it from Z98. This is the direct analogue of the C89 seam, with a .s in place of the .c. The hand-written side is a leaf routine that returns a constant: 

	.text
	.globl asm_forty_two
	.type asm_forty_two, @function
asm_forty_two:
	movl $42, %eax
	ret
	.size asm_forty_two, .-asm_forty_two

Its prototype goes in a header, for the same reason the previous chapter put c_add's prototype in one: a bare non-variadic extern gets no emitted prototype, so without a header the generated C call is an implicit declaration to the C compiler. 

/* asm_forty_two.h */
int asm_forty_two(void);

The Z98 side declares the routine as extern "c", includes the header, and calls it like any other function: 

@cInclude("asm_forty_two.h");

const std = @import("std");

extern "c" fn asm_forty_two() i32;

fn twice(x: i32) i32 {
    return x + x;
}

pub fn main() void {
    std.io.print("twice={}\n", .{twice(21)});
    std.io.print("asm={}\n", .{asm_forty_two()});
}

The emitted main translation unit contains an ordinary call to the declared name, and the compiler writes the prototype into the module header from the @cInclude: 

    std_print("asm=");
    zT_4 = asm_forty_two();
    zF_9FD0BAD6_printI32(zT_4);

Compile, assemble the hand-written source, link everything together, and run. The transcript is a real run on the seed compiler: 

$ mkdir -p out && /tmp/manual_seed/zig1_5_clean -o out asm.z98
$ cd out && cp ../asm_forty_two.h ../asm_forty_two.s .
$ gcc -m32 -std=c89 -O0 -Wno-long-long -Wno-pointer-sign -Wno-implicit-function-declaration -I . -c *.c
$ gcc -m32 -Wa,--noexecstack -c asm_forty_two.s -o asm_forty_two.o
$ gcc -m32 *.o -o asm
$ ./asm
twice=42
asm=42

That is the whole drop-and-link-back path. The emitted Z98 module and the hand-written assembly are both object files by the time the linker sees them, and the linker does not care which produced which. Z98 keeps its checks and its error unions for the hundreds of routines that do not need assembly; the one leaf routine that does is written by hand and called across the C ABI. The calling convention is the ordinary one, and the routine is a leaf that takes no arguments and returns in %eax; a routine with arguments uses the same register and stack conventions the compiler uses for any C function.

Inner loops and interrupt handlers

Now the cases where the step down is the better choice. The first is a hot inner loop. You reach it the way you reach any optimization: by measuring, not by guessing. Compile with -ffast, find the routine the profiler or the clock blames, and look at its emitted assembly. If the compiler already produces the tight sequence — and for most short functions it does — there is nothing to do. If the routine is a tight leaf whose cost is the instruction sequence itself, and if a hand-written version measurably beats the compiler's, then for that routine assembly is the better choice, and it is the better choice for a reason you can show: fewer instructions, no helper calls, the loop variable left in a register. A hand-written loop for a long function with many live values is a losing trade, because register allocation across a whole function is exactly what the compiler is good at.

The second case is the interrupt handler, and here the honest split matters. On the era machine the hardware and the OS decide how an interrupt is entered: which stack, which registers are saved, how the handler returns. That entry sequence is assembly by definition, and no C compiler will write it for you, because the contract is not the C calling convention. This is era context and it is marked as such: this host has no DOS or Windows 9x kernel, so an interrupt handler cannot be run here, and this chapter does not claim it was. What transfers is the mechanism. The handler's assembly entry can save the machine state and then call a Z98 function compiled as ordinary C89, so the work of the handler is written in Z98 and only the fixed entry and exit are assembly. That is the same link-back shown above, entered from the other direction.

The third case is an instruction the C compiler will not emit for you: port I/O, a time-stamp read, an atomic prefix, or an MMX/SSE sequence. When the instruction is the requirement, the assembler is the only tool that can express it, and the routine is normally a tiny wrapper around that one instruction. The compiler is not being obstinate; those instructions are outside the C89 abstract machine, so the language has no way to ask for them.

The fourth case is worth naming because it is the one that looks like a reason for assembly and is not. Memory-mapped I/O does not need an assembler in Z98. The language has *volatile T and [*]volatile T for exactly this, and it enforces the qualifier: a *volatile T cannot be silently converted to *T, and @volatileCast is the one explicit way to drop the qualifier. A hardware register at a fixed address is a *volatile u32, read and written in Z98, with the compiler forbidden to cache the read. Reach for assembly when you need the instruction; for the address, Z98 already has the feature. That distinction is checkable in the Language Spec, and it keeps the chapter from recommending assembly where the language is sufficient.

The trade

Choosing assembly for a routine buys control and pays for it in every kind of safety the rest of the project has. On the buying side, the sequence is exactly what you wrote: no helper call around an arithmetic operation, no run-time check you did not ask for, no instruction the compiler would not emit, no register allocation decision you disagree with. For a five-instruction leaf in a loop that runs a million times, that is a real gain, and it is the gain the chapter says is worth taking.

On the paying side, the routine is outside everything the language provides. It is outside the type checker, so a wrong operand size is not a diagnostic but a corrupted register. It is outside the error-union model, so a failure has no place to go. It is outside the static analyzers, so an out-of-bounds access is not caught. It is fixed to one instruction set and one assembler's syntax, so it does not port — the same routine written for one era assembler is not the text another accepts. And it is the least readable code in the project: a future maintainer must know the calling convention and the register use from memory, because the routine has no signature that says what it takes.

The honest verdict is therefore narrow and firm. For a measured hot inner loop and for the fixed entry of an interrupt handler, assembly is sometimes the better choice, and the manual says so without hedging. For everything else, the order of operations is measure, then -ffast, then — only if the C compiler genuinely cannot produce what the routine needs — a hand-written leaf. That ordering is the chapter's opinion, and it is marked as one; it is also the ordering the era's own programmers used, because writing a whole program in assembly was the thing C89 was invented to stop.

Honest note. Assembly is the sharpest tool on the machine and the least forgiving. It can be the right answer for one leaf routine — a hot inner loop or the fixed entry of an interrupt handler — and it is the wrong answer for a program. The chapter's rule is the rule of the whole tradeoff series: measure first, try -ffast before an assembler, and hand-write only the routine the measurement points at. Z98 emits C89, so that one routine is an object file beside the rest; nothing else in the project has to give up its checks because one function went down a rung.

The way over it

The way over is a short recipe with a decision at the top. Work it in order, and stop as soon as the routine is fast enough.

Step one: measure. Build with -ffast and find out whether the routine is actually the cost. This is not ceremony. The default -fsafe emission carries the six run-time checks, so a first measurement under -fsafe often shows a cost that is the checks, not the algorithm. The honest first move for a slow inner loop is -ffast, because it removes the checks without giving up the language.

Step two: read the emitted assembly. Run gcc -m32 -S on the emitted translation unit and read the routine. If the compiler already produces the sequence you want, stop; there is nothing to hand-write. If it does not, the assembly you are reading is the exact starting point for the drop.

Step three: drop. Either take the emitted .c, compile it to .s, and hand-edit the one routine, or write a fresh .s and declare it in Z98 with extern "c" and a header prototype. Both end the same way: a hand-written object on the link line. 

$ mkdir -p out && /tmp/manual_seed/zig1_5_clean -o out asm.z98
$ cd out && cp ../asm_forty_two.h ../asm_forty_two.s .
$ gcc -m32 -S -I . asm_FF935E89.c -o asm.s        # read the hand-off
$ gcc -m32 -std=c89 -O0 -Wno-long-long -Wno-pointer-sign -Wno-implicit-function-declaration -I . -c *.c
$ gcc -m32 -Wa,--noexecstack -c asm_forty_two.s -o asm_forty_two.o
$ gcc -m32 *.o -o asm
$ ./asm
twice=42
asm=42

Keep the assembly with the source. The emitted dump tree is not a project file. Its filenames carry a hash of the input path (asm_FF935E89.c here), and re-emitting produces them fresh. The hand-written .s, its header, and the one line that adds its object to the link are the parts that belong in the project; the emitted .c is regenerated every build. If you hand-edit an emitted translation unit, keep the edited .s beside your source and put it on the link line, rather than editing the dump tree in place.

Name the symbol in plain C. The linker sees the emitted C, so a hand-written routine must carry a plain C symbol, and the Z98 side declares that same plain name with extern "c". You cannot cleanly replace an emitted Z98 function from assembly by its source name, because Z98 mangles its identifiers: the function above is zF_B4A7D5F3_twice in the object file, not twice. The pattern that works is the one shown: the hand-written routine has its own plain name, and Z98 calls it as an extern.

Put together, the rule is the previous chapters' rule with the assembler in the last slot. Choose assembly where the instruction sequence is the requirement and the routine is small and measured; choose Z98 everywhere else; connect the two at the C ABI. The load-bearing fact of chapter 3 is what makes this usable here too: Z98 emits C89, so its objects link with a hand-written object, whether that object came from a C89 compiler or an assembler. The step down does not change the machine or the linker; it changes the language of one routine.

There is one lingering question the recipe does not answer, and the honest answer is that it is an era question rather than a Z98 one. On the real machine the assembler is the era's, and its syntax is not GNU assembler's. The instruction set is the same 32-bit x86, so the routine you tuned on this host transfers, but the source text does not; you rewrite it in the era assembler's dialect, and OpenWatcom's wasm is the one that belongs with the build_owc.bat path. That boundary is stated rather than hidden: the mechanism is verified here, the era assembler is not run here.

Common mistakes

The mistakes below are the ones a reader makes when the layer under the language is treated as the first answer instead of the last.

Reaching for the assembler before measuring. A slow routine is far more often a -fsafe-vs--ffast difference or an algorithmic problem than a code-generation problem. Build with -ffast, measure, and read the emitted assembly before writing any. The chapter's whole ordering exists to prevent this one mistake.

Trying to write inline assembly in Z98. There is no asm keyword and no assembly builtin; the parser rejects the token. The way over is an extern "c" declaration plus a hand-written .s, linked like any other object. Do not wait for an inline-asm feature; it does not exist.

Calling a hand-written routine without a prototype. A bare non-variadic extern gets no emitted prototype, so the generated call is an implicit declaration to the C compiler. Put the prototype in a header and @cInclude it, exactly as chapter 3 does for a C function. The supported build suppresses the warning, but the header is the correct code.

Expecting to override a Z98 function by name from assembly. Z98 mangles its identifiers, so the symbol is zF_<hash>_name, not name. A hand-written routine carries its own plain name and is called through extern; it does not replace an emitted Z98 function by pretending to be it.

Editing the emitted C in the dump tree. The dump directory is regenerated on every build with hash-named files, so an edit there is lost. Keep the tuned .s in the project and add its object to the link; leave the emitted C to the compiler.

Assuming assembly ports. It is the least portable code on the machine: one instruction set, one assembler syntax. The era assembler is not GNU assembler, so even a routine tuned on this host has to be retyped in the era's dialect. Portability is one of the things the step down gives up, and it is given up on purpose.

Writing the whole program in assembly. The compiler wins across a function with many live values, and it certainly wins across a program. The step down is for a measured leaf, not a design. If a program feels like it wants to be all assembly, that is a signal to re-measure, not to keep going.
