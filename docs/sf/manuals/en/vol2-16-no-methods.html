No Methods, No Generics, No Comptime

Chapter 15 listed the builtins one by one. This chapter is about the three Zig features whose absence those builtins help cover: methods, generics, and comptime. None of the three exists in Z98, and the compiler has no hidden version of any of them. What it has instead is three ordinary patterns. A receiver is an ordinary first parameter. Polymorphism is a struct of function pointers you build by hand. Compile-time work is a fixed list of builtin calls. The chapter's program, docs/sf/manuals/src/vol2/shapes2.z98, is a small shape interface built exactly that way.

Two of the absences are load-bearing in daily code. Method syntax is the one every reader reaches for first, and obj.method() is rejected with a measured error[3060]. Generics are the one every library reaches for, and a comptime T: type or anytype parameter is rejected before it reaches the type checker. The third, comptime, is a keyword the compiler never sees at all: constant folding stays, but the user-facing surface is the builtin catalog, so @sizeOf, @offsetOf, @intCast, and @bitCast are how compile-time facts and conversions are spelled. Chapter 12 and chapter 14 moved failure and memory into types; this chapter moves behavior, containers, and compile-time work into patterns.

Honest note. You will reach for methods, generic containers, and comptime; here is the Z98 way. The C++ habit is to put behavior in the type (Shape::draw), to instantiate a container over the element (List<Shape>), and to let the compiler generate the per-type code. Z98 has none of that: behavior is free functions with the receiver as an ordinary parameter, the per-type code is written out by hand once for each type, and the compile-time work is a short list of builtins. What you gain is a compiler small enough to fit on the machine and a generated C program you can read line by line. What you lose is the compiler writing the repetition for you. The manual vtable below is the pattern that recovers polymorphism without the machinery, and it costs exactly one data pointer and one function pointer per operation.

No methods: free functions with a receiver

A method is two things at once: a receiver — the object the function operates on — and a call shorthand that hides it. Z98 keeps the receiver and drops the shorthand. The receiver is just the first parameter, and the call is just a call. The example's two dispatch functions are the pattern in miniature: 

fn draw(s: Shape) void {
    s.draw_fn(s.data);
}

fn area(s: Shape) f32 {
    return s.area_fn(s.data);
}

A caller writes draw(sh) and area(sh), never sh.draw() or sh.area(). The compiler rejects the shorthand wherever it appears, because an aggregate type has fields but no function members. On a struct the rejection names the kind: 

const S = struct { x: i32 };
...
const s = S{ .x = 1 };
s.bar();
// error[3060]: no field or member function named 'bar' in struct type
// note: struct declared here

On a builtin scalar the same rule fires with the same wording, minus the kind: 

const x: i32 = 5;
x.foo();
// error[3060]: no field or member function named 'foo' in type

The other half of the rule is at the declaration. A function written inside a struct is not a method that lost its receiver; it is a parse error, because the struct grammar has named fields or positional fields and nothing else: 

const Counter = struct {
    n: i32,

    fn bump(self: *Counter) void {
        self.n += 1;
    }
};
// error[2000]: struct fields must be all named or all positional (tuple)

One dot spelling survives, and it is worth naming so its presence is not confusing: module members are reached with a dot (std.io.print), because a module is a namespace, not a value. The rule is about receivers, not about dots. A struct value never has functions; a module always does.

Manual virtual tables

The shape interface is a manual virtual table, and it is the direct translation of the method table a compiler would otherwise generate. The interface struct holds the operations as function pointers plus one erased data pointer; each concrete shape is an ordinary struct; each operation is a free function that takes the erased pointer and casts it back with @ptrCast: 

const Shape = struct {
    draw_fn: fn (*void) void,
    area_fn: fn (*void) f32,
    data: *void,
};

const Circle = struct { r: f32 };
const Square = struct { side: f32 };

fn circleDraw(data: *void) void {
    const c = @ptrCast(*Circle, data);
    std.io.print("circle r={}\n", .{c.r});
}

fn circleArea(data: *void) f32 {
    const c = @ptrCast(*Circle, data);
    const pi: f32 = 3.14159;
    return pi * c.r * c.r;
}

Construction is a struct literal that names the functions and stores the object's address as *void. @ptrCast names the result type in both directions, so the same pointer that went in as *Circle comes back out as *Circle: 

fn circle_init(c: *Circle, r: f32) Shape {
    c.r = r;
    return Shape{ .draw_fn = circleDraw, .area_fn = circleArea, .data = @ptrCast(*void, c) };
}

Dispatch is an ordinary call through the field, with the data pointer as the argument: 

fn draw(s: Shape) void {
    s.draw_fn(s.data);
}

There is no receiver magic here and nothing to look up at run time: the field holds a C function pointer, and calling it compiles to a call through that pointer. The interface is not free, and the sample measures it. The first line of its output is: 

Shape size=12 align=4 fn=4

Three words for the interface on the 32-bit target: two function pointers and the data pointer, at four bytes each. The emitted C for the two function-pointer types shows what a Z98 function pointer becomes: 

typedef void (*zT_8BB7E506_FP_void_void_)(void*);
typedef float (*zT_67B853D6_FP_float_void_)(void*);

The mangled names are irrelevant; the signatures are the claim. fn (*void) void becomes void (*)(void*) and fn (*void) f32 becomes float (*)(void*). A Z98 function pointer is an ordinary C function pointer with no hidden receiver argument, which is exactly why the receiver has to be passed by hand at every call.

The data pointer is erased to *void, so the pair of function and data is a contract the type checker only partly sees: it knows the function signature, and it does not know what the function will cast the data to. Nothing stops a program from building a Shape whose operations cast a *Square to *Circle. The init functions below are where that contract is established, which is why they matter more here than a constructor in a language with classes.

The init-function pattern

An object is ready when two things are true: its payload fields are set, and an interface value names the operations. The init function does both. It takes the destination as its first parameter — the caller owns the storage — and returns the interface value: 

fn square_init(s: *Square, side: f32) Shape {
    s.side = side;
    return Shape{ .draw_fn = squareDraw, .area_fn = squareArea, .data = @ptrCast(*void, s) };
}

Callers declare the payload, then hand its address to the init function: 

var sq: Square = undefined;
var list: ShapeList = undefined;
list.len = 0;
shapeList_push(&list, square_init(&sq, 3.0));

The form the sample uses is not the only measured one. A value-returning fn shape_init(f: fn (*void) void, d: *void) Shape that does nothing but build the literal compiles and runs, and a pointer-init fn shape_init(s: *Shape, f: fn (*void) void, d: *void) void that fills an already-declared interface in place compiles and runs as well. The first form is used here because one call sets the payload and returns the interface that points at it, so the two cannot drift apart at the call site.

Storage belongs to the caller because Z98 has no hidden allocation. The example puts the payloads on the stack, which is correct for the program's lifetime. When an object has to outlive the frame that created it, chapter 14's arena supplies the storage and the init function returns an error union, the way Point_init(arena: *std.arena.Arena, x: i32, y: i32) std.arena.ArenaError!*Point does in that chapter. The shape of the pattern is the same; only the source of the memory changes.

No generics: concrete types instead

Zig's generics are built from type parameters: a comptime T: type parameter, an anytype parameter, and functions that are instantiated once per type. Z98 has none of the three, and each absence is enforced by a different phase. A comptime parameter never parses: 

fn id(comptime T: type, x: T) T {
    return x;
}
// error[2000]: expected ':' but found identifier

A plain type parameter parses, and then the name it binds never becomes a type the signature can use: 

fn id(T: type, x: T) T {
    return x;
}
// error[20]: identifier 'T' is not declared or imported in this module

anytype fails the same way from the caller's side: the parameter never becomes a name inside the function body. 

fn show(x: anytype) void {
    std.io.print("{}\n", .{x});
}
// error[20]: identifier 'x' is not declared or imported in this module

In place of a List(T), write the concrete container. The example needs a list of shapes, so it declares exactly that type: 

const ShapeList = struct {
    items: [4]Shape,
    len: i32,
};

fn shapeList_push(list: *ShapeList, s: Shape) void {
    list.items[@intCast(usize, list.len)] = s;
    list.len += 1;
}

A second element type means a second container. That is not a workaround for a missing feature; it is the design. The compiler's own source, which is written in Z98, hand-writes the concrete hash maps it needs — the U64ToU32Map in sf/src/util/hash.zig is one — instead of instantiating a generic one. The repetition is real and the code is longer than the Zig version would be. In exchange, every type in the program is a concrete type at every phase: the type checker never has to instantiate anything, and the emitted C names real structs, not a template expansion.

No comptime: specific builtins instead

comptime is Zig's user-facing compile-time keyword. It does three jobs: evaluate constants, inspect and construct types, and instantiate the generic functions of the previous section. Z98 keeps constant folding inside the compiler but exposes no comptime surface at all. The replacement is the builtin catalog of chapter 15, and the three families that matter here are introspection (@sizeOf, @alignOf, @offsetOf, @bitSizeOf), conversion (@intCast, @ptrCast, @bitCast, @as), and target folding (@isWindows). A measured slice, compiled and run as a standalone program: 

const std = @import("std");

const Vec = struct { x: i32, y: i32 };
const Flags = packed struct { a: u1, b: u1, c: u2 };
const Color = enum { red, green };

pub fn main() void {
    std.io.print("size {} align {} offset {} bits {}\n", .{ @sizeOf(Vec), @alignOf(Vec), @offsetOf(Vec, "y"), @bitSizeOf(Flags) });

    const wide: i32 = 200;
    const narrow = @intCast(u8, wide);

    var n: i32 = 42;
    const raw = @ptrCast(*void, &n);
    const back = @ptrCast(*i32, raw);
    const same = @intFromPtr(&n) == @intFromPtr(raw);

    const pattern = @bitCast(u32, @as(i32, -1));

    std.io.print("intCast {} ptrCast {} {}\n", .{ narrow, back.*, same });
    std.io.print("bitCast {x} as {} enum {} {d}\n", .{ pattern, @as(i64, 5), @intToEnum(Color, 1), @enumToInt(Color.green) });
    std.io.print("isWindows {}\n", .{@isWindows()});
}
// size 8 align 4 offset 4 bits 4
// intCast 200 ptrCast 42 true
// bitCast ffffffff as 5 enum .green 1
// isWindows false

Every one of those calls is in chapter 15's inventory: the four introspection builtins fold to integers at compile time, the three conversions change width, representation, or pointer type, and @isWindows folds to the target's answer (false on the Linux build, true on the Win9x build). What is missing is the general facility around them. There is no @Type to build a type at compile time and no @typeInfo to inspect one; both are unsupported builtins, and so is any name the compiler does not know: 

const T = @Type(5);
// error[3000]: unsupported builtin function

The sample's first line is the same idea in miniature. @sizeOf(Shape) and @sizeOf(fn (*void) void) produce the two numbers the vtable section quoted, and there is no expression anywhere in the program that needs a compile-time type computation to produce them.

The example

The whole chapter in one program. Two concrete shapes and their operations are wrapped into a manual vtable by two init functions; a concrete ShapeList holds three interface values; main pushes them, then draws and measures each one through the function pointers. The first line is the interface's size, taken with @sizeOf. It is docs/sf/manuals/src/vol2/shapes2.z98: 

const std = @import("std");

const Shape = struct {
    draw_fn: fn (*void) void,
    area_fn: fn (*void) f32,
    data: *void,
};

const Circle = struct { r: f32 };
const Square = struct { side: f32 };

fn circleDraw(data: *void) void {
    const c = @ptrCast(*Circle, data);
    std.io.print("circle r={}\n", .{c.r});
}

fn circleArea(data: *void) f32 {
    const c = @ptrCast(*Circle, data);
    const pi: f32 = 3.14159;
    return pi * c.r * c.r;
}

fn squareDraw(data: *void) void {
    const s = @ptrCast(*Square, data);
    std.io.print("square side={}\n", .{s.side});
}

fn squareArea(data: *void) f32 {
    const s = @ptrCast(*Square, data);
    return s.side * s.side;
}

fn circle_init(c: *Circle, r: f32) Shape {
    c.r = r;
    return Shape{ .draw_fn = circleDraw, .area_fn = circleArea, .data = @ptrCast(*void, c) };
}

fn square_init(s: *Square, side: f32) Shape {
    s.side = side;
    return Shape{ .draw_fn = squareDraw, .area_fn = squareArea, .data = @ptrCast(*void, s) };
}

fn draw(s: Shape) void {
    s.draw_fn(s.data);
}

fn area(s: Shape) f32 {
    return s.area_fn(s.data);
}

const ShapeList = struct {
    items: [4]Shape,
    len: i32,
};

fn shapeList_push(list: *ShapeList, s: Shape) void {
    list.items[@intCast(usize, list.len)] = s;
    list.len += 1;
}

pub fn main() void {
    std.io.print("Shape size={} align={} fn={}\n", .{ @sizeOf(Shape), @alignOf(Shape), @sizeOf(fn (*void) void) });

    var c1: Circle = undefined;
    var sq: Square = undefined;
    var c2: Circle = undefined;

    var list: ShapeList = undefined;
    list.len = 0;
    shapeList_push(&list, circle_init(&c1, 1.0));
    shapeList_push(&list, square_init(&sq, 3.0));
    shapeList_push(&list, circle_init(&c2, 2.0));

    var i: i32 = 0;
    while (i < list.len) {
        const sh = list.items[@intCast(usize, i)];
        draw(sh);
        std.io.print("  area {}\n", .{area(sh)});
        i += 1;
    }
    std.io.print("shapes drawn {}\n", .{list.len});
}

Build the compiler once from the committed seed, then emit and compile the program, exactly as in chapter 15: 

bash scripts/seed/build_from_seed.sh release/seed/zig1-seed.tgz /tmp/manual_seed

The result is /tmp/manual_seed/zig1_5_clean with the standard library beside it in /tmp/manual_seed/lib/. This example compiles with no diagnostics; the program then runs to the end: 

$ mkdir -p /tmp/manual_out
$ /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol2/shapes2.z98
$ cd /tmp/manual_out && sh build_target.sh linux shapes2
Building for linux...
Built: shapes2
$ ./shapes2
Shape size=12 align=4 fn=4
circle r=1
  area 3.14159
square side=3
  area 9
circle r=2
  area 12.56636
shapes drawn 3

Four commands and eight lines of program output. The size line is the vtable's cost and the only @sizeOf call in the program. The three draw lines come through s.draw_fn(s.data) and the three area lines through s.area_fn(s.data); each operation casts the erased pointer back to the concrete type it was built with. The last line counts the list, which is an ordinary concrete struct — no template was instantiated and no method was looked up. The exit status is 0.

Two of the chapter's claims are target-independent and one is not. The function-pointer sizes, the vtable layout, and every rejection are the same on both targets. The @isWindows result in the builtin slice above is the only line that changes: it folds to true for the Win9x build, which is the point of a target-folding builtin.

Common mistakes

The mistakes below are the ones a programmer arriving from a language with classes, templates, and compile-time evaluation makes first. Each has a measured diagnostic or a corrected shape, and each corrected shape is the compiler's rule, not a style preference.

Calling obj.method(). The receiver is not hidden in Z98. Write the function free and pass the value: draw(sh), not sh.draw(). The shorthand is rejected wherever it appears, with the type checker naming exactly what is missing: 

error[3060]: no field or member function named 'bar' in struct type

Declaring the method inside the struct. A function written among the fields does not become a member; it does not parse. Structs have named fields or positional fields, and the parser says so: 

error[2000]: struct fields must be all named or all positional (tuple)

The fix is the same as the previous item: a free function with the receiver as its first parameter.

Expecting a template to be instantiated. A comptime T: type parameter stops the parse with error[2000]: expected ':' but found identifier; a type parameter leaves the bound name undeclared, so the signature fails with error[20]: identifier 'T' is not declared or imported in this module; and an anytype parameter leaves the argument's name undeclared in the body. There is no instantiation step to reach. Write the concrete type: the sample's ShapeList is a list of shapes, and a list of integers would be a second, separate container.

Reaching for comptime or @typeInfo. The keyword does not parse, and the type-introspection builtins do not exist. @Type, @typeInfo, and any unknown builtin name are rejected as unsupported: 

error[3000]: unsupported builtin function

The measured subset in chapter 15's catalog is the whole surface. Reach for @sizeOf, @offsetOf, @intCast, and the rest of the inventory, and the question "what type is this, at compile time?" usually disappears — the program already knows, because it was written for one concrete type.

Forgetting the data contract. The payload pointer is erased to *void, and the function pointer's signature is the only thing the vtable records. The cast back to *Circle inside the operation has to match what the init function stored. Build every interface through an init function, keep the payload and its operations in the same file, and the contract stays in one place instead of being spread across call sites.
