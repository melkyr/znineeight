The Win32 Debug API

A debugger is not a feature of a language; it is a program that runs another program under supervision. On this machine that supervision is an operating system service, and the service is a small set of Win32 functions: you launch a process with a flag that says "stop at every interesting event," you wait for event records, you look at and change the target's memory, and you tell the system to continue. This chapter is how Z98 reaches that service, and it ships a complete debugger small enough to read in one sitting.

The surface is bigger than the socket surface of chapter 12 and the C calls are more dangerous, but the rule is unchanged. Every function here is an ordinary extern declaration with the stdcall convention, exactly as chapter 11 taught, and every structure is an ordinary Z98 struct laid out field for field against the header. There is no debugger syntax in Z98 and no runtime to link. The sample, dbg-mini.z98, launches the command interpreter, breaks on its entry point, reads its context and a 32-bit word of its image, and lets it finish.

This is also the chapter where the honesty of the volume matters most in the details. A debugger can corrupt its target, fail silently when it forgets an API precondition, or report a start that never happened and then hang. Every claim on this page is backed by the committed sample and by the actual run under the Windows oracle, and the section Under Windows 98 states exactly what ran, on what, and what was only emitted.

What is measured here. Every Win32 declaration on this page was checked against the system header's own signature, and every Z98 statement was checked against docs/reference/Language_Spec_Z98.md and the compiler source. The sample dbg-mini.z98 is cross-built with i686-w64-mingw32-gcc and run under a dedicated 32-bit wine prefix (wine-8.0); the transcript below is that run, and it reproduced byte for byte across repeated runs. The program is Win-only: it includes windows.h, so its Linux build stops at #include "windows.h" and there is no Linux transcript to compare against. The OpenWatcom build_owc.bat path is emitted and not run here, exactly as chapter 8 states; the real-machine screenshot stays the figure.

What the debug API is for

A user-mode debugger on Windows is a client of the kernel's debugging service. The service has three jobs. It lets you create a process already attached to yourself, so that the process stops before it has run any of its own code. It delivers a record each time something happens that the service considers noteworthy — a process or thread starts, a module loads, an exception is raised, a string is printed to the debug channel. And it lets you inspect and modify the stopped target through the ordinary process-memory functions, so you can read a register, disassemble an instruction, or overwrite a byte with a breakpoint.

That is the whole model. There is no scripting language, no symbol server, no UI. What the operating system gives you is a stop-and-report loop plus raw access to the target's address space. Everything a commercial debugger adds on top — breakpoint lists, watch expressions, a call stack, a source window — is bookkeeping the debugger builds from those two primitives. This chapter builds a very small one, and the point of building it is that on this machine you will occasionally need one, and now you can read the source.

The reason a Z98 program can be a debugger at all is the reason the whole volume keeps returning to: chapter 3's load-bearing fact that Z98 emits C89. A debugger is not a privileged program. It is an ordinary process that calls Win32 functions with the right arguments, and an ordinary process is what Z98 emits. The three calls that matter most — reading, writing, and mapping the target — are the same kernel32 entry points any C debugger would call.

Starting the target: CreateProcess with a debug flag

The first Win32 function of the loop is one you may have met already if you have launched a child process from C: CreateProcessA. Its ten parameters are the application name (usually null), the command line, process and thread security attributes, an inheritance flag, a creation-flags word, the environment block, the current directory, a STARTUPINFO, and a PROCESS_INFORMATION the function fills in. The creation flags are where the debugger enters: 

#define DEBUG_PROCESS              0x00000001
#define DEBUG_ONLY_THIS_PROCESS    0x00000002

Those two names are easy to confuse and important to separate. Passing DEBUG_PROCESS asks the system to debug the new process and every process it creates; DEBUG_ONLY_THIS_PROCESS is the narrower flag and debugs only the process you launch. For a debugger whose subject is one program, DEBUG_ONLY_THIS_PROCESS is the right flag: the target stops and reports, but the programs it spawns do not also stop and report to you, which keeps the event stream from exploding. The sample passes that flag (0x2) and nothing else.

The declaration is straight from the header: 

extern "stdcall" fn CreateProcessA(a: *void, cmd: [*]u8, pa: *void, ta: *void, inherit: i32, flags: u32, env: *void, cwd: *void, si: *void, pi: *void) i32;

Every parameter that may be a null pointer is spelled *void and passed as @intToPtr(*void, 0). The command line is a writable, null-terminated buffer, because CreateProcessA is documented to be allowed to modify it. The STARTUPINFO and PROCESS_INFORMATION are the two structures a debugger does not need to interpret: it only has to give them storage, zeroed, and read back the process handle the system writes into the second one. The sample uses plain byte buffers for both, which is the C89-shaped way to say "opaque fill-in structure" and is exactly the trick chapter 10 used for the coroutine pool.

There is one detail that is honest about the target rather than the API. The sample does not hard-code the name of the command interpreter. It reads the COMSPEC environment variable and appends /c exit, so the same source names command.com on a Windows 98 machine and cmd.exe on the development host. That is not essential to the debug API, but a sample that hard-codes cmd.exe would fail on the era machine the manual is written for, so the extra call earns its place: 

extern "stdcall" fn GetEnvironmentVariableA(name: [*]const u8, buf: [*]u8, size: u32) u32;

DEBUG_EVENT: a structure you declare yourself

Once the target exists, the system reports to you with a stream of DEBUG_EVENT records. The header's definition is a header and a union: 

typedef struct _DEBUG_EVENT {
    DWORD dwDebugEventCode;     // offset 0
    DWORD dwProcessId;          // offset 4
    DWORD dwThreadId;           // offset 8
    union {                     // offset 12
        EXCEPTION_DEBUG_INFO      Exception;
        CREATE_THREAD_DEBUG_INFO  CreateThread;
        CREATE_PROCESS_DEBUG_INFO CreateProcessInfo;
        EXIT_THREAD_DEBUG_INFO    ExitThread;
        EXIT_PROCESS_DEBUG_INFO   ExitProcess;
        LOAD_DLL_DEBUG_INFO       LoadDll;
        UNLOAD_DLL_DEBUG_INFO     UnloadDll;
        OUTPUT_DEBUG_STRING_INFO  DebugString;
        RIP_INFO                  RipInfo;
    } u;
} DEBUG_EVENT;

The event code decides which union member is valid, and each member begins its own structure. Z98 has no @cImport (chapter 11 measured the reject), so the program declares the part it needs as an ordinary struct whose fields land on the header's offsets. Because the target is 32-bit and pointers are four bytes, the layout is exact: 

const DebugEvent = struct {
    code: u32,           // 0
    pid: u32,            // 4
    tid: u32,            // 8
    hFile: *void,        // 12  (start of CREATE_PROCESS_DEBUG_INFO)
    hProcess: *void,     // 16
    hThread: *void,      // 20
    baseOfImage: *void,  // 24
};

That is the same choice chapter 12 made for sockaddr_in and chapter 11 made in general: a boundary struct is an aligned Z98 struct whose field order and widths match the header, laid out by the compiler's frozen 32-bit model. The fields line up because the model does not depend on the host compiler; a *void is four bytes, a u32 is four bytes, and the offset sequence is the one the Windows headers declare.

Two event codes carry the sample. CREATE_PROCESS_DEBUG_EVENT is code 3, and it is the first event you receive: its union member hands you the target's process handle, its main thread handle, and the base address of its image, which are the three things the rest of the debugger needs. The second is EXIT_PROCESS_DEBUG_EVENT, code 5, which is the last event and the loop's exit condition. A full debugger also handles the exception, load-module, create-thread, and debug-string events; the sample handles the two it needs and continues past the rest, which is the correct default.

Waiting and continuing

The loop is two calls. WaitForDebugEvent blocks until an event is available, fills the buffer, and returns nonzero; a zero return means the timeout expired, and a timeout means something is wrong — the target is stuck, or was never really attached. The second parameter is a millisecond timeout, and using a finite value instead of INFINITE is what keeps a mistake from becoming a hang on a single-tasking console. 

extern "stdcall" fn WaitForDebugEvent(ev: *void, ms: u32) i32;
extern "stdcall" fn ContinueDebugEvent(pid: u32, tid: u32, status: u32) i32;

ContinueDebugEvent is the release. It takes the process id and thread id from the event you just handled, plus a status word that says whether the exception (if any) was handled by the debugger: 

#define DBG_CONTINUE                0x00010002
#define DBG_EXCEPTION_NOT_HANDLED   0x80010001

The status word is the one place where a debugger's intent matters to the operating system. When the event is a breakpoint you placed and have handled, you report DBG_CONTINUE, and the system resumes the thread without passing the exception to the target. When it is an exception you do not understand, you report DBG_EXCEPTION_NOT_HANDLED, and the system gives the target its normal chance to handle it or die. A debugger that reports DBG_CONTINUE for everything will swallow the target's crashes, which looks like a hang; a debugger that reports DBG_EXCEPTION_NOT_HANDLED for its own breakpoints will let them crash the target. The sample reports DBG_CONTINUE, because the only exception it recognizes is its own breakpoint.

GetThreadContext and the CONTEXT block

When the target is stopped, its registers are available through the thread handle you received in the create-process event: 

extern "stdcall" fn GetThreadContext(hThread: *void, ctx: *void) i32;

The second argument points at a CONTEXT structure, which on x86 is roughly seven hundred bytes of register save area. Z98 does not need to declare the whole thing to use it; like STARTUPINFO, the context can be an opaque byte buffer as long as one precondition is met. GetThreadContext requires the ContextFlags field, the first four bytes of the structure, to name the register groups you want before the call. On x86 the CONTEXT granularity flags combine to CONTEXT_FULL: 

#define CONTEXT_CONTROL   0x00000001   /* EBP, EIP, CS, EFLAGS, ESP, SS */
#define CONTEXT_INTEGER   0x00000002   /* EAX, EBX, ECX, EDX, ESI, EDI */
#define CONTEXT_SEGMENTS  0x00000004   /* segment registers */
#define CONTEXT_FULL      (0x00010000 | 0x00000001 | 0x00000002 | 0x00000004)  /* 0x00010007 */

Forget to set ContextFlags and GetThreadContext fails with a zero return and an invalid-parameter error, which is easy to misread as "the debug API does not work under this environment." The sample sets the word before the call: 

var ctx: [1024]u8 = undefined;
const flags = @ptrCast(*u32, &ctx);
flags.* = CONTEXT_FULL;
const gc = GetThreadContext(hdr.hThread, @ptrCast(*void, &ctx));

One write through a typed pointer is all it takes. After the call succeeds, the register groups named by the flags are populated; the sample does not decode them, because the point is that the call succeeds and the registers are there. A real debugger would read Eip out of the block to know where the target stopped, and write it back with SetThreadContext to steer the target — the write twin is the same structure with the same flags.

Reading and writing the target: INT3

A stopped target's address space is a memory range you can read and write with the same API you would use on your own process: 

extern "stdcall" fn ReadProcessMemory(hProcess: *void, base: *const void, buf: *void, size: u32, read: *u32) i32;
extern "stdcall" fn WriteProcessMemory(hProcess: *void, base: *void, buf: *const void, size: u32, written: *u32) i32;

Both return nonzero on success and write the number of bytes actually moved into the trailing out-parameter. Those two calls are all a user-mode debugger needs to set a breakpoint, because a breakpoint on x86 is one byte. The instruction INT3 is the single opcode 0xCC; when the CPU executes it, it raises a breakpoint exception and stops. A software breakpoint is therefore the sequence: 

1. ReadProcessMemory(hProcess, address, &orig, 1, &n);   /* save the byte */
2. write 0xCC into a one-byte buffer
3. WriteProcessMemory(hProcess, address, &cc, 1, &n);     /* plant INT3 */
4. ContinueDebugEvent(...);                                /* target runs, hits it */
5. WaitForDebugEvent(...) returns EXCEPTION_DEBUG_EVENT
6. WriteProcessMemory(hProcess, address, &orig, 1, &n);  /* put it back */

The save-and-restore is not optional. 0xCC is a real instruction that overwrites a real byte of the target; leaving it in place means the target runs a one-byte instruction where your program had a real one, and the breakpoint fires again forever. The sample reads the byte at the entry point before it patches, writes 0xCC, confirms the write by reading the byte back, waits for the breakpoint, and restores the original byte before continuing. The 204 the sample prints after the patch is the decimal value of 0xCC.

The address to break on is the target's entry point, and the sample finds it the way a linker would: from the Portable Executable header. The two-byte MZ signature at the image base is followed at offset 0x3C by e_lfanew, the file offset of the PE signature. The optional header begins twenty-four bytes (0x18) after that signature, and the entry-point relative virtual address is at offset 0x10 within the optional header — offset 0x28 from the PE signature overall. Adding the RVA to the image base gives the address to patch: 

const elfanew = readU32(target, base, 60);      /* e_lfanew at 0x3C */
const entryRva = readU32(target, base + elfanew, 40);  /* entry RVA at PE+0x28 */
entryAddr = base + entryRva;

The sample's readU32 helper reads four bytes with ReadProcessMemory and assembles them little-endian as a usize. That is deliberately explicit: the debugger is reading bytes out of another process, so it treats every field as four bytes it fetched, rather than casting a raw pointer across the boundary. It is the same discipline chapter 11 recommended for a C boundary, applied to a target that may be a different process entirely.

Mapping the target: the _MEMORY_BASIC_INFORMATION workaround

The last function the sample calls answers the question "what is this memory?" VirtualQuery takes an address, a buffer, and the buffer's size, and fills in one _MEMORY_BASIC_INFORMATION describing the region that contains the address: 

extern "stdcall" fn VirtualQuery(addr: *const void, mbi: *void, size: u32) u32;

The return value is the number of bytes written, not a boolean, and a full structure is twenty-eight bytes on this target. The structure is the workaround the chapter title has been promising, and it is a workaround for exactly one limitation: Z98 has no @cImport, so it cannot ask the C compiler for the header's definition. The header is still included — @cInclude("windows.h") puts it in the translation unit — and the C compiler therefore knows the real type. Z98 only needs a place to receive the data, so the program declares the same fields under its own name: 

const MemoryBasicInformation = struct {
    baseAddress: *void,       //  0  PVOID
    allocationBase: *void,    //  4  PVOID
    allocationProtect: u32,   //  8  DWORD
    regionSize: usize,        // 12  SIZE_T (four bytes on 32-bit)
    state: u32,               // 16  DWORD
    protect: u32,             // 20  DWORD
    typ: u32,                 // 24  DWORD
};                            // 28 bytes total

The field order is the header's, the widths are the header's, and the total is the header's twenty-eight bytes. This is not a hack around a missing language feature so much as a restatement of the C boundary rule of chapter 11: declare the shape the library expects, and let the layout model guarantee it. The one difference from chapter 11's structs is that the structure is filled by the library rather than passed to it, so the debugger is the receiver and the header's field order is the contract that makes the received bytes interpretable.

The sample's use is minimal: it calls VirtualQuery on the image base and prints the region size. A real debugger uses the same call to walk the target's address space, decide which pages are committed and readable before calling ReadProcessMemory, and know where the image ends. The point of showing it here is that the structure you need is definable in Z98 without a binding generator, and that windows.h included by @cInclude supplies the compiler-side definition that checks the call.

The sample: dbg-mini.z98

The sample is a complete, if minimal, debugger. It builds the command line from COMSPEC, launches the interpreter under DEBUG_ONLY_THIS_PROCESS, waits for events, reads the image's entry point out of the PE header, reads the context and memory, plants an INT3, waits for the breakpoint, restores the byte, and follows the target to its exit. 

@cInclude("windows.h");

const std = @import("std");

// dbg-mini: the smallest complete Win32 debugger. It launches a copy of the
// command interpreter under DEBUG_ONLY_THIS_PROCESS, waits for debug events,
// reads the target's thread context and image header, writes an INT3 (0xCC)
// over the entry point, waits for the breakpoint, restores the original byte,
// and follows the target to its exit event. Everything here is a Win32 API
// call reached through the extern rules of chapter 11.
//
// The DebugEvent record is the first part of the Win32 DEBUG_EVENT structure:
// the event code and process/thread ids, then the union that begins with the
// CREATE_PROCESS_DEBUG_INFO handles. Z98 has no @cImport, so the fields the
// program reads are laid out as an ordinary Z98 struct in the header's order.
const DebugEvent = struct {
    code: u32,
    pid: u32,
    tid: u32,
    hFile: *void,
    hProcess: *void,
    hThread: *void,
    baseOfImage: *void,
};

// The _MEMORY_BASIC_INFORMATION workaround: Z98 has no @cImport, so the
// structure VirtualQuery fills is declared here field for field. On the 32-bit
// target a pointer and a SIZE_T are four bytes, so this is the header's 28
// bytes exactly (windows.h still supplies its own copy to the C compiler; we
// only need a place to receive the data).
const MemoryBasicInformation = struct {
    baseAddress: *void,
    allocationBase: *void,
    allocationProtect: u32,
    regionSize: usize,
    state: u32,
    protect: u32,
    typ: u32,
};

extern "stdcall" fn GetEnvironmentVariableA(name: [*]const u8, buf: [*]u8, size: u32) u32;
extern "stdcall" fn CreateProcessA(a: *void, cmd: [*]u8, pa: *void, ta: *void, inherit: i32, flags: u32, env: *void, cwd: *void, si: *void, pi: *void) i32;
extern "stdcall" fn WaitForDebugEvent(ev: *void, ms: u32) i32;
extern "stdcall" fn ContinueDebugEvent(pid: u32, tid: u32, status: u32) i32;
extern "stdcall" fn GetThreadContext(hThread: *void, ctx: *void) i32;
extern "stdcall" fn ReadProcessMemory(hProcess: *void, base: *const void, buf: *void, size: u32, read: *u32) i32;
extern "stdcall" fn WriteProcessMemory(hProcess: *void, base: *void, buf: *const void, size: u32, written: *u32) i32;
extern "stdcall" fn VirtualQuery(addr: *const void, mbi: *void, size: u32) u32;

// DEBUG_ONLY_THIS_PROCESS: attach to the new process (and no children of it).
const DEBUG_ONLY_THIS_PROCESS: u32 = 0x00000002;
// ContinueDebugEvent status words.
const DBG_CONTINUE: u32 = 0x00010002;
// The event codes the loop cares about.
const CREATE_PROCESS_DEBUG_EVENT: u32 = 3;
const EXCEPTION_DEBUG_EVENT: u32 = 1;
const EXIT_PROCESS_DEBUG_EVENT: u32 = 5;
// EXCEPTION_BREAKPOINT, and the 0xCC byte the x86 INT3 instruction is.
const EXCEPTION_BREAKPOINT: usize = 0x80000003;
const INT3: u8 = 0xCC;
// CONTEXT_FULL: the context flags GetThreadContext requires before the call.
const CONTEXT_FULL: u32 = 0x00010007;

// Little-endian assembly of four bytes read out of the target's memory.
fn le32(b: []const u8) usize {
    var v: usize = @intCast(usize, b[0]);
    v = v | (@intCast(usize, b[1]) << 8);
    v = v | (@intCast(usize, b[2]) << 16);
    v = v | (@intCast(usize, b[3]) << 24);
    return v;
}

// Read one 32-bit word out of the target at addr + off.
fn readU32(h: *void, addr: usize, off: usize) usize {
    var b: [4]u8 = undefined;
    var nr: u32 = 0;
    _ = ReadProcessMemory(h, @intToPtr(*const void, addr + off), @ptrCast(*void, &b), @intCast(u32, 4), &nr);
    return le32(b[0..4]);
}

// Build the command line from COMSPEC so the same sample names the right
// interpreter on a Windows 98 machine (command.com) and on this host (cmd.exe).
fn buildCmdLine(out: []u8) void {
    var name: []const u8 = "COMSPEC";
    var env: [260]u8 = undefined;
    var i: usize = 0;
    while (i < 260) : (i += 1) { env[i] = 0; }
    const n = GetEnvironmentVariableA(name.ptr, &env, @intCast(u32, 260));
    var m: usize = 0;
    while (m < n and m < 260 and m < out.len - 1) : (m += 1) { out[m] = env[m]; }
    var suffix: []const u8 = " /c exit";
    var s: usize = 0;
    while (s < suffix.len and m + s < out.len - 1) : (s += 1) { out[m + s] = suffix[s]; }
    out[m + s] = 0;
}

pub fn main() void {
    var cmdline: [300]u8 = undefined;
    var i: usize = 0;
    while (i < 300) : (i += 1) { cmdline[i] = 0; }
    buildCmdLine(cmdline[0..300]);

    // STARTUPINFO and PROCESS_INFORMATION are opaque byte buffers: we only
    // need them zeroed so the API fills in the defaults.
    var si: [128]u8 = undefined;
    i = 0;
    while (i < 128) : (i += 1) { si[i] = 0; }
    var pi: [32]u8 = undefined;
    i = 0;
    while (i < 32) : (i += 1) { pi[i] = 0; }

    const ok = CreateProcessA(@intToPtr(*void, 0), &cmdline, @intToPtr(*void, 0), @intToPtr(*void, 0), 0, DEBUG_ONLY_THIS_PROCESS, @intToPtr(*void, 0), @intToPtr(*void, 0), @ptrCast(*void, &si), @ptrCast(*void, &pi));
    if (ok == 0) {
        std.io.print("dbg-mini: CreateProcessA failed\n", .{});
        return;
    }
    std.io.print("dbg-mini: target created under DEBUG_ONLY_THIS_PROCESS\n", .{});

    var ev: [512]u8 = undefined;
    var patched: bool = false;
    var entryAddr: usize = 0;
    var origByte: u8 = 0;
    var target: *void = @intToPtr(*void, 0);
    var n: i32 = 0;
    while (n < 100) : (n += 1) {
        i = 0;
        while (i < 512) : (i += 1) { ev[i] = 0; }
        const w = WaitForDebugEvent(@ptrCast(*void, &ev), @intCast(u32, 3000));
        if (w == 0) {
            std.io.print("dbg-mini: WaitForDebugEvent timed out\n", .{});
            break;
        }
        const hdr = @ptrCast(*DebugEvent, &ev);
        const code: u32 = hdr.code;
        const pidv: u32 = hdr.pid;
        const tidv: u32 = hdr.tid;

        if (code == CREATE_PROCESS_DEBUG_EVENT and !patched) {
            patched = true;
            target = hdr.hProcess;
            const base: usize = @intFromPtr(hdr.baseOfImage);

            // The PE header holds e_lfanew at 0x3C and the entry-point RVA at
            // optional-header offset 0x10 (e_lfanew + 0x28 overall).
            const elfanew = readU32(target, base, 60);
            const entryRva = readU32(target, base + elfanew, 40);
            entryAddr = base + entryRva;

            // GetThreadContext requires Context.ContextFlags to be set first.
            var ctx: [1024]u8 = undefined;
            i = 0;
            while (i < 1024) : (i += 1) { ctx[i] = 0; }
            const flags = @ptrCast(*u32, &ctx);
            flags.* = CONTEXT_FULL;
            const gc = GetThreadContext(hdr.hThread, @ptrCast(*void, &ctx));
            std.io.print("dbg-mini: GetThreadContext = {}\n", .{gc});

            // VirtualQuery is where _MEMORY_BASIC_INFORMATION lands; the struct
            // above is the workaround for having no @cImport.
            var mbi = MemoryBasicInformation{ .baseAddress = @intToPtr(*void, 0), .allocationBase = @intToPtr(*void, 0), .allocationProtect = 0, .regionSize = 0, .state = 0, .protect = 0, .typ = 0 };
            _ = VirtualQuery(hdr.baseOfImage, @ptrCast(*void, &mbi), @intCast(u32, 28));
            std.io.print("dbg-mini: VirtualQuery region = {}\n", .{mbi.regionSize});

            // Save the original entry byte, then overwrite it with INT3.
            var one: [1]u8 = undefined;
            var nr: u32 = 0;
            _ = ReadProcessMemory(target, @intToPtr(*const void, entryAddr), @ptrCast(*void, &one), @intCast(u32, 1), &nr);
            origByte = one[0];
            var cc: [1]u8 = undefined;
            cc[0] = INT3;
            var nw: u32 = 0;
            _ = WriteProcessMemory(target, @intToPtr(*void, entryAddr), @ptrCast(*const void, &cc), @intCast(u32, 1), &nw);
            _ = ReadProcessMemory(target, @intToPtr(*const void, entryAddr), @ptrCast(*void, &one), @intCast(u32, 1), &nr);
            std.io.print("dbg-mini: INT3 patch = {}\n", .{@as(u32, one[0])});
        }

        if (code == EXCEPTION_DEBUG_EVENT and patched) {
            // The exception record begins the union: ExceptionCode at offset 12
            // and ExceptionAddress at offset 24. Only our own breakpoint, at the
            // entry address, is acted on.
            const ecode = le32(ev[12..16]);
            const eaddr = le32(ev[24..28]);
            if (ecode == EXCEPTION_BREAKPOINT and eaddr == entryAddr) {
                std.io.print("dbg-mini: breakpoint hit at the entry point\n", .{});
                var one: [1]u8 = undefined;
                one[0] = origByte;
                var nw: u32 = 0;
                const r = WriteProcessMemory(target, @intToPtr(*void, entryAddr), @ptrCast(*const void, &one), @intCast(u32, 1), &nw);
                std.io.print("dbg-mini: original byte restored = {}\n", .{r});
            }
        }

        if (code == EXIT_PROCESS_DEBUG_EVENT) {
            _ = ContinueDebugEvent(pidv, tidv, DBG_CONTINUE);
            std.io.print("dbg-mini: target exited\n", .{});
            break;
        }
        _ = ContinueDebugEvent(pidv, tidv, DBG_CONTINUE);
    }
    std.io.print("dbg-mini: done\n", .{});
}

Walking the sample

The program opens by building its command line. It asks for COMSPEC into a 260-byte buffer, copies the shell path into the command-line buffer, and appends " /c exit" so the interpreter runs one no-op command and exits. Appending the suffix rather than passing it as a second parameter is the ordinary command-line convention; CreateProcessA with a null application name parses the first token itself. The rest of the setup is zeroing the two opaque structures, which must be zeroed before the API reads them.

The CreateProcessA call is the one line that makes the program a debugger. DEBUG_ONLY_THIS_PROCESS in the flag word attaches the new process; a non-zero return means the target exists and is stopped, and the program prints the first line of the transcript. If the call fails, the sample prints one line and returns rather than proceeding into an event loop with no target.

The loop is the heart. Each iteration clears the event buffer, waits, and reads the event code. On the create-process event it saves the target's process handle into a variable that outlives the event — this is the important bookkeeping point, because the hProcess field is only valid in the union member for that event code, and an exception event's union has no process handle at all. It computes the entry address from the PE header, sets the context flags and calls GetThreadContext, calls VirtualQuery, reads the original entry byte, writes 0xCC, and reads the byte back to confirm. On an exception event whose exception code is EXCEPTION_BREAKPOINT and whose exception address is the entry address — the check that distinguishes the debugger's own breakpoint from any other — it restores the saved byte. Every other event, and every branch that is not one of those two, falls through to ContinueDebugEvent.

The exit-process event is handled before the fall-through continue so that the loop can break cleanly after releasing the target. The loop also bounds itself at one hundred events and times out each wait after three seconds, so a target that stops reporting cannot hang the debugger; both guards are the kind of discipline a debugger needs everywhere.

The trade

Writing a debugger in Z98 is the same trade as writing any Win32 program in Z98, with the stakes raised. You get the real operating-system service, declared with the real calling convention, in a program that compiles to the same C89 an era compiler would have seen. There is no debugger library to link, no event framework to learn, and no runtime that has to be present on the target machine. The generated C is a sequence of kernel32 calls a 1998 programmer would recognize immediately.

What you pay is that every precondition is yours to remember. The debug flag must be right; the event union must be read through the correct member for the event code; the process handle from the create event must be saved because no later event carries it; the context flags must be set or the context call fails; the patched byte must be restored or the target loops on the breakpoint. None of those is checked by the compiler. They are checked by the target, and the target's way of reporting a mistake is to hang or to crash.

For the amount of tooling most programs for this machine need, that is the right side of the trade: a small debugger is a few hundred lines, and once it exists it is the one program on the machine that can inspect any other. The cost is concentrated in the parts this chapter has shown — the event union, the context flags, and the restore — and the way to pay it is to keep those parts small and to copy the sample's structure rather than to improvise it.

Honest note. This is a debugger for one target, one thread, and one breakpoint, and it is honest about being a starting point rather than a tool. It does not decode registers, disassemble instructions, read symbols, handle multi-threaded targets, or recover from exceptions it does not recognize. What it does do is exercise every primitive a full debugger is built from — attach, wait, inspect, patch, restore, continue — and it does all of it on this target and verified under the Windows oracle. When you need more, the additions are the ones this chapter's sections name: SetThreadContext to steer the target, a table of saved bytes for many breakpoints, and the other DEBUG_EVENT codes for the events a real debugger must not ignore.

Common mistakes

These are the mistakes a first debugger makes, roughly in the order it makes them. Each is paired with the correction.

Forgetting the debug flag. CreateProcessA with 0 in the creation-flags word launches a process that is not attached to you. You get a handle and a process id, but no events, so the first WaitForDebugEvent times out and the target has already run to completion. Pass DEBUG_ONLY_THIS_PROCESS (0x00000002).

Reading the wrong union member. The DEBUG_EVENT union is valid member by member, chosen by the event code. Reading a process handle out of an exception event reads unrelated bytes and produces a garbage handle. Read the handle you need in the branch for the event that supplies it, and save it into a variable that outlives the event.

Calling GetThreadContext without ContextFlags. The context call requires Context.ContextFlags to name the register groups before the call, because the structure is used for both reading and writing. With the field at zero the call fails with a zero return and an invalid-parameter error. Set CONTEXT_FULL (0x00010007 on x86) into the first four bytes first.

Leaving the INT3 in place. 0xCC overwrites a real byte of the target. If you do not restore the saved byte before continuing, the target still holds the breakpoint, hits it again, and the event loop repeats forever. Read the original byte, keep it, and write it back when the breakpoint fires.

Reporting DBG_CONTINUE for every event. A debugger that claims every exception has swallowed the target's real crashes, and the target appears to hang or misbehave with no diagnostic. Report DBG_CONTINUE for the breakpoints you planted and DBG_EXCEPTION_NOT_HANDLED (0x80010001) for exceptions you do not recognize.

Waiting forever. WaitForDebugEvent takes a millisecond timeout, and passing INFINITE turns a mistake into a hang. Pass a finite timeout and treat a zero return as an error, and bound the whole loop at a maximum event count as the sample does.

Writing the target with an unmapped or read-only address. WriteProcessMemory fails when the page is not writable; a breakpoint on a read-only code page needs the page made writable first (VirtualProtectEx). VirtualQuery is how you check the region's state and protection before you touch it.

Declaring the boundary structures sloppily. DEBUG_EVENT and _MEMORY_BASIC_INFORMATION are read at fixed offsets. A field in the wrong order, or a SIZE_T declared too wide, shifts every field after it and the debugger reads nonsense. Copy the header's field order and widths exactly, and keep 64-bit fields out of a structure the header does not have them in, as chapter 11 instructed.

Expecting the debug target's output to be yours. The target inherits the debugger's standard handles unless the STARTUPINFO redirects them, so a chatty target prints into the debugger's console and mixes with its output. The sample's target runs /c exit precisely so the transcript stays clear; redirect the target's handles when you debug something that talks.
