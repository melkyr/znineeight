Packaging and Shipping

Chapter 8 got a Z98 program to a .exe, and chapter 16 made it small enough to fit the machine it runs on. This chapter is the last step: turning the output directory the compiler writes into something you can hand to another person, and that person can run on a 1998 machine without you standing next to them.

There is no zig1 package command, and this chapter will not pretend there is. The compiler does not produce an installer; it produces C89 and the scripts to build it. So the release you ship is a decision you make from the pieces the compiler leaves on disk, and the honest work of this chapter is to show you exactly what those pieces are, which of them a release needs, and which of them are era convention rather than a Z98 feature. The blueprint gives this chapter no sample program, and none is needed: the evidence is the compiler's actual output tree and the build scripts it writes.

What is measured here. The compiler under test is the seed build /tmp/manual_seed/zig1_5_clean, fixed point 8216fedc8dd69db084d453be80f3c010. The output tree quoted below is the real result of zig1 -osw -o out docs/sf/manuals/src/vol1/hello.z98 run on this host; the two companion scripts are the tracked files docs/sf/manuals/src/build_linux.sh and docs/sf/manuals/src/build_owc.bat. The module-name suffixes the tree shows are path-derived: they are stable for a given source path and a given compiler install path, and a different path yields different suffixes (the same fact chapter 15 established for the debugger). Nothing on this page claims OpenWatcom or MSVC was run; on this host they are emitted, not executed, exactly as chapter 8 stated. No dist/ tree is generated by this chapter.

What a release has to answer

Every distributable answers two questions, and they are not the same question. The first is can the user run it? That is a compiled binary: something double-clickable on the target machine. The second is can the user rebuild it? That is source plus a build script: the emitted C89 and the command lines that turn it back into the binary. A release can answer either, or both, and the choice is a tradeoff rather than a default.

On a modern machine the answer is usually “the source, from a package manager” or “the binary, from an app store,” and the toolchain that builds it is assumed to be present. The 1998 machine has neither assumption. The user may have an OpenWatcom install, or MSVC, or neither; they may have the Z98 compiler, or only a C compiler, or only the ability to run an .exe. This is why the answer this volume has been building toward is the same one chapter 3 gave: Z98 emits C89, so a Z98 release can hand the user C89 and a script, and the user builds it with whatever C compiler the era put on their machine.

Release shape The user needs Buys you Costs you
The binary alone nothing but the target machine smallest download; runs at once no rebuild, no source to read or repair; one target per binary
The C89 tree and the build scripts a C compiler and the platform SDK rebuildable and portable across the era's compilers; readable source larger; the user must know how to run a build
Both either runs immediately and rebuilds if wanted largest; duplicates the program in two forms

The rest of this chapter works through the middle row, because that is the one that is specific to Z98. A binary-alone release is a fact about your C linker, not about this language; a source release is the one the compiler's own output makes possible. Where the two differ, the page says so.

What the compiler hands you

Emit a program for Windows and the compiler writes a complete, self-contained tree into the output directory. It is not a single .c file and it is not a project file for an IDE; it is every source the build needs, side by side, including the runtime and the platform layer. Here is the tree for vol1/hello.z98, the four-line program from chapter 8: 

$ mkdir -p out
$ /tmp/manual_seed/zig1_5_clean -osw -o out docs/sf/manuals/src/vol1/hello.z98
$ ls out
build_owc.bat        build_target.bat     build_target.sh
c_exit.c             hello_F63FD80A.c     hello_F63FD80A.h
net_prelude.h        std_io_59DB29D9.c    std_io_59DB29D9.h
std_net_A15200CC.c   std_net_A15200CC.h   zig_compat.h
zig_pal.c            zig_runtime.c        zig_runtime.h
zig_special_types.h

Read the listing in four groups, because that is how a release is assembled. There is your module (hello_….c and its header). There are the standard modules the program pulled in by importing std: std_io and, because the seed emits the network translation unit for every std-importing program, std_net. There are the runtime and platform sources: zig_runtime.c, zig_pal.c, c_exit.c, plus the headers zig_runtime.h, zig_special_types.h, zig_compat.h, and net_prelude.h. And there are the build scripts: build_target.sh, build_target.bat, and build_owc.bat, one per target toolchain.

Two properties of the tree matter for packaging. The first is that it is self-contained: every .c a module needs is in the directory, so a release is a file copy, not a dependency resolution. The second is that the standard modules and the runtime are copied into the tree, not referenced from the compiler's install. You do not have to ship the compiler, and the user does not have to install it; they need a C compiler and the platform headers the era already had.

The tree also contains files you should not ship: the compiler's own scratch files, written into the same directory and named with a leading dot (.zig1_ast.tmp, .zig1_lir.tmp, and the rest). They are intermediate state the compiler needed while emitting and are dead weight in the bundle. Delete them, or copy only the files you mean to ship, before you pack.

If the program is a library rather than an application — C89 the user will link into their own program — the tree is the same shape minus the entry point, and the interface is the one chapter 11 described: the exported symbols carry the emitter's mangled names, and the C side reaches them through extern declarations or @cInclude. That path is a packaging choice too, but the chapter that owns it is chapter 11, and this page does not restate it.

The build_owc.bat convention

The three build scripts are the release's build contract, and the OpenWatcom one is the chapter's named subject because it is the classic era toolchain: cheap, fast, and good at tight 32-bit code. The compiler writes a per-program build_owc.bat into every output directory, and the manual also ships a companion, docs/sf/manuals/src/build_owc.bat, that follows the same convention for the whole example tree. Here is the companion, which is a stable tracked file rather than a generated one: 

@echo off
REM build_owc.bat - build the manual's Z98 example programs for Win9x with
REM OpenWatcom. This is the Win9x companion to build_linux.sh.
REM
REM Emit the Windows-target C89 for an example first:
REM     zig1 -osw -o out hello.z98
REM zig1 writes a self-contained tree into out\ and, because the target is
REM Windows, its own build_target.bat (MSVC) and build_owc.bat (OpenWatcom).
REM This companion follows those emitted conventions; run it from inside an
REM emitted output directory to compile every .c and link one console exe:
REM
REM     cd out
REM     build_owc.bat [OUT]
REM
REM wcc386 /za /we /dZIG_WIN32 /i=.  strict ANSI C, warnings as errors
REM wlink system console op q opt stack=65536 ... library wsock32
REM wsock32 matches the emitted build_owc.bat: the seed emits std_net_*.c for
REM every @import("std") program, so the socket symbols must resolve.
setlocal
if "%~1"=="" (set OUT=prog.exe) else (set OUT=%~1)
echo Compiling...
wcc386 /za /we /dZIG_WIN32 /i=. *.c
if errorlevel 1 goto fail
echo Linking...
wlink system console op q opt stack=65536 file {*.obj} library wsock32 name %OUT%
if errorlevel 1 goto fail
echo Built: %OUT%
goto :eof
:fail
echo Build failed.
exit /b 1

Read the flags as the dialect in miniature, the way chapter 7 read the emitted per-module lines. /za turns OpenWatcom's extensions off and asks for strict ANSI C; /we promotes every warning to an error, so the build is a correctness gate as well as a compile; /dZIG_WIN32 selects the Windows code path; /i=. makes the current directory the include root, which is why the companion must be run from inside the emitted tree. The link asks for a console subsystem, a 64 KB stack, and wsock32, and stack=65536 is the same figure the emitted per-program script uses.

The generated per-program script is the same command with the module list spelled out. Its compile lines and link line look like this, with the path-derived suffixes the tree above showed: 

wcc386 /za /we /dZIG_WIN32 /i=. hello_F63FD80A.c
wcc386 /za /we /dZIG_WIN32 /i=. std_io_59DB29D9.c
wcc386 /za /we /dZIG_WIN32 /i=. std_net_A15200CC.c
wcc386 /za /we /dZIG_WIN32 /i=. zig_runtime.c
wcc386 /za /we /dZIG_WIN32 /i=. zig_pal.c
wcc386 /za /we /dZIG_WIN32 /i=. c_exit.c
wlink system console op q opt stack=65536 file hello_F63FD80A.obj,std_io_59DB29D9.obj,std_net_A15200CC.obj,zig_runtime.obj,zig_pal.obj,c_exit.obj library wsock32 name prog.exe

Both scripts carry a warning-policy comment at the top, and it is worth reading before you edit anything: /we is deliberate, and if a build fails on a warning you believe is harmless, the script tells you to drop /we and see the warning. If a hard error remains after that, the emitted C is not valid for OpenWatcom and should be reported as a bug rather than papered over.

And here is the boundary this manual has to keep, because a claim about a toolchain that was never run is exactly the kind of thing that breaks a reader's trust. wcc386 and wlink are not installed on this development host. The script above is emitted, quoted from the directory the compiler wrote and from the tracked companion, and it is not executed. Nothing in this volume should be read as saying OpenWatcom was run. The same is true of MSVC's cl: its build_target.bat is emitted and quoted, and it is not executed here. What was run is the mingw path on the emitted C89, under wine, with LF-normalized stdout parity — the harness chapter 8 described. The era toolchains are the release's contract; the mingw-and-wine run is the local proof that the C89 those toolchains would compile is real.

Three build scripts, one release

The compiler writes one script per C compiler the era offered, and a release ships whichever one matches the user's machine. The choice is not Z98's; it is the user's, and the scripts exist so the choice does not require you to guess.

Script Toolchain What it is for
build_target.sh gcc on era Linux, or mingw on Windows one script, two targets; the default is the Linux host, and sh build_target.sh mingw cross-compiles the Windows binary. This is the only branch this host can execute.
build_target.bat MSVC cl and link the Windows command-prompt build. Emitted here; not run here, because cl is not installed.
build_owc.bat OpenWatcom wcc386 and wlink the OpenWatcom 32-bit build, the classic era toolchain. Emitted here; not run here, because wcc386 is not installed.

The shapes differ because the compilers differ, not because the program does. The mingw and gcc branches use the flag vocabulary of the gcc family (-m32 -std=c89 -O0 -Wall and three -Wno- flags for the small extensions strict C89 lacks); the MSVC script uses /c /Za /W3 /WX /DZIG_WIN32 and links kernel32.lib and wsock32.lib; the OpenWatcom script uses /za /we /dZIG_WIN32 and links wsock32. All three compile the same emitted C89 and produce the same program, which is the load-bearing fact of chapter 3: because Z98 emits C89, the release is portable across the era's C compilers without the program knowing which one will build it.

One consequence is worth stating plainly. A release that ships all three scripts is larger than it needs to be for any one user, and a release that ships only the script for your own compiler asks the user to have the same one. The honest middle is the source tree plus the scripts, which is small next to the era's media and lets each user pick their toolchain: 

$ wc -c out/*.c out/*.h out/*.sh out/*.bat | tail -1
124340 total

About 121 KB of C89 for the four-line program, including the runtime and the standard modules it pulled in. The number is dominated by the runtime and the standard library, not by the program, so it does not grow much as the program does; the next section is about what that buys on the era's media, and it is where the number stops being academic.

What goes on the diskette

The era's medium is the 3.5-inch, 1.44 MB floppy, and it is not a constraint to design around, it is simply the envelope the release has to fit or be split across. The blueprint's own framing is the correct one: a four-diskette set was a normal release, and once an archive format is in play the size is not the binding constraint at all. What matters is that the release is self-describing and copy-installable: the user should be able to put the disk in, copy something to the hard drive, and run it, with no dependency on a network none of these machines had.

The compiler's output tree gives you the first property for free and asks you to decide the second. Because every source is in one flat directory and the include root is the current directory (/i=. or -I .), the release is a file copy with no path rewriting, which is precisely what makes it a diskette release and not merely a directory on your machine. A Z98 application diskette therefore holds what the output tree holds, filtered to what the user needs:

On the diskette Why
The compiled .exe (or the Linux binary) the run-it-now path, for a user who has no C compiler
The emitted .c / .h files the rebuild path, and the readable source
The build script(s) for the target toolchain(s) the command lines, so the user does not reconstruct them
A short readme which script to run, and what the program does — the one file the compiler does not write for you

Do not ship the compiler's scratch .zig1_*.tmp files, and do not ship the emitted tree without the runtime sources: zig_runtime.c, zig_pal.c, and c_exit.c are as much part of the program as your own module is. The compiler writes them beside your source precisely so that a release is a directory rather than a dependency graph, and a release that drops them is not smaller, it is broken.

The manual you are reading is itself a diskette artifact, and its shape is the same idea at the scale of a whole document set. The blueprint fixes the rules: pages in a language are flat siblings (every link is vol3-06-era-limits.html, never a path), assets are self-contained per language so one diskette can ship one language with no dangling reference, and the short page names and depth-one links are what make the whole thing a file copy. The generated dist/ tree the blueprint describes — a cd/ directory and floppy-1/ through floppy-N/, one per language per medium — is the build that packs it. That build is out of scope for this volume and is not generated here; this page describes the shape, and the HOWTO's vol5-19-pack-for-diskette (planned) is where the packing itself will live.

Self-extracting archives

The era's answer to “how do I get a multi-diskette archive onto the hard drive without asking the user to own an unzip tool” was the self-extracting archive: a single .exe that contains the compressed files and the unpacker together, so double-clicking it is the whole installation. The packager builds the archive as an executable, splits it across floppies when it is larger than 1.44 MB, and the user runs disk one and feeds the rest when prompted. It is a genuinely good fit for the machine and the medium, and it is the convention a 1998 release was expected to follow.

This is era practice and opinion, not a Z98 feature, and the chapter marks it as such. The compiler emits C89 and a build script; it has no packer and no archive format, and it should not, because the format is the packager's tool and not the language's job. What the language contributes is that the thing being packed is a self-contained tree with a build that works from the current directory, which is exactly what an archive needs to reconstruct. The rest — which packer, how many disks, whether the archive installs to C:\PROGRAM or runs in place — is your release's convention, and the era's tools (the self-extractors that shipped with the common archivers, and the installers of the day) are what you would reach for.

The honest cost is that a self-extracting archive holds a compressed copy inside an executable, so it is larger than the files it contains, and a split archive is larger still. On a machine with 32 MB of disk to spare that is a real trade, and the alternative — a plain copy of the tree, uncompressed, plus a one-line readme — is often the better one for a small program. Reach for the self-extractor when the release is large enough that the floppy split is unavoidable or the user genuinely cannot run a build; for a few hundred kilobytes of C89, the copy is honest and sufficient.

Honest note. This chapter describes the shape of a release; it does not build one. No dist/ tree is generated, no archive is packed, and neither OpenWatcom nor MSVC was run to produce the scripts quoted above — they are emitted by zig1 -osw and verified as text, exactly as chapter 8 stated. The only build that actually ran on this host is the emitted C89 through mingw and wine, with LF-normalized stdout parity. The era toolchains are the release's contract; the screenshot on a real Windows 98 machine remains the operator's job, and it is the figure on chapter 8, not a claim this page makes. When a claim here and the tools on your machine disagree, the tools win: the output tree and the scripts are what the compiler actually wrote, and the method — emit, then ship the tree — is what to keep.

Common mistakes

Packaging is where a program that built and ran on your machine fails on someone else's, and the failures are a small set. They are listed in the order they are usually made.

Shipping the compiler's scratch files. The output directory contains .zig1_ast.tmp, .zig1_lir.tmp, and the rest of the hidden .zig1_*.tmp intermediate files. They are dead weight and they are not source. Copy the files you mean to ship, or delete the scratch files, before you pack.

Shipping the tree without the runtime sources. zig_runtime.c, zig_pal.c, and c_exit.c are not optional extras; they are the program's runtime and its platform layer. A release that drops them does not link. The tree is self-contained on purpose — keep it that way.

Claiming OpenWatcom or MSVC built it when only the script was emitted. The scripts are the contract; on this host they are quoted, not run. If you tell a reader the release was built with wcc386, you owe them the run that proves it, and on this host you do not have it. Say instead which path you verified — the mingw-and-wine run on the emitted C89 — and let the real-machine screenshot carry the rest.

Treating the path-derived module suffixes as stable names. The _F63FD80A style suffix is derived from the module's source path and the compiler's install path. A release built from a different directory gets different suffixes, and a script that hard-codes a suffix from your machine will fail to find the file on someone else's. Ship the script the compiler wrote; do not hand-edit module names into it.

Shipping C89 without the build scripts, or scripts without the sources. The two halves are a pair. The source tree plus the scripts is the rebuildable release; either one alone is incomplete, and a user who has both but not the matching pair cannot build.

Overriding the struct packing. The emitted C's layout has a default packing, and forcing a different one (the era flags like /Zp4 or -zp4) changes the layout the program was compiled against and breaks it. Build with the scripts as written; if you must change a flag, change it in the script and rebuild the whole tree, never half of it.

Assuming every target needs every script. You need the script for the toolchain the user has, or all three if you do not know. Shipping the MSVC script to a user with only OpenWatcom is a file they cannot use; shipping all three is a slightly larger diskette. Weigh the two; do not assume.

Forgetting that the release is the tree, not your working directory. The include root is the output directory, not the repository. A release packed from the repository root, with the source files at their development paths, will not build from the current-directory convention the scripts assume. Pack the output tree as it was emitted.

Reaching for the era's packers when a copy would do. A self-extracting archive is the right tool for a large, split release and the wrong one for a few hundred kilobytes of C89. Use the smallest release that solves the actual problem.
