Report a Bug

This guide turns a failing Z98 program into a bug report: the compiler fixed point, the smallest program that still fails, the exact command, the expected and actual output, and the diagnostic quoted verbatim — and shows how to reduce a program until nothing can be removed without changing the failure.

Prerequisites

  • The repository checked out at /workspace/znineeight and the compiler rebuilt from the seed at /tmp/manual_seed/zig1_5_clean, with the standard library beside it in /tmp/manual_seed/lib/. If it is not there yet, follow Rebuild the Compiler from Seed.
  • Build a Single File, for the zig1 -o DIR prog.z98 then build_target.sh recipe, and Read the Diagnostics, for the four parts of a message and the exit statuses.
  • The reproduction fixtures under repro/: repro/mi_matrix/ holds the large pinned corpus of green and reject cases, and repro/vol2_defects/ holds the defect set with its runner and README.md.
  • Contribute, whose seed and amendment section governs what happens when a report turns out to be a real compiler defect.

The idea

A bug report is a reproduction. Five fields make it actionable, and the same five make it a regression test after it is fixed: the compiler that produced the result (identified by its fixed point), the smallest program that still fails, the exact command, the expected and actual output, and the diagnostic. The repository already stores reports in exactly that shape, so writing one is not free prose — it is a fixture under repro/. A report that omits the compiler, the command, or the verbatim diagnostic cannot be reproduced, and a report whose program still contains unrelated code cannot be reduced.

The reduction is the work. You begin with the program that fails, delete a declaration, a statement, or a branch, and recompile; if the same failure survives, the deletion stays. You stop when removing anything else would change the result, so that the program states one fact about the compiler and nothing else. The corpus's small main.zig files are the product of that loop.

Steps

  1. Pin the compiler. The same source can behave differently on two builds, so a report names the compiler by its fixed point — the seed build's md5, the value its two-hop closure gate reproduces: 

    $ md5sum /tmp/manual_seed/zig1_5_clean
0b8c3e4ac0b1fc49c0bdf8caf9d39945  /tmp/manual_seed/zig1_5_clean

    That hex string is the compiler's identity for the report. If the reader built the compiler from the same seed, md5sum prints the same value; if it does not, the two reports are not comparable. The rebuild command is the one in Rebuild the Compiler from Seed; its gate ends === [seed] Done: /tmp/manual_seed ===. Record the md5sum line, not a version label.

  2. Minimise the program. Delete until the failure is the only thing left. Keep a name that is declared and the one construct that misbehaves; drop every import, every print, and every function the failure does not touch. The body of a pinned reject fixture is the result — two lines of code and the two captures that trip the rule: 

    body of repro/mi_matrix/error_union_capture_reject_xmod/main.zig
(comment header omitted)
const E = error{Bad};
fn h() E!i32 { return 42; }

pub fn main() void {
    if (h()) |v| {
        _ = v;
    }
    while (h()) |v| {
        _ = v;
        break;
    }
}

    The fixture keeps one if and one while because it pins both spellings of one rule; a report needs only the first failing one. The command to re-check after each deletion is the one in the next step. When no import remains, the program no longer depends on the module graph, and when no unrelated statement remains, the output cannot be blamed on them.

  3. Record the exact command. Write the command character for character, as you ran it. The output directory for -o must already exist: 

    $ mkdir -p /tmp/manual_bug
$ timeout 120 /tmp/manual_seed/zig1_5_clean -o /tmp/manual_bug repro/mi_matrix/error_union_capture_reject_xmod/main.zig

    An absolute path or a relative one both work, but the report must say which. The mkdir -p is part of the command because -o does not create the directory; invoking it against a missing one is a status-1 usage error, not the bug: 

    $ timeout 120 /tmp/manual_seed/zig1_5_clean -o /tmp/manual_bug_nope repro/mi_matrix/error_union_capture_reject_xmod/main.zig
error: output directory does not exist: /tmp/manual_bug_nope
$ echo $?
1

    Run every binary under timeout 120 so a hung compiler cannot stall the report; a timeout is itself a result worth recording. Redirect standard output and standard error to separate files if the two streams interleave in the terminal.

  4. Capture the expected and actual output. The actual output is what the command just printed; the expected output is what the language rule says should happen. The fixture stores both sides, so the comparison is a diff, not a judgement. Run the command and read the exit status: 

    $ timeout 120 /tmp/manual_seed/zig1_5_clean -o /tmp/manual_bug repro/mi_matrix/error_union_capture_reject_xmod/main.zig
repro/mi_matrix/error_union_capture_reject_xmod/main.zig:16:14: error[3058]: error union capture is not supported; use 'catch', 'switch', or 'orelse'
    if (h()) |v| {
              ^
repro/mi_matrix/error_union_capture_reject_xmod/main.zig:19:17: error[3058]: error union capture is not supported; use 'catch', 'switch', or 'orelse'
    while (h()) |v| {
                 ^
$ echo $?
2

    The expected side is the pinned census and status: 

    $ cat repro/mi_matrix/error_union_capture_reject_xmod/expected_error.txt
3058 2
$ cat repro/mi_matrix/error_union_capture_reject_xmod/expected.rc
2

    Here expected and actual agree: two error[3058] lines and exit status 2, with no .c emitted. That is what a resolved report looks like, and it is why the fixture is also the regression pin. A new report uses the same two fields with the two sides differing: the wrong diagnostic, the missing reject, the wrong stdout, or the wrong status. For a program that builds and runs but prints the wrong bytes, the expected.txt golden beside a green fixture is the expected side and the program's stdout is the actual side; repro/vol2_defects/ calls that failure kind wrong.

  5. Quote the diagnostic verbatim. Paste the whole block: the header file:line:column: level[code]: message, the repeated source line, and the caret line, with the carets exactly where the compiler put them. Do not paraphrase the message or trim the caret, and do not summarise several diagnostics as one. The bracket number is meaningful on its own — it is whatever the emission site passed, not the digits in the code's name — so the message and the caret are what identify the site. The reading method is on Read the Diagnostics, and the code catalogue is Volume IV — Diagnostics.

  6. Run the reproduction set. The defect set ships a runner that compiles and runs every case with the seed compiler and prints one line each, so a report can be checked in place. It prints <case>: rc=<n> <RED|ok>, where RED means the expected defect reproduced and ok means it did not: 

    $ sh repro/vol2_defects/run_all.sh
D01_defer_segfault: rc=0 ok
D02_enum_switch_ranges: rc=0 ok
D03_missing_else: rc=2 ok
D04_tuple: rc=0 ok
D05_slice_to_manyptr: rc=0 ok
D06_float_union: rc=0 ok
D07_nontuple_print: rc=2 ok
D08_errset_capture: rc=0 ok
D09_bare_union_offsetof: rc=2 ok
D10_single_ptr_index: rc=2 ok
D11_qualified_capture: rc=0 ok
D12_const_discard_slice: rc=2 ok
S01_print_nontuple_args: rc=2 ok

    Each case declares its expected failure kind, which fixes what RED means for it: crash (the compiler must die from a signal), reject (it must reject), accept (it must wrongly accept), gccfail (the emitted C must fail under gcc), wrong (the run's stdout must differ from expected.txt), runok (it must build, run, and match), and fixedreject (it must reject with the exact <code> <count> census in expected_error.txt). The kinds, the per-case claims, and the fixture layout are in repro/vol2_defects/README.md; every stage runs under timeout 120.

  7. File it in the repository's shape. A report enters the corpus as a directory, not an issue thread. The smallest fixture is a program, a status, and a census or a stdout golden: 

    $ ls repro/mi_matrix/error_union_capture_reject_xmod
expected.rc
expected_error.txt
main.zig

    The names carry the fields: main.zig is the minimal program; expected.rc is the exit status; expected.txt is the expected stdout for a program that should build and run, or expected_error.txt is the <code> <count> diagnostic census for one that should reject; and a NOTES.md, where the corpus keeps one, records the defect claim, the exact commands, the seed md5, and the observed versus expected output. A fixture that ships expected_error.txt must be force-added, because the repository ignores *.txt by default. The compiler fixed point from step 1, the command from step 3, and the diagnostic from step 5 are already inside it.

    If the reduction exposes a real compiler defect, stop: report the minimal reproduction and do not patch sf/src around it or document around it. A fix enters only as an operator-ruled amendment, as a read-only investigation followed by a fix task that adds the fixture above; that rule is Contribute, step 4.

Verify it worked

A report is complete when the five fields can be read off it and a second machine can reproduce the result. For the worked example they assemble as: 

compiler:   0b8c3e4ac0b1fc49c0bdf8caf9d39945  (zig1_5_clean)
program:    repro/mi_matrix/error_union_capture_reject_xmod/main.zig
command:    /tmp/manual_seed/zig1_5_clean -o /tmp/manual_bug repro/mi_matrix/error_union_capture_reject_xmod/main.zig
expected:   rc 2; expected_error.txt "3058 2"
actual:     rc 2; two error[3058] blocks
diagnostic: error[3058]: error union capture is not supported; use 'catch', 'switch', or 'orelse'

The runner closes the loop: every case prints one line and the set is read as a whole, RED for a reproduced defect and ok for one that no longer reproduces. The commands in steps 1, 2, 3, 4, and 6 were run against the seed compiler at /tmp/manual_seed and their output is quoted above. If a fresh md5sum matches the fixed point, the exact command prints the same diagnostic, and the exit status is the one in expected.rc, the report is reproducible.
