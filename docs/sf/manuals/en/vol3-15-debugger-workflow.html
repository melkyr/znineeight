The Debugger Workflow

By now two facts about this toolchain are settled. Z98 emits C89, and it emits no more than that — the compiler's job ends when it has written the C. The C compiler is the one that turns those files into a binary, and the C compiler's debugger, not a Z98 debugger, is the one that watches the binary run. That is the whole debugger story, and this chapter is how to use it: build the generated C with debug information, point gdb at it, and set breakpoints against the emitted files and their mangled names.

There is a second surface, for a different bug. When the program is correct and the compiler is wrong, gdb is the wrong tool; the compiler's own trace is the right one. The compiler has a built-in marker channel, turned on with --markers, that reports what the pipeline is doing as it runs: which types it created, which strings it interned, how its arenas grew, which functions it has declared so far. Reading that stream is the second half of this chapter. One workflow is for your program; the other is for the compiler. Both are real, both are documented here from captured runs, and neither needs a feature Z98 does not have.

What is measured here. This chapter has no sample program and no figure, because the blueprint gives neither and because the subject is a workflow rather than a program. Every transcript on the page is, nevertheless, a real run on this host: the seed-built compiler (v89, fixed point 8216fedc…) emitting the Volume II arena example, gcc 12.2 building the result with -m32 -g, and gdb 13.1 resolving the generated C. The marker extracts are that same compile with --markers. Addresses in the gdb output vary from run to run; the file names, line numbers, and function names do not.

Why this chapter has no sample

Every other chapter in the second half of this volume ends with a program that really ran: the coroutine scheduler of chapter 10, the socket of chapter 12, the debug loop of chapter 13. This chapter is different in kind. Its subject is not a program you write; it is what you do when a program you already wrote misbehaves. A sample here would be a bug, and a bug is not something the manual can ship as an example you are meant to reproduce.

So the page uses the arena example of Volume II chapter 14 as its stand-in, compiles it, and debugs it, and every fragment below is copied from that session. You do not need that particular program to follow along; you need any program that compiles, because the technique is the same for all of them. The point of the chapter is the method, and the method is small.

The debugger belongs to the C compiler

A modern toolchain ships the debugger with the language: the compiler knows the source format, so the debugger knows it too, and the two agree on file names, line numbers, and variable names. Z98 breaks that assumption on purpose. It does not ship a debugger, and — the correction this manual makes against the original blueprint — it does not ship a sidecar debugger either: there is no .z98dbg format anywhere in the toolchain. What it ships is a program in C89.

That is not a loss to work around; it is a change of instrument. The generated C is the same C a 1998 programmer would have written by hand: one plain function per Z98 function, a struct per struct, a file per module. It carries no #line directives — the emitted files were checked, and the preprocessor is never told to pretend the code came from a .z98 file — so gdb reports the generated file names and line numbers directly. Those are stable across builds, which is all a breakpoint needs. The upshot is that you debug a language you can read, with a debugger that has existed for decades.

The habit this chapter teaches is the one chapter 7 named as the way over its "no debugger UI" friction: treat the generated C as the debugging surface. The compiler has already done the hard part. It moved your program into C; the rest is standard C tooling.

Emit, then build

The first step is the one from chapter 8 and every build in this volume: point the compiler at your source and an output directory. The directory must already exist. The compiler creates files but not the directory that holds them, and if it is missing it says so and stops: 

$ /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol2/arena.z98
error: output directory does not exist: /tmp/manual_out

Create the directory, run the command again, and the result is a self-contained tree rather than one file. Here is the arena example's output directory with the directory created first: 

$ mkdir -p /tmp/manual_out
$ /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol2/arena.z98
$ ls /tmp/manual_out
arena_F3DC0DA4.c      arena_F3DC0DA4.h      build_target.sh
c_exit.c              net_prelude.h
std_arena_7156573C.c  std_arena_7156573C.h
std_fmt_5E28752C.c    std_fmt_5E28752C.h
std_io_59DB29D9.c     std_io_59DB29D9.h
std_net_A15200CC.c    std_net_A15200CC.h
zig_compat.h          zig_pal.c
zig_runtime.c         zig_runtime.h
zig_special_types.h

Read the names and you already know the shape of the debug session. Your module, arena.z98, became arena_F3DC0DA4.c; the standard modules it pulled in each got their own hashed file; and the runtime and platform sources are sitting beside them. The hash suffix is the emitter's way of keeping module names unique, and it is derived from the module's path, so for your own module it is stable for a given source path — the file you open today is the file you open tomorrow. The standard modules are resolved from the compiler's own lib directory, so their hashes track the compiler's install path as well: the std_… names this listing shows belong to a compiler installed at /tmp/manual_seed, and a compiler built in another directory emits different std_… suffixes for the same program. Read the hashes in a transcript as belonging to the run that produced it, and grep the file in front of you for the real one. The build script carries the compile and link commands for the target — here Linux: 

$ cd /tmp/manual_out
$ sh build_target.sh linux arena
Building for linux...
$CC -m32 -std=c89 -O0 -Wall -Wno-long-long -Wno-pointer-sign -Wno-implicit-function-declaration -I . -c arena_F3DC0DA4.c
…
Built: arena

The script is the supported build, and the gdb workflow starts from it. It does not, however, pass -g, because a shipping build should not carry debug information; that is the one thing you add yourself, in the next section. If you want only to see the C without building it, --dump-c89 remains the debug alias: with -o it writes the per-module .c/.h files, and without -o it writes a single file to standard output.

The cd DIR gotcha and the include path

Before the debug information, one trap, because it is the first wall a reader hits. The emitted tree carries its own headers, and the emitted C includes them by angle brackets — #include <net_prelude.h> and the like. An angle-bracket include is not searched for next to the including file; it is searched on the include path. The build script handles this by doing two things in one breath: it moves into its own directory, and it passes -I .. 

cd "$(dirname "$0")"
…
CFLAGS="… -I ."

So the rule is the script's rule: compile from inside the emitted directory, and let -I . point at it. Break the first half of that rule and the second half silently stops meaning what you think it means. A reader who runs the compiler's flags from the repository root gets a startling error far from the real cause: 

$ gcc -m32 -std=c89 -I . -c /tmp/manual_out/arena_F3DC0DA4.c
In file included from /tmp/manual_out/arena_F3DC0DA4.h:9,
                 from /tmp/manual_out/arena_F3DC0DA4.c:1:
/tmp/manual_out/std_net_A15200CC.h:6:10: fatal error: net_prelude.h: No such file or directory
    6 | #include 
      |          ^~~~~~~~~~~~~~~

The header exists. It is sitting in /tmp/manual_out. But the command was run from somewhere else, and -I . pointed at that somewhere else, so the include path never reached it. (The std_net_… hash in that message is the same /tmp/manual_seed name discussed above; your compiler's will differ.) The fix is either to run from inside the directory, exactly as the build script does, or to name the directory absolutely: 

$ gcc -m32 -std=c89 -I /tmp/manual_out -c /tmp/manual_out/arena_F3DC0DA4.c -o /tmp/manual_out/arena.o

Both work; the absolute -I is the one to reach for when a script or a Makefile invokes gcc from a different working directory. The second half of the same trap is the object files. gcc -c DIR/*.c run from outside writes the .o files into the caller's directory, not into DIR, so a later link of DIR/*.o finds nothing. Compile inside DIR, or give every output an absolute path. Either way, know which directory the command thinks it is in.

Build with debug information

The build script is the ordinary build. For debugging you rebuild the emitted C by hand with -g added and -O0 kept — the same flags the script uses, plus debug symbols and no optimization, so the source lines and the values you inspect are the ones the compiler actually meant. From inside the emitted directory: 

$ cd /tmp/manual_out
$ gcc -m32 -std=c89 -O0 -g -Wall -Wno-long-long -Wno-pointer-sign \
    -Wno-implicit-function-declaration -I . -c *.c
$ gcc -m32 -O0 *.o -o arena_g

Nothing Z98-specific happens in those two lines. -g is ordinary gcc debug information, and the layout it records is the Z98 layout, because the generated C has the Z98 layout: a struct you declared is the struct gdb inspects, field for field. That is the payoff of chapter 1's frozen 32-bit layout model. The one adjustment to keep in mind is that the names in the symbol table are the emitter's, not yours, and the next section is how to find them.

If you forget -g, gdb still runs the binary but has no source-level symbols: a breakpoint on main resolves to a bare address with no file and no line, and stepping shows instructions rather than C. The error is silent, so the habit is to add -g the first time, not after an hour of confused stepping.

A first gdb session

With a -g binary in hand, the session is standard. Start by stopping at the C entry point and asking where you are. This is a real batch session against the arena binary: 

$ gdb -batch -ex 'set pagination off' -ex 'break main' -ex run \
      -ex 'bt' -ex 'info line' --args ./arena_g
Breakpoint 1 at 0x31e5: file arena_F3DC0DA4.c, line 406.

Breakpoint 1, main () at arena_F3DC0DA4.c:406
406	    zF_780653D2___module_init();
#0  main () at arena_F3DC0DA4.c:406
Line 406 of "arena_F3DC0DA4.c" starts at address 0x… <main+29> and ends at 0x… <main+34>.

Read it carefully, because it contains the first surprise. You asked for main, and you got a main — but not yours. The emitted tree has two: the C entry point, which the runtime calls, and your Z98 pub fn main, which the C entry point calls after it has initialized the modules. The C entry point is the one gdb names plainly: 

int main(void) {
    zF_780653D2___module_init();
    zF_780653D2___module_init_1();
    zT_08A61393_EU_1 zT_main_result;
    zT_main_result = zF_EA90E208_main();
    return zT_main_result.is_error ? zT_main_result.err : 0;
}

So break main stops in the module initializers, at arena_F3DC0DA4.c:406. That is a fine place to watch initialization happen, but to stop at the start of your program's own main — the body zF_EA90E208_main, declared at the top of the file and defined at line 376 — you name that function directly. The section after the next one does exactly that for a function that takes arguments, so you can see values as well as lines.

Finding your function in the generated C

The names are the only part of the debug session that is genuinely different from ordinary C. Every Z98 function becomes a C function named zF_<hash>_<name>, where the hash is derived from the module and the trailing piece is your function's own name. The arena example compiles to these, among others: 

zF_3439BCE0_Point_init(arena, x, y)
zF_7F2346E9_single()
zF_BE36B55F_dual()
zF_EA90E208_main()

You do not have to guess the hash. It is printed in the generated file itself, in the comment above each definition, and the definition line is one grep away. This is the habit QUICK_REF.md records: search the generated C for the plain name, and the mangled name is on the line with it. 

$ grep -n 'Point_init' arena_F3DC0DA4.c
30:/* Point_init */
31:zT_D17889A1_EU_47 zF_3439BCE0_Point_init(zT_F22A6288_Arena* arena, int x, int y) {
144:    zT_22 = zF_3439BCE0_Point_init(zT_14, (int)((int)zT_18), (int)((int)zT_20));
176:    zT_42 = zF_3439BCE0_Point_init(zT_34, (int)((int)zT_38), (int)((int)zT_40));
312:    zT_31 = zF_3439BCE0_Point_init(zT_23, (int)((int)zT_27), (int)((int)zT_29));
328:    zT_45 = zF_3439BCE0_Point_init(zT_37, (int)((int)zT_41), (int)((int)zT_43));

Now break on that name and run. This transcript stops at the first call, prints the two scalar parameters, and walks the stack back to the entry point: 

$ gdb -batch -ex 'set pagination off' \
      -ex 'break zF_3439BCE0_Point_init' -ex run \
      -ex 'print x' -ex 'print y' -ex 'bt' --args ./arena_g
Breakpoint 1 at 0x2548: file arena_F3DC0DA4.c, line 40.
cap=32 used=0

Breakpoint 1, zF_3439BCE0_Point_init (arena=0xffe38df8, x=3, y=4) at arena_F3DC0DA4.c:40
40	    zig_poison_fill((void*)&zT_8, (unsigned int)sizeof zT_8);
$1 = 3
$2 = 4
#0  zF_3439BCE0_Point_init (arena=0xffe38df8, x=3, y=4) at arena_F3DC0DA4.c:40
#1  0x… in zF_7F2346E9_single () at arena_F3DC0DA4.c:144
#2  0x… in zF_EA90E208_main () at arena_F3DC0DA4.c:384
#3  0x… in main () at arena_F3DC0DA4.c:409

That is the whole technique. The breakpoint resolved to a generated file and a line; the arguments are the arguments your Z98 function declared; the backtrace is the call chain, with the Z98 functions in the middle and the C entry point at the bottom. cap=32 used=0 is the program's own output that ran before the breakpoint. Everything after the break is ordinary gdb: next, step, print, finish, watchpoints, conditional breakpoints. None of it is Z98-specific, so there is nothing to translate.

Two smaller habits make the names pleasant to work with. First, gdb completes: type zF_ and the tab key lists the mangled functions, which is faster than copying a hash by hand. Second, a breakpoint by file:line works just as well once you have looked at the file — break arena_F3DC0DA4.c:40 is the same breakpoint as the named one above. The name is stable across builds; the line number shifts when you edit the source, so use the name when you can.

Reading the generated C

The reason this workflow is workable is that the generated C is legible. Ask gdb to list the function you stopped in and you see the emitted body, not an opaque dump: 

  31	zT_D17889A1_EU_47 zF_3439BCE0_Point_init(zT_F22A6288_Arena* arena, int x, int y) {
  32	    zT_F22A6288_Arena* zT_4;
  33	    zT_4270ECBF_EU_16 zT_8;
  34	    unsigned char zT_9;
  35	    int zT_10;
  36	    zT_D17889A1_EU_47 zT_11;
  37	    unsigned char* zT_12;
  38	    zT_EAA8EF31_Point* zT_14;
  39	    zT_D17889A1_EU_47 zT_15;
  40	    zig_poison_fill((void*)&zT_8, (unsigned int)sizeof zT_8);
  41	    unsigned char* raw;
  42	    zT_EAA8EF31_Point* p;

The names tell you what the emitter did. The zT_ locals are the temporaries it created; a few of them, like raw and p, keep your own local names, so the code reads as a slightly noisier version of what you wrote. zig_poison_fill is the safety machinery: the default -fsafe mode fills a fresh local with a poison pattern so that a read before a write is a visible, deterministic value rather than whatever happened to be on the stack. The EU_47 return type is an error union lowered to a struct with an is_error flag and a payload, and the payload is the giveaway: in the generated zig_special_types.h it is a zT_EAA8EF31_Point*, which is exactly Point_init's ArenaError!*Point return. The zT_4270ECBF_EU_16 on line 33 is a different error union — ArenaError![*]u8, the type of allocBytes. The if (zT_1) goto z_bb_1; style is how the emitter spells control flow; the block labels are numbered from z_bb_1, and a z_bb_0: label is emitted only for a function whose block zero is a loop's self-recursion target, which is why this function has none.

None of this has to be memorized. It only has to be readable, and it is, which is the property the whole volume keeps returning to: the output is C89 you can inspect, so when a value looks wrong you can look at the C that produced it. The layout model of chapter 1 and the manual-vtable idiom of Volume II chapter 16 both come back here: the structs you print in gdb are laid out exactly as the C says, because the C is the layout.

Debugging the compiler: the --markers channel

Sometimes the bug is not in your program. The output is wrong, you have read your source twice, and the suspicion settles on the compiler that translated it. gdb is still a tool you can use — the compiler is a C program and can be built with -g, and chapter 7's two-hop seed rebuild is how you get a compiler binary to debug — but for most compiler bugs the faster instrument is the compiler's own trace. Z98 has one, and it is turned on with a single flag.

--markers turns on the marker channel. The compiler writes a line to standard error every time something interesting happens in the pipeline: a type is created, a string is interned, an arena grows, a function is forward-declared. It is not a logging framework and it has no levels; it is a running commentary the compiler was built with so that its authors could watch a compile the way you watch a program. Without the flag the channel is quiet. With it, a single compile of the arena example produces a few thousand lines, and the first ones show the phases in order. Here is the top of that stream: 

$ /tmp/manual_seed/zig1_5_clean --markers -o /tmp/manual_out docs/sf/manuals/src/vol2/arena.z98
arena perm: grew 4096 -> 16384
arena perm: grew 16384 -> 32768
arena perm: grew 32768 -> 65536
DC:k0n0t0
DC:k1n0t1
DC:k2n0t2
DC:k3n0t3
DC:k4n0t4
…
DC:k40n0t21
INT:new1
INT:new2
INT:new3
INT:new4
…
INT:new1259

and near the end, as the emitter writes out forward declarations and function bodies: 

FWD:n=395 m=9
P0:lc=2
FE:p0
FWD:n=397 m=9
P0:lc=2
FE:p0
FWD:n=400 m=9
P0:lc=2
FE:p0

Those prefixes are shorthand, and the compiler's own source is the only authoritative dictionary for them. A few are worth learning because they cover most of the stream. DC:k<kind>n<name>t<id> comes from the type registry: it is announcing that a new type has been appended, carrying the type's kind, the id of its name string, and the new type's own id. X:<id> follows when that type is a struct. INT:new<id> is the string interner adding a new string, and INT:dup<id> is it reusing one it already had — watch those and you can see whether the same identifier is being interned once or a hundred times. arena <name>: grew old -> new is the allocator reporting a bucket growth; the arena names — perm, module, scratch, type_db, import_scratch, diag_read — are the tiers of the compiler's own memory model, which is the subject of chapter 16 (planned). And FE:, FWD:n=… m=…, and P0:lc= are the emitter showing its work as it walks the functions.

The practical steps are small. Capture the stream to a file, because it is larger than a terminal should show: 

$ /tmp/manual_seed/zig1_5_clean --markers -o /tmp/manual_out docs/sf/manuals/src/vol2/arena.z98 2> markers.txt

then filter it. If you are chasing a type, look at the DC: lines; if you are chasing an identifier, count the INT:new lines; if a crash smells like memory pressure, follow the arena lines. One caution from the toolchain's own reference: read the file with grep -a, not strings. The marker channel can carry bytes that strings silently drops, so a pipeline built on strings can hide exactly the entry you were looking for. 

$ grep -a '^INT:new' markers.txt | wc -l
$ grep -a '^DC:' markers.txt | head
$ grep -a '^arena ' markers.txt | tail

Two things about the markers are worth saying plainly. First, they are diagnostic text, not a contract. The labels and their meanings live in the compiler's source and can change with the compiler; a script that depends on a particular prefix is a script that may break at the next rebuild. Read them the way you read a compiler's internal comments, not the way you read a command-line interface. Second, they trace the compiler, not your program. If a value is wrong at run time, markers will not show it, because they are all gone by then — they were written while the compiler was producing the binary you are now running. That division is the whole reason this chapter has two halves: gdb for the binary, --markers for the build that made it.

A related switch. The compiler's memory profiler is reachable through the same channel: --track-memory reports the peak of each arena, but it emits through the marker stream, so it only shows anything when --markers is on as well. The pairing and the numbers are chapter 16 (planned).

Two debuggers, side by side

Put the two halves together and the decision is a single question: is the wrong answer in the program or in the compiler? The table is the map.

What is wrong The tool How you reach it
Your program computes the wrong value, crashes, or loops gdb on the generated C emit, build the C with -m32 -g -O0, break on the mangled zF_… name or the generated file:line
The compiler emits wrong C, rejects a valid program, or crashes the --markers trace, then gdb on the compiler rebuild the compiler through the seed script, capture --markers to a file, and read the pipeline; build the compiler itself with -g only if the trace is not enough
You want to know how a Z98 construct lowers read the generated C --dump-c89 for a single file, or open the module .c in the emitted directory

The first row is the common case and the one the debugger exists for. The third row is the pleasant surprise of a compiler that emits C: a great many questions about Z98's semantics are answered not by documentation but by reading the C it produced. The second row is the rare case, and even it does not require a debugger UI; it requires a trace and the discipline to read it.

Honest note. There is no debugger UI in Z98, and there is no sidecar debugger: there is no .z98dbg. If you came expecting a window with a variable pane and a call stack you can click, this toolchain does not have one and will not grow one soon. What it has instead is a generated C file that reads like the C a 1998 programmer wrote, and a marker stream that shows the compiler thinking. Both are seams rather than products: you point the tooling and read the output rather than clicking through a front end. That is the same trade chapter 7 named, and it is worth naming here one more time because debugging is where the absence is felt most. The compensation is real, though: the C you debug is the code you could ship, so the thing you learn in the debugger is knowledge about the binary, not knowledge about a source map.

Common mistakes

The chapter has no program sample, but the workflow has a small set of failures that account for most of the wasted time. They are listed in the order they are usually made.

Running the compile from the wrong directory. The emitted headers are included by angle brackets and found on the include path, so a relative -I . only works from inside the emitted directory. Run the build script, or pass the directory absolutely. The symptom is a fatal error: net_prelude.h: No such file or directory even though the header is plainly there.

Forgetting that gcc -c DIR/*.c writes into the caller's directory. Compiling from outside DIR scatters the .o files next to you, not in DIR, and the link cannot find them. Do the compile inside DIR, as the build script does.

Building without -g and wondering why there are no line numbers. The build script intentionally omits debug information. Add -g and keep -O0; then break resolves to the generated file and line, and print knows your variable names.

Breaking on main and expecting your program. The plain C main is the runtime entry point, which initializes the modules before it calls your Z98 main. To stop at the start of your own program, break on the mangled zF_…_main instead.

Searching for a source file that is not there. gdb reports the generated names — arena_F3DC0DA4.c, not arena.z98. There are no #line directives, so the debugger never pretends otherwise. Find the function's mangled name with grep in the generated file and break on that.

Hunting for .z98dbg. The blueprint once imagined a sidecar debugger format; it does not exist. No file, no format, no tool. The debugging surface is the generated C.

Using --markers to find a bug in the program. The markers trace the compiler as it builds your program; by the time your program runs, the markers are long gone. They answer compiler questions, not program questions.

Trusting a marker prefix as a stable interface. The labels come from the compiler's own source and can change. Use them to look at a live compile, not as the contract of a permanent script.

Extracting markers with strings. The marker channel can carry bytes that strings drops, silently losing entries. Use grep -a on the raw capture, as the toolchain's own reference insists.

Debugging optimized C. Build with -O0. Optimization reorders statements and can make a source line step in an order that does not match the code you are reading, which turns a debugger into a source of confusion.

Where to go next

The ingredient this chapter relies on is the one chapter 3 made load-bearing: Z98 emits C89, so the C toolchain — and its debugger — applies. The friction this chapter answers is chapter 7's "no debugger UI," and the build it starts from is chapter 8, where the same emitted tree and build script appear for the Win9x target. When the fix is to make the emitted C faster or tighter, the hand-off to hand-written assembly is chapter 5; when the fix is to reach data the program was not built to expose, the interop rules are chapter 11. The memory profiler behind the --markers pairing is the subject of chapter 16 (planned), and the arena example this page debugged is Volume II chapter 14.

For lookup, Volume IV — Builtins catalogues the language surface the generated C lowers to, and the Reference volume will hold the marker and diagnostic references when the planned pages of it ship. The everyday debugger for the compiler's own output is gdb; the everyday reader of the generated C is you.
