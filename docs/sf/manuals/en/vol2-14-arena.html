The Arena — the Second Big Shift

Chapter 12 took the error code out of your hands. This chapter takes the heap. It is the second big shift for a C programmer, and the one that changes the shape of the programs you write: where a C program says malloc and free, a Z98 program owns a buffer and bumps through it.

If chapter 12 could be summarized as "the failure is in the type", this chapter summarizes as "the lifetime is in the scope". You do not allocate objects one at a time from a machine-wide pool; you set aside one block of bytes, hand it out in order, and reclaim everything at once when the work is done. There is no free, no destructor, and no hidden allocation. What there is instead is a small, exact API that you can read in full before lunch, and a discipline of resetting between phases that replaces the ownership questions malloc and free spend your career asking.

Honest note. You will reach for malloc; here is the Z98 way. The instinct is right and the tool is missing: Z98 has no malloc to call and no free to call, and the std surface re-exports std.arena, not a general-purpose heap allocator. What the language gives you instead is a contract you can read in ten lines: you supply the bytes, the arena hands them out in order, and reset takes them all back. The malloc-shaped question — "who frees this, and when?" — is answered before the allocation by the scope that owns the buffer. The cost is real, and this chapter is honest about it: one buffer size has to be chosen up front, and a phase that outgrows it fails with error.OutOfMemory rather than asking the operating system for more. That failure is the point. It is visible, it is typed, and it happens where you can see it.

The shift: no malloc, no free

In C, malloc answers "give me N bytes" with a pointer from a machine-wide pool, and free returns them. The pair is flexible and it is the source of the genre's classic failures. Every allocation needs a matching free on every path, including the error paths; the compiler cannot check the match; a missed free is invisible until the program runs out of memory, and a double free or a use after free is invisible until it corrupts something unrelated. The pool itself is shared and stateful: two libraries allocating in different orders can fragment it, and the amount of memory the program needs stops being a number you can point at in the source.

Z98 answers a different question. There is no machine-wide pool in the language, and no allocator function to call like malloc. The memory a program uses is memory it declared: arrays, structs, globals, locals. When a program needs "somewhere to put things whose count is only known at run time", it declares a byte buffer and hands an arena over that buffer. The arena is not a pool. It is a cursor: it remembers the buffer, its capacity, and how much has been handed out, and alloc moves the cursor forward.

That is the whole memory model in one sentence: allocation is bumping a cursor; reclamation is putting the cursor back to zero. Everything in this chapter follows from it. Allocation is a few instructions and cannot fail unless the bump would cross the end of the buffer. There is nothing to free individually, because there is no individual bookkeeping to do. And the lifetime of everything allocated in a phase is exactly the lifetime of the arena's current fill, which is exactly what reset rewinds.

The standard library's arena is one of the modules the standard surface re-exports, as std.arena. The implementation lives in sf/src/std_arena.zig, and it is small enough to read in full; the rest of this section quotes it. The honesty note above deserves one detail, because the name can mislead: the shipped library also carries a module named heap, but std_heap.zig is a binary min-heap — a priority-queue data structure whose own table is allocated from an arena. It is not a heap allocator, and std does not re-export it. There is no allocator in the surface to reach for.

The arena API

Four declarations, a struct, and one error tag. Here is the module, with the bodies trimmed for space: 

pub const Arena = struct {
    data: [*]u8,
    capacity: usize,
    used: usize,
};

pub fn init(data: []u8) Arena { ... }

pub const ArenaError = error{OutOfMemory};

pub fn alloc(self: *Arena, size: usize) ArenaError![*]u8 { ... }

pub fn reset(self: *Arena) void { ... }

Z98 has no method syntax, so these are plain functions called with the arena as the first argument. init takes a slice — the caller's buffer, usually written buf[0..] — and records the data pointer, the capacity, and used = 0: 

pub fn init(data: []u8) Arena {
    var a = Arena{ .data = data.ptr, .capacity = data.len, .used = 0 };
    return a;
}

alloc is the cursor bump. It checks that size still fits in the remaining capacity, returns the current position as a raw many-pointer to bytes, and advances used by size: 

pub fn alloc(self: *Arena, size: usize) ArenaError![*]u8 {
    if (self.used + size > self.capacity) return error.OutOfMemory;
    var result: [*]u8 = self.data + self.used;
    self.used += size;
    return result;
}

reset is the whole of reclamation: 

pub fn reset(self: *Arena) void {
    self.used = 0;
}

There is no deinit. The arena owns nothing to release: the bytes are yours, and the arena is a cursor over them. There is no alignment argument either; alloc hands back a byte position, and you get a typed object by casting that pointer with @ptrCast and computing the size with @sizeOf.

The API table, then, is four lines long:

Call Meaning
std.arena.init(buf[0..]) Build an Arena over a byte slice. Success is an Arena, never an error: the buffer already exists, so there is nothing to fail.
std.arena.alloc(&arena, n) Bump for n bytes. Success is [*]u8; failure is error.OutOfMemory. The return type is ArenaError![*]u8.
std.arena.reset(&arena) Set used back to zero. Every allocation made through the arena is reclaimed at once. There is no per-object free.
arena.used, arena.capacity The fields are public, so you can observe the cursor. The example below prints them.

Because the target is C89, the arena lowers to a plain struct with no runtime support at all. The emitted header for this chapter's example contains: 

struct zT_F22A6288_Arena {
    unsigned char* data;
    unsigned int capacity;
    unsigned int used;
};

The mangled type name is irrelevant, exactly as it was for chapter 12's error union; the shape is the point. A pointer, two counts, and functions that move a number. Nothing a C89 compiler cannot compile, and nothing that allocates behind your back.

ArenaError![*]u8: try or catch, never orelse

Look again at the one declaration that can fail: 

pub fn alloc(self: *Arena, size: usize) ArenaError![*]u8

This is chapter 12's error union, applied to memory. Success is a [*]u8 — raw bytes, no type attached. Failure is the one tag the arena can produce, error.OutOfMemory, declared as pub const ArenaError = error{OutOfMemory};. A caller reading the signature knows both things without reading the body: what it gets, and the one way it can fail.

Because the result is an error union, the tools are try and catch. try passes the failure on; the enclosing function must return a compatible error union, or the compiler rejects it: 

error[3075]: expected type 'void', found error set
note: function cannot return an error

catch handles it where it happens. A block capture binds the tag, and on a typed error set the tag prints as error.OutOfMemory: 

const big = allocBytes(&arena, 64) catch |err| {
    std.io.print("caught: {}\n", .{err});
    return;
};

The type is an error union, not an optional, and this is where C programmers reach for the wrong operator. orelse belongs to ?T; the arena's failure is not "absent", it is "failed". Asking orelse to handle the allocation is rejected, with a message that names the right tool: 

error[3016]: orelse requires an optional operand; use 'catch' for error unions

So the rule from chapter 12 carries over intact: ?T takes orelse, E!T takes catch. The difference matters philosophically as well as mechanically. "No memory available" is a failure of a request you made, and the compiler makes you say what happens next; it is not an absent value that quietly disappears.

One more consequence of the typed return: like every error union, an allocation result cannot be silently discarded (the error[3015] rule from chapter 12). Every call to alloc either trys, catches, or keeps the result in a variable for later. Memory is not something Z98 lets you ask for and then forget.

The init-function pattern

A cursor of raw bytes is not yet a useful object, so the standard pattern is a function that allocates, casts, fills in the fields, and returns the typed pointer. The language spec calls this the initialization pattern, and this chapter's example uses it: 

const Point = struct {
    x: i32,
    y: i32,
};

fn Point_init(arena: *std.arena.Arena, x: i32, y: i32) std.arena.ArenaError!*Point {
    const raw = try allocBytes(arena, @sizeOf(Point));
    const p = @ptrCast(*Point, raw);
    p.x = x;
    p.y = y;
    return p;
}

Read it as four steps: compute the size from the type with @sizeOf; ask the arena for that many bytes; promise the layout with @ptrCast; fill the fields. The return type says the call can fail the same one way the arena can, so the caller sees the failure in the signature rather than discovering it at run time. On success the caller has a *Point whose storage came from a buffer it controls.

This is also where the error union becomes visible in a signature you write yourself. The helper in the example names the arena's set exactly: 

fn allocBytes(arena: *std.arena.Arena, n: usize) std.arena.ArenaError![*]u8 {
    return std.arena.alloc(arena, n);
}

std.arena.ArenaError![*]u8 is the chapter in one type: a pointer to bytes on success, OutOfMemory on failure. Every fallible step above it uses try or catch; none of them uses orelse.

reset is the free

There is no per-object free, so the question "when is this object's memory released?" has a different answer: when the arena that handed it out is reset. Reclamation is all-at-once, and that is the feature. A phase that allocates twenty objects does not need twenty matching frees on twenty exit paths; it needs one reset when the phase's work is done, and the compiler's ordinary control flow — return, break, defer — decides when that is.

reset sets used to zero. It does not zero the bytes, and it does not run code. Two consequences follow; the first is visible in the example's transcript:

  • The next alloc hands out the same bytes again. A pointer from before the reset now points into the new allocation. The compiler cannot warn about this: the pointer is valid C, and the memory is valid C. What died was the ownership contract, not the address.
  • Nothing in the old phase gets cleaned up automatically. If an object owns an external resource — a file handle, a socket — close it before the reset. The spec is explicit: if a type manages external resources, it must clean them up manually before the arena is reset.

The spec's other line is worth repeating for anyone who came here from C: memory obtained from std.arena.alloc should not be passed to free(). It was never the heap's to free, and on these targets there is no heap in the language to free it back to.

The dual-arena pattern

One arena per program works, but it forces an unhappy choice: data that must live for the whole run and data that dies every phase share one fill level, so you can never reset without losing the long-lived data. The standard answer in Z98 is the dual-arena pattern: two arenas, two lifetimes.

Arena Holds Reset
Permanent Data that lives for the whole run: global symbols, persistent nodes, the structures the program is "about". Never, or once at the very end.
Scratch Temporary data: per-file, per-request, per-phase working memory. At every phase boundary, after the phase's results are copied or summarized.

The pattern is not a library feature; it is two Arena values. The example's dual function sets up both, allocates into each, then resets only the scratch arena and prints both fill levels to show that the permanent data survived. That is the whole discipline: long-lived data goes in one arena and is never reset; phase data goes in the other and is reset at each boundary.

On a 1998 machine the second arena is not just a hygiene measure. It keeps the active working set small — the scratch arena is sized for one phase, not for the union of all phases — and it keeps allocation predictable, because the same phase run twice sees the same bumps in the same order. The language spec introduces the pattern for exactly this reason and names the Lisp interpreter as the working example: a compiler or interpreter is a loop of phases over permanent state, and the scratch arena is what makes the loop reusable.

The example

The whole chapter in one program. single uses one arena from the first byte to the OutOfMemory path; dual uses two arenas and resets only the scratch one. Point_init is the init-function pattern, built on allocBytes, whose return type is the chapter's one signature: std.arena.ArenaError![*]u8. 

const std = @import("std");

const Point = struct {
    x: i32,
    y: i32,
};

fn allocBytes(arena: *std.arena.Arena, n: usize) std.arena.ArenaError![*]u8 {
    return std.arena.alloc(arena, n);
}

fn Point_init(arena: *std.arena.Arena, x: i32, y: i32) std.arena.ArenaError!*Point {
    const raw = try allocBytes(arena, @sizeOf(Point));
    const p = @ptrCast(*Point, raw);
    p.x = x;
    p.y = y;
    return p;
}

fn single() !void {
    var buf: [32]u8 = undefined;
    var arena = std.arena.init(buf[0..]);
    std.io.print("cap={} used={}\n", .{ arena.capacity, arena.used });

    const p = try Point_init(&arena, 3, 4);
    std.io.print("p={} {} used={}\n", .{ p.x, p.y, arena.used });

    std.arena.reset(&arena);
    std.io.print("used after reset={}\n", .{arena.used});

    const p2 = try Point_init(&arena, 9, 8);
    std.io.print("p2={} {} reused p.x={}\n", .{ p2.x, p2.y, p.x });

    const big = allocBytes(&arena, 64) catch |err| {
        std.io.print("caught: {}\n", .{err});
        return;
    };
    std.io.print("unreachable {}\n", .{@intFromPtr(big)});
}

fn dual() !void {
    var perm_buf: [128]u8 = undefined;
    var scratch_buf: [64]u8 = undefined;
    var perm = std.arena.init(perm_buf[0..]);
    var scratch = std.arena.init(scratch_buf[0..]);

    const p = try Point_init(&perm, 3, 4);
    const q = try Point_init(&scratch, 5, 6);
    std.io.print("perm={} {} scratch={} {}\n", .{ p.x, p.y, q.x, q.y });
    std.io.print("perm used={} scratch used={}\n", .{ perm.used, scratch.used });

    std.arena.reset(&scratch);
    std.io.print("scratch used after reset={} perm used={}\n", .{ scratch.used, perm.used });
}

pub fn main() !void {
    try single();
    try dual();
}

$ cd /tmp/manual_out && sh build_target.sh linux arena

perm used=8 scratch used=8
scratch used after reset=0 perm used=8

Read the eight lines as the chapter's arc. The arena starts at cap=32 used=0. One point takes eight bytes (2 × i32), so used=8 and the fields read back as written. The reset puts the cursor back to zero. Then the same bytes are allocated again — and because p still points at them, p.x now reads the new object's 9: the old pointer was never invalidated, it was simply reused. That is the ownership rule made visible in one line. The 64-byte request then cannot fit in the 32-byte buffer, and the failure is typed and caught: caught: error.OutOfMemory. The program never reaches the unreachable line.

The dual-arena half shows the pattern's payoff. Both arenas hold their allocation, the permanent one is left alone, and the scratch reset returns scratch used to zero while perm used=8 stands. The program exits with status 0.

Common mistakes

The mistakes below are the ones a C programmer makes first with this API. Each has a diagnostic or a corrected shape, and the first one is the reason this chapter exists.

Reaching for malloc and free. There is no malloc to call, no free to call, and no allocator in the std surface to reach for instead; the arena is the answer, and its buffer is memory you declared. The old habit does not merely fail to compile — it asks a question the language has no way to answer well. A C program answers "when is this released?" at every call site, by hand, on every path; an arena answers it once, at the reset. If you bring a general-purpose allocator in through C interop anyway, the spec's rule stands: memory obtained from std.arena.alloc must not be passed to free().

Using orelse on the allocation. The result is ArenaError![*]u8, an error union; orelse is the optional's operator. The compiler rejects the confusion and names the right one: 

error[3016]: orelse requires an optional operand; use 'catch' for error unions

Write try when the caller can pass the failure on, and catch |err| when it must handle it. Chapter 13 (planned) is where optionals and orelse live.

Forgetting reset between phases. The arena never reclaims on its own, so a program that allocates per phase without resetting behaves like a leak: used climbs to capacity and every later allocation fails with error.OutOfMemory even though the phase data is long dead. The failure is loud, which is the good news; the fix is one call at the phase boundary. In the example the buffer is small enough that the 64-byte request fails either way — but in a long-running loop the missing reset is the difference between a program that keeps running and one that stops on phase N. Reset the scratch arena when the phase ends, not when the arena is full.

Assuming the memory is zeroed. alloc does not clear bytes; it moves a cursor. The example shows the reused block reading back as the new object's fields, not as zeros. The related trap is undefined: in Z98 an uninitialized i32 is not zero. Under the default safe build, undefined is poison-filled and reads back as -1431655766 (0xAAAAAAAA), a value that hides very well until it reaches a pointer or a loop bound. Set every field you are going to read; do not treat arena bytes as a fresh zero page.

Growing a dead reference after reset. After the reset in the example, p and p2 point at the same bytes, and the transcript prints that aliasing as reused p.x=9. Nothing in the language stops you from reading p afterwards, because nothing in the language tracks which fill level a pointer came from. The compiler sees a valid pointer to valid memory; only you know that its ownership contract ended. The corrected shape is a rule, not a diagnostic: after a reset, every pointer that came from the arena is dead — use the pointers from the current fill or none.
