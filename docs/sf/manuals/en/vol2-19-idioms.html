Idioms and Best Practices

Chapter 18 closed the language. The format string was the last surface feature this volume had to explain, and after it there is nothing new to introduce. This chapter is the one that collects the working habits the previous chapters have been demonstrating all along. Every idiom below was already taught by a chapter; none of them is a new compiler behavior, and this page adds no code of its own. It is the volume's cross-reference hub: when a later program needs the arena, the init function, the manual vtable, or the rule about uninitialized memory, this is the page that names where each one was learned.

The six idioms are the ones that separate a Z98 program from a C program that happens to compile under Z98. The language spec keeps them in one place, its section 6, under the heading "Z98 Idioms and Best Practices", and the shipped chapters have each worked one in full. Read in order they are:

  • Arena ownership — the buffer is yours and the arena is a cursor over it; allocation is fallible and reclamation is one reset. (Chapter 14.)
  • Init functions — an object becomes usable through a free function that fills its fields and returns it, because there are no constructors. (Chapter 14, chapter 16.)
  • Manual virtual tables — a struct of function pointers plus one erased data pointer, because there are no methods and no classes. (Chapter 16.)
  • Dual arenas — one arena for data that lives for the whole run, one for data that dies every phase, so a reset never costs you the permanent state. (Chapter 14.)
  • Runtime initialization — complex global state is built by a dedicated init() called at startup, not by a large constant initializer.
  • undefined is not zero — an uninitialized value holds the poison fill under the default safe build and nothing at all under -ffast; it is never quietly zeroed. (Chapter 14, chapter 4.)

The working programs behind the first four are the shipped examples docs/sf/manuals/src/vol2/arena.z98 and docs/sf/manuals/src/vol2/shapes2.z98. Neither is reproduced here; this chapter cites them by path and describes the shape they share. If you want to see an idiom run, that is where to look.

Honest note. You will reach for the constructor and the destructor; here is the Z98 way. The habit is the deepest one a C++ programmer brings: an object knows how to create itself, and it knows how to clean itself up when its scope ends. Z98 has neither half of that pair. There is no constructor keyword, no destructor, no new, no delete, and no automatic call when a value goes out of scope. An object is ready when a free init function has filled its fields, and a resource is released when you release it — by defer at the end of a scope, by errdefer on the failure path, or by the one reset that ends a phase. The trade is the same one the whole language makes: you write the lifetime down instead of letting the compiler infer it, and in exchange nothing runs behind your back and the generated C has no hidden control flow. It is more spelling and fewer surprises.

The arena owns the memory

The first idiom is the one the volume returns to in every later program: a program that needs storage whose count is only known at run time declares a byte buffer and hands an arena over it. Chapter 14 introduced the API and its four lines are the whole contract. std.arena.init(buf[0..]) records the buffer's pointer, its capacity, and used = 0; std.arena.alloc bumps the cursor forward and returns ArenaError![*]u8; std.arena.reset puts the cursor back to zero; and the used and capacity fields are public so a program can observe the fill level. There is no deinit, because the arena owns nothing of its own — the bytes belong to the caller.

Ownership is the part that is easy to say and easy to get wrong. The rule the spec states is that functions should accept a *std.arena.Arena rather than "owning" their memory: the caller declares the storage and decides its lifetime, and the callee receives a cursor it may bump. That is why Point_init in docs/sf/manuals/src/vol2/arena.z98 takes an arena as its first parameter and returns a pointer, instead of allocating on its own and returning something whose storage it secretly manages. Any function on the page that allocates follows the same shape, and a caller that reads only the signature can see where the memory comes from and who can reclaim it.

The second half of ownership is the reset. Chapter 14's transcript makes the consequences concrete: after std.arena.reset(&arena) the next allocation hands back the same bytes, and a pointer taken before the reset now reads the new object's fields. The transcript prints that aliasing as reused p.x=9. Nothing about the old pointer became invalid in the C sense — it still points at valid bytes — but its ownership contract ended with the reset. The corrected habit is a rule rather than a diagnostic, because the compiler cannot check it: after a reset, every pointer that came from the arena is dead, and only pointers from the current fill may be used.

Two smaller rules ride along with arena ownership, and both come from the same chapter. Allocation is fallible, so try or catch unwraps it; orelse is rejected with error[3016] because orelse belongs to optionals. And a resource that lives outside the buffer — a file handle, a socket — must be closed before the arena is reset, because reset only moves a number; it runs no cleanup code. Chapter 14 puts the arena's one signature where a reader can see it, std.arena.ArenaError![*]u8, and the phrase to carry away is: the success is raw bytes, the failure is error.OutOfMemory, and both are in the type.

Init functions build the object

A cursor of raw bytes is not yet a useful object, so every type that wants one gets an init function. Chapter 14 showed the four steps: compute the size with @sizeOf, ask the arena for that many bytes, promise the layout with @ptrCast, and fill the fields. Its Point_init is the pattern in one function, and its return type std.arena.ArenaError!*Point carries the allocation failure up to the caller. Chapter 16 then generalized the idea: an object is ready when its payload fields are set and, when it takes part in an interface, an interface value names its operations. The two jobs belong together in one function so they cannot drift apart at the call site.

The spec names the same pattern in its initialization section, and it is worth restating why it is a function rather than a language feature. Z98 targets C89 and avoids complex destructors, so the "constructor" is deliberately an ordinary function that takes a pointer to the destination and returns the initialized value. The caller owns the storage, which means the caller can put it on the stack, in a global buffer, or in an arena. Global aggregate constants use a related shape: the compiler's own source declares them as pub var and initializes them in a dedicated function rather than in a large literal. That is the next idiom but one, and it is the same idea at module scope.

Chapter 16 measured three accepted forms of the pattern, which is worth knowing because a reader may see any of them. A value-returning fn shape_init(f: fn (*void) void, d: *void) Shape that does nothing but build the literal compiles and runs; a pointer-init fn shape_init(s: *Shape, f: fn (*void) void, d: *void) void that fills an already-declared interface compiles and runs; and the form the sample uses takes the payload destination, fills it, and returns the interface in one call. The chapter chose the third because one call sets both halves, but the compiler does not force a favorite. The shape that matters is not which form you pick but that construction goes through a named function and not through a hidden language mechanism.

The absence the idiom replaces is real: there is no constructor to call and no destructor to rely on. Chapter 4 already warned about the C++ habit in its common-mistakes list — there is no Sprite.init() — and chapter 16 supplied the replacement in full. The sample's circle_init and square_init in docs/sf/manuals/src/vol2/shapes2.z98 are init functions that also build the manual vtable, and they are the pattern exercised twice on two concrete types.

Manual virtual tables

The third idiom is the one the volume's second mental shift made necessary. Z98 has no methods and no classes, so polymorphism is not a language feature; it is a struct of function pointers that you build by hand. Chapter 16 writes the interface as struct { draw_fn: fn (*void) void, area_fn: fn (*void) f32, data: *void }: two operations and one erased data pointer. Each concrete shape is an ordinary struct, each operation is a free function that receives the erased pointer and casts it back with @ptrCast, and dispatch is an ordinary call through the field with the data pointer as the argument. There is no receiver magic and nothing to look up at run time.

The chapter measured the cost and it is the reason the pattern is a best practice rather than a workaround. The sample's first output line is Shape size=12 align=4 fn=4: on the 32-bit target the interface is three words, two function pointers and the data pointer, at four bytes each. The emitted C shows a Z98 function pointer becoming an ordinary C function pointer — fn (*void) void becomes void (*)(void*) — with no hidden receiver argument. That is exactly why the receiver has to be passed by hand at every call, and it is why the generated C is readable line by line.

The vtable's one real hazard is the erased data pointer. The type checker knows the function signature and does not know what the function will cast the data to, so a program can build a Shape whose operation casts a *Square to *Circle. Chapter 16's answer is the reason the init-function idiom sits beside this one: the init function is where the payload and its operations are paired, so the contract lives in one place instead of being spread across call sites. Build every interface through an init function, keep the payload and its operations in the same file, and the cast back always matches what was stored. The sample does this in docs/sf/manuals/src/vol2/shapes2.z98, where circle_init and square_init are the only places a Shape is ever constructed.

It is worth naming what a vtable is not, because the erasure invites the wrong comparison. A Z98 manual vtable is not a class with virtual functions and it is not a language object with a hidden type tag; it is a plain struct of C function pointers that you could have written in C89 by hand. The language adds no table, no metadata, and no dispatch. What it adds instead is the checker on the function-pointer signatures, so the fields of the vtable are typed even though the data behind them is not.

Two arenas, two lifetimes

The fourth idiom is the answer to the question the single arena forces: what if some data must live for the whole run while other data dies every phase? One fill level cannot serve both, because any reset that reclaims the phase data would also throw away the permanent state. Chapter 14 gives the standard answer: the dual-arena pattern, two arenas with two lifetimes. The permanent arena holds data that lives for the whole run and is never reset, or is reset once at the very end; the scratch arena holds per-file, per-request, or per-phase working memory and is reset at every phase boundary, after the phase's results have been copied out or summarized.

The pattern is not a library feature. It is two Arena values, and the chapter's dual function in docs/sf/manuals/src/vol2/arena.z98 is the whole of it: it sets up both arenas, allocates into each, then resets only the scratch arena and prints both fill levels to show that the permanent data survived. The spec describes the same pattern for the same reason and names the Lisp interpreter as the working example — a compiler or interpreter is a loop of phases over permanent state, and the scratch arena is what lets the loop run again without leaking a phase's worth of memory into the next.

On the era's hardware the pattern earns its keep twice over. It keeps the active working set small, because the scratch arena is sized for one phase rather than for the union of every phase the program will ever run, and it keeps allocation predictable, because the same phase run twice sees the same bumps in the same order. The chapter's own words are the best summary: reset the scratch arena when the phase ends, not when the arena is full. A missing reset does not fail quietly — used climbs to capacity and the next allocation is error.OutOfMemory — but the fix is one call at the phase boundary, and that is the discipline.

Runtime initialization

The fifth idiom moves the init function to module scope. For complex global state the spec's rule is explicit: avoid large constant initializers and use a dedicated init() function called at startup. Its example is a global array declared undefined and filled by a named function, the module counterpart of the Point_init pattern from chapter 14. The compiler's own source follows the rule, and it is why global aggregates there are declared pub var and filled in an init function rather than in one enormous literal. The reason is not style: a C89 program has no place to run a non-constant global initializer before main, so the work has to happen in code you can point at.

The rule interacts with the next idiom directly, because the global is declared undefined first. That undefined is a promise to the compiler that the value will be written before it is read, not a request for zeroes. The program then keeps the promise in the init function. This is the same declaration shape chapter 4 describes for a local: write every field you intend to read, or write = undefined and fill the value before using it. Chapter 4 also names the diagnostic for a declaration with no initializer at all, error[3014], whose message is the direct instruction: use = undefined to opt out.

One global-initializer detail is worth recording here because it is the failure mode of the idiom. When globals do have literal initializers, the compiler orders them by dependency so a forward reference is materialized before use, and it rejects only a genuine cycle. Chapter 8 captured that rejection: two globals whose initializers refer to each other are error[3064]: cyclic global initializer dependency. Runtime initialization sidesteps the whole question, because a function body is a sequence of statements rather than a graph of initializers; a cycle cannot be expressed when the assignment order is the order you wrote.

undefined is not zero

The sixth idiom is the one that ruins a C programmer's first debugging session, so it is worth stating flatly: an uninitialized value in Z98 is not zero. The spec is unambiguous. Under the default safe build, -fsafe, storage initialized with undefined is byte-filled with 0xAA so that an uninitialized read is visible. Under -ffast there is no fill at all, and the bytes hold whatever was there before. Chapter 14 put the poison value on the page: an uninitialized i32 reads back as -1431655766 (0xAAAAAAAA), a value that hides very well until it reaches a pointer or a loop bound. Neither mode zeroes.

This is the opposite of the C habit it replaces, and the difference shows up in three places the earlier chapters each named. A struct literal that omits a field does not zero it: chapter 4 explains that the literal compiles and the omitted field holds whatever the memory contained, unlike C's aggregate initializer where the fields you skip are quietly zeroed. Arena memory is not zero either: std.arena.alloc moves a cursor and does not clear bytes, so the reused block in chapter 14's transcript reads back as the new object's fields rather than as zeroes. And the poison itself is not a value you can test for and handle; 0xAAAAAAAA is just a number that a program will happily add to an offset or use as an index.

The corrected habit is the one both chapters reach for: set every field you are going to read. Reach for = undefined only when you mean it as a promise, and then keep the promise before the next read. The rule is not a safety net that will catch a forgotten assignment; it is a marker that makes one visible. If a program needs zeros, it has to write them, because no part of Z98 — not the declaration, not the arena, not the safe build — will write them for you.

The idioms together

The six are easier to keep once they are seen as one shape instead of six rules, and the two shipped examples are that shape split in half. docs/sf/manuals/src/vol2/arena.z98 is the memory half and docs/sf/manuals/src/vol2/shapes2.z98 is the object half. Read in order, they walk through the same sequence a real program does.

Storage is declared first and owned by the caller. arena.z98 opens with a byte buffer and an arena over it; shapes2.z98 opens with the payload structs and a concrete list. In both cases the bytes exist before any object does, and no call in either program asks the system for memory. That is the first idiom in one sentence: the program owns the storage and the arena or the list is a cursor over it.

Each object is then built by its init function rather than by a constructor. arena.z98's Point_init takes the arena and returns a typed pointer; shapes2.z98's circle_init and square_init take the payload destination and return an interface value. Both are ordinary functions with the destination as a parameter, and both are fallible where the storage is fallible, which is why arena.z98's return type is an error union and its callers use try. Construction and ownership stay in the same signature, so a reader can see where the memory came from and how the object was made without leaving the call site.

The object half of shapes2.z98 adds the manual vtable, and it shows why the vtable and the init function are taught together. The interface struct holds the operations and one erased pointer; the init function is the only place the payload and its operations are paired; dispatch is an ordinary call through the field. Nothing about the interface outlives the payload the init function filled, and the payload lives in the storage the caller declared, which is the point where the object half meets the memory half.

The dual-arena pattern is what lets the memory half run more than once. arena.z98's dual function keeps one arena for the whole run and resets only the other, so the phase can repeat without discarding the permanent state. A global registry would go in the permanent arena, or in a pub var filled by a runtime init function when it is aggregate state rather than arena-backed state. And every value that is declared before it is filled — the payloads, the list, the buffer — is declared undefined, which is the marker that says a value is not yet written and is not zero. Fill it before you read it, and the six idioms become one discipline: declare the storage, build the object with a function, pair it with its operations, give the long-lived and short-lived data separate lifetimes, initialize global state at run time, and never read a value before something has written it.

Common mistakes

The mistakes below are the ones that arrive with the habits of C, C++, or modern Zig. Each has a measured correction from a chapter already written, and each correction is the language's rule rather than a style preference.

Reaching for a constructor or a destructor. There is no constructor keyword, no destructor, no new, and no delete. Construction is a named init function that fills a destination the caller owns; chapter 16 documents the pattern and chapter 4 records the rejection a C++ reader meets first, Sprite.init() failing because a struct has fields and no members. Destruction is not automatic either. An object that owns an external resource must release it by hand before its storage is reclaimed, which in practice means defer or errdefer at the end of the owning scope, or an explicit close before the arena reset. There is no scope exit that runs code for you.

Zeroing by default. C's {0} aggregate initializer and calloc have no counterpart. An omitted struct field holds garbage, an arena block holds whatever the last phase left there, and undefined holds the poison fill under -fsafe and nothing under -ffast. The correction is to write the fields you will read and to stop treating fresh storage as a zero page. If a value must start at zero, assign zero.

Expecting a hidden allocation. No operation in the language allocates behind your back. A container does not grow itself — chapter 16's ShapeList is a concrete struct with fixed capacity and a length field, and its shapeList_push writes into storage the caller declared. The standard library follows the same rule: std.arena.alloc bumps a buffer you supplied, the string and byte functions take slices you own, and there is no general-purpose allocator re-exported to reach for. When a program needs storage whose count is only known at run time, the answer is an arena and an init function, and both make the allocation visible in a signature.

Using orelse on a fallible call. An allocation result is an error union, not an optional, so orelse is the wrong operator and the compiler says so with error[3016]. Write try when the caller can pass the failure on and catch |err| when it must handle it. Optionals and orelse live in chapter 13; error unions and try/catch live in chapter 12.

Assuming a reset cleans up. std.arena.reset sets used to zero and does nothing else. It does not zero bytes, does not run destructors, and does not close handles; a pointer from before the reset is still valid C memory, which is why the compiler cannot warn. The correction is the ownership rule from the first section: release external resources before the reset, and treat every pointer from the old fill as dead afterward.
