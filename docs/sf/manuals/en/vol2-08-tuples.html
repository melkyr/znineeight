Aggregates V: Tuples

The tuple is the aggregate that has no names. A struct gives every field a name; a tuple gives every element a position. It is written down like a struct whose members are only types, built with a positional literal, and read back through an ordinal: p.0, the first element, p.1, the second. That is the whole feature.

This is the last of the aggregate chapters. The previous four built records out of structs and packed structs, gave small sets of numbers names with enums, and overlapped storage with unions. The tuple adds no new storage rules; it takes the struct layout and removes the field names. What is left is exactly what a call boundary needs: an ordered bundle of values that everyone can address by position because there is nothing to get wrong about the spelling.

The chapter's program is docs/sf/manuals/src/vol2/pair.z98. It uses a tuple for the two jobs the blueprint names for it — the argument list of print, and a function's grouped return — and shows the field access that unpacks the return: 

17/5 = 3 remainder 2
pair .{ 7, 3 }
spellings 7 7 3 3
copy 3 sum 10

Everything else about tuples in this chapter is measured on the compiler shipped with this manual, and every diagnostic quoted below is the one the compiler actually prints.

A struct with positional fields

A tuple type is a struct declaration whose members are plain types. The type is named the way every aggregate in this dialect is named, through a const: 

const Pair = struct { i32, i32 };

That declaration names the type {i32, i32}: two elements, both i32, the first at position 0 and the second at position 1. A value of the type is built with an anonymous positional literal, .{ a, b }, where the elements appear in the order the type declares them: 

const p: Pair = .{ 7, 3 };

The literal's elements are typed by what they are, and the literal is coerced to the surrounding tuple shape: write const q = .{ 7, 3 }; and the compiler infers the same pair shape from the two values. The two spellings interchange freely; assignment and argument passing copy the elements field-wise, and a shape-identical tuple is assignable to a named type and back. The chapter's program leans on that: it copies a named Pair into another, and the chapter's probe copied an inferred .{ 7, 3 } into a Pair variable and printed 7 3. A mismatched arity or element type is a clean reject, as elsewhere: 

error[3000]: type mismatch in assignment -- internal type representations differ; generated code may be incorrect
note: source: tuple
note: target: tuple

Reading an element is the interesting part, because there are three spellings and they all lower to the same positional field: p.0 and p.1 (the spec's original spelling), p._0 and p._1 (the emitted C field spelling), and p[0] and p[1]. The chapter's program prints one line through all three spellings, using both positions: 

std.io.print("spellings {} {} {} {}\n", .{ p.0, p._0, p[1], p.1 });
// spellings 7 7 3 3

For C programmers the representation is exactly what the ._0 spelling suggests: the compiler lowers a tuple to a C struct whose fields are named _0, _1, and so on, in declaration order. The ordinal forms (.0, ._0) and the comptime index form (t[0]) are front-end spellings for that same field; you never need to pick one because of where the value is stored.

The index in bracket form must be comptime-known. A runtime index is rejected with the rule's own wording: 

error[3069]: tuple field index must be comptime-known

An ordinal past the end of the tuple is rejected by name and count, and a negative one by the type the index has to have: 

error[3070]: index 2 outside tuple of length 2
error[3062]: type 'usize' cannot represent integer value '-1'

And a numeric member on something that is not a tuple is the ordinary unknown-member reject: a slice sl.73 reports error[3060]: no field or member function named '73' in slice type, and an i32 reports the same error with in type. A numeric member is never treated as a name lookup; if the base is not a tuple, there is nothing for the ordinal to mean.

The layout follows the struct rules from chapter 4 with the frozen 32-bit alignment model of chapter 2: each element sits at its natural offset, the tuple's alignment is its widest element's, and the total is padded to that alignment. Probe types measure:

Type Elements @sizeOf @alignOf @bitSizeOf
Pair {i32, i32} 8 4 64
Wide {u8, i64, u8} 24 8 192

Wide is the interesting row: it is declared the same way, struct { u8, i64, u8 }, and the i64 in the middle is size 8 and alignment 8, so the first byte pads to offset 8 and the tuple ends at 24 bytes. A tuple is a record with the same layout arithmetic as a named struct; the only difference is that its fields cannot be spelled with names.

One introspection builtin does not take a tuple. @offsetOf and @bitOffsetOf expect a struct type, and a tuple type is rejected outright: 

error[3072]: expected struct type, found 'Pair'

There is nothing surprising about the refusal: a tuple's members are positional, and the builtin asks for a field by name. Use chapter 4's named structs when an offset is part of the question. @sizeOf, @alignOf, and @bitSizeOf accept tuple types as the table above shows.

Global tuple variables work like any other global; a module-level literal may even reference a global declared later in the file, because the module's initializers are emitted in dependency order. A probe compiled var g = .{ b, 7 }; const b = 5; and printed g 5 7. A cycle in that dependency graph is the one shape with no valid order, and it is a clean reject: 

error[3064]: cyclic global initializer dependency

Cross-module tuples are ordinary values too: an imported module can export a tuple type and a function returning it, and the importing module can declare variables of that type, call the function, and copy the result. A probe's two-module program printed xmod 3 2 4 9 for exactly that shape.

Why tuples exist

The blueprint gives the tuple two reasons to exist: print and grouped return values. Both are call-boundary jobs, and both are about handing over several values as one.

The first reason is visible in every printing call in this manual. The second argument of print is a tuple literal: 

std.io.print("{} {}\n", .{ 1.5, 7 });

The compiler decomposes that literal and emits one runtime print per placeholder, so the argument list is exactly an ordered bundle whose positions are fixed by the format string. The container may also be a tuple variable, which reads each element for its placeholder: 

const t = .{ 1, 2, 3 };
std.io.print("t {} {} {}\n", t);
// t 1 2 3

The rule for what may be a container is narrow, and its diagnostic says so: 

error[3065]: print arguments must be a tuple literal

That is the error for a bare value, a non-tuple variable, an expression such as a == b, or an anonymous struct initializer. A call with a format plus more than one container is rejected by arity instead: 

error[3061]: expected 2 argument(s), found 3

The second reason is the grouped return. A function with several results to hand back declares one tuple return type and returns one literal: 

fn divmod(a: i32, b: i32) Pair {
    return .{ a / b, a % b };
}

The caller receives one value and unpacks it by position: q.0 is the quotient and q.1 is the remainder. That is the shape the chapter's program prints as 17/5 = 3 remainder 2. A tuple can be a parameter the same way — the program's sum takes a Pair and returns p.0 + p.1 — and a tuple literal can be passed directly where a tuple parameter is expected, as in sum(.{ 1, 2 }).

Those two jobs are the whole intended surface. Between the call and the return, a tuple is a transient: it carries the values across the boundary and the positions take their meaning from the callee's parameter list or the caller's format string. Storing one is where the trouble starts.

Why not to use them anywhere else

The tuple's lack of names is a convenience at a call boundary and a liability everywhere else. Four reasons, in the order they bite.

Positional access does not document itself. q.0 is a value whose meaning lives in the function that produced it; six months later the reader has to find divmod to learn that position 0 is the quotient. A named struct costs one declaration and makes every access self-describing, and the layout arithmetic is identical. 

const Quotient = struct { q: i32, r: i32 };

Layout introspection refuses tuples. @offsetOf rejects a tuple with error[3072], because there is no field name to ask about. When offsets, sizes, or a wire layout matter, chapter 4's structs and chapter 5's packed structs are the tools; a tuple is the wrong container for a record whose bytes are part of the contract.

Serialization has nothing to hold on to. The emitted C field names _0, _1 are implementation spellings, not a data format; the order is the declaration order and the padding follows the alignment model. Writing a tuple to a file or a network buffer as if its C layout were the wire format is the same mistake as assuming a struct's padding. Use a packed struct (chapter 5) or an array (chapter 9, planned) when bytes are the contract.

Tuples are structural, and walking them is not a thing. Every struct { i32, i32 } is the same type for assignment purposes; two tuples with the same shape are interchangeable whether or not the program thinks of them as different concepts. And the index must be comptime-known (error[3069] on a runtime index), so a tuple cannot be iterated with a loop variable the way an array can. A tuple is a bundle, not a collection.

The working rule: use a tuple at the boundary where the callee's parameter list or the format string supplies the names, and use a named struct or an array the moment the value gets stored or serialized.

Honest note. The tuple surface is small, and its edges are worth knowing before they surprise you. Printing a tuple with {} works and shows the elements in C-like braces (pair .{ 7, 3 }), but the printer is depth-limited: a nested tuple deeper than three levels prints its deepest level as .{ ... }, as in the probe line nested .{ .{ .{ .{ ... }, 3 }, 4 }, 5 }. An element whose type has no printer makes the whole tuple reject with error[3063]: print argument type is not supported (no std.fmt printer) — a type used as an element such as .{ i32, 5 } and a void element both reject that way. Chained access after an ordinal does not parse: e.0.w is error[2000]: expected field name or index after '.', while (e.0).w and e[0].w read the struct field normally. @offsetOf rejects a tuple type (error[3072]), and a spelled tuple type with an array element is refused at the declaration with error[3000]: tuple types with array elements are not supported. A placeholder beyond the container's arity is silently dropped rather than diagnosed. An untyped integer literal element takes a carrier chosen from its value, so const big = .{ 3000000000, -3000000000 }; prints 3000000000 -3000000000 exactly. And the copy is field-wise: a shape-identical tuple assigns to a named tuple type and back, but a mismatched arity or element type is error[3000].

The example

The whole chapter in one program. It declares Pair, returns one from divmod, passes one to sum, prints a whole tuple variable with {}, and reads the elements through all three access spellings. It is docs/sf/manuals/src/vol2/pair.z98: 

const std = @import("std");

// A tuple type: a struct whose members are just types, in order.
const Pair = struct { i32, i32 };

// A grouped return: the function's two results travel as one value.
fn divmod(a: i32, b: i32) Pair {
    return .{ a / b, a % b };
}

// A tuple parameter: the caller hands the two fields over as one value.
fn sum(p: Pair) i32 {
    return p.0 + p.1;
}

pub fn main() void {
    // One tuple from a grouped return, unpacked by position.
    const q = divmod(17, 5);
    std.io.print("17/5 = {} remainder {}\n", .{ q.0, q.1 });

    // A tuple variable printed whole with {}.
    const p: Pair = .{ 7, 3 };
    std.io.print("pair {}\n", .{p});

    // All three spellings address the same positional field.
    std.io.print("spellings {} {} {} {}\n", .{ p.0, p._0, p[1], p.1 });

    // The copy is field-wise, and a tuple crosses a call as one value.
    var copy: Pair = p;
    std.io.print("copy {} sum {}\n", .{ copy.1, sum(copy) });
}

Build the compiler once from the committed seed, then emit and compile the program, exactly as in chapter 3: 

bash scripts/seed/build_from_seed.sh release/seed/zig1-seed.tgz /tmp/manual_seed

The result is /tmp/manual_seed/zig1_5_clean with the standard library beside it in /tmp/manual_seed/lib/. This example compiles with no diagnostics; the program then runs to the end: 

$ mkdir -p /tmp/manual_out
$ /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol2/pair.z98
$ cd /tmp/manual_out && sh build_target.sh linux pair
Building for linux...
Built: pair
$ ./pair
17/5 = 3 remainder 2
pair .{ 7, 3 }
spellings 7 7 3 3
copy 3 sum 10

Four lines. The first unpacks the grouped return: q.0 is 3 and q.1 is 2, the quotient and remainder of 17/5. The second prints a whole tuple variable through the tuple printer, braces and all. The third reads the two positions through all three spellings — .0, ._0, [1], and .1 — showing that they are aliases for the positional field. The fourth copies the tuple field-wise into another variable and hands it to a function that takes a tuple parameter, returning the sum 10. The exit status is 0.

Common mistakes

The mistakes below are the ones a programmer arriving from C (or from a newer Zig) makes first with tuples. Each one has a corrected shape, and the corrected shape is the compiler's rule, not a style preference.

Expecting named fields. A tuple has no names. p.x is the ordinary unknown-member reject, error[3060]: no field or member function named 'x' in type, and the same happens to a numeric member on a non-tuple such as sl.73. In the other direction, an ordinal past the end reports error[3070]: index 2 outside tuple of length 2, a runtime index reports error[3069]: tuple field index must be comptime-known, and a negative index reports error[3062]: type 'usize' cannot represent integer value '-1'. If a field needs a name, declare a named struct; if the access needs a loop, use an array.

Serializing them like structs. A tuple lowers to a C struct with fields _0, _1, but that is emission detail: the field spellings are not a data format, the padding follows the alignment model, and @offsetOf refuses the type with error[3072]: expected struct type. Use a named struct when the field order is a contract, and a packed struct or an array when the bytes themselves are.

Chaining access after an ordinal. e.0.w — an ordinal followed by a struct field — does not parse; error[2000]: expected field name or index after '.' points at the second dot. Parenthesize the element or index it, and the struct access works: (e.0).w and e[0].w are both accepted.

Passing something that is not a container to print. The second argument must be a tuple literal (.{ ... }) or a tuple variable. A bare value, a non-tuple variable, an expression such as a == b, or an anonymous struct initializer rejects with error[3065]: print arguments must be a tuple literal; a format plus two containers rejects with error[3061]: expected 2 argument(s), found 3. Wrap the arguments in .{ ... }, one container per call.

Assuming every tuple is printable. An element type without a printer makes the whole tuple reject with error[3063]: print argument type is not supported (no std.fmt printer); a type used as an element and a void element are the two measured cases. Print the elements you can print and leave the rest out of the format argument.

Coming from Zig

The tuple is one of the places where this dialect is closest to the Zig it is a subset of, and the differences that remain are small.

The literal and the index are the same. .{ 1, 2 } is a tuple literal in both languages, and t[0] reads the first element in both. Measured on the Zig 0.15.2 oracle, const t = .{ 7, 8 }; followed by t[0] and t[1] prints 7 8.

The ordinal spellings are Z98 additions. Zig rejects t.0 with expected pointer dereference, optional unwrap, or field access, found 'a number literal', and rejects t._0 with no field named '_0' in tuple .... Z98 accepts .0, ._0, and t[0] as the same access, so code ported from Zig that used t[0] keeps working unchanged, and Z98 code may use whichever spelling is clearest.

Element types are concrete here. In Zig, the elements of an untyped literal are comptime integers (the oracle's own diagnostic calls the element comptime comptime_int = 7); Z98 has no comptime, so an element takes a concrete carrier chosen from its value and a tuple's shape is settled at the declaration the way a struct's is. The layout and the printed values are the same either way; the difference only shows if ported code expected a comptime-known element type.
