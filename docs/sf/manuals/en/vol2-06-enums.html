Aggregates III: Enums

An enum gives a name to each value in a small, fixed set. The last three chapters grouped memory into records; an enum does the opposite: it takes one integer and gives its interesting values names. A protocol's status byte, a token kind, a color — places where C programmers write #define RED 0 or a handful of constants — become one type with a list of members: 

const Color = enum { Red, Green, Blue };

That declaration creates a type, not an integer. Colors can be assigned, compared, and passed around, and the compiler knows the set. A switch over an enum can name ranges of members, the way a switch over integers names ranges of numbers. And crossing between the name and the number is an operation with a name: @enumToInt and @intToEnum, never an implicit step.

This chapter declares plain enums and enums with an explicit backing integer, converts values in both directions, and switches over member ranges, including the mandatory else prong that catches everything the listed members do not. The example is docs/sf/manuals/src/vol2/color.z98.

A name for a small set

The syntax is enum, braces, and a comma-separated member list. The members are identifiers; by default they number from zero in declaration order. The declaration below is the chapter's Color, and the program prints the member Green and its number: 

var c: Color = .Green;
std.io.print("c={} int={d}\n", .{ c, @enumToInt(c) });

The short spelling .Green works wherever the compiler already knows the type — a typed declaration, an argument, a return — and the long spelling Color.Green works everywhere. Both are the same value. Red is 0, Green is 1, and Blue is 2, and the chapter program verifies that with @enumToInt.

A plain enum like Color does not promise a width. The compiler picks the backing integer that stores the members, and the layout builtins report it. On this compiler a plain enum is backed by a 32-bit unsigned integer, so the three-member Color measures like the u32 it is built on:

Type @sizeOf @bitSizeOf Backing
Color (plain) 4 32 32-bit unsigned
Code (enum(u8)) 1 8 u8

The C habit is to reach for an int and a set of #defines, or a C enum whose members are really integers that travel anywhere. In Z98 the type is carried: an enum value is not an integer unless a conversion says so, an integer is not an enum unless a conversion says so, and a function that takes a Color cannot be handed a bare 1 without a diagnostic. That is the same bargain the last two chapters made with struct and packed struct layouts: the declaration says what the bytes mean, and the compiler holds the program to it.

Choosing the backing integer

When the width matters, name the backing type: enum(uN) stores every value in an unsigned integer of width N. The chapter's second enum is the status byte of a small protocol, spelled with a u8 backing and explicit numbers: 

const Code = enum(u8) { Ok = 0, Warning = 4, Error = 9 };

The explicit values are the members' numbers, exactly as written; the program prints 0, 4, and 9 for the three members with @enumToInt. The type measures @sizeOf 1 and @bitSizeOf 8 — one byte, which matters when the value is a field in a wire format or an entry in a table. A backing of u16 or u32 is chosen the same way. Only unsigned backings exist: enum(i32) is rejected with error[3000]: enum(iN) signed backings are not supported; use an unsigned backing (enum(uN)).

Values may be explicit, automatic, or a mix. Automatic numbering starts at zero and continues from the previous member; after an explicit value, the next member continues from there: 

const Level = enum { Low, Mid = 4, High };

Low is 0, Mid is 4, and High is 5. The numbers do not need to be contiguous, and that is the point of the explicit form: the gaps are as real as the values, and the switches later in this chapter skip them correctly. What the compiler does not have is a way to say "and any other number" — the member list is the whole type.

Members to numbers: @enumToInt

@enumToInt(e) reads the number under a member. The result has the backing integer's type: a u32 for a plain enum like Color, a u8 for the Code above. That matters when the number travels to a differently typed place; storing it in an i32 is not free on this compiler: the declaration gets a warning[3000] whose note says source: u32 and target: i32. The explicit form @intCast(i32, @enumToInt(c)) says what is happening and is warning-free.

Printing has one wrinkle worth learning now. A bare {} on an enum value prints the member name with a leading dot: 

std.io.print("c={}\n", .{ c });              // c=.Green
std.io.print("int={d}\n", .{ @enumToInt(c) }); // int=1

The first line prints .Green, and the second prints 1. The wrinkle is that @enumToInt(c) still prints as .Green under {} — the member name, not the number — because the printer looks at where the value came from. Use {d} (or {x}) when the number is what you want to see, exactly as the example does.

Numbers to members: @intToEnum

@intToEnum(T, n) is the way back. It takes the type and an integer and produces a value of that enum type whose number is n. The chapter program decodes a Code from its number and checks that a Color read from number 1 is the same Green it started with: 

var back: Color = @intToEnum(Color, 1);
var same: bool = back == c;

The run prints back=.Green same=true. A conversion in each direction makes a round trip: @intToEnum(Color, @enumToInt(c)) is the value you started with.

One honest boundary belongs here rather than in a footnote: @intToEnum does not check the number against the member list. An integer with no member is accepted and produces an enum value whose only visible form is the fallback spelling @enumFromInt(n); a probe on this compiler printed @enumFromInt(2) for a gap in a u8 enum and @enumFromInt(7) for a plain enum with three members. An enum is a typed name for an integer, not a runtime membership test. The validation rule is the one stated in prose: the number should be one the enum declares, and the program that converts is the program that knows.

Switch: the exact prongs

Enums are made for switch. A prong may name a member with the short spelling (.Red) or the qualified one (Color.Red), the same two spellings as everywhere else, and several members may share a prong: 

return switch (c) {
    .Red, .Blue => "primary",
    else => "unknown",
};

Each prong matches the member's underlying number. Two rules come with the feature. First, the else prong is mandatory in Z98, in every switch, value or statement position; a switch that lists every member must still spell one out. Leaving it off is a compile-time reject, not a default: 

error[3068]: switch must have an 'else' prong

This is one place where Z98 is stricter than the Zig it is a subset of: Zig rejects a redundant else on an otherwise exhaustive switch, while Z98 requires one and tolerates it. The example's functions always carry a real fallback, so there is no doubt about what an unlisted value does.

Second, a prong that names something the enum does not have is rejected instead of quietly falling to else. A typo such as Color.Purple reports error[3071]: no field or member function named 'Purple' in enum type, and a qualifier that names a different enum reports the type-mismatch error[3071] instead. The old C shape — a mistyped case label that simply never matches — cannot happen here.

Switch: ranges

A prong may match a run of members instead of one. The inclusive form start...end covers both ends; the exclusive form start..end covers the start and stops before the end: 

Color.Red...Color.Green => "warm",   // Red and Green
.Green.. .Blue => "acid",            // Green only

On an enum condition the endpoints resolve to the members' underlying numbers, so the inclusive range above is the run 0 through 1 and the exclusive range is the single value 1. The two bounds may be qualified members, shorthand literals, or a mix, and a range may share a switch with exact items, as the example's exclusiveBand does with .Red, .Blue. The else rule from the previous section applies unchanged.

Ranges are a compile-time convenience: the compiler expands each one into the ordinary case labels of the emitted C. This is what makes gaps exact. The chapter's codeBand switches on Code.Ok...Code.Warning, which is the run 0 through 4; because Warning is 4, the prong matches both members, and Error at 9 is left to its own prong. The exclusive Code.Ok..Code.Error covers 0 through 8, so it too admits Warning but not Error. The emitted switch for the first of those is a handful of integer labels: 

case 0: goto z_bb_1;
case 1: goto z_bb_1;
case 2: goto z_bb_1;
case 3: goto z_bb_1;
case 4: goto z_bb_1;
case 9: goto z_bb_2;
default: goto z_bb_3;

Nothing about the range survives to run time; the run and the gaps are already baked into the case list.

Honest note. The enum surface is deliberately small, and it is better to know its edges now. There are exactly two conversion builtins, @enumToInt and @intToEnum; the reflection builtins of modern Zig (@tagName, @memberCount, @memberName, @typeInfo) do not exist here — a probe on this compiler rejects @tagName(c) with error[3000]: unsupported builtin function. There is no open or catch-all form, no anyerror for enums: a member list with _ in it is a parse error, so the set is fixed at the declaration. @intToEnum does not verify the member, as the previous section shows, so the enum does not enforce membership at run time. The only name the program can get back is what {} prints; if the program needs the name as data, it writes the table itself. And a plain enum is a 32-bit value whatever the member count is, so an enum used as a byte on the wire or in a table should say so: enum(u8).

The example

The whole chapter in one program. It declares the plain Color and the u8-backed Code, prints sizes, numbers, and names, round-trips a value through @intToEnum and @enumToInt, and switches over an inclusive range, an exclusive range, and an enum with a gap. It is docs/sf/manuals/src/vol2/color.z98: 

const std = @import("std");

// A plain enum. The compiler chooses the backing integer; on this
// compiler it is a 32-bit unsigned type, which @sizeOf reports as 4.
const Color = enum { Red, Green, Blue };

// An enum with an explicit backing. enum(u8) stores every value in
// one byte, the shape a wire field or a table of bytes wants.
const Code = enum(u8) { Ok = 0, Warning = 4, Error = 9 };

// Inclusive range: Red and Green match, Blue falls to else.
fn inclusiveBand(c: Color) []const u8 {
    return switch (c) {
        Color.Red...Color.Green => "warm",
        Color.Blue => "cool",
        else => "unknown",
    };
}

// Exclusive range: Green only. The exact prongs cover the other two,
// and the else prong is still mandatory.
fn exclusiveBand(c: Color) []const u8 {
    return switch (c) {
        .Green.. .Blue => "acid",
        .Red, .Blue => "primary",
        else => "unknown",
    };
}

// Ranges on an enum(u8) use the underlying values, gaps included:
// Ok is 0 and Warning is 4, so they share a band; Error is 9.
fn codeBand(c: Code) []const u8 {
    return switch (c) {
        Code.Ok...Code.Warning => "quiet",
        Code.Error => "loud",
        else => "unknown",
    };
}

pub fn main() void {
    var c: Color = .Green;
    std.io.print("Color size={} bits={}\n", .{ @sizeOf(Color), @bitSizeOf(Color) });
    std.io.print("c={} int={d}\n", .{ c, @enumToInt(c) });

    var back: Color = @intToEnum(Color, 1);
    var same: bool = back == c;
    std.io.print("back={} same={}\n", .{ back, same });

    std.io.print("Code size={} bits={}\n", .{ @sizeOf(Code), @bitSizeOf(Code) });
    std.io.print("Code ints {d} {d} {d}\n", .{ @enumToInt(Code.Ok), @enumToInt(Code.Warning), @enumToInt(Code.Error) });
    var loud: Code = @intToEnum(Code, 9);
    std.io.print("loud={} int={d}\n", .{ loud, @enumToInt(loud) });

    std.io.print("inclusive Green={s} Blue={s}\n", .{ inclusiveBand(.Green), inclusiveBand(.Blue) });
    std.io.print("exclusive Green={s} Red={s}\n", .{ exclusiveBand(.Green), exclusiveBand(.Red) });
    std.io.print("code Warning={s} Error={s}\n", .{ codeBand(.Warning), codeBand(.Error) });
}

Build the compiler once from the committed seed, then emit and compile the program, exactly as in chapter 3: 

bash scripts/seed/build_from_seed.sh release/seed/zig1-seed.tgz /tmp/manual_seed

The result is /tmp/manual_seed/zig1_5_clean with the standard library beside it in /tmp/manual_seed/lib/. This example compiles with no diagnostics; the program then runs to the end: 

$ mkdir -p /tmp/manual_out
$ /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol2/color.z98
$ cd /tmp/manual_out && sh build_target.sh linux color
Building for linux...
Built: color
$ ./color
Color size=4 bits=32
c=.Green int=1
back=.Green same=true
Code size=1 bits=8
Code ints 0 4 9
loud=.Error int=9
inclusive Green=warm Blue=cool
exclusive Green=acid Red=primary

Nine lines, in three groups. The first three are Color: 4 bytes and 32 bits for the plain backing, the member's name and number, and the round trip through number 1. The next three are Code: 1 byte and 8 bits, the three explicit numbers 0, 4, and 9, and a decode of number 9 back to .Error. The last three are the switches: the inclusive range makes Green warm and sends Blue to cool; the exclusive range makes Green acid and sends Red to primary; and the gapped band puts Warning (4) with Ok (0) and gives Error (9) its own answer. The exit status is 0.

Common mistakes

The mistakes below are the ones a programmer arriving from C (or from a newer Zig) makes first with enums. Each one has a corrected shape, and the corrected shape is the compiler's rule, not a style preference.

Using the modern Zig spellings. The builtins here are @enumToInt(e) and @intToEnum(T, n). The newer names @intFromEnum and @enumFromInt are not implemented, and the compiler says so plainly: error[3000]: unsupported builtin function. When a builtin is not recognized, that is the diagnostic to look for.

Printing @enumToInt with {}. The reflex is print("int={}", .{@enumToInt(c)}) and the output is int=.Green, because the bare printer shows the member name for both an enum and its converted number. Use {d} for the number, or {x} for its hex form. If the page's example prints Code ints 0 4 9, that is because it asks for {d}.

Comparing members as integers. a == b and a != b are supported directly on enum values; converting both sides with @enumToInt first is a C habit that adds a step and nothing else. The conversion builtins are for when the number is the point — a wire field, a table index, a printout — not for equality.

Forgetting the mandatory else. Every switch in Z98 needs an else prong, even one whose items cover every member of the enum. The reject is error[3068]: switch must have an 'else' prong. If the case really is impossible, spell it honestly (else => {} for a statement switch, or a real fallback value); else => unreachable traps under both build modes, so reserve it for a branch the program proves it cannot reach.

Assuming the backing integer. A plain enum is 4 bytes and 32 bits here regardless of how many members it has; three colors cost the same as a hundred. That is fine for a variable and wasteful for a million of them, a file record, or a wire field. When the width is part of the design, write enum(u8) (or u16, u32) and let the declaration carry the size.

Mixing enums and integers like C. In C the two directions blur freely. Here var c: Color = 1; is diagnosed with a warning[3000] at the declaration, and var n: i32 = c; is an error[3000] outright. The explicit forms are @intToEnum(Color, 1) and @enumToInt(c), plus @intCast when the result needs a different width or signedness. Both directions then say what they mean.

Typos that would have been silent. A prong naming a member the enum does not have does not fall to else: Color.Purple rejects with error[3071] and a note at the declaration, and a qualifier that names a different enum rejects with the type-mismatch error[3071]. That is a feature to lean on when renaming members: the switches that still spell the old name stop compiling.
