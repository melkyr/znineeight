Variables and Types

The first program printed one fixed line. A program becomes useful when it can give names to the values it works with and change those values as it runs. That is what a variable is: a name for a value, held in memory, with a type that says what kind of value it is and how much room it takes. This chapter adds the variable to the program from chapter 5.

The program

const std = @import("std");

pub fn main() !void {
    var count: i32 = 41;
    count = count + 1;

    const max_u8: u8 = 255;

    var ready: bool = false;
    ready = true;

    const ratio: f32 = @floatCast(f32, 1.5);

    std.io.print("count  (i32)   = {}\n", .{count});
    std.io.print("max_u8 (u8)    = {}\n", .{max_u8});
    std.io.print("ready  (bool)  = {}\n", .{ready});
    std.io.print("ratio  (f32)   = {}\n", .{ratio});

    std.io.print("sizeOf(i32)    = {}\n", .{@sizeOf(i32)});
    std.io.print("sizeOf(u8)     = {}\n", .{@sizeOf(u8)});
    std.io.print("sizeOf(bool)   = {}\n", .{@sizeOf(bool)});
    std.io.print("sizeOf(f32)    = {}\n", .{@sizeOf(f32)});
    std.io.print("sizeOf(usize)  = {}\n", .{@sizeOf(usize)});
}

It declares four values, changes two of them, and prints each value and the size of its type. Nothing else happens; the program is a tour of the pieces a declaration is made from.

What the lines mean

var count: i32 = 41;

This is a declaration. It has four parts, and it is worth naming them because every declaration in Z98 is built the same way.

  • var says the name may be given a new value later.
  • count is the name being introduced.
  • : i32 is the type of the value the name will hold. The colon reads as "of type".
  • = 41 is the value it starts with.

The semicolon ends the declaration. A var with no value is not allowed: the compiler insists every variable start with something, because a value read before it is written is a bug. (If you really want an empty slot, = undefined is the explicit way to ask for one; a later chapter explains why that is rarely what you want.)

count = count + 1;

This is an assignment, and it is shorter than the declaration on purpose. There is no var and no type: the name already exists, and its type was fixed when it was declared. Read the line right to left: take the current value of count, add one, and store the result back under the same name. After it runs, count holds 42.

Because count was declared var, the assignment is allowed. The next declaration shows the other kind.

const max_u8: u8 = 255;

const introduces a name exactly as var does, but the value may not be reassigned. max_u8 is u8, an unsigned eight-bit number, and it starts at 255. Nothing later in the program changes it, and if something tried to, the compiler would refuse before writing any C.

The rule of thumb is to reach for const first and use var only when the value must change. A name that cannot change is one less thing to keep in your head.

var ready: bool = false; ready = true;

bool is the boolean type: its only two values are true and false. This variable is declared var, so the second statement is allowed to flip it. The same two-step pattern — declare, then assign — works for every type.

const ratio: f32 = @floatCast(f32, 1.5);

f32 is a 32-bit floating-point number: a number with a fractional part. The literal 1.5 is read by the compiler as a 64-bit float (f64), so @floatCast(f32, 1.5) narrows it to f32 before it is stored. @floatCast is a builtin, a compiler-provided function whose name begins with an at sign. Without the cast the compiler warns that the literal and the declared type differ; with it, the narrowing is explicit and quiet.

The std.io.print lines

These are the print calls from chapter 5, now with a value to show. The string "count (i32) = {}\n" is the format; the {} is the placeholder that the value fills, and .{count} is the one-element tuple that carries it. The label before the equals sign is only text the program prints; it does no work.

The last five calls use @sizeOf. @sizeOf(T) is a builtin that asks the compiler how many bytes a value of type T occupies. It is answered at compile time and becomes an ordinary number in the program.

The primitive types you have met

Five of the names in the program are types. They are not arbitrary: each one says how many bytes a value takes and therefore how large the value may be.

Type Holds Bytes Values
i32 a signed whole number 4 about −2,000,000,000 to 2,000,000,000
u8 an unsigned whole number 1 0 to 255
bool a truth value 1 true or false
f32 a fractional number 4 about seven significant digits
usize a length or count 4 0 to about 4,000,000,000

usize is the type Z98 uses for lengths and counts; on this target it is four bytes, the same size as an i32, but it is a distinct type. The u in u8 and usize means unsigned: those types cannot hold a negative number. The i in i32 means signed: it can hold both signs. f stands for floating point.

Why the width matters

The number after the i, u, or f is the width in bits. It is the whole reason these types exist. The machine this manual targets has 32 MB of memory, not gigabytes, and every value a program keeps spends some of it. One i32 and one u8 hardly differ; a thousand of them differ by three kilobytes, and a million of them differ by three megabytes.

So the rule is to choose the smallest type that holds every value the variable will ever see. A count that cannot be negative and will not exceed 255 belongs in a u8; one that may be large belongs in an i32 or usize. The program prints @sizeOf for each type so you can see the price directly: i32 is four bytes, u8 is one.

Warn. A narrow type is a promise about the values it will hold. Break the promise and the result is not a message, it is a wrong number. The common mistakes below show both the silent wrap and the runtime trap that catch the two ways a value can fall outside its type.

Building and running it

The commands are the ones from chapter 5, with types in place of hello. The compiler is still at /tmp/manual_seed, built in chapter 4: 

$ mkdir -p /tmp/manual_out
$ /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol1/types.z98
$ cd /tmp/manual_out && sh build_target.sh linux types
Building for linux...
Built: types
$ ./types
count  (i32)   = 42
max_u8 (u8)    = 255
ready  (bool)  = true
ratio  (f32)   = 1.5
sizeOf(i32)    = 4
sizeOf(u8)     = 1
sizeOf(bool)   = 1
sizeOf(f32)    = 4
sizeOf(usize)  = 4

Read the output one line at a time. The first four lines are the values: count is 42 because the program added one to 41, max_u8 is the 255 it was given, ready is true because the assignment flipped it, and ratio is 1.5. The last five lines are @sizeOf: the sizes the compiler gave those types. They are the same on every build, because they are a property of the target machine, not of the program.

Common mistakes

These are the mistakes declarations attract. Each one has a symptom you can recognize.

Using a variable before giving it a value. A var with no initializer is rejected, not silently zero-filled: 

types.z98:4:4: error[3014]: variable must be initialized; use '= undefined' to opt out
    var x: i32;
    ^^^^^^^^^^^

The message names the fix: write a starting value, or = undefined if you really mean an empty slot. A value read from an uninitialized variable would be garbage, so the compiler refuses to let the program get that far.

Trying to change a const. The value is fixed at the declaration and cannot be reassigned: 

types.z98:5:4: error[3002]: cannot assign to immutable variable
    limit = 11;
    ^^^^^

The caret points at the name, not at the value. If the value must change, declare it var.

A value too big for the type. This one is not an error, which is why it is dangerous. A u8 holds 0 to 255; put 300 into one and the compiler says nothing, the program builds, and it prints 44: 

$ ./types
b = 44

300 wrapped around to 44, the same way the hands of a clock wrap around. The width of the type is the whole story. The same thing happens at run time when a calculation overflows: adding one to a u8 that holds 255 wraps too, but under the default safety checks it stops with a trap instead of a wrong number.

Mixing two integer types without a cast. The compiler warns but does not stop. Here a u8 is stored into an i32: 

types.z98:5:4: warning[3000]: type mismatch in variable declaration — initialization type may not be compatible with declared type
    var m: i32 = b;
    ^^^^^^^^^^^^^^^
note: source: u8
note: target: i32

The program still builds and runs; the warning is a nudge, not a wall. The same warning appears when you mix i32 and usize: on this target both are four bytes, so the program keeps working, but the compiler is telling you the two types are not the same. Write the conversion out loud with @intCast, as in var m: i32 = @intCast(i32, b);, and the warning goes away because the conversion is no longer a guess.

Check yourself

Answer these before moving on. The last two ask you to change the program and run it.

  1. What is the difference between var and const, and which should you reach for first?
  2. What does the colon in var count: i32 = 41; mean, and what is the 41 called?
  3. Why does the program print @sizeOf for each type? What does the number tell you?
  4. Why is u8 one byte and i32 four, and what is the price of choosing the smaller one?
  5. Change max_u8 from 255 to 300, rebuild, and run it. What does the program print, and why? Then change the type to i32 and run it again.
  6. Add a var named total of type usize, set it to count with @intCast, and print it. Why does the compiler want the cast?
