Coroutines — The Third Big Shift

Volume II described two shifts in how you think about a program. The first was the error union: a failure became a value the type system carries, not a flag you might forget. The second was the arena: memory acquired a lifetime you can plan instead of a call you must pair. This chapter is the third shift, and it is the one that changes the shape of a function. A Z98 function does not have to run to completion before it can do anything else. It can suspend in the middle, remember where it was, and be resumed later. The mechanism is called a coroutine, and in Z98 it is built into the language as four @async* builtins plus the ordinary library module std.async.

This is the chapter the rest of the volume leans on. Chapter 6 named no multithreading worth the cost as a limit of the era, and this is the way over it: not threads, not preemption, but cooperative tasks that yield by choice. Chapter 10 turns the mechanism into a full program, and the network chapters use the same scheduler to give each connection its own little state machine without writing one. Before any of that, you need the mental model, because the surface is deliberately small and the compiler does real work underneath it that you should be able to read.

What is measured here. Every builtin name, every frame number, and the state-word width in this chapter were read from the compiler built from the committed seed, not from a design document. The tasks.z98 program is compiled and run in this chapter, and the transcript is that run. The emitted C quoted below is the compiler's own output for that program, with the identifiers as they appear in the dump. Where a statement is a promise of the design rather than a measurement, the text says which.

What you expect

If you have written concurrent code in a modern language, three words arrive with the idea of a coroutine: a keyword, a future, and a scheduler. You expect async in front of a function and await in front of a call, a typed handle you can pass around and await more than once, and a runtime that decides what runs when. You expect the language to hide the bookkeeping: the compiler stores the suspension points, the runtime moves the frames, and you write straight-line code that magically pauses.

Z98 gives you the pause and the resume, and it gives you a scheduler, but it refuses the rest of the packaging. There is no async keyword and no await keyword. There is no Future(T) type, and there cannot be one, because Z98 has no generics. A coroutine's state is erased to *void, and the thing that drives it is not a hidden runtime but a library you can read. You are closer to the machine than a modern language puts you, and that closeness is the point on a 1998 PC: nothing is allocated that you did not ask for, and no scheduler thread exists because there are no threads worth their cost on this machine.

The honest way to hold the difference is this: Z98 ships the hard part (the compiler rewriting a suspending function into a resumable step machine) and leaves the visible part (which task runs next, how many run, when one waits on another) to a library you drive from main. That division is why the chapter is mostly about a frame and a scheduler and not about syntax. The syntax is a single call, @asyncSuspend(null), and it marks the place where the function is allowed to stop.

A function that suspends

The compiler does not make every function resumable. It would be wasteful and unnecessary. Instead it computes which functions suspending, and only those are rewritten. The rule is stated exactly in the Language Spec and the compiler implements it literally: a function is suspending when its body directly contains @asyncSuspend, or when it directly calls a function that is suspending. The property is a fixed point over the call graph. If a calls b and b calls @asyncSuspend, then b is suspending and so is a, and the analysis keeps propagating until nothing new is marked. Mutual recursion is ordinary propagation, not recursive descent, so a cycle cannot hang the compiler.

The analysis runs once, early, before type resolution, and it is program-wide: it sees every module, so a suspending function in one file makes its callers suspending in another. This matters as soon as you put a coroutine in a helper module, which is what a real program does. The property is also not something you write down. You never declare a function suspending; it is suspending because of what its body does.

The one restriction that follows is that a suspending function's address may not be taken. That is diagnostic error[3017], and it is deliberate: a suspending function has been replaced by a step machine, and a raw function pointer to it would be a pointer to a function that no longer has the signature you think it has. Here is the compiler refusing the address of the tiny suspending function from the sample, when a program tries to store it: 

error[3017]: taking the address of a suspending function is not allowed

The compiler also refuses @asyncFrameSize on a function that is not suspending, because a function with no suspension points has no frame to size. That is error[3046], and it is the first mistake a reader makes when they reach for the builtin with the wrong function: 

bad_frame.z98:3:44: error[3046]: @asyncFrameSize argument must be a known suspending function
std.io.print("{}\n", .{@asyncFrameSize(plain)});
                             ^^^^^^^^^^^^^^^^^^^^^^

And the builtins that only make sense at a suspension point are rejected inside defer and errdefer, because a deferred block that suspends would have to be re-entered on every resume, which the model does not support. That is error[3019]: 

bad_defer.z98:2:26: error[3019]: @async builtin used inside a defer/errdefer body
fn f() void { defer { _ = @asyncSuspend(null); } }
                          ^^^^^^^^^^^^^^^^^^^

Read those three diagnostics together and the boundary is clear. A suspending function is a distinct kind of function, the compiler knows which functions those are without being told, and it refuses the operations that would break the model. There is one more diagnostic in the family, error[3018], for @asyncSuspend used where no suspension is possible; it is part of the same family and the Language Spec lists it beside the others.

Builtin Result What it does
@asyncFrameSize(fn) integer constant the byte size of fn's root frame; fn must be a known suspending function, else error[3046]
@asyncInit(ctx, buf, fn, args) *void initialize a fresh root frame for fn in buf, using the per-task pool ctx; returns the frame
@asyncSuspend(data) *void an explicit suspension point; valid only inside a suspending function, and not inside defer/errdefer
@asyncResume(frame, arg) ?*void resume a step; returns null when the coroutine has finished and a non-null value while it is still suspended

The step machine

When a function is suspending, the compiler does not emit its body as an ordinary function. It emits a step function named __Z98Step_<f> with a fixed shape: 

fn __Z98Step_<f>(frame: *void, arg: ?*void) ?*void

The step loads a hidden state word out of the frame, jumps to the resume segment for whatever suspension point that word names, and runs forward until it reaches the next @asyncSuspend or the end of the function. At a suspension it saves the values it will need, writes the next state number, and returns a non-null ?*void to say "I am still suspended". At the end it returns null to say "I am done". The original synchronous body is not emitted at all; it has been replaced.

The driver that actually resumes a step is @asyncResume(frame, arg). It reads the pointer-sized step word stored at offset zero of the frame, calls the step with (frame, arg), and returns the step's result. For the sample in this chapter, the compiler wrote the step word and the state word like this in the emitted C (the frame pointer is zT_67, the step function is zF_CD850BCC___Z98Step_task): 

zT_95 = zF_CD850BCC___Z98Step_task;
zT_100 = (unsigned int*)(...zT_67... + 0);
*zT_100 = (unsigned int)(zT_95);                 /* step word  @ offset 0 */
zT_104 = (void**)(...zT_67... + 4);
*zT_104 = zT_65;                                  /* ctx pointer @ offset 4 */
zT_109 = (unsigned char*)(...zT_67... + 8);
*zT_109 = (unsigned char)(0);                     /* state = 0   @ offset 8 */
zT_113 = (zT_CFCE7101_TaskArgs**)(...zT_67... + 12);
*zT_113 = zT_85;                                  /* parameter   @ offset 12 */

Notice what is not there. There is no saved program counter, no machine stack, no per-coroutine stack allocation. The coroutine's whole memory is the frame buffer you supplied, and its position is the state word inside it. That is what "stackless" means, and it is why a coroutine is cheap enough for this machine. The cost of a coroutine is the size of its frame, and the frame is a struct the compiler computes at compile time.

The frame

A frame is laid out in a fixed order, and the order is worth memorizing because the emitted C will refer to it by offset. The header is three fields: the step word at offset 0, the context pointer at the next pointer-sized slot, and the state word after that. Then come the coroutine's parameters in declaration order, then any locals that are live across a suspension, then hidden tail slots for the awaits it performs. The Language Spec states the order as {step, ctx, state} followed by parameters, live values, and child/result slots.

Order Field Meaning
0step pointer-sized address of __Z98Step_<f>
1ctx the per-task child-frame pool pointer
2state u8, u16, or u32 (see below)
3param each coroutine parameter, in order
4live each local live across at least one suspension
5child one child-frame slot when the function awaits
6result one slot for a value returned through an await
7parent_result one slot per value-returning await, in program order

For the sample's task, the emitted frame is 168 bytes and the offsets are step = 0, ctx = 4, state = 8, the ta parameter at 12, and four live values (a counter, the loop bound, a comparison temp, and the id temp) at 16, 20, 24, and 28. The frame size is larger than the fields you can see because the compiler sizes it from a conservative AST-level pass that reserves room for every reachable node, then pads the result up to a multiple of 8. The precise LIR pass checks that its own smaller layout fits inside that reservation; the authoritative size is the padded, conservative one, and it is what @asyncFrameSize returns.

That padding is not cosmetic. Every frame is rounded up to 8 bytes so that consecutive frames in a pool stay 8-aligned given an 8-aligned pool base. On a 32-bit target that keeps a f64 or a pointer inside any frame correctly aligned. The sample prints its own frame size at the top of the transcript: 

frame size = 168

Use @asyncFrameSize(fn) to size the buffer, never a guess. It is a compile-time constant, so it can size a fixed array directly, and it is correct across compiler versions in a way a hard number is not.

The state word

The state word is the smallest integer that can name every suspension point in the function. The compiler counts the suspension points and picks the width: u8 when the count is at most 255, u16 when it is at most 65535, and u32 otherwise. The rule is deliberately frugal: a coroutine that suspends three times does not carry a four-byte state word, and on a machine where memory is the binding constraint that choice is worth stating plainly. The width is decided once, in the same analysis that computes the frame sizes, and the transform fails closed if it ever sees more points than the chosen width can name.

The sample's task has a single @asyncSuspend program point, reached twice at run time because it sits inside the loop. One program point fits in a byte with room to spare, so the state word is a single byte, and the dispatch guard allows the two states that point needs. The emitted C says so: the state is written through an unsigned char* at offset 8, and the step's dispatch is a switch on that unsigned char with a trap if it ever exceeds the known maximum: 

zT_30 = *zT_29;                                  /* load state (u8) */
zT_32 = zT_30 <= (unsigned char)(1);
if (!(zT_32)) { pal_trap(); }
switch (zT_30) {
case 0: goto z_bb_2;
case 1: goto z_bb_5;
default: goto z_bb_1;
}

There is a pleasant consequence you should notice: the state word already names the resume segment, so the resume logic is a bounded switch over small integers. That is exactly the shape you would write by hand, except the compiler writes it for you, for every suspension point, and keeps it consistent when you move a line.

The child-frame pool

So far a coroutine suspends only where you told it to. The more interesting case is a suspending function that calls another suspending function. That call is an implicit await: the caller allocates a child frame for the callee, copies the arguments into it, drives the child forward, and yields to its own driver while the child is still suspended. When the child returns, the caller delivers the awaited value and pops the child frame. You did not write await; the direct call is the await.

Child frames come from a per-task pool owned by a Context. The Context occupies the first 16 bytes of a caller-supplied buffer and the pool bytes follow it. Its header is {used@0, capacity@4, oom@8} with padding to 16, and the usable pool starts at ctx + 16. The 16-byte header (not the 12 you might write after seeing only three 4-byte fields) is what keeps ctx + 16 8-aligned whenever the caller's buffer is 8-aligned. That is why the sample backs both its pools and its root frames with [K]u64 arrays and never with a bare [N]u8: a u8 array is only 1-aligned, and contextInit traps on a misaligned buffer on purpose rather than corrupting every frame that follows.

Allocation is a bump pointer. contextAlloc rounds used up to a multiple of 8, checks that the rounded size still fits in capacity, and on exhaustion sets a sticky oom flag and returns error.OutOfFrame instead of crashing. A child frame is reclaimed either when it returns (the transform pops it) or explicitly with contextMark / contextRelease, which bracket the pool like a stack. Bounded, deterministic, and no allocator call in sight. If your coroutine's implicit awaits need more room than a pool holds, the failure is a named error you can handle, not a corrupt heap.

The scheduler

The language provides the step machine and the frame; it deliberately does not provide a policy for which coroutine runs when. That lives in std.async, an ordinary module you can read in full. The model is round-robin and cooperative: a task runs until it suspends, and the scheduler moves to the next ready task. Nothing preempts anything, so there are no data races between tasks and no need for locks — a direct consequence of the era's no threads worth the cost.

Piece What it is
Context the per-task child-frame pool described above
Task { frame, ctx, state, cancel_requested, result, arg, waiting_on, has_waiting_on }; it stores no step pointer
Scheduler { tasks: [*]*Task, capacity, count, current, in_task }; wraps a caller-owned array of task pointers
schedulerInit(tasks) wrap a caller-owned []*Task
addTask(s, t) register a task; idempotent, and resets a settled task in place so slots can be reused
tick(s) resume every ready or suspended task once, in order
waitAll(s) tick until every task is done or cancelled
waitFor(s, t) tick until t settles; safe from main
awaitTask(s, t) a coroutine waits on another task; coroutine-internal only
cancel(s, t) / cancelAll(s) request cooperative cancellation, observed at a tick boundary

The detail that makes the design click is the one you cannot see from the table: Task stores no step function. When tick resumes a task it calls @asyncResume(t.frame, t.arg), and @asyncResume reads the step word out of the frame. That is why one scheduler can drive tasks built from completely different suspending functions without knowing their types — the type is erased into the frame, and the frame remembers. It is also why the scheduler needs no generics and works on this machine.

Two drive styles exist and they are not interchangeable. waitFor and waitAll tick every registered task, so they are right when the tasks you are not waiting on are safe to run. awaitTask parks only the currently running task on a dependency and is only legal inside a coroutine. Chapter 10 and the network chapters use both, and the rule of thumb is in the tech doc: when other registered tasks would block, drive only the one you mean to.

The program

Here is tasks.z98 in full. Three tasks, each suspending twice, are registered with one scheduler and driven to completion. The program prints the frame size, then every step in the order the round-robin scheduler runs it, then the number of tasks that finished. 

const std = @import("std");

// The @asyncInit argument record's fields ARE the coroutine's parameters, so
// this one-field record maps positionally onto task's single `ta` parameter.
const TaskArgs = struct {
    id: i32,
    budget: i32,
    done: *i32,
};

const TaskArgsRec = struct { ta: *TaskArgs };

// A suspending function: its body contains @asyncSuspend. The compiler rewrites
// it into a step machine and chooses its state word from the suspension count.
fn task(ta: *TaskArgs) void {
    var step: i32 = 0;
    while (step < ta.budget) : (step += 1) {
        std.io.print("task {} step {}\n", .{ ta.id, step });
        @asyncSuspend(null);
    }
    ta.done.* += 1;
    std.io.print("task {} done\n", .{ta.id});
}

const NTASKS: usize = 3;
const BUDGET: i32 = 2;
const POOL_WORDS: usize = 64;

pub fn main() void {
    std.io.print("frame size = {}\n", .{@asyncFrameSize(task)});

    // Per-task child-frame pool and root frame. Both buffers must be
    // 8-aligned, so back them with [K]u64, never a bare [N]u8.
    var pools: [NTASKS][POOL_WORDS]u64 = undefined;
    var frames: [NTASKS][POOL_WORDS]u64 = undefined;
    var tasks: [NTASKS]std.async.Task = undefined;
    var task_ptrs: [NTASKS]*std.async.Task = undefined;
    var args: [NTASKS]TaskArgs = undefined;
    var recs: [NTASKS]TaskArgsRec = undefined;
    var sched_tasks: [NTASKS]*std.async.Task = undefined;

    var done: i32 = 0;
    var sched = std.async.schedulerInit(sched_tasks[0..]);

    var i: usize = 0;
    while (i < NTASKS) : (i += 1) {
        args[i] = TaskArgs{
            .id = @intCast(i32, i),
            .budget = BUDGET,
            .done = &done,
        };
        recs[i] = TaskArgsRec{ .ta = &args[i] };
        task_ptrs[i] = &tasks[i];
        task_ptrs[i].ctx = std.async.contextInit(
            @ptrCast([*]u8, &pools[i])[0 .. POOL_WORDS * 8],
        );
        task_ptrs[i].frame = @asyncInit(
            task_ptrs[i].ctx,
            @ptrCast([*]u8, &frames[i]),
            task,
            @ptrCast(*const void, &recs[i]),
        );
        task_ptrs[i].state = .ready;
        task_ptrs[i].cancel_requested = false;
        task_ptrs[i].result = @ptrCast(*void, &done);
        task_ptrs[i].arg = @ptrCast(*void, &recs[i]);
        task_ptrs[i].waiting_on = task_ptrs[i];
        task_ptrs[i].has_waiting_on = false;
        _ = std.async.addTask(&sched, task_ptrs[i]);
    }

    std.async.waitAll(&sched) catch {
        std.io.print("pool exhausted\n", .{});
        return;
    };
    std.io.print("done = {}\n", .{done});
}

Read it in three movements. First the coroutine: task loops, prints, and suspends. The @asyncSuspend(null) is the only new syntax, and the loop is perfectly ordinary — that is the whole point of the rewrite, that you write a loop and the compiler makes it resumable. Second the setup: for each task the program builds an 8-aligned pool, turns it into a Context, initializes a root frame with @asyncInit, and fills the Task fields. The args record TaskArgsRec{ ta } has one field, matching the one parameter of task; @asyncInit copies it positionally, and it must be passed as a plain *const void, never a ?*const void. Third the drive: waitAll ticks the scheduler until every task has returned null.

The captured run is the cleanest possible demonstration of round-robin order. Each of the three tasks prints its step, and the ticks interleave them deterministically: 

frame size = 168
task 0 step 0
task 1 step 0
task 2 step 0
task 0 step 1
task 1 step 1
task 2 step 1
task 0 done
task 1 done
task 2 done
done = 3

The order is not luck and not timing. tick walks the registered tasks in the order they were added, so task 0 runs, suspends, and yields to task 1, which suspends and yields to task 2. On the next tick each resumes at its saved state, prints its second step, suspends again. On the third tick each falls out of its loop and finishes. Because the scheduler is cooperative and single-threaded, that order is exactly reproducible, which is what makes a coroutine program testable.

Why this replaces hand-rolled state machines

Every experienced C programmer has written the thing this chapter is asking you to stop writing. You have a job that must happen over several calls — read a line, then a header, then a body; walk a path across several frames; send a big response without blocking on the send. So you add a field to a struct, call it state, and write a switch: 

switch (conn->state) {
case READ_LINE:  ... if (no newline yet) return;  conn->state = READ_HEADER;  /* fall */
case READ_HEADER: ... conn->state = READ_BODY;   /* fall */
case READ_BODY:   ... conn->state = DONE;
}

This works, and it is the right thing to do in C89, where you have no better option. It is also where the bugs live. The state is an int that the type system cannot check, so a missing transition is a silent stall and a repeated one is a loop nobody meant. Every local that must survive the return has to be promoted into the struct by hand, so the function's live state is scattered across the file. The switch has to be re-entered from the top on every call, so the same code does a little work and returns, inverts the natural shape of an algorithm that wants to read a line and then use it.

The Z98 way is the same algorithm with the bookkeeping removed. You write the plain, blocking version of the function:

fn handle(conn: *Conn) void {
    var line: []const u8 = readLine(conn);
    std.io.print("got {}\n", .{line});
    var body: []const u8 = readBody(conn);
    send(conn, body);
}

and if readLine and readBody are suspending, then handle is suspending too, and the compiler does the state-machine work you used to do by hand. There is no state field in your struct, no switch to keep exhaustive, no locals to hoist. The suspension points become numbered resume segments in the step; the locals live across a suspension become frame fields the compiler lays out; and the resume logic is the compiler's bounded switch on the state byte, not yours. When you will reach for a switch on a state variable — and you will, because that is the habit a C programmer carries — that is the signal to write the function straight through and put @asyncSuspend where the return used to be. The state variable is still there. You just stopped writing it.

The trade is real, so state it. The compiler's step machine is conservative: it reserves frame space for every reachable node, so a hand-tuned state machine can sometimes be smaller, and a coroutine is a struct in a buffer you must keep alive for the task's whole life. It also cannot express a suspension inside defer, and a suspending function's address cannot be taken. None of those costs falls on the common case, and all of them are visible in the emitted C, which is the compensation this whole volume keeps returning to. You give up a little control and you stop writing the bug-prone part.

The trade

The third shift buys a way to write long-lived, multi-step logic without threads, and it pays for that with a smaller, stricter model than a modern runtime. Four limits are worth naming, each with what you do instead.

No preemption and no threads. A coroutine yields only where @asyncSuspend says so, and the scheduler is round-robin. A task that never suspends starves the others. That is not a bug to route around; it is the property that makes locks unnecessary and the program deterministic. The way over is to place your suspension points where the work genuinely pauses — a read that would have blocked, a send that would have filled a buffer — which is exactly where the old state machine returned anyway.

No typed futures. There is no Future(T) because there are no generics. A coroutine's state is erased to *void and a result slot is a *void you point at your own storage. The way over is the result field of Task and the args record pattern: you own the storage, you know its type, and the erasure happens only at the scheduler boundary where nothing needs the type. It is more typing than await future and it is completely transparent.

The scheduler is driven by you. Nothing runs until a tick or a wait call does it. That is another way of saying the same absence: there is no event-loop thread behind your back. The way over is the drive table above; the choice between waitFor and awaitTask is the only real decision, and the tech doc states the rule.

The root-main pool is fixed at 256 bytes. A suspending pub fn main gets a synthesized synchronous driver, and that driver's child-frame pool is a fixed 256 bytes, so a main whose implicit awaits need more overflows. A non-suspending main that drives an explicit pool — which is what this sample does — has no such cap. The way over is to keep the scheduler in main and let the tasks, not main, suspend.

Honest note. The strongest temptation with coroutines is to reach for the compiler's machinery when a plain function would do. Not every function that calls a loop, or returns early, or keeps a cursor is a state machine waiting to be suspended; most are ordinary functions and should stay ordinary. A suspending function costs a frame in permanent memory for the task's whole life, and a suspension point is a promise that the function will be re-entered, which is true only when a scheduler actually drives it. Reach for @asyncSuspend when the work genuinely spans time — a read, a send, a multi-frame animation — and keep the rest synchronous. The compiler will tell you when a function is suspending; it will not tell you when it should not be.

Common mistakes

The mistakes below are the ones a reader makes first with coroutines, and each has a diagnostic or a corrected shape.

Passing the args record as ?*const void. The fourth argument to @asyncInit is @ptrCast(*const void, &record), a plain *const void. A ?*const void is a non-scalar optional in this position and emits invalid C89. The record is quite literally the parameter list: its fields are copied positionally into the coroutine's parameters, so the number and order must match exactly.

Backing a pool or frame with [N]u8. A u8 array is 1-aligned, and contextInit traps on a misaligned buffer. Back the context and the root frame with a [K]u64 array and cast a slice to []u8. This is a -fsafe trap, not undefined behavior, so you will see it immediately — but you will see it as a crash on the first run unless you follow the rule.

Taking the address of a suspending function. It is error[3017] by design: the function is a step machine, and a function pointer to it would not have the signature you expect. If you need to select behavior, select data (a task's args record) and self-dispatch through @asyncResume; the scheduler already does exactly this.

Expecting a suspending function to still be callable synchronously. Only the root pub fn main and an export fn keep a synthesized synchronous entry. Every other suspending function is replaced by its step and must be driven through a frame. Calling it as an ordinary function is not something you can accidentally do, but expecting its synchronous body to exist is a design misread.

Forgetting the frame must outlive the task. The root frame you hand to @asyncInit is where the coroutine lives. If it is a local in a function that returns, the task resumes into stale memory. Put the frames and pools in memory that lives as long as the scheduler — a permanent buffer or a dedicated arena, never the short-lived scratch arena that gets reset.

Reaching for switch on a state variable. The habit is stronger than the need. If you catch yourself adding a state field and a switch to a struct only to make one function resumable, write the function straight through and suspend instead. The compiler's step machine is the state machine; two of them is one too many.
