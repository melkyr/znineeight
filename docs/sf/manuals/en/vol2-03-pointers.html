Pointers

A C programmer already knows what a pointer is, and Z98 does not pretend otherwise. The vocabulary is the one you expect: &x takes an address, p.* reads through it, and a struct pointer reaches a field with a dot rather than an arrow. What changes is how carefully the compiler watches the pointer and what survives into the C89 it emits. This chapter works the five pointer shapes, the two address operators, the indexing rule, the auto-deref rule, and the five pointer builtins, and it shows the emitted C for the two qualifiers that behave differently from C.

The guiding fact is that Z98 splits the two qualifiers apart. const is a promise made to the Z98 frontend only; the C that comes out drops it. The emitted C is plain C, and a plain C pointer can be written through whether the source said const or not. volatile goes the other way: Z98 keeps it in the emitted C, so the C compiler honors it too. One qualifier protects Z98 code from itself; the other protects a memory-mapped register from the optimizer. Everything below follows from that split and from an indexing rule that is stricter than C's.

The five pointer shapes

Z98 spells pointer types in the Zig style: a * followed by the pointee type. There are five shapes the chapter uses, and each is a distinct type to the compiler.

Shape Means Emits as
*T One item; read and write through it T*
*const T One item; read through it, not write (frontend-enforced) T* (const dropped)
*volatile T One item whose reads and writes the compiler must not elide volatile T*
[*]T A many-item pointer with no length; C-style p[i] T*
**T A pointer to a pointer; multi-level runs deeper still T**

A [*]T is the shape C calls a plain T*: it points at the first of some number of items, and the number is not part of the type. The length-carrying shape is the slice, []T, and it is chapter 9 (planned). Z98 accepts [*]const T and [*]volatile T too, but not the slice-side []volatile T; memory-mapped I/O uses *volatile T or [*]volatile T.

& and .*

Two operators carry the basic reads. &x produces a pointer to x, and p.* is the value the pointer points at. They compose with assignment, so p.* = 42; writes through the pointer and the underlying variable sees it: 

var n: i32 = 41;
var p: *i32 = &n;
p.* = 42;

The example's first line proves the round trip: it prints *T n=42 p.*=42. Note the punctuation: Z98 dereferences with a postfix .*, not with C's prefix *. A C habit of writing *p = 42; does not transfer; the compiler wants p.* = 42;.

& needs an addressable value. It takes a variable, a field, or an array element; you cannot take the address of a literal or of a temporary. In C this is the same rule, so it should feel familiar.

ptr.field auto-dereferences

A single-level pointer to a struct reaches a field with the ordinary dot, and the compiler inserts the dereference for you. This is the one place Z98 is more forgiving than C, where a struct Point * needs p->x: 

var pt: Point = .{ .x = 1, .y = 2 };
var sp: *Point = &pt;
sp.x = 5;

sp.x and sp.*.x are the same lvalue; the emitted C uses sp->x. Auto-deref applies through one level of pointer. A **Point needs its dereferences spelled out, exactly as in C.

Indexing belongs to many-item pointers

This is the rule that catches C programmers, because C lets you index any pointer. In Z98, p[i] is defined only for a many-item pointer ([*]T) and for a pointer to a fixed-size array (*[N]T, Zig's auto-deref indexing). Indexing any other single-item pointer — *T, *const T, *volatile T, or a multi-level pointer — is rejected at compile time: 

error[3066]: type '*i32' does not support indexing
note: operand must be an array, slice, tuple, or vector

That is Zig's own rule, not a Z98 invention. The reason is the type: a *i32 promises exactly one i32, so an index other than zero is meaningless and even p[0] hides an intent the type does not carry. If you want an indexed run of items, ask for the type that says so. A [*]T says it with no length; a *[N]T says it with the length in the type; a slice says it with a length at runtime. The example uses a decayed array: 

var arr: [3]i32 = .{ 10, 20, 30 };
var mp: [*]i32 = arr;
mp[1] = 25;

A fixed array coerces to a [*]T by giving up its length, which is why the coercion is written with the target type visible. After that, mp[0] through mp[2] are ordinary C subscripts. The type carries no length, so a many-pointer index is exactly as unchecked as C's p[i]; the checkable form is a slice, and that is chapter 9's subject.

Honest note. const is a promise to the Z98 frontend, not to the C compiler. The emitted C for const cp: *const i32 = &n; is int* cp; — the qualifier is gone. Z98 will reject an assignment through cp.*, but any C function that receives the pointer sees a plain int* and can write through it. volatile is the opposite: Z98 keeps it in the emitted C, so the C compiler honors it too. The two qualifiers promise to different audiences, and only one of those audiences is the C compiler.

const stops at the frontend

The *const T shape is the read-only one. A write through it is a compile error, and the diagnostic is the same one the language uses for an immutable variable: 

error[3002]: cannot assign to immutable variable

Reads are ordinary, and the example prints *const T cp.*=42 through a *const i32 bound to the same variable that p points at. The guarantee is real inside Z98 and it costs nothing: the emitted C for the declaration is just int* cp;. That is the honest boundary drawn in the note above, and it is why the manual says const is a frontend guarantee rather than a C-level one.

volatile survives into C

A *volatile T is read and written on exactly the terms you wrote, so the C compiler may not cache, reorder, or delete the access. Z98 enforces the qualifier at the frontend and then keeps it in the emitted C: 

volatile int* vp;

The example writes vp.* = 9; and reads it back; the run shows *volatile T vn=9 vp.*=9. The important half is what you are not allowed to do. A *volatile T cannot quietly become a *T, because that would drop the guarantee while the code still looked correct: 

var np: *i32 = vp;
error[3000]: cannot implicitly discard 'volatile' qualifier; use @volatileCast to remove it

@ptrCast cannot discard it either; it reports @ptrCast cannot discard the 'volatile' qualifier; use @volatileCast to remove it. The only way from *volatile T to *T is @volatileCast, which names the removal on purpose. That is the difference between const and volatile in one sentence: Z98 lets C forget the first and refuses to let it forget the second.

Multi-level pointers

**T, ***T, and deeper are supported, and every level is dereferenced explicitly. The example takes the address of the *i32 it already has: 

var pp: **i32 = &p;
pp.*.* = 43;

pp.* is the inner *i32 and pp.*.* is the i32, so the write lands on the same variable the chapter started with; the line prints **T n=43 pp.**=43. Deeper levels follow the same pattern, one .* per pointer hop.

The pointer builtins

Five builtins carry the casts and conversions that pointer code needs. They are recognized by name, and the name is the whole API; there is no pointer library to import.

Builtin Does
@ptrCast(T, expr) Reinterpret a pointer as another pointer type; the target is explicit
@intFromPtr(expr) / @ptrToInt(expr) Pointer to integer; the two names are the same operation
@intToPtr(T, expr) Integer to pointer, result type named explicitly
@ptrFromInt(expr) Integer to pointer, result type taken from context
@bitCast(T, expr) Same-size integer-to-integer bit reinterpretation
@volatileCast(T, expr) Remove volatile; source must be volatile and the base type must match

@ptrCast reinterprets without looking at the pointee. The example erases *i32 to *void and casts it back, and the round trip returns 43 because the address never changed. This is the tool for the arena pattern later in the volume, where a block of bytes is cast to the type that will live in it.

@intFromPtr and @ptrToInt are aliases: both turn a pointer into a usize, and the example shows both spellings agreeing on the same address. The reverse direction comes in two forms. @intToPtr(*i32, addr) names the result type inside the call; @ptrFromInt(addr) takes nothing but the integer and reads the result type from where the value is going. That second form needs a context to read from, so it must be assigned to an annotated variable or passed where the target type is known: 

const from_addr: *i32 = @ptrFromInt(addr_from);

Written without that annotation, @ptrFromInt has nothing to infer the pointer type from and is rejected: 

error[19]: cannot infer pointer type for @ptrFromInt; annotate the target variable type

@bitCast is the pointer chapter's integer tool rather than a pointer tool, but it belongs beside the casts because it reinterprets representation: same-size integers trade their bit pattern without arithmetic. The example turns i32 -1 into u32 and prints both views, @bitCast u32(-1)=4294967295 hex=ffffffff. The source and destination must be integers of equal size; @bitCast(u32, -1) with an untyped literal is rejected, so the value is bound to an i32 first.

@volatileCast is the only sanctioned way to shed volatile, and it insists on a real volatile source with the same base type. The example removes the qualifier from the *volatile i32 it wrote earlier and prints the value it now reads: @volatileCast read=9.

The example

The whole chapter in one program. It declares one variable and takes every pointer shape at it, decays an array to a many-pointer, auto-dereferences a struct pointer, and exercises the five builtins in a round trip. It is docs/sf/manuals/src/vol2/pointers.z98: 

const std = @import("std");

const Point = struct {
    x: i32,
    y: i32,
};

pub fn main() void {
    var n: i32 = 41;

    var p: *i32 = &n;
    p.* = 42;
    std.io.print("*T n={} p.*={}\n", .{ n, p.* });

    const cp: *const i32 = &n;
    std.io.print("*const T cp.*={}\n", .{cp.*});

    var vn: i32 = 7;
    var vp: *volatile i32 = &vn;
    vp.* = 9;
    std.io.print("*volatile T vn={} vp.*={}\n", .{ vn, vp.* });

    var pp: **i32 = &p;
    pp.*.* = 43;
    std.io.print("**T n={} pp.**={}\n", .{ n, pp.*.* });

    var arr: [3]i32 = .{ 10, 20, 30 };
    var mp: [*]i32 = arr;
    mp[1] = 25;
    std.io.print("[*]T mp[0]={} mp[1]={} mp[2]={}\n", .{ mp[0], mp[1], mp[2] });

    var pt: Point = .{ .x = 1, .y = 2 };
    var sp: *Point = &pt;
    sp.x = 5;
    std.io.print("ptr.field x={} y={}\n", .{ sp.x, sp.y });

    const erased: *void = @ptrCast(*void, p);
    const restored: *i32 = @ptrCast(*i32, erased);
    std.io.print("@ptrCast roundtrip={}\n", .{restored.*});

    const addr_from: usize = @intFromPtr(p);
    const addr_to: usize = @ptrToInt(p);
    std.io.print("@intFromPtr!=0={} @ptrToInt!=0={}\n", .{ addr_from != 0, addr_to != 0 });

    const from_addr: *i32 = @ptrFromInt(addr_from);
    const to_addr: *i32 = @intToPtr(*i32, addr_from);
    std.io.print("@ptrFromInt roundtrip={} @intToPtr roundtrip={}\n", .{ from_addr.*, to_addr.* });

    var neg: i32 = -1;
    const all_ones: u32 = @bitCast(u32, neg);
    std.io.print("@bitCast u32(-1)={} hex={x}\n", .{ all_ones, all_ones });

    const mutable: *i32 = @volatileCast(*i32, vp);
    std.io.print("@volatileCast read={}\n", .{mutable.*});
}

Common mistakes

The mistakes below are the ones a C programmer makes first with Z98 pointers. Each one has a corrected shape, and the corrected shape is the compiler's rule, not a style preference.

Indexing a one-pointer. In C, int *p and p[0] are synonyms for *p, and p[1] is how arrays are walked. In Z98, p[i] on a *i32 is rejected with error[3066]. The corrected shape depends on what you mean: a single item keeps p.*, a run of items with no length becomes a [*]T, and a run with a known length becomes a *[N]T or a slice. Do not reach for a cast to silence it; the rejection is telling you the type does not say "an array".

Assuming const reaches C. A *const T stops writes in Z98 and then emits as a plain T*. If a C function is handed that pointer, it can write through it, and the compiler that emits the C will not stop it. Read the qualifier as "the Z98 frontend will not let this source write through it", not as a guarantee that the object is immutable for the whole program. If that distinction matters, put the pointer behind an interface that does not hand it out.

Reaching for a modern-Zig pointer builtin. The names here are the Z98 names. @intFromPtr, @ptrFromInt, @bitCast, and @volatileCast all exist, but the modern Zig set is larger than this compiler implements, and an unsupported name is not close enough: @intFromFloat, for example, is 

error[3000]: unsupported builtin function

The rule is that the builtins in the Reference are the builtins that exist; no other @name is treated as a near miss. The five on this page are cross-checked against Volume IV — Builtins.

Forgetting that @ptrFromInt reads its type from context. @intToPtr takes the result type as its first argument; @ptrFromInt does not, and an unannotated binding has nothing to infer from. The compiler says so rather than guessing: error[19]: cannot infer pointer type for @ptrFromInt; annotate the target variable type. Annotate the variable, or use @intToPtr.

Dropping volatile with @ptrCast. A cast that removes the qualifier is rejected, and so is an implicit conversion. Use @volatileCast; a cast that leaves the qualifier in place is fine, but the removal is an operation with a name because it is a decision.
