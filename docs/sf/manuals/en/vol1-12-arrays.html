Lists of Things

The last chapter bundled related values into a struct: a fixed shape with a name for every field. This chapter bundles values the other way: a list of items that are all the same type, in a fixed count. Z98 calls it an array, and writes its type as [N]T — N values of type T. One name, one count, one type of item. The chapter adds the brackets that hold the count and the position, the .len property that answers how many items there are, and the list form of the for loop from chapter 9. A class's scores, a row of pixels, a tally per month: each is one array instead of five variables that have to be kept in step by hand.

The program

const std = @import("std");

pub fn main() void {
    const scores = [5]i32{ 90, 72, 85, 60, 98 };

    std.io.print("the list has {} scores\n", .{scores.len});
    std.io.print("first is {}, last is {}\n", .{ scores[0], scores[scores.len - 1] });

    var total: i32 = 0;
    for (scores) |score, i| {
        std.io.print("scores[{}] is {}\n", .{ i, score });
        total = total + score;
    }
    std.io.print("total is {}\n", .{total});

    const all = scores[0..scores.len];
    std.io.print("scores[0..len] has {} items, last is {}\n", .{ all.len, all[all.len - 1] });

    const all_but_last = scores[0..scores.len - 1];
    std.io.print("scores[0..len-1] has {} items, last is {}\n", .{ all_but_last.len, all_but_last[all_but_last.len - 1] });
}

It builds a list of five scores, prints how many there are and the first and the last, walks the whole list with a for loop that keeps a running total, and then takes two slices — one holding every score, one without the last. The two slices are the same list seen with different end marks, and the difference between them is the one rule this chapter turns on.

An array is one name for N values

The declaration is the chapter's new syntax: 

const scores = [5]i32{ 90, 72, 85, 60, 98 };

Read it piece by piece. [5] is the count, and the brackets say that this is a list; the 5 says how many items fit. i32 is the type of every item: a list has one item type for the whole list, not one type per item the way a struct has one type per field. The braces hold the items themselves, in order, separated by commas. const scores names the whole list, exactly as const named a single value in chapter 6 and a shape in chapter 11.

The count is fixed when the program is built. The compiler knows [5]i32 is five i32 values and reserves room for exactly five; an array cannot grow or shrink while the program runs. That is not a limitation to work around here — it is what makes the list cheap, because the machine never has to go looking for more room for it. When a count really must change at run time, the language's answer is the slice, which Volume II covers.

Because every item is an i32, the five items together take the space of five i32 variables: @sizeOf([5]i32) is 20, five times the four bytes of one i32. The items sit next to each other, and that is all the size arithmetic there is to an array.

Asking for one item

One item is named by its index, written in brackets after the list: 

std.io.print("first is {}, last is {}\n", .{ scores[0], scores[scores.len - 1] });

scores[0] is an expression like any other: it can be printed, stored, added, or passed to a function. Indexing starts at zero, so the first of five scores is scores[0] and the last is scores[4]. The index between the brackets does not have to be a literal; scores[i] with an i from a loop or a variable works the same way, and the index expression is computed first and then used to pick the item.

scores.len is a built-in property: the number of items in the list, 5 here. The dot names something inside the value, the dot of chapter 11; what it names here is not a field the program declared but the count the compiler already knows. Because indexing starts at zero, the last valid index is scores.len - 1, which is how the second line above names the last score without writing 4. The two numbers are always one apart: .len is the count, 5, and the last index is 5 - 1, 4.

Note. .len is always a count, never a position: five items have length 5 and indices 0 through 4. Every off-by-one in this chapter is that one confusion between the two numbers.

Walking the list with for

Chapter 9's for loop walked a range of numbers. Given a list instead of a range, it walks the items: 

var total: i32 = 0;
for (scores) |score, i| {
    std.io.print("scores[{}] is {}\n", .{ i, score });
    total = total + score;
}

Read the first line as "for each score in scores". The parentheses hold the iterable — here the array itself. The first capture, score, is the current item; the second, i, is its index, starting at 0. A range loop needs one capture because a number already is its index; a list needs the second name so the body can say where it is as well as what it found. Both captures are read-only, the rule from chapter 9: the loop hands you the items, and changing one means assigning to scores[i], not to score.

With one capture, for (scores) |score|, the loop visits the same items and leaves the index out. The same loop shape also walks a slice; a slice holds items of the same type as the array, so there is nothing new to learn for it.

The range form still works when the index is what you want. The range 0..scores.len stops before .len, so it visits exactly the valid indices, and the same five items the walk above does: 

for (0..scores.len) |i| {
    std.io.print("scores[{}] is {}\n", .{ i, scores[i] });
}

scores.len is the exclusive end of the range, exactly as 10 was in chapter 9's 0..10: it is one past the last valid index. That is the chapter's one rule showing up again, and it is worth slowing down for.

The half-open rule

A run of items is taken with the same two-dot range used for numbers: 

const all = scores[0..scores.len];
const all_but_last = scores[0..scores.len - 1];

start..end keeps the item at start and stops before the item at end. The end is an exclusive mark, not the last item you want: it is one past it. So scores[0..5] asks for the items at indices 0, 1, 2, 3, and 4 — all five scores. scores[0..4] asks for indices 0 through 3 — four scores, everything except the last. Move the end by one and the result changes by one item, always at the far end.

That is why [0..N] is not the same as [0..N-1] for a list of N items. [0..N] names all N of them. [0..N-1] names N-1 of them and leaves the last one out. When you mean "the whole list", the end you write is N, or .len; when you mean "the list without its last item", it is .len - 1. Writing the index of the last item as the end mark is the commonest off-by-one in this chapter, and the mistakes below dwell on it.

The result of the range is a slice: a view of that run of items, with the same item type. A slice answers .len the way the array does, and its items are indexed the same way, so all[all.len - 1] is the last score of the slice. Nothing is copied; the slice names items that already exist in the array.

Building and running it

The commands are the ones from the last chapters, with scores in place of point. The compiler is still at /tmp/manual_seed, built in chapter 4: 

$ mkdir -p /tmp/manual_out
$ /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol1/scores.z98
$ cd /tmp/manual_out && sh build_target.sh linux scores
Building for linux...
Built: scores
$ ./scores
the list has 5 scores
first is 90, last is 98
scores[0] is 90
scores[1] is 72
scores[2] is 85
scores[3] is 60
scores[4] is 98
total is 405
scores[0..len] has 5 items, last is 98
scores[0..len-1] has 4 items, last is 60

Read the output against the source. The first line is .len: 5 items. The second is the first item and the last, the last named as scores[scores.len - 1]: 90 and 98. The five lines after that are the walk, one line per item, with the index in front. total is 405 is the sum, 90 + 72 + 85 + 60 + 98. Then the two slices: [0..len] has all five items and ends at 98; [0..len-1] has four and ends at 60. The last score is exactly the one missing when the end mark moves back by one. The program exits with status 0.

Common mistakes

These are the mistakes a first list attracts. One is caught only when the program runs, one is the same mistake made by confusing two numbers, and one is caught by the compiler.

Asking for an item that is not there. The valid indices for five scores are 0 through 4. An index of 5 is one past the end. The compiler builds the program without a word — it does not check the index, even when the index is a literal — and the bad access stops the run: 

const scores = [5]i32{ 90, 72, 85, 60, 98 };
std.io.print("the list has {} scores\n", .{scores.len});
const sixth = scores[5];
std.io.print("the sixth is {}\n", .{sixth});

$ ./bounds_mistake
the list has 5 scores

The first line prints and nothing else does: when the program reaches scores[5] it stops with a trap, the safety check that runs under the default build. The trap has no message of its own; on this Linux host the shell reports the trace trap and the exit status is 133. The fix is to keep every index inside 0 up to .len - 1, and to check the boundary arithmetic when a while loop counts the index by hand.

Confusing .len with the last index. .len is the count — how many items — not the position of the last one, because counting starts at 0 and the positions stop at .len - 1: 

const scores = [5]i32{ 90, 72, 85, 60, 98 };
std.io.print("last is {}\n", .{scores[scores.len]});

For five scores this asks for scores[5], the same out-of-bounds access as the mistake above; the program builds and then stops with the same trap. The item the author meant is scores[scores.len - 1], the expression the program's own second line uses. A useful habit: say ".len is the count" out loud whenever the two numbers get mixed, and write the last index as .len - 1 every time.

Changing an item of a const list. A const array is read-only down to its items, so assigning to one is rejected before the program is built: 

const scores = [5]i32{ 90, 72, 85, 60, 98 };

pub fn main() void {
    scores[0] = 100;
}

const_mistake.z98:4:12: error[3002]: cannot assign to immutable variable
    scores[0] = 100;
            ^

The caret points at the index inside the brackets, and the message is the one chapter 6 met for a const variable and chapter 11 for a field: immutable. The whole list is fixed, so every item in it is fixed. When an item must change, declare the list with var instead — var scores = [5]i32{ ... }; — and then scores[0] = 100; is accepted, exactly as assigning to a var variable is. Making the list a var does not change its count; it only allows the items to be replaced.

Check yourself

Answer these before moving on. The last three ask you to change the program and run it.

  1. What does the type [5]i32 say about the list? How many items are there, and of what type?
  2. Which index holds the first item? Which index holds the last item of a five-item list? Write the last index using .len.
  3. In for (scores) |score, i|, what does each capture hold? Which one tells you where in the list you are?
  4. What does scores[0..3] ask for, and how many items come back? What about scores[0..4]? Why do the two answers differ by one?
  5. For the five-score list, why is scores[0..5] the whole list while scores[0..4] drops the last score?
  6. What does .len answer for the slice all? Why is .len not the same as the last valid index?
  7. Change the list to six scores, count included, rebuild, and run. What do total and the two slice lines print now? Predict before you run.
  8. Add a line printing scores[2] after the first/last line, rebuild, and run. What prints?
  9. Write a loop that adds only the scores above 80 and prints the sum. What is it for the five scores?
