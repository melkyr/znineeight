Honesty: What You Cannot Do on a Pentium II

The three chapters before this one answered a question about tools: when C89 wins, when C++98 wins, when assembly wins. This chapter asks a different question, and it is the last of the honesty spine that is about a hard boundary. It asks what the machine itself will not let you do. The answer is not in Z98's feature list and not in the C89 emitter. It is in the 1998 PC: one 32-bit processor, a fixed amount of memory, a display that is small by modern standards, and no hardware that a modern project would recognize. Some things a modern program assumes it can do are not available there, and no choice of language changes that.

The distinction that organizes the chapter is the one between a language limit and a machine limit. A language limit is something you can leave: if you want templates, you write that module in C++98, and chapter 4 said so. A machine limit is something every tool on the machine shares. Z98, C89, C++98, and assembly all run on the same processor, use the same memory, and write to the same display. Swapping the language does not move the boundary. What the language can do is make the parts of the work that are not the bottleneck cheaper to write and harder to get wrong; it cannot make the bottleneck disappear. This chapter names the bottlenecks, pairs each with its way over, and states the rule the volume is built on: the era had limits, and respecting them is the point.

Era framing. Statements here about the era's processors, memory, display hardware, audio, and operating system are era context, and where a statement is an opinion the text says so. This host has no Pentium II, no 1998 display adapter, and no Windows 95/98, so an era hardware claim cannot be run here; the text marks those as the era's facts and readings rather than measurements. Statements about Z98 are a different kind, and those are checked against docs/reference/Language_Spec_Z98.md, the compiler source, and the compiler built from the committed seed: the concurrency and networking limits are the compiler's own, and the evidence for them is named where they appear.

What you expect

A reader arriving from a modern machine expects a limit to be a feature that is missing, and a missing feature to be something a library can supply. That is usually true. Need a data structure? Write it. Need a protocol? Link a library that speaks it. The compiler is the constraint, and the constraint bends when you write or fetch the right code. This chapter is about the limits where that reading fails, because the constraint is not in the compiler and not in any library. It is the machine.

There are two ways to get this wrong, and they look opposite but come from the same place. The first is to blame the language for the machine: to say Z98 “cannot do 3D” when the truth is that this class of machine cannot do the 3D the reader has in mind, in any language. The second is the opposite error, and it is the more common one: to believe that enough cleverness beats the envelope — that a hand-tuned rasterizer, a smarter allocator, or a better algorithm will let a 233 MHz machine hold a 1024×768 32-bit framebuffer and a scene with tens of thousands of polygons at a playable rate. It will not. The machine sets an envelope, and the work of the era is designed inside it.

So the frame for this chapter is not “look how little the old machine could do.” That would be the modern scoreboard the volume refuses to keep, and it measures the wrong thing besides: a modern toolchain was never a candidate for this target, because it cannot be built for it and its binaries do not run on it. The frame is the working one. The envelope is given; the question is what fits inside it, and what you reach for when the thing you want does not. Chapter 1, The 1998 Machine (planned) draws the envelope in full, and the CPU-versus-memory point it makes is the one that returns in every limit below: it is memory, not processor speed, that is the binding constraint.

What you get

Five hard limits and their ways over. The table is the map; the sections after it are the argument. Each limit is stated as an era fact or an era reading and marked as such; each is paired with the era's answer, because a limit with no way over is a complaint, and the volume drops complaints. The last column names the Z98 angle where one exists — the place where the language or its standard library does something about the limit rather than simply standing under it.

No hardware 3D at modern resolutions

This is an era fact, marked as one, and it needs a careful statement because the era did have 3D. By 1998 there were real 3D accelerators — 3dfx's Voodoo2, NVIDIA's RIVA 128, and others — and games that used them. The limit is about the machine this volume targets, which is the baseline: a Pentium II with 32 MB of memory and the display the era shipped. On that machine the processor is the renderer. The resolution and color depth a modern project assumes — 1024×768 or more, 32 bits per pixel, a depth buffer, heavy overdraw — are not reachable in software at an interactive rate, and no article about the era claims otherwise.

The numbers make it concrete. A 640×480 framebuffer at 16 bits per pixel is about 600 KB, and clearing and filling it costs memory bandwidth on every frame; at 320×200 it is about 128 KB, and the era's software renderers were designed around exactly that smaller buffer. The point is not that the processor is slow in the abstract. The point is that a frame has a budget, and geometry, textures, and shading all spend from it. A software rasterizer can draw a simple scene at a small resolution; it cannot draw a modern scene at a modern resolution, and the difference is an order of magnitude, not a tuning pass.

The way over is to design inside the resolution, not to fight for the one you wanted. Render at 320×200 or 640×480, use 8-bit or 16-bit color, keep the polygon counts low, and lean on sprites and pre-rendered backgrounds, which is what the era's games actually did. Where an accelerator is present, target it through the era's 3D API — Direct3D 7 or 8 under CINTERFACE, the subject of chapter 14 (planned) — but never require it: the baseline machine has to run the game, and the accelerator is an optional second path. The Z98 angle here is narrow and honest. The language contains no 3D and does not pretend to; the era's 3D is a set of COM interfaces reached through extern declarations and @cInclude, and the memory budget of chapter 16 (planned) decides how much vertex and texture data can exist at once. Z98's contribution is the substrate the rest of the program is written on, not the renderer.

No large textures

This limit is the previous one wearing different clothes, and it is the reason the chapter keeps saying that memory is the binding constraint. Texture memory is the clearest arithmetic in the whole volume. A single 32-bit 1024×1024 texture is 4 MB: the size is 1024 × 1024 × 4 bytes. Four of them are 16 MB, which is the entire peak budget the compiler itself is held to (chapter 16, planned), before the program has a framebuffer, a working set, or a line of logic. An 8-bit 256×256 texture, by contrast, is 64 KB, and a whole atlas of them fits where one modern texture does not.

The way over is the era's texture discipline: palettized 8-bit art, small tiles assembled into larger pictures, a handful of distinct textures rather than hundreds, and a bounded cache that holds only the textures the current scene needs and streams the rest off disk. Procedural and tiled art stretches a small palette across a large world for almost nothing. The Z98 angle is real and it is the arena. A level's textures are a phase, not the whole game, so they belong in a pool that is sized once and reclaimed in a single reset when the level ends; Volume II chapter 14 measured the arena's cap/used/reset behavior, and chapter 16 (planned) measures the budgeting and --track-memory that let you see the pool before it overflows. This is a marked opinion, but it is the manual's: the right texture budget is the largest one that still leaves the rest of the program its memory, and the arena is how you enforce it.

No real-time MP3 on a PII-233

The blueprint states this one plainly, and the manual repeats it as the era's reading: decoding and mixing an MP3 stream at fidelity while the rest of the program runs does not fit the machine. It is an era claim about the whole machine being busy, and it is marked as such — it cannot be measured on this host, which has no Pentium II and no 1998 sound hardware. The honest version of the claim is not that no MP3 decoder existed for the era. A dedicated player with the whole processor to itself could decode a stream on hardware like this. The claim is that a game or a full-screen application cannot also hold a frame budget while the processor decodes audio, and that is a statement about the envelope, not about the codec.

The way over is the era's sound. Tracker modules (MOD and its descendants) mix cheaply because they are small samples and pattern data rather than a compressed stream; MIDI costs almost nothing to play and offloads synthesis to the sound card's wavetable; Red Book CD audio is played by the drive and costs the processor nothing at all; and a short piece mixed into a buffer once can be looped for free. The right answer is to choose the audio to the budget: a menu can afford more than a busy scene, and the scene's music is the first thing to give. The Z98 angle is mostly a warning dressed as an angle. Audio is another extern surface, and the cooperative scheduler of the next section is not a real-time engine: a coroutine keeps the machine until it suspends, so it cannot promise to fill the sound buffer on a deadline. The buffer is filled by the sound hardware's DMA, and the code hands it data in time; the scheduler schedules, and the deadline belongs to the hardware.

No multithreading worth the cost

This is the limit with the strongest Z98 answer, and it is worth separating the two things people mean by “threads.” On a single-core Pentium II, extra threads do not give extra compute. The processor can run one instruction stream at a time; two threads that both want to do arithmetic take turns, and the total is the same work plus the cost of switching. Windows 95/98 did have threads, and they were useful for one thing: letting a program wait on a slow device — a socket, a disk — without freezing everything else. They were not useful for making a program's own calculation faster, and the era's threaded code was hard precisely because shared state needed locks and the locks were easy to get wrong.

Z98's position is a language fact, and it is in the spec. The compiler has no thread API and no preemption; its concurrency is the cooperative, round-robin coroutine described in Volume II chapter 15 and specified in docs/reference/Language_Spec_Z98.md §4.1 and §7.2, which states plainly that preemption, threads, and typed futures are not implemented and that the @async* coroutines are cooperative and round-robin only. A coroutine keeps the machine until it reaches a suspension point, so no shared value can change under it and there are no locks to buy. That property is the reason the limit is not a hardship for the era's interactive software.

The way over is std.async, and it is the mental shift chapter 9 (planned) takes apart. A routine that would have waited writes the pause where the pause belongs: 

@asyncSuspend(null);

The scheduler in sf/src/std_async.zig — Scheduler, addTask, tick, waitAll, suspendUntil — resumes every runnable task once per tick and lets a task suspend until the thing it is waiting for is ready. The shipped coroutine program docs/sf/manuals/src/vol2/builtins/async.z98 reports frame=88 and n=3 steps=4 on this compiler. Real parallelism, where a program genuinely needs it, is the operating system's job and is reached through extern declarations, not through the language; but on one core, and for the era's workload, cooperative concurrency is not a compromise. This is a marked opinion, and it is the manual's: interlacing work with std.async is the correct model for this machine, and it removes a whole class of bugs that locks only ever manage.

No networking beyond the socket API

The blueprint says “no networking beyond what WinSock 2 provides,” and the manual has to correct the version, because the compiler was measured and the blueprint was aspirational. Z98's network surface is std.net, and on the Windows target it binds Winsock 1.1 through wsock32, initializing with WSAStartup(1,1) (sf/src/std_net.zig). The system may supply Winsock 2, but the surface Z98 offers is the classic 1.1 socket API and not a byte more. On the Linux side of this host the same surface runs over libc, which is why the chapter can cite it as a compiler fact rather than a Windows-only one. What is in the surface is the socket primitive set: init, TCP server and client creation, bindListen, accept, connect, send, recv, close, and select, plus non-blocking modes and UDP helpers. Handles are signed i32 with -1 for failure, and fd_set is an opaque [128]u32 blob passed to select. What is not in it is everything a modern program means by “networking”: no HTTP client, no TLS, no DNS resolution helper, no asynchronous network stack, no ready-made protocol.

The way over is to speak the protocol yourself. std.net gives you sockets; the wire format is your code. Multiplex several connections with select, or give each connection a coroutine and let the scheduler interleave them, and the two approaches meet in chapter 10 (planned). This much the Task 0 inventory measured: a socket program built through the harness binds and serves under a 32-bit Wine environment on this host, so the surface is real and not merely described. Chapter 12 (planned) is the surface in full. The era framing is worth stating: in 1998 the network you reach is small. The web is young, bandwidth is thin, and a game's netcode or a simple client is built on raw sockets, exactly as Z98 asks you to build it.

The trade

Read the five limits together and one statement covers all of them: the envelope is fixed, and the way over is always a change to the design rather than a missing feature. That is the trade, and it cuts both ways. On the buying side, a program designed inside the envelope runs — on the machine the project set out to serve, with the memory it actually has — and it stays small enough to understand and to debug. The era's software was shaped by this discipline, and the programs that are remembered are largely the ones that were designed to the machine rather than against it. On the paying side, the feature you wanted is still gone. You cannot have the modern resolution, the modern texture, the compressed soundtrack, the parallel speedup, or the network stack. No Z98 idiom conjures those back, because they are not language properties; they are the machine's.

Where another tool genuinely wins, it wins in the chapters before this one. If the limit is code generation — a hot loop that even the checked emission cannot tighten — assembly is the answer (chapter 5). If the limit is an abstraction the design needs, C++98 is the answer (chapter 4). If it is a library that already exists in C89, C89 is the answer (chapter 3). What none of those chapters does is raise the envelope, and that is the honest core of this one. Z98's contribution is not that it outruns the machine; it is that the parts of the program that are not the bottleneck are written in a language whose runtime is small enough to leave the machine room to breathe. No hidden allocator, no unwinder, no garbage collector, no dynamic loader — the absence this volume's chapter 2 listed as a trade is also, here, the reason the program fits.

The register matters as much as the arithmetic. This chapter does not apologize for the machine, and it does not pretend the limits are virtues. It says what the machine will not do and what you do instead, in the same breath, because that is the only useful form of the answer. A limit named without a way over is a complaint, and the volume drops it; a limit named with its way over is a design constraint you can work with. This is a marked opinion: the craft of the era lived in designing inside the envelope — in choosing the small resolution, the tiled texture, the tracker module, the cooperative task — and the discipline is the point, not a consolation for hardware that is old.

Honest note. The single sharpest limit is memory, and every other limit in this chapter is a version of it. The framebuffer, the textures, the audio buffer, the per-connection state, and the coroutine frames all spend from the same 32 MB, against the same 16 MB peak budget the compiler is held to. That is why the answers above all look alike: render smaller, cache less, mix cheaper, share the machine cooperatively, speak the protocol yourself. Respect the memory budget and the machine stays usable; ignore it and none of the other cleverness helps. The era had limits, and respecting them is the point.

The way over it

The way over a machine limit is a recipe, not a library. It begins before the first line of code and it ends with a feature cut rather than a correctness promise broken. Worked in order:

Step one: write down the envelope. Resolution and color depth, a memory ceiling for the whole program, the processor you are targeting, and the operating system. These are the terms every later decision is measured against, and they are the subject of chapter 1 (planned). An envelope that says 640×480 at 16 bits and a few megabytes of working set produces one design; an envelope copied from a modern machine produces a program that will not ship.

Step two: design the content to the envelope. Textures, audio, geometry, entity counts, and connection counts are chosen against the ceiling, not afterwards. This is where the texture and audio limits are actually met: at design time, where a 64 KB texture is an artistic choice rather than a late optimization.

Step three: measure in the target's terms. The compiler can show you what a program uses; --track-memory reports the arena peaks, and -mm0 relaxes the combined-peak check when a program has a reason to exceed it (chapter 16, planned). Measure before the envelope is breached, not after.

Step four: use the Z98 angles where the limit is structural. When the limit is concurrency, the answer is std.async (chapter 9, planned). When it is storage, the answer is the arena (Volume II chapter 14). When it is the network, the answer is std.net (chapter 12, planned). These are the places the language and its library do real work against the envelope.

Step five: when the limit is not structural, use the other tool. A hot loop that must be tight is chapter 5; an abstraction the design needs is chapter 4; a library already written in C89 is chapter 3. The envelope does not change; only the language of the part that meets it does.

Step six: if it still does not fit, cut the feature — never the checks. The one thing the envelope must not cost is the correctness the language exists to provide. Turning off a bounds check to save a kilobyte, or dropping a failure path to save a frame, trades a limit you can design around for a bug you cannot. When a feature does not fit, the feature goes.

Stated once, compactly, the limits and their ways over:

  • 3D at a modern resolution? Render small in software, use the era 3D API as an optional accelerator path, and cut geometry. The baseline machine must run the game.
  • Textures too large? Palettized, tiled, and small; a bounded arena cache that holds the current level and resets when the level ends.
  • Music too expensive? A tracker module, MIDI, CD audio, or a short mixed buffer; choose the audio to the frame budget.
  • Need concurrency? A coroutine suspends where the work waits; std.async is round-robin and cooperative, so no locks are needed, and real parallelism stays the operating system's.
  • Need the network? The std.net socket surface, with the protocol written by hand and connections multiplexed with select or with coroutines.
  • Running out of memory? That is the limit under all the others: size the arenas, budget the working set, and measure with --track-memory.

If an item in the table had no line here, it would be a complaint, and the chapter would have dropped it rather than list it. Every limit above carries a way over, and three of the ways over — C89, C++98, and assembly — are whole chapters with their own verdicts.

Common mistakes

The chapter has no code sample, because the limits it describes are not fixed by code. The mistakes below are design mistakes, and they are the ones a reader makes when the machine is treated as a detail rather than as the target.

Blaming the language for the machine. “Z98 cannot do 3D” is the wrong sentence. The machine cannot do the 3D you meant, in any language; Z98's part is to call the era's 3D API through extern and to keep the rest of the program small enough to leave room for it. A limit that survives a change of language is not a language limit.

Believing cleverness beats the envelope. A better algorithm helps, and the chapter would not deny it; the envelope is still the envelope. A 1024×1024 32-bit texture is 4 MB no matter how well the code is written, and a single-core processor cannot compute two instruction streams at once no matter how many threads you start. Tune after you have designed to the envelope, not instead of it.

Designing to the accelerator instead of the baseline. The machine this volume targets may or may not have a 3D card. A program that requires one does not ship to the baseline. Target the small path and treat the accelerator as an optional improvement, which is what the era's own dual-path games did.

Spawning a thread to solve a design that should be cooperative. On one core there is no parallel speedup for computation, and the locks that shared state demands are new bugs. The Z98 shape is a coroutine that suspends where the work waits; reach for OS threads through extern only when the job is genuinely blocking I/O that the scheduler cannot cover.

Assuming the network is the modern one. std.net is sockets — Winsock 1.1 on the Windows target, libc elsewhere — not an HTTP client and not a TLS stack. The protocol is your code, and the era's protocols are the ones that fit the wire.

Measuring on the development host. This host is not the target. A program that is comfortable here can still be over the era's memory budget, and a texture that loads instantly here can still be too large there. Measure the program the way the target would, with the budget in front of you.

Cutting a check to fit the envelope. The limits are a reason to cut a feature, not a reason to drop the error unions, the bounds checks, or the failure paths that are the language's whole point. A limit that costs a feature is a design decision; a limit paid for with a bug is a defect.
