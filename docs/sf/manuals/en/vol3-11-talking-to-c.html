Talking to C

Sooner or later every program for this machine has to call something that is not Z98. It is the Win32 API, or a C89 library someone shipped as a .lib and a header, or the C run-time the operating system already provides. The 1998 machine is not a place where you can pretend those libraries do not exist; they are the platform. This chapter is the exact contract for reaching them from Z98, and for letting them reach back.

It is also the shortest conceptual distance in the whole volume, because chapter 3 already stated the load-bearing fact: Z98 emits C89. A Z98 function is a C function by the time the linker sees it, and a Z98 module is a C translation unit. It is compiled by the same C compiler as everything else on the machine, against the same headers, with the same calling convention. So talking to C is not a bridge, a runtime, or a foreign-function interface. It is one C translation unit declaring a symbol that another translation unit defines, which is the oldest kind of interoperability there is.

What this chapter fixes is the surface: how to write the declaration (extern fn), how to pull in the header (@cInclude, module level only), what calling conventions mean ("c", "stdcall"), what happens to structs passed by value, which identifiers the language reserves, and how Z98 renames its own symbols so that they never collide with the C names it calls. Each of those is a rule with a diagnostic or an emitted line behind it, and each is shown from a run on the seed-built compiler.

What is measured here. Every Z98 statement on this page was checked against docs/reference/Language_Spec_Z98.md and the compiler source, and every transcript is a real run of the seed-built zig1. The sample, getenv.z98, is compiled on Linux and cross-built and run under the committed Windows harness; its Windows output below is that run, not a sketch. The struct-by-value layout is inherited from the compiler's frozen 32-bit model (FX14) and the coroutine plan's Win32 ABI oracle, which matched WNDCLASSEX, POINT, and MSG against the system headers. Where this chapter states an era fact about the Win32 API it says so; where it states a Z98 fact it shows the emitted C or the diagnostic.

The seam is the C ABI

Start with the model, because it removes most of the anxiety. A Z98 module compiles to one C translation unit and one header. A function you write becomes a C function; a struct you define becomes a C struct; a pointer becomes a C pointer. The emitted code is C89, so the seam between your module and a C library is the ordinary C ABI: symbol names, argument passing, and the calling convention. There is no marshalling layer, no generated glue, and no runtime that has to be initialized before the call.

That means the declaration is the whole contract. When you write an extern declaration you are telling the compiler two things: that a symbol with this name exists somewhere else, and that it has this signature. The compiler checks your Z98 call sites against the signature you gave it. It does not, and cannot, check that the signature matches what the C library actually defines — that is the C ABI's job, and it is why the prototype in the library's header matters. If your Z98 declaration and the C header disagree, the type checker on the Z98 side is silent and the error shows up as a corrupted argument at run time. The chapter returns to this in Common mistakes, because it is the one mistake in this area that the compiler cannot catch for you.

The seam runs in both directions, and it is worth naming both now. In the first direction, Z98 calls out: you declare a C function and call it. In the second, C calls in: you mark a Z98 function so that the emitter writes its plain, unmangled name into the object file, and the C side calls it like any other C function. The two directions use the same ABI and the same linker; the only difference is which side writes the declaration.

Calling out: extern fn

A C function that Z98 calls is declared with extern. The ordinary form names the return type and the parameters exactly as a Z98 function does, but there is no body and the declaration ends in a semicolon: 

extern "c" fn getenv(name: [*]const u8) [*]u8;
extern "c" fn strlen(s: [*]const u8) usize;

The type mapping is direct, and it is worth reading the two declarations above carefully. A C char * is [*]const u8 when Z98 only reads through it and [*]u8 when it may write through it; the [@intFromPtr]-style null check the sample uses reflects that a C pointer may be null where a Z98 many-pointer usually is not. A C size_t is usize, which on this 32-bit target is four bytes wide. The compiler emits the Z98 type as the matching C type in the declaration it writes into the module header.

The calling convention is optional and the default is cdecl. Writing extern fn f() and extern "c" fn f() declare the same thing; the second is the explicit spelling, and the sample uses it because it documents the intent. The other convention on this target is stdcall, the one the 32-bit Win32 API uses: 

extern "stdcall" fn MessageBoxA(hwnd: ?*void, text: [*]const u8, caption: [*]const u8, flags: u32) i32;

A word about that declaration before the details below: ?*void is the Z98 spelling of a possibly-null void * in a parameter position, but as chapter 9 and chapter 10 warned, a non-scalar optional in some positions emits invalid C89. At the extern boundary the safe habit is the one the sample follows: use [*]const u8 for a string and an explicit null test rather than a rich optional type. The point of this chapter is the rule, not a Win32 tutorial; the API itself is chapter 13, The Win32 Debug API (planned).

The prototype rule

There is one asymmetry in the emitted C that is easy to miss and that costs a warning if you do. A non-variadic extern declaration does not by itself emit a prototype into the generated C. A variadic one does. The rule follows from what the C compiler needs: a call to a variadic function must have a prototype in scope so the default argument promotions are applied, while a fixed-argument call can be left to an implicit declaration.

Emit a module that declares one of each and you can see it. The declaration 

extern "c" fn printf(fmt: [*]const u8, ...) i32;
extern "c" fn c_add(a: i32, b: i32) i32;

produces a module header whose forward declarations contain the variadic prototype and nothing for the fixed one: 

/* Forward declarations */
int printf(unsigned char*, ...);
void zF_EA90E208_main(void);
/* Storage globals (extern decls) */

The call site is ordinary either way — zT_6 = c_add((int)((int)zT_2), (int)((int)zT_4)); — but the C compiler never saw a declaration of c_add. Under the supported build that is only a warning (-Wno-implicit-function-declaration is on, as chapter 5 showed), and for a function whose return type is int the implicit declaration is correct by luck. It is not correct in general, and the fix is not to hope. Put the C prototype in a header and include that header with @cInclude. Then the C compiler has the real declaration, and it also checks your Z98-side argument types against the same text the library defines.

@cInclude: module level, and only there

@cInclude("header.h") writes a C #include into the module's generated header. It is the way you bring the C library's own declarations into the translation unit, so that argument passing and returns are checked against the real header instead of an implicit declaration. The sample begins with two of them: 

@cInclude("stdlib.h");
@cInclude("string.h");

The emitted header carries the includes verbatim, in the order written, after the compiler's own runtime headers: 

#include "zig_compat.h"
#include "zig_special_types.h"
#include "stdlib.h"
#include "string.h"
#include "std_io_59DB29D9.h"
...

Two details in that listing are worth calling out. First, the include is emitted with quotes rather than angle brackets, exactly as written. That does not stop the compiler from finding the C library — a quoted include falls back to the system search path after the local one — but it does mean the header is searched for in the module's own directory first, which is what you want for a project header and harmless for a system one. Second, the includes land in the module header, not the .c. Every translation unit that includes this module's header — including the generated std modules — therefore sees the C declarations too, which is exactly what you want when a struct you defined for the C boundary has to be visible where the call is emitted.

The rule that matters is where the builtin may appear: module level only. At the top of a file, beside the declarations, it is handled and emitted. In statement position, inside a function body, it parses but the type resolver has no case for the node, and the compiler reports an internal error rather than a designed diagnostic: 

$ /tmp/manual_seed/zig1_5_clean -o out cinclude_stmt.z98
cinclude_stmt.z98:1:2: error[3020]: internal error: unhandled node kind in type resolution
pub fn main() void {
  ^

Read that honestly: the location is not meaningful and the message says internal error. This is the compiler's existing behavior, not a designed rejection of the form, and it is the same reject that the Volume II baseline recorded; the chapter documents what is there. It emits no .c and returns a non-zero status, so the compiler does stop — you cannot ship a build that put an include in the wrong place. The way over is one line of discipline: includes go at module level. Move the statement to the top of the file and it compiles; the sample's two includes are where they belong.

Calling conventions

A calling convention is the agreement about how arguments are passed and who cleans up the stack. On this 32-bit target there are two that matter. The C default, cdecl, is what every ordinary C function and every libc function uses; the caller pushes the arguments and the caller pops them. The Win32 stdcall convention is what the 32-bit Windows API uses; the callee pops the stack, and a function whose declaration and definition disagree about that corrupts the stack.

Z98 spells the convention as a string after extern. The accepted spellings are "c" (or "cdecl") and "stdcall". Anything else is rejected at the string, before any code is emitted: 

$ /tmp/manual_seed/zig1_5_clean -o out callconv_bad.z98
callconv_bad.z98:1:7: error[3045]: unknown calling convention in `extern`
extern "watcom" fn foo(x: i32) i32;
       ^^^^^^^^

error[3045] is a parser-level diagnostic: the parser classifies the string and, when it cannot, the build stops with no C. There is no silent fallback to cdecl, which is the safe choice — a stdcall function mis-declared as cdecl would link and then corrupt the stack on the era machine, and a diagnostic before emission is far better than that.

The standard library is the reference for how this is done in practice. The networking module declares every Winsock entry point stdcall and the one POSIX-only helper cdecl, exactly because the two platforms differ: 

extern "stdcall" fn socket(af: i32, typ: i32, proto: i32) i32;
...
extern "stdcall" fn WSAStartup(wVersion: u16, lpWSAData: *void) i32;
extern "stdcall" fn WSAGetLastError() i32;
extern "c" fn __errno_location() *i32;

The emitted C makes the convention a macro so that one source builds for every toolchain. The compiler writes this into zig_compat.h, and the standard headers beside the program: 

#if !defined(_WIN32)
#define Z98_STDCALL
#elif defined(_MSC_VER) || defined(__WATCOMC__)
#define Z98_STDCALL __stdcall
#else
#define Z98_STDCALL __attribute__((stdcall))
#endif

Off Windows the macro is empty, because there is no stdcall in the Linux ABI and a Z98 program that declares a stdcall function would only do so when targeting Windows. On Windows it becomes the toolchain's own spelling — __stdcall for MSVC and for OpenWatcom's wcc386, __attribute__((stdcall)) for mingw. That three-way spelling is the kind of detail a manual-vtable C89 project usually has to carry by hand; on this target the compiler carries it, and the declaration is all you write.

One consequence reaches into the language's type rules. A function pointer's type includes its calling convention, so a function-pointer value may only be assigned or coerced to a target whose convention matches. A stdcall function value put in a cdecl function-pointer slot is rejected with the level-0 error[3000], on every assignment and argument position (FX17-F). That is the type system enforcing the same ABI rule the parser enforces on the declaration string.

What crosses the boundary

The types that cross are the types C has. Integers map to their C widths, with usize and isize four bytes on this target; bool to C's one-byte boolean convention; pointers to pointers. A slice does not cross as a slice, because there is no C type for one: pass s.ptr and s.len as the two C parameters the library expects, which is exactly what a C caller would do with an array and a length. An enum crosses as its backing integer. A struct crosses as a C struct, including by value, which is the next section.

What does not cross is the part of Z98 that has no C representation. Error unions and optionals are Z98 control-flow values, not C values; an E!T has no agreed C spelling, and a rich optional may be a tagged struct or a sentinel depending on the payload. Keep them on the Z98 side of the seam. The idiomatic shape is the one the sample uses for the null pointer: call the C function with the C-shaped arguments, then translate the result into Z98's world immediately. A C pointer that may be null is tested with @intFromPtr(v) != 0 and turned into whatever Z98 value you want; a C integer error code is compared to its sentinel and turned into an error union. The boundary is where the two type systems meet, so do the translation once, at the call, rather than passing Z98-shaped values across.

There is one more restriction worth stating because it is a real limit with a real way over. Z98 does not have extern struct, opaque, or vector types (Language Spec §7.2). You define a boundary struct as an ordinary Z98 struct with the fields the C header declares, and you use a pointer to void where C uses an opaque handle. That is sufficient for every API this volume touches, and it is the same choice C89 forces on everyone: the handle is an address and the layout is whatever the header says.

Struct-by-value and the 32-bit layout

A Z98 struct is a C struct laid out by the same rules, so passing one by value to a C function is direct. Declare the struct, declare the extern with the struct as a parameter, and the emitter writes both the struct and the call: 

const Point = struct { x: i32, y: i32 };
const Boxed = struct { tag: u8, value: i64 };

extern "c" fn c_point_sum(p: Point) i32;
extern "c" fn c_boxed_take(b: Boxed) i32;

The emitted definitions are the C structs you would have written by hand, and the call is a by-value C call: 

struct zT_EAA8EF31_Point {
	int x;
	int y;
};
struct zT_2E48BFE3_Boxed {
	unsigned char tag;
	zT_C69B2266_i64 value;
};
...
zT_12 = p;
zT_13 = c_point_sum(zT_12);

The layout is fixed by the compiler's frozen model (FX14), and the model is worth knowing because it is what makes the boundary predictable. On this 32-bit target i64, u64, and f64 are size 8 and alignment 8; every struct, union, optional, error union, tuple, and array inherits the maximum alignment of its members, so any composite containing a 64-bit scalar is alignment 8 and padded accordingly. Boxed above is the example: a one-byte tag, seven bytes of padding, a 64-bit value, for a size of 16 and alignment 8. The compiler pins that model on every host compiler by routing every 64-bit declaration through an aligned carrier typedef (typedef long long <carrier> Z98_ALIGN8;), so gcc, mingw, MSVC, and OpenWatcom all produce the same bytes.

That is also why the manual's rule for a struct that has to match an operating system structure is: define it without 64-bit fields unless the header really has them, and do not override the packing. The 32-bit defaults (/Zp8 for MSVC, -zp8 for OpenWatcom) already align 64-bit scalars to eight, and a /Zp4 or -zp4 override breaks the pin. Structures that genuinely must be byte-packed are a different feature — Z98's packed structs, the subject of Volume II chapter 5 — and they reject 64-bit packed fields. Keep the two ideas apart: a boundary struct that matches an API is an ordinary aligned struct; a wire format is a packed one.

The Win32 side of this inherited its proof rather than assuming it. The coroutine plan's ABI oracle cross-compiled the frame and Context layouts with i686-w64-mingw32-gcc and matched them, and the same oracle checked the system structures this chapter's boundary style produces: WNDCLASSEX, POINT, and MSG came out at the sizes and offsets the Windows headers define. A struct defined the Z98 way and passed by value is a struct the 32-bit Windows API accepts.

Names: reserved identifiers and mangling

C and Z98 disagree about which names belong to whom, and the compiler settles the disagreement in Z98's favor with two rules. The first rule is about the platform's reserved names. Identifiers beginning with two underscores are reserved for the C implementation, and the Language Spec states the Z98 side plainly: user-defined identifiers starting with __ are automatically mangled to avoid collisions with internal compiler symbols. You may write them; the compiler will not let them collide with the runtime's.

The second rule is broader, and it is the one that changes what you see in the emitted C: Z98 mangles every identifier it defines. The form is z<kind>_<hash>_<name>, where the kind character is F for a function, G for a module-level variable or constant, and T for a named type, the hash is an eight-hex-digit FNV-1a of the name, and the original name follows. So the function you wrote as find is emitted as zF_BDF0855A_find, a module variable counter as zG_9CACDE23_counter, and the type Point as zT_EAA8EF31_Point. The design document behind the mangler is docs/reference/name_mangling.md; the emitted forms above are what the seed compiler actually writes, and it is the emitted form that the linker sees. What matters here is that the name in your source is never the symbol in the object file.

Three special cases finish the rule. A name that is a C89 keyword is prefixed with z_ instead, so a Z98 function named double — double is not a Z98 keyword — is emitted as z_double, and one named unsigned as z_unsigned. A name that begins with an underscore or a double underscore is pushed out of the reserved space by the same z prefix, so _Test becomes zF_839A0C56__Test and __foo becomes zF_69D92BAD___foo; the leading z is what keeps them from colliding with the runtime's own _-names. And the mangled name is truncated to 31 characters for MSVC 6 compatibility, with a numeric suffix appended when two mangled names would otherwise collide.

Now the part that makes the seam work: a name you declare extern is not mangled. An extern declaration is a promise about an existing C symbol, so the emitter writes it exactly as you declared it. That is why the sample's calls to getenv and strlen appear in the generated C as getenv and strlen, and why the hand-written c_point_sum in the struct example is called under that plain name. The mangling rule applies to what Z98 defines; the extern rule applies to what Z98 borrows.

The reverse direction has its own keyword. An export function is a Z98 function whose plain, unmangled name is written into the object file so that C can call it: 

pub var counter: i32 = 3;

export fn c_callable(x: i32) i32 {
    return x + counter;
}

The emitted definition keeps its C name, and the module header carries the prototype a C caller needs: 

int zG_9CACDE23_counter;
/* c_callable */
int c_callable(int x) {
    ...
}
...
/* Forward declarations */
int c_callable(int);
void zF_EA90E208_main(void);

That closes the loop. extern borrows a C name; export lends one. A Z98 module can call into a C library and offer functions back to it, and the module's internal helpers keep their zF_-mangled names throughout, so nothing you define can accidentally shadow a C symbol and nothing C defines can accidentally shadow you.

The sample: getenv.z98

The sample is small on purpose. It calls two C run-time functions through extern, handles the one case where a C function returns a pointer that may be null, and prints what it finds. It exercises the whole surface a first C call needs: a module-level include, a cdecl extern declaration, a pointer parameter, a pointer return, a null test, and an integer return value. 

@cInclude("stdlib.h");
@cInclude("string.h");

const std = @import("std");

extern "c" fn getenv(name: [*]const u8) [*]u8;
extern "c" fn strlen(s: [*]const u8) usize;

// Look up one environment variable. getenv returns a C `char *`: the address
// of the value, or a null pointer when the name is not set.
fn find(name: []const u8) [*]u8 {
    return getenv(name.ptr);
}

pub fn main() void {
    var present: []const u8 = "PATH";
    var missing: []const u8 = "Z98_CH11_NOT_SET";

    var p: [*]u8 = find(present);
    if (@intFromPtr(p) != 0) {
        std.io.print("PATH: set\n", .{});
    } else {
        std.io.print("PATH: unset\n", .{});
    }

    var q: [*]u8 = find(missing);
    if (@intFromPtr(q) != 0) {
        std.io.print("Z98_CH11_NOT_SET: set\n", .{});
    } else {
        std.io.print("Z98_CH11_NOT_SET: unset\n", .{});
    }

    var msg: []const u8 = "talking to C";
    std.io.print("strlen: {}\n", .{strlen(msg.ptr)});
}

Walking the sample

The first two lines are the includes. They are module-level, so the compiler emits them into getenv's generated header, and the C compiler then has the real prototypes of getenv and strlen when it compiles the call sites. Without them the same program still compiles under the supported build, but the calls are implicit declarations and the argument types are unchecked on the C side; the includes are how the declaration you wrote and the declaration the library defines stay the same.

The two extern declarations are the contract. getenv takes a C string and returns a C string; both are getenv's own types, so the Z98 spellings are a many-pointer to bytes in and a many-pointer to bytes out. strlen takes a C string and returns a size_t, which is usize here. The convention string "c" is explicit even though it is the default, because a declaration is documentation and a reader should not have to remember the default.

The find helper is where the Z98-to-C translation happens. A Z98 slice carries its own pointer and length; C wants a pointer to a terminated string. The helper takes the slice but passes only name.ptr to getenv, and returns the raw C pointer. That keeps the seam narrow: one function turns a Z98 value into a C argument and a C result into a Z98 value, and the rest of the program never sees a half-translated type.

In main, the null test is the C idiom translated honestly. getenv signals "not set" with a null pointer, and a Z98 many-pointer has no optional wrapper here, so the program tests the address with @intFromPtr(p) != 0. When the name is set, it prints a fixed line; when it is not, it prints the other. The two names are chosen so the result is deterministic on both targets: PATH is set in every environment the program runs in, and Z98_CH11_NOT_SET is chosen so that it is not. Finally strlen is called on a literal and its integer result is printed; the value 12 is a number computed by C and consumed by Z98.

The trade

The C seam is cheap by design, and the price is that it is manual. Z98 gives you the declaration, the include, the convention, and the ABI; it does not give you a binding generator. There is no @cImport — the Language Spec lists it among the designed-but-not-implemented features, and a program that tries it stops at error[3000]: unsupported builtin function. There is no tool that reads a header and produces Z98 declarations; every function you call, you declare. For a handful of run-time calls that is nothing. For a large API it is real typing, and the honest way to reduce it is to declare only the subset you use, in a module of your own, and treat that module as the binding.

That is the trade in one sentence: you write the declarations, and in exchange the generated C is exactly the C you wrote — no glue layer to debug, no runtime to ship, no generated code that hides the ABI. On a machine with a 16 MB memory budget and no debugging UI, a seam that is only a declaration is the right side of the trade. The one thing you must do is double-check the declaration against the library's header, because the Z98 type checker cannot: it checks your calls against your declaration, and the C compiler checks the header when you include it. Include the header, and both checks are real.

Honest note. The C boundary is the one place in Z98 where a mistake the compiler stays silent about can still be fatal. Declare a function with the wrong signature, or forget extern "stdcall" on a Win32 entry point, and the program links and runs until the call corrupts an argument or the stack. The manual cannot type-check the library for you, but it can give you the habit that prevents the mistake: put the real prototype in a header, @cInclude it at module level, write the Z98 declaration to match the header line for line, and let both compilers check the same text. The extern seam is not dangerous because it is fragile; it is dangerous only when it is declared twice, differently.

Common mistakes

These are the mistakes a reader makes first at the C boundary. Each has a corrected shape, and most of them are caught by a diagnostic if you let the compiler see the real declaration.

Putting @cInclude inside a function. The builtin is module level only. In statement position the compiler reports error[3020]: internal error: unhandled node kind in type resolution and emits no C. Move the include to the top of the file, beside the declarations. The message says "internal error" because this is the compiler's pre-existing behavior, not a designed diagnostic; read it as "this form is not supported here."

Expecting a bare extern to emit a prototype. A non-variadic extern declaration does not write a prototype into the generated C; only a variadic one does. The call then compiles as an implicit declaration, which is a warning under the supported build and can be wrong for any return type other than int. Put the prototype in a header and @cInclude it. That is the difference between the C compiler checking your call and guessing.

Letting the Z98 declaration drift from the header. The type checker checks your call sites against your declaration, not against the library. If you write i32 where the header says u32, or omit a parameter, the Z98 side is clean and the C side is an ABI bug. Write the declaration from the header, not from memory.

Forgetting extern "stdcall" on a Win32 entry point. The 32-bit Windows API cleans its own stack; declaring an API function as the default cdecl links and then corrupts the stack at the call. The standard library is the pattern: every Winsock entry point is declared stdcall. An unknown convention string stops the build with error[3045]; a wrong but accepted convention does not.

Calling a Z98 function from C without export. Z98 mangles every definition, so a function written as helper has the symbol zF_<hash>_helper and cannot be called by its source name from C. Mark the function export and the emitter writes the plain name and a prototype; leave it unmarked and C cannot find it.

Trying to use @cImport. It is not implemented. The supported pattern is the one this chapter uses: bare extern declarations for the functions you call, plus @cInclude for the header that declares them. A program that writes @cImport stops at error[3000]: unsupported builtin function.

Passing a rich optional through the seam. Error unions and optionals have no C representation, and a non-scalar optional in a boundary position can emit invalid C89 (the trap chapters 9 and 10 name). Pass C-shaped types — a pointer, a length, an integer code — and translate at the call.

Overriding the struct packing. The 32-bit layout is pinned by the compiler's default alignment (8 for 64-bit scalars). A /Zp4 or -zp4 override breaks that pin and changes the bytes a boundary struct occupies. For a struct that must match an operating system structure, leave the default packing alone and define no 64-bit fields the header does not have.

Assuming the include uses angle brackets. @cInclude("stdlib.h") is emitted as #include "stdlib.h", with quotes. The quoted form still finds system headers, so this is usually invisible; it matters only when a header of the same name sits beside your module, which is precisely when you want the local one anyway.
