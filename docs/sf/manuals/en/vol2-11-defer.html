defer and errdefer

Chapter 10 traced every way a scope can end: fall off the end, return, break, continue, and the error paths behind try and return error.X. This chapter is the two statements that exist to run code at exactly those moments. defer schedules a statement for the end of the current scope, on every exit. errdefer schedules a statement for the exits that carry an error, and only those.

They are the replacement for the C cleanup label. Where C needs a goto cleanup at each error return, plus a flag to decide whether the cleanup is a commit or a rollback, Z98 names the two cases directly: defer is the cleanup that always runs, and errdefer is the cleanup that runs only when the function fails. Braces are optional on both; defer close(f); and defer { close(f); } are the same statement.

Three rules carry the chapter. First, deferred statements run in reverse order of registration — last registered, first run (LIFO). Second, defer runs on all paths out of the scope, and errdefer only on the error paths. Third, a cleanup body cannot transfer control out of itself: return, break, continue, and try are all rejected inside it. The chapter's program is docs/sf/manuals/src/vol2/defer.z98. It walks the success and error paths, mixes both kinds of cleanup at one scope, and exercises the loop exits:

Everything below is measured on the compiler shipped with this manual, and every diagnostic quoted is the one the compiler actually prints. Where the behavior differs from official Zig 0.15.2, the difference is called out at the point where it bites.

LIFO: last registered, first run

Deferred statements execute in reverse order of declaration. A function that registers two cleanups runs the second one first, so the resources come apart in the reverse of the order they were put together. The chapter's success path nests a block inside the function: 

fn successPath() !i32 {
    defer note("success: outer defer");
    {
        defer note("success: inner B");
        defer note("success: inner A");
        note("success: block body");
    }
    const v = try loadConfig(true);
    return v + 1;
}
// success: block body
// success: inner A
// success: inner B
// config: body
// config: defer (always)
// success: outer defer
// success value 12

inner A was registered after inner B, so it runs before it; the block's cleanups finish before the function's outer defer, because the block scope ends first. The rule is per scope, not per function: each scope exits its own defers in LIFO order, and the enclosing scopes follow.

The order holds across both kinds of cleanup. defer and errdefer share one stack, so the reverse-order rule is not "defers first" or "errdefers first" — it is strictly the order the statements were written, backwards. The error path registers a defer and two errdefers: 

fn errorPath() !i32 {
    defer note("error: defer");
    errdefer note("error: errdefer 1");
    errdefer note("error: errdefer 2");
    const v = try loadConfig(false);
    return v;
}
// config: body
// config: errdefer (rollback)
// config: defer (always)
// error: errdefer 2
// error: errdefer 1
// error: defer
// error path caught

On the error path all three run: errdefer 2 first, errdefer 1 next, and the plain defer last. The inner function's cleanup has already finished by then, because its scope ended before the error reached the outer function.

defer runs on every exit; errdefer only on errors

defer is not a "cleanup on failure" statement. It runs when the scope ends for any reason: falling off the end, return, break, or continue. The chapter's loops make the loop exits visible. The first loop hits continue on its first iteration; the second leaves with break: 

var i: i32 = 0;
while (i < 2) : (i += 1) {
    defer note("loop defer");
    if (i == 0) continue;
    note("loop tail");
}
// loop defer
// loop tail
// loop defer

var j: i32 = 0;
while (true) {
    defer note("break-loop defer");
    j += 1;
    if (j == 2) break;
}
// break-loop defer
// break-loop defer

The continue at i == 0 skips loop tail but does not skip the deferred statement: the cleanup for that iteration runs before the next iteration starts. The break at j == 2 leaves the loop and the defer still runs. Nothing special is needed at the exit, because the defer belongs to the loop body's scope.

errdefer is the other half of the pair, and it is silent on success. In the chapter's loadConfig, the error cleanup is skipped when the function returns a value: 

fn loadConfig(ok: bool) !i32 {
    defer note("config: defer (always)");
    errdefer note("config: errdefer (rollback)");
    note("config: body");
    if (!ok) return error.BadConfig;
    return 11;
}
// config: body
// config: defer (always)
// success: outer defer
// success value 12

Only config: defer (always) printed; the errdefer was registered but never ran because the function returned the value 11 and the caller added one. An explicit return error.BadConfig; runs it, which is the config: errdefer (rollback) line in the chapter's transcript. Propagation through try is an error path too: an error that passes through a scope runs that scope's errdefers on the way out. A probe makes both halves of the difference concrete: 

fn dynamic(e: !i32) !i32 {
    defer note("dynamic defer");
    errdefer note("dynamic errdefer");
    return e;
}

const bad: !i32 = error.Boom;
dynamic(bad) catch {
    note("dynamic caught");
};
// dynamic errdefer
// dynamic defer
// dynamic caught

const good: !i32 = 42;
const e2 = dynamic(good) catch 0;
std.io.print("e {}\n", .{e2});
// dynamic defer
// e 42

Returning an error-union value that holds an error runs both cleanups; returning one that holds 42 runs only the plain defer. This is also how try behaves in the middle of a function, without an explicit return error; in the failing scope.

One caution belongs here, not on the success path: the order in which a defer and the return expression run is a measured divergence from Zig. See the honesty note.

The boundary: no control flow out of a cleanup

A cleanup body is run during a scope exit that is already in progress. It cannot start a second exit. The compiler rejects all four ways of trying, with the specific code for each: 

defer {
    return;
}
// error[3051]: cannot return from defer expression

defer {
    break;
}
// error[3052]: cannot break out of defer expression

defer {
    continue;
}
// error[3053]: cannot continue out of defer expression

defer {
    try g();
}
// error[3054]: 'try' not allowed inside defer expression

The same rule applies to errdefer, and the reject is a frontend error: zero .c files are emitted. The try case has one extra wrinkle inside a void function; the honesty note records the second diagnostic it co-emits.

The boundary is about transfers that leave the cleanup body, not about control flow in general. A loop declared inside the body may break or continue normally, because that transfer stays within the cleanup: 

defer {
    var i: i32 = 0;
    while (i < 3) : (i += 1) {
        if (i == 1) break;
    }
    std.io.print("defer body ran\n", .{});
}
// defer body ran

A break or continue that targets a loop or labeled block declared outside the body is the rejected case; one whose target is declared inside is ordinary loop control. The distinction is the target's scope, not the keyword.

Honesty: the edges of the measured rules

Honest note. The order of a defer and the return expression is a divergence from official Zig, and it is easy to write code that depends on it. On Z98's static return path, the deferred statements run before the return expression is evaluated. This probe mutates x in a defer and returns it through a function call: 
fn bump(x: i32) i32 {
    std.io.print("bump {}\n", .{x});
    return x;
}
fn order() i32 {
    var x: i32 = 1;
    defer x = 100;
    return bump(x);
}
const r = order();
std.io.print("{}\n", .{r});
// Z98:                // Zig 0.15.2:
// bump 100            // bump 1
// 100                 // 1
The same program under Zig 0.15.2 prints bump 1 and returns 1: official Zig evaluates the return expression, then runs the defers. Z98 runs the defers first, so the return expression sees the post-defer state. The dynamic error-union return path (the return e; in the previous section) evaluates its operand before the defers, like Zig: a probe whose operand is a call printed bump 1, the pre-defer value. Do not depend on either order when a defer mutates state that the return expression reads.

Terminal builtins do not run pending defers. A function that calls @panic or @exit after registering a defer dies without running it: a probe printed only before on stdout, then the panic: boom line on stderr with exit status 133 under both -fsafe and -ffast; the @exit(7) probe exited with status 7 and never printed the cleanup line. Cleanup that must happen before a terminal builtin has to be written before the call, not deferred.

A try inside a cleanup body in a void function rejects twice. The defer rule fires first — error[3054]: 'try' not allowed inside defer expression — and the enclosing-return rule follows with error[3075]: expected type 'void', found error set and the note function cannot return an error. In a function whose return type is an error union, only error[3054] is reported.

A defer registered inside a cleanup body belongs to the cleanup body's own scope, so it runs at the end of that body, after the rest of the cleanup's statements. The chapter's probe: 
fn nested() void {
    defer note("outer cleanup");
    defer {
        note("cleanup start");
        defer note("deferred inside cleanup");
        note("cleanup end");
    }
    note("body");
}
// body
// cleanup start
// cleanup end
// deferred inside cleanup
// outer cleanup
That is still before the caller resumes and before the enclosing scope's other cleanups; it does not push the cleanup later, and it cannot redirect where the exit goes.

The example

The whole chapter in one program. It exercises nested defers on a success path, a defer and two errdefers on one error path, an errdefer that rolls back a transaction while two resource cleanups run in LIFO order, continue and break exits from loops, and the function-scope defer. It is docs/sf/manuals/src/vol2/defer.z98: 

const std = @import("std");

fn note(tag: []const u8) void {
    std.io.print("{s}\n", .{tag});
}

fn loadConfig(ok: bool) !i32 {
    defer note("config: defer (always)");
    errdefer note("config: errdefer (rollback)");
    note("config: body");
    if (!ok) return error.BadConfig;
    return 11;
}

fn commit(ok: bool) !void {
    defer note("commit: release writer");
    errdefer note("commit: roll back transaction");
    defer note("commit: release reader");
    if (!ok) return error.CommitFailed;
    note("commit: committed");
}

fn successPath() !i32 {
    defer note("success: outer defer");
    {
        defer note("success: inner B");
        defer note("success: inner A");
        note("success: block body");
    }
    const v = try loadConfig(true);
    return v + 1;
}

fn errorPath() !i32 {
    defer note("error: defer");
    errdefer note("error: errdefer 1");
    errdefer note("error: errdefer 2");
    const v = try loadConfig(false);
    return v;
}

pub fn main() void {
    const a = successPath() catch 0;
    std.io.print("success value {}\n", .{a});

    errorPath() catch {
        note("error path caught");
    };

    commit(false) catch {
        note("commit failed");
    };

    var i: i32 = 0;
    while (i < 2) : (i += 1) {
        defer note("loop defer");
        if (i == 0) continue;
        note("loop tail");
    }

    var j: i32 = 0;
    while (true) {
        defer note("break-loop defer");
        j += 1;
        if (j == 2) break;
    }
}

Twenty-three lines. The first seven are the success path: the block's two defers unwind before the outer defer, the config's plain defer runs while its errdefer is skipped, and the value comes out as 12. The next seven are the error path: the config rollback runs before its always-defer, then the two errdefers run in reverse order, and the plain defer runs last, all before the call site catches the error. The next four are the transaction: commit(false) releases the reader, rolls back, releases the writer, and reports the failure. The last five cover loop exits: continue in the first loop, then break in the second, each running its iteration's defer. The exit status is 0.

Common mistakes

The mistakes below are the ones a programmer arriving from C (or from a newer Zig) makes first with scope-exit cleanup. Each corrected shape is the compiler's rule, not a style preference.

Translating goto cleanup literally. A C function collects a goto cleanup at every failure exit and decides at the label whether to commit or roll back, usually with a flag. In Z98 the two cases are separate statements registered once: defer always runs, errdefer runs only on the error paths, so the rollback does not need a flag and the commit path does not need to skip anything. What a goto can do and a defer cannot is jump: a cleanup body cannot return, break, continue, or try out of itself.

Expecting a defer inside cleanup to redirect. A defer written inside a cleanup body is registered for that cleanup block, not for the scope that is exiting. It runs at the end of the cleanup body, after the rest of that body's statements, still during the same scope exit. It cannot postpone the cleanup, and it cannot send the exit somewhere else; if the cleanup has to run at the end, it has to be written at the end.

Writing return in cleanup. The most common duplicate of the C cleanup label is a function-level cleanup that tries to return a status. That is error[3051]: cannot return from defer expression; the same applies to break (error[3052]) and continue (error[3053]). Decide the exit before the scope ends; the cleanup only gets to release things. Loops entirely inside the cleanup body may still break and continue normally.

Assuming the return expression is evaluated first. In official Zig the return expression is computed and then the defers run. In Z98's static return path the defers run first, so a defer that mutates a variable the return expression reads changes the returned value (the honesty note has the measured probe: Z98 returns 100, Zig 0.15.2 returns 1). Keep deferred mutations and return expressions independent, or copy the value before the scope starts unwinding.

Expecting errdefer on the success path. errdefer is not a second defer that happens to be sorted after it; it is conditional on the exit carrying an error. A function that returns a value runs its defers and skips its errdefers, and the difference is visible in the chapter's output. If the cleanup has to happen on both paths, write defer; if it is a rollback, write errdefer.

Expecting a terminal builtin to run the cleanups. @panic and @exit end the process where they are called; pending defer and errdefer bodies do not run after them. The measured probes are in the honesty note. Release what has to be released before the terminal call.
