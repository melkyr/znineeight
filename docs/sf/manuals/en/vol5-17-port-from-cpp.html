Port a C++98 File to Z98

This guide translates a C++98 file to Z98 one idiom at a time. Three of C++98's abstractions have a Z98 shape — a template becomes a concrete container, a destructor becomes defer, and an exception becomes an error union — and one honestly does not: the run-time type oracle, where Z98's answer is the manual vtable or a C++98 module kept behind an extern "C" seam. It is the C++ companion to Port a C File to Z98, and it is the harder of the two because C++98 sits above Z98 rather than beside it.

Prerequisites

  • The compiler rebuilt from the seed at /tmp/manual_seed/zig1_5_clean, with the standard library beside it in /tmp/manual_seed/lib/. If it is not there yet, follow Rebuild the compiler from seed first.
  • A Linux host with a 32-bit-capable g++ -m32 -std=c++98. That modern compiler is what stands in for the era's MSVC 6 and Borland C++ 5.02 on this host; the C++ figures quoted below are the ones measured with it in Volume III, Honesty: When C++98 Is the Better Choice. The era tools themselves are not run here and the guide does not claim they were.
  • The repository checked out, so the Z98 samples below are present. Every command runs from the repository root, /workspace/znineeight.
  • The language practices the port rests on: Model and propagate errors for error unions, Use the arena correctly for object lifetime, and Port a C File to Z98 for the idiom checklist this guide extends.

The idea

A C++98 port is not symmetrical with a C89 port. In a C89 file the discipline is carried by convention — a status int, a hand-written free — and Z98 moves each convention into the type system, so the translation is mostly mechanical. C++98 is the other direction: it gives abstraction the compiler implements with run-time machinery, and Z98 deliberately withholds that machinery. A polymorphic object carries a hidden pointer, a class emits a table and its type information, a template emits a body per type, and a throw needs an unwinder. The port's job is to keep the module's behavior while dropping the machinery, and to say plainly which parts cannot be dropped.

So the checklist has two columns. What translates has a Z98 shape, and the guide builds that shape and runs it. What does not translate has no Z98 equivalent at all — Z98 has no run-time type oracle and no open generic — and there the honest move is to leave that part in C++98 and join it at the declared extern "C" boundary. Both columns are real; a port that pretends the second column is empty is the port this guide exists to prevent.

Steps

  1. Templates: Stack<T> to one concrete container per element type. A template is the abstraction Z98 most deliberately lacks. C++98 writes one container once and instantiates it for every element type; the shape a C++98 reader reaches for is the bounded stack from Volume II, The Honest Comparison: 

    template <typename T>
class Stack {
public:
    Stack() : count(0) {}
    void push(const T& v) { if (count < 8) data[count++] = v; }
    bool pop(T& out) {
        if (count == 0) return false;
        out = data[--count];
        return true;
    }
    int count;
private:
    T data[8];
};

    It compiles and runs; the transcript is the one measured on this host in Volume III chapter 4: 

    $ g++ -m32 -std=c++98 -O0 stack.cpp -o stack
$ ./stack
out=3

    The cost is not on the page, it is in the binary. Each instantiation is its own function body, one per type. The probe below uses a separate small function template, twice, not the Stack above, because one body per type is easiest to see on the smallest template: 

    $ nm -C tmpl | grep ' twice'
0000121c W double twice<double>(double)
000011f4 W int twice<int>(int)
00001208 W long twice<long>(long)

    The Z98 replacement is the concrete container: one struct and one set of functions for the element type you actually have, written by hand and readable in the source. It is the same code the template would have generated, made visible. The shipped sample docs/sf/manuals/src/vol2/shapes2.z98 is exactly this shape for a list of interface values: 

    const ShapeList = struct {          /* Z98: one concrete container per element type */
    items: [4]Shape,
    len: i32,
};

fn shapeList_push(list: *ShapeList, s: Shape) void {
    list.items[@intCast(usize, list.len)] = s;
    list.len += 1;
}

    Volume II chapter 16 measures the idiom and the compiler's own source uses the same pattern for its concrete hash maps. Choose Z98 when the element types are a handful and known; keep the template in C++98 when the type genuinely must stay open across the program, or when a wide set of types makes the per-instantiation bodies the deliberate cost you have accepted.

  2. RAII: a destructor to defer and errdefer. A C++98 class runs its destructor automatically on every exit path, including the one where an exception leaves the scope, which is the feature that makes RAII work. Z98 has no destructor; it has defer, which runs on every exit, and errdefer, which runs only on the failure path. Register the release once where the resource is acquired and the language runs it as the scope closes: 

    defer close(f);            /* runs on every exit from the scope */
errdefer release(conn);    /* runs only when the function fails */

    The shipped sample docs/sf/manuals/src/vol2/defer.z98 walks the success path, the error path, and the loop exits; its output is recorded in Volume II chapter 11. Build and run it the ordinary way: 

    $ mkdir -p /tmp/portcpp_defer
$ timeout 120 /tmp/manual_seed/zig1_5_clean -o /tmp/portcpp_defer docs/sf/manuals/src/vol2/defer.z98
$ cd /tmp/portcpp_defer && timeout 120 sh build_target.sh linux defer

    For the object whose whole lifetime is owned by one region, the arena removes the release entirely: allocate from the region, reset it once, and there is no per-object destructor to write and no unwinder to run it. That is Use the arena correctly and Volume II chapter 14.

  3. Exceptions: throw to an error union. C++98's throw is the heaviest abstraction in the module, because the failure is handed to a runtime that walks the stack. The references the linker must satisfy for a program that throws are visible in its symbols: 

    $ nm exc | grep -E '__cxa_(throw|begin_catch|end_catch)|_Unwind_Resume'
         U _Unwind_Resume@GCC_3.0
         U __cxa_begin_catch@CXXABI_1.3
         U __cxa_end_catch@CXXABI_1.3
         U __cxa_throw@CXXABI_1.3

    Z98 has no such runtime because failure is a value in the return type. The translation of a throwing function is an error union, try to propagate, catch to handle, and errdefer to roll back partial work: 

    fn divide(a: i32, b: i32) error{DivideByZero}!i32 {
    if (b == 0) return error.DivideByZero;
    return a / b;
}

    The shipped sample docs/sf/manuals/src/vol2/error_unions.z98 is the worked version; its output is recorded in Volume II chapter 12: 

    $ mkdir -p /tmp/portcpp_eu
$ timeout 120 /tmp/manual_seed/zig1_5_clean -o /tmp/portcpp_eu docs/sf/manuals/src/vol2/error_unions.z98
$ cd /tmp/portcpp_eu && timeout 120 sh build_target.sh linux error_unions
Building for linux...
Built: error_unions
$ timeout 120 ./error_unions
5
caught: DivideByZero

    The checked path costs a branch, not a runtime. The full error mechanics are Model and propagate errors.

  4. What honestly does not translate: the run-time type oracle and the open generic. C++98's virtual dispatch is only half the story; the other half is that a program can ask a pointer what it really is. dynamic_cast and RTTI need the type information tables the compiler emits per polymorphic class: 

    $ nm -C rtti | grep -E ' (vtable|typeinfo) for '
00003ee0 V typeinfo for Base
00003ed4 V typeinfo for Derived
00003ec8 V vtable for Base
00003ebc V vtable for Derived

    Z98 has no run-time type oracle. What it has is the manual vtable: a struct of function pointers plus one erased data pointer, built by an init function, with the type known at the call site. The shipped sample docs/sf/manuals/src/vol2/shapes2.z98 builds one and measures it: 

    $ mkdir -p /tmp/portcpp_shapes2
$ timeout 120 /tmp/manual_seed/zig1_5_clean -o /tmp/portcpp_shapes2 docs/sf/manuals/src/vol2/shapes2.z98
$ cd /tmp/portcpp_shapes2 && timeout 120 sh build_target.sh linux shapes2
Building for linux...
Built: shapes2
$ timeout 120 ./shapes2
Shape size=12 align=4 fn=4
circle r=1
  area 3.14159
square side=3
  area 9
circle r=2
  area 12.56636
shapes drawn 3

    Dispatch through the manual vtable is exactly as fast and exactly as small as the interface value you put in it — three words for the measured Shape — and it carries no hidden pointer and no per-class table. But it dispatches only to the operations the interface declares, for types the call site already knows. A program that genuinely needs to name a type at run time, or a container that must stay open across element types it never sees, has no Z98 shape that matches. That part is the honest exception: keep it in C++98, and connect it at the seam in the next step.

  5. The seam: extern "C", because C++98 mangles and Z98 does not. A C89 module joins a Z98 project invisibly, because Z98 emits C89. A C++98 module does not, because its names are encoded. A two-line probe shows the difference, and it is the measured transcript from Volume III chapter 4: 

    $ nm mangle | grep add
0000117d T _Z11mangled_addii
00001194 T unmangled_add

    So a C++98 module that Z98 is to call must expose plain extern "C" entry points, and those entry points must be written not to let an exception cross: a throw reaching a frame compiled as C has no unwinder to catch it and the behavior is undefined. The wrapper translates failures to status codes and out parameters — the C++ side doing by hand what Z98 does in the type. The full interop surface is Call C from Z98 and Link Z98 output against C89 libraries.

  6. Decide per module, and write the decision down. A port is a sequence of per-module choices, not one verdict. Use the table below for each module in front of you; it is the trade of Volume III chapter 4 reduced to a checklist.

    The module needs Z98 shape keep C++98 when
    a container for a few known element types one concrete container per type the type must genuinely stay open
    cleanup on every exit defer/errdefer, or the arena reset a destructor is the only correct cleanup and the unwinder is affordable
    an expected failure carried across frames an error union with try/catch the failure is truly exceptional and the module already throws
    an object with behavior, type known at the call site the manual vtable the dispatch must choose on a run-time type
    a run-time type oracle or an open generic none always — join it with extern "C"

Verify it worked

All three Z98 twins above build with the seed compiler and run to the ends their recorded transcripts reach. The defer.z98 transcript is in its step above; the other two are the recorded output of Volume II chapter 12 and chapter 16, reproduced by the commands in the steps: 

$ ./error_unions

$ ./shapes2

  area 3.14159

  area 9

  area 12.56636

On the C++98 side, the measured facts are the three that bound the trade: the template body appears once per instantiation (twice<int>, twice<long>, twice<double>), a polymorphic object is one word larger and a polymorphic class brings its vtable and typeinfo, and a throw pulls in __cxa_throw and _Unwind_Resume. The acceptance test for the port is that every abstraction with a Z98 shape has a twin that builds and runs, and that the one with no shape is named and left where it belongs rather than half-translated.

Common mistakes

  • Dropping the error union. The C++98 habit of ignoring a return value meets a compiler that refuses: 
    error[3015]: error union result is ignored; use 'try', 'catch', or assign the result
    Use try to propagate or catch to handle. This is measured in Volume II chapter 12.
  • Propagating from a void function. C++98 can throw from anywhere; a Z98 try needs a return type that can carry the error: 
    error[3075]: expected type 'void', found error set
note: function cannot return an error
    Declare the function error{DivideByZero}!i32, not void.
  • Calling a C++98 method directly from Z98. The name is mangled, so the symbol Z98 would link against does not exist under that name. Expose an extern "C" wrapper and call that.
  • Letting an exception cross the extern "C" boundary. A throw that leaves C++98 into a frame compiled as C has no unwinder to catch it, and the behavior is undefined. Catch inside the wrapper and return a status or an out parameter the C side can check.
  • Using exceptions for ordinary control flow. The most expensive way to write a branch on this machine is a throw/catch for a condition the caller expects, because it drags in the unwinder's tables for a path that is not exceptional. The Z98 shape is the error union; the C++98 shape for an expected failure is a return value the caller checks.
  • Assuming the era C++ compiler implements the whole 1998 standard. MSVC 6 and Borland C++ 5.02 shipped around ratification and neither implemented all of it; member templates, partial specialization, and parts of the standard library were missing or buggy. A template written for the era machine is written to that machine's dialect. This is era context and marked as opinion in Volume III chapter 4, and the era tools are not measured on this host.
  • Rewriting a working C++98 module “for purity.” A stable, tested module is not improved by being moved to another language. Move it when it is about to be reworked and its abstraction turns out not to be needed; until then let it work and write the new code in Z98 beside it.
