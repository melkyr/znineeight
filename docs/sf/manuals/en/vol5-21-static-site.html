Build the Static Site

This guide runs the manual's document pipeline: the checker that validates every page and the generator that rebuilds the search index. It ships no program, and the artifact it operates on is the documentation tree itself; it also states the one step that is not runnable on this host, the dist build, with the workaround that replaces it.

Prerequisites

  • The repository checked out at /workspace/znineeight, with the shipped English edition under docs/sf/manuals/en/. This guide needs no compiler; it is a documentation task.
  • Python 3, which docs/sf/manuals/check.sh runs through check.py.
  • The HTML contract every page obeys, on Volume IV — HTML style: the doctype, the ISO-8859-1 meta, the rel links, the sidebar, the language bar, and the prev/contents/next footer.
  • The HOWTO index, for how the volume is laid out.

The idea

The manual is a flat static tree: one page per topic, always at depth one inside en/, and no server. Two scripts generate the site from that source tree. build.sh assembles a dist/ copy and regenerates en/search-data.js; check.sh validates the source tree and writes nothing. On this host build.sh cannot run (step 3), so the pipeline is exercised as its two halves: the gate, and an index-regeneration script that writes only under /tmp. The search index is the only generated file in the tree; every HTML page is hand-authored.

Steps

  1. Read the tree layout. Confirm the source shape: a few root pages, one flat en/ directory, and the generated search index sitting beside the hand-authored assets. 

    $ cd /workspace/znineeight/docs/sf/manuals
$ ls en | grep -v '\.html$'
doc.js
gfx
search-data.js
z98-print.css
z98.css
$ ls en/*.html | wc -l
107

    The one non-page file the generator owns is en/search-data.js; the stylesheets, doc.js, and the gfx/ assets are hand-authored. The full layout is in docs/sf/manuals/README.md.

  2. Run the gate. check.sh wraps check.py, a Python 3 standard-library validator. It parses every *.html under docs/sf/manuals/ except dist/, and fails nonzero on the first problem, naming the offending file. 

    $ cd /workspace/znineeight
$ bash docs/sf/manuals/check.sh
check.py: OK - 110 HTML pages, links, rel, lang, forbidden list, figures, no-CSS baseline

    The nine checks, in order: every local href/src resolves to an existing file; every en/ page carries the four rel="home|up|prev|next" links; the language bar links only the shipped language root (en/); lang="en" and the ISO-8859-1 <meta> are present; the forbidden list (HTML5 structural tags, <div>, PNG/SVG/web fonts, external http(s)://, inline <style>, any <script src> other than doc.js, and CSS2/CSS3 tokens) is clean; doc.js is within its 2048-byte cap; the two stylesheets carry no CSS2/CSS3 tokens; the figure placeholders match todo-figures-list.html one-to-one; and the no-CSS baseline survives with the stylesheet links stripped. The printed count is the number of pages walked, this guide included. A green run means the tree is internally consistent before it is ever copied.

  3. Know why build.sh and serve.sh are not run here. build.sh is the documented assembler: it clears and recreates dist/, regenerates en/search-data.js, and copies the root pages plus the whole en/ tree into dist/. Its first action is the recursive delete of the output directory: 

    $ grep -n 'rm -rf' docs/sf/manuals/build.sh
26:rm -rf "$DIST_DIR"

    On this host that rm -rf docs/sf/manuals/dist hangs, so build.sh never reaches its generator, and serve.sh (a python3 -m http.server preview of the same directory) is not needed. Do not run build.sh or serve.sh, and do not touch dist/. The site is static, so the source tree is readable directly. The validation half is the gate in step 2; the generator's search-index half has a /tmp-only substitute in the next step.

  4. Regenerate the search index with the host workaround. The substitute runs the same loop as build.sh but writes nothing into the tree: its directory variables point at en/ for input and /tmp/z98_dist_tmp and /tmp/z98_search-data.regen.js for output. 

    $ grep -n 'EN_DIR=\|DIST_DIR=\|SEARCH_DATA=' /tmp/z98_build_tmp.sh
5:EN_DIR="$SCRIPT_DIR/en"
6:DIST_DIR="/tmp/z98_dist_tmp"
7:SEARCH_DATA="/tmp/z98_search-data.regen.js"
$ bash /tmp/z98_build_tmp.sh
build_tmp: indexed 107 pages, copied 149 files to /tmp/z98_dist_tmp

    The loop scans en/*.html in filename order and records each page's <title>, <meta name="keywords"> content, and first <h1>, escaping backslashes and double quotes and flattening newlines, into one JavaScript array: 

    $ grep -n 'for page in' /tmp/z98_build_tmp.sh
14:	for page in "$EN_DIR"/*.html; do
$ head -c 120 docs/sf/manuals/en/search-data.js; echo
var z98SearchData = [{file:"index.html",title:"Z98 Manual: English Edition",keywords:"Z98 manual English title page",hea

    The shipped en/search-data.js is that generated file, so the two must match byte for byte. Compare them: 

    $ diff /tmp/z98_search-data.regen.js docs/sf/manuals/en/search-data.js
$

    diff prints nothing and exits zero when the files are identical. A nonempty diff means the tree changed since the index was last generated; after reading it, copy the regenerated file over docs/sf/manuals/en/search-data.js. Never hand-edit the index — it is generated data, and the gate does not size-cap it for that reason.

  5. Add a page. Authoring a guide is the workflow every shipped vol5-* page follows. Copy the canonical skeleton en/vol4-24-html-style.html to the new flat filename under en/; set its <title>, keywords meta, and <h1>; and keep the doctype, the four rel links, the sidebar, the language bar, the prev/contents/next footer, and the single doc.js include exactly as the skeleton ships them. Link only files that exist; a target that has not shipped is prose (planned). Then wire the page into the tree in the same change: its sidebar row becomes a link on every shipped page, its row in toc.html and its entries in the A–Z and themed lists of the HOWTO index stop being (planned), and the nearest shipped neighbours’ rel and footer links are re-pointed at it. Because the generator globs en/*.html, a new page needs no separate registration: it is discovered by the next regeneration in step 4, and its index entry is inserted at its filename position.

Verify it worked

The tree is consistent when the gate is green and the regenerated index matches the shipped one exactly: 

$ cd /workspace/znineeight
$ bash docs/sf/manuals/check.sh
check.py: OK - 110 HTML pages, links, rel, lang, forbidden list, figures, no-CSS baseline
$ bash /tmp/z98_build_tmp.sh
build_tmp: indexed 107 pages, copied 149 files to /tmp/z98_dist_tmp
$ diff /tmp/z98_search-data.regen.js docs/sf/manuals/en/search-data.js
$

The gate walked 110 pages — the 107 English pages, the root selector, readme.html, and todo-figures-list.html — and found no broken link, missing rel, wrong charset, forbidden tag, orphan figure, or CSS dependency. The generator indexed all 107 English pages and copied the whole tree into /tmp/z98_dist_tmp, leaving dist/ untouched; the silent diff confirms the shipped en/search-data.js is byte-identical to a fresh regeneration. If the diff is nonempty, the index is stale: copy the regenerated file over, re-run the gate, and ship both together.
