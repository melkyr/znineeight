Honesty: The Friction You Will Hit

This is the last chapter of the honesty spine. The five before it answered questions about what Z98 is and what the machine can do: chapter 2 gave the inventory, chapters 3–5 said when to leave for another language, and chapter 6 named what the 1998 PC will not do in any language. This chapter is about neither the language nor the machine. It is about the workflow: the commands you type, the toolchain that turns your source into a shipping binary, and the friction you meet when you push against it for the first time.

None of the five items below is a design flaw, and none of them is hidden. Each is a cost that a small, self-hosting, no-frills toolchain pays in a place a larger toolchain would hide: you are closer to the generated C, the compiler is rebuilt from a seed you can hold, the diagnostics come from the compiler's own tables, and the documentation is the manual you are reading. The blueprint's rule for this chapter is exact: not pessimistic — accurate — and it ends by saying what to do about each. So every friction below is stated once, plainly, and immediately paired with the move that gets you past it. A friction named without a way over would be a complaint, and the volume drops complaints.

What is measured here. Statements about Z98's compiler are checked against the compiler built from the committed seed. The two-hop rebuild gate, the numbered diagnostics, and the gdb session in this chapter are real runs, captured on this host, and the transcripts are those runs. Statements about OpenWatcom's wcc386 are a different kind: that compiler is not installed on this host, so its dialect is described from the emitted build script and the compiler's own compatibility header, and the text says so. The absence of a community forum is a statement about the project, marked where it appears; it is not an era claim.

What you expect

A reader arriving from a modern toolchain expects the workflow to be a product. You install one thing, and it brings its own package manager, its own language server, its own debugger with a graphical front end, its own error reference on the web, and a community that has already answered your question. The compiler is a service you consume. When something is awkward, the ecosystem smooths it: the editor underlines the mistake, the debugger shows you the variable, and a search finds the error text with the fix beside it.

That expectation is reasonable, and it is not what this workflow is. Z98 emits C89, so the debugger belongs to the C compiler, not to Z98. The compiler is self-hosting, so rebuilding it is a build of the compiler, not the install of one. The diagnostics are the compiler's own sentences, not a curated catalogue. And the community is, for now, the manual. None of that is an apology; it is a description of where the seams are. Knowing where the seams are is what lets you work without surprise, and the rest of this chapter is the seam-by-seam account.

The one thing to keep out of your head is the modern scoreboard. Comparing this workflow to a modern toolchain measures nothing useful, because that toolchain was never a candidate for the target machine: it cannot be built for a 1998 PC and its binaries do not run there. The question is not whether this workflow is as smooth as a modern one. The question is whether each rough edge has a way over, and the answer for all five is yes.

OpenWatcom's C89 dialect is not gcc's

Z98 does not ship a backend for each compiler; it emits one dialect of C89 and lets a C compiler finish the job. That is the load-bearing fact of chapter 3, and it is also the first friction, because “C89” is a smaller agreement than it sounds. The emitted C has to satisfy every C compiler you might build with, and those compilers do not agree on the edges. On this host two of the four candidate compilers are the gcc family — gcc for Linux and i686-w64-mingw32-gcc for Windows — and the emitter also targets Microsoft's cl and OpenWatcom's wcc386, neither of which can be run here.

The friction is not that one of those compilers is broken. It is that each is a separate dialect, and the emitter has to speak all of them. The evidence is in the build scripts it writes for you. Emit a program for the Win9x target and the output directory contains three scripts: build_target.sh for gcc/mingw, build_target.bat for MSVC's cl, and build_owc.bat for OpenWatcom. The OpenWatcom script compiles every module with a command of exactly this shape: 

wcc386 /za /we /dZIG_WIN32 /i=. hello_F63FD80A.c

and links with wlink system console op q opt stack=65536 … library wsock32. Read the flags as the dialect in miniature. /za turns OpenWatcom's language extensions off, asking for strict ANSI C; /we promotes every warning to an error; /dZIG_WIN32 selects the Windows code path. The mingw script uses a completely different vocabulary — -m32 -std=c89 -O0 -Wall -Wno-long-long -Wno-pointer-sign -Wno-implicit-function-declaration — and the fact that it needs three -Wno- flags tells you the emitted C leans on a small set of extensions that strict C89 does not have. The emitter is candid about this. Its compatibility header, zig_compat.h, branches on the compiler: for _MSC_VER it uses __int64; for __WATCOMC__ it drops the alignment attribute and uses long long; for gcc and everything else it spells an 8-byte 64-bit scalar with __attribute__((aligned(8))) and calling conventions with __attribute__((stdcall)). In other words, the dialect differences are handled for you, at the header, by design.

What can be measured here is the gcc end. Compiling the emitted hello with the strictest switch — gcc -m32 -std=c89 -pedantic -Wall — succeeds, and its only complaint about the language is that long long is not ISO C90; everything else is the harmless “defined but not used” set from the runtime header. That is exactly the one extension the gcc build flags silence with -Wno-long-long. The OpenWatcom end is the item that cannot be run on this host: wcc386 is not installed, so the script above is emitted and documented, not executed here. Read it as the boundary it marks, not as a promise that was tested on your machine.

The way over is built into the thing that causes the friction. The emitter already carries the per-compiler branches and already writes a script for each compiler, with the correct flags for that compiler baked in. The OpenWatcom script even carries its own warning policy: if /we fails the build on a warning you believe is harmless, you remove /we and see the warning without the failure; if a hard error remains after that, the emitted C is invalid for OpenWatcom and should be reported as a compiler bug. That is the right division of labor. You develop and test on the gcc/mingw path, which is the path this manual verified end to end, and you build the shipping Win9x binary with OpenWatcom on a machine that has it. If you do not have OpenWatcom, the mingw path produces a working Windows binary too; the OpenWatcom script exists because the era's own tool was OpenWatcom, not because it is the only way to ship.

Rebuilding the compiler is a two-hop process

A compiler you install is compiled once, by someone else, and you never see the build. Z98's compiler, zig1, is self-hosting: it is written in Z98 and compiles itself. That is a strong property — the compiler is subject to the language it implements — but it costs a rebuild shape you will meet the first time you change the compiler's own source.

The rebuild is not one compile. It is a closure of two. A committed bootstrap seed, release/seed/zig1-seed.tgz, plays the part of a trusted first compiler. In the first hop the seed dumps the current compiler source, sf/src/main.zig, to C89, and gcc builds a new zig1. In the second hop that new compiler dumps the same source again, and gcc builds a second binary. Then the gate compares them byte for byte: the two binaries must have the same MD5, because the compiler is supposed to be deterministic. The closure is the whole point — a self-compiling compiler that produces a different binary on the second pass is not finished. Here is the gate from this host, run with the recipe in the box below: 

[seed] hop1 binary md5: 8216fedc8dd69db084d453be80f3c010
[seed] hop2 binary md5: 8216fedc8dd69db084d453be80f3c010
[seed] two-hop closure OK: hop1 == hop2 == 8216fedc8dd69db084d453be80f3c010
[seed] recorded fixed point OK: 8216fedc8dd69db084d453be80f3c010
=== [seed] Done: /tmp/manual_seed ===

The recipe that produces that gate is one command, run from the repository root: 

FIXED_POINT_MD5=8216fedc8dd69db084d453be80f3c010 \
  bash scripts/seed/build_from_seed.sh \
    release/seed/zig1-seed.tgz /tmp/manual_seed

The FIXED_POINT_MD5 is optional; when set, the script refuses to succeed unless the closure lands on the known seed version. When it is unset, the script still runs both hops and prints both hashes, so you can see for yourself whether your change kept the fixed point or moved it. If the committed seed is older than the source you are building, the first hop produces a different binary on purpose, and the script proves convergence with a third hop instead of failing — the moving-point case, handled automatically.

Two hops is the cost, and it is the honest cost of a deterministic self-hosting compiler: you build the compiler twice, because the second build is the proof. The way over is that you almost never pay it. You rebuild the compiler only when you change the compiler. To build an ordinary program you run zig1 once — a single compiler pass that emits the C89 and the per-target build scripts — and then compile that C. The seed follows the compiler through the tree, and a seed archive is small enough to keep alongside a release, so you can always rebuild the compiler from a known state without needing a second compiler to start from. The two-hop cost is the floor under compiler work, not the cost of using the compiler.

There is no debugger UI

A modern workflow puts a debugger in the editor: click in the margin, set a breakpoint, step, and watch the variable. Z98 has no such thing. It ships no debugger UI, and — a correction the manual makes against the original blueprint — it ships no sidecar debugger either; there is no .z98dbg format anywhere in the toolchain. The compiler's job ends when it has written the C89.

What you have instead is the C compiler's debugger, pointed at the generated C. That is not a consolation prize. The emitted C is plain, deterministic, and close to your source, and gdb finds it without ceremony. Rebuild the emitted program by hand with debug information, and a batch gdb session stops exactly where you asked: 

Breakpoint 1 at 0x24df: file hello_F63FD80A.c, line 16.
Breakpoint 1, main () at hello_F63FD80A.c:16
16	    zF_780653D2___module_init();
#0  main () at hello_F63FD80A.c:16

The invocation is ordinary gdb over a binary built with gcc -m32 -g. The one adjustment is that the file names are the emitter's, not yours: the module hello.z98 becomes a C file with a hash suffix such as hello_F63FD80A.c, so the first thing you do is find the generated .c that corresponds to the Z98 module you are chasing. The function names are mangled in the same way — zF_780653D2___module_init is a module initializer — but they are stable across builds, which is all a breakpoint needs.

The way over is to treat the generated C as the debugging surface, not as an opaque artifact. Build it with -g, set breakpoints in gdb against the generated file, and read the values there; the data layout is the Z98 layout, so a struct you declared is the struct you inspect. When the bug is not in your program but in the compiler that emitted it, the debugger is the wrong tool and the compiler's own trace is the right one: --markers writes the compiler's internal phase trace to the marker channel, which is how you watch a program make its way through the pipeline. The full workflow — the cd rule that keeps the emitted headers resolvable, the absolute include path, gdb, and markers — is chapter 15 (planned). There is no debugger UI today; there is gdb on code you can read.

The error messages are numbered but sparse

Modern compilers pair each error with a documentation page: a permanent link, a long explanation, the common causes, and the fix. Z98's diagnostics are the compiler's own sentences. Each carries a number, and the number is stable enough to cite; but the set is sparse. There is no dense catalogue, no online error index, and no paragraph per code. The message is one precise sentence, the location is exact, and then it is on you.

Numbering is real. A few wrong programs show the shape. Asking print for a format specifier it does not know: 

/tmp/t6/bad_print.z98:4:17: error[3013]: invalid print format specifier
    std.io.print("{q}\n", .{1});
                 ^^^^^^^

Calling a method on a struct in a language with no methods: 

/tmp/t6/bad_method.z98:9:29: error[3060]: no field or member function named 'mag' in struct type
    std.io.print("{}\n", .{p.mag()});
                             ^^^
/tmp/t6/bad_method.z98:3: note: struct declared here

and a plain syntax slip, reported by the parser before the semantic phases even run: 

/tmp/t6/bad_syntax.z98:1:4: error[2000]: expected ';' but found identifier
use std.io;
    ^^^

Read one diagnostic and you can see its four parts: the file:line:column location, the bracket code, the message, and the caret span under the offending tokens, sometimes followed by a note that names the related declaration. The message is specific to the situation, not generic. It is what “sparse” means that when you go looking for more, there is no encyclopedia. The codes are grouped by the phase that added them and are not contiguous: in the semantic block 3016 sits next to 3020, and the 3020s give way to the 3040s, with the coroutine codes numbered apart. The number is a fingerprint for the check, not a chapter in a book.

The way over is to read the four parts and to keep two references open. The caret and the note are usually enough to name the problem without any lookup at all; when they are not, the language reference is docs/reference/Language_Spec_Z98.md, which states the rule the diagnostic is enforcing, and Volume I chapter 13, Reading the errors, is the habit: read the first error, fix it, rebuild, and ignore the cascade, because one early parse error can manufacture a page of later ones. When you want the definitive list, the compiler's own source is the answer: sf/src/diagnostics.zig holds every code and its name, and it is authoritative in a way a generated web page never is. The numbering is not a user interface. It is a stable handle on the compiler's own checks.

There is no community forum yet

This is the one friction that is not about the machine and not about the compiler's design, and it is the only one in this chapter that is a statement about the project rather than about Z98: there is no community forum yet. There is no board where a question has already been asked and answered, no chat where a maintainer is idling, and no archive of other people's mistakes to search. If you are stuck, there is no crowd to ask.

The reasons are structural, and stating them is not an excuse. Z98 is a deliberately small toolchain for a deliberately old target; it is not trying to grow an ecosystem, and most of the questions a reader will have are answered by the compiler itself rather than by a community. But the friction is real: the first time something confuses you, the nearest human may be far away, and the answer has to come from the documentation.

The way over is that the documentation is built to be the substitute, and it is searchable. The Search page indexes every page in the manual, so a word in an error message or a builtin name finds the chapter that discusses it; the Contents is one page that lists all six volumes, so you can see what the manual covers before you conclude that it does not; the Reference volume is for lookup, and its shipped pages today include Builtins and HTML style, with the rest (planned); and the examples tree under examples/ and docs/sf/manuals/src/ holds complete, runnable programs rather than fragments. The manual also expects a bug-report page to exist in the Volume V HOWTO (planned), so there is a named path for the case the documentation does not cover. Until a forum exists, the manual is the forum. That is an observation about where Z98 is today, marked as one, not a claim that it will always be so.

The trade

Read the five frictions together and one statement covers them. All five are the same trade seen from different angles: this toolchain trades ecosystem and polish for three properties it keeps instead — the output is C89 you can read, the compiler is deterministic to the byte, and the whole thing rebuilds from a seed you can hold in your hand. Each friction is the shadow of one of those properties. The dialect is the shadow of emitting one language for four compilers. The two-hop rebuild is the shadow of self-hosting and determinism together. No debugger UI is the shadow of ending at the C. Sparse diagnostics are the shadow of a compiler whose checks live in its own source rather than in a documentation team. No forum is the shadow of a small project.

On the buying side, the properties are worth the roughness. The generated C can be inspected, hand-tuned, or replaced, which is the subject of chapter 5; the two-hop closure means the compiler cannot silently drift, because a non-identical second build fails the gate; and the absence of a large runtime — no garbage collector, no unwinder, no dynamic loader — is the same absence that made the program fit the machine in chapter 6. On the paying side, none of that buys you a debugger window or a forum post. The friction is not imaginary and this chapter does not pretend otherwise.

Where another tool genuinely wins, it wins for reasons the chapters 3–5 already gave. If what you want is a mature toolchain with every convenience, the honest answer is that a modern toolchain has that and this one does not — but it also cannot target the machine, so the comparison does not apply to the job. The register of this chapter is the volume's register: state the cost, state the compensation, and move on. Each of the five frictions above ends in a way over, and not one of the ways over requires the ecosystem a modern toolchain brings. That is the point. The friction is what you pay for a toolchain small enough to understand, and the way over is what you already hold.

Honest note. The sharpest friction is not on this list because it is not a toolchain fact: it is the temptation to fight the toolchain instead of using it. You will want a graphical debugger, so you will not read the generated C. You will be annoyed by the two-hop rebuild, so you will reach for a rebuild shortcut that skips the closure gate. You will get a terse diagnostic and change code at random rather than read the caret. Every one of those moves trades a small inconvenience you can name for a larger problem you cannot see. The way over is the same in each case: use the seam as designed — gdb on the generated C, the seed script with its gate, the four parts of the diagnostic — and the friction stays a friction rather than becoming a defect.

The way over it

The way over friction is a set of habits, not a feature you install. Worked in order, they cover all five items above:

Step one: keep an inner loop you can actually run. Develop and test on the gcc/mingw path, which this manual verified end to end; keep the OpenWatcom build for the shipping binary, on a machine that has wcc386. The emitted build scripts encode each compiler's flags, so you do not have to remember the dialect; you only have to choose the path you can run today.

Step two: rebuild the compiler only when you change the compiler. Use scripts/seed/build_from_seed.sh and read the closure line it prints. When you set FIXED_POINT_MD5, the script refuses to pass unless the fixed point is unchanged; when you do not, it still proves hop 1 equals hop 2. Building an ordinary program is one compiler pass and a C compile, which is the common case and costs nothing like a two-hop rebuild.

Step three: debug the generated C. Build the emitted C with gcc -m32 -g and use gdb against the generated file. Reach for the compiler's --markers trace only when the bug is in the compiler rather than in your program. The workflow is chapter 15 (planned).

Step four: read a diagnostic in its four parts. Location, code, message, caret — and the note when there is one. The caret and the note usually name the problem; the Language Spec states the rule; Volume I chapter 13 is the habit of fixing the first error and rebuilding; and sf/src/diagnostics.zig is the definitive code list.

Step five: when there is no forum, search the manual. The Search page indexes every page, the Contents lists all six volumes, the Reference volume is for lookup, and the examples tree is full programs. The manual is the knowledge base until a community exists.

Step six: never trade a check for convenience. The same rule as chapter 6: a friction is a reason to change how you work, never a reason to drop the error unions, the bounds checks, or the closure gate. The gate is the toolchain's whole promise. Keep it.

Stated once, compactly, the frictions and their ways over:

  • Another compiler's dialect? The emitted build scripts carry that compiler's flags and the compatibility header carries its branches; run the path you have, ship with the path you can.
  • A two-hop rebuild? Run scripts/seed/build_from_seed.sh, read the closure line, and remember it is the price of a compiler proved deterministic — paid only when you change the compiler.
  • No debugger UI? gdb on the generated C; --markers for the compiler.
  • Sparse errors? Read the location, code, message, and caret; then the Language Spec and Volume I chapter 13.
  • No forum? Search, the Contents, the Reference, and the examples tree.

If an item in the table had no line here, it would be a complaint, and the chapter would have dropped it rather than list it. Every friction above carries a way over, and none of the ways over requires the ecosystem a modern toolchain brings.

Common mistakes

The chapter has no code sample, because its subject is the workflow rather than a program. The mistakes below are workflow mistakes, and they are the ones a reader makes when a friction is treated as a defect to route around instead of a seam to use.

Expecting one compiler. The emitted C is built by at least two compilers on the dev host and by OpenWatcom or MSVC on the target, and they are different dialects. That is why there are three build scripts and a compatibility header. Pick the script for the compiler you have; do not expect one command to fit them all.

Treating a seed rebuild as a one-hop build. The closure gate is the second hop, and skipping it means you never learn whether your change kept the compiler deterministic. Run the script and read the hop1 == hop2 line; a rebuild that skips the gate is not a verification, it is a hope.

Hunting for a debugger that is not there. There is no Z98 debugger UI and no sidecar debugger. The debugging surface is the generated C: build it with -g and use gdb. Wishing for a debugger window costs time that reading the generated file would have spent well.

Fixing the first message and ignoring the caret. A diagnostic is precise about where, and the caret is part of the message. Reading only the sentence and editing nearby code at random is how one error becomes three. Read the location and the span; fix that; rebuild.

Waiting for a forum. There is no community forum yet, so a question posted nowhere gets no answer. Search the manual, read the Reference, and run the examples; in a self-hosting compiler the source tree is part of the documentation.

Loosening /we to make a warning go away. The OpenWatcom script invites you to drop /we to see a warning, not to ship past a hard error. If a real error remains after the warnings are visible, the emitted C is wrong for that compiler and the correct move is to report it, not to disable the check that found it.

Rebuilding from source when a built compiler already exists. The seed path is for changing the compiler. If you only need to compile a program, run the zig1 you already have; the two-hop rebuild is not the cost of using the tool.
