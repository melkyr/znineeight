What You Have Learned, What Is Next

The title page opened this volume with a promise: enter here if you have never written a program, leave able to write small working programs. This chapter is the accounting. There is no new code in it and no example program, only what the volume actually taught, what it deliberately did not, and where to go next. Read it as the manual being straight with you one last time before it hands you to Volume II.

The ground you covered

Fifteen pages are behind you. One table, one row per page, is the shortest honest summary of what each one gave you:

What you can do now

Put the rows together and the shape of the skill is clear. You can write a program in a single Z98 file: declare variables and constants with the width each value needs, do arithmetic on them, decide and repeat, group related values in functions and structs, keep lists in arrays, and read what the compiler says when you get it wrong. You can build that program for Linux with the seed compiler, or emit it for Windows 98, and you can feed it input and read its output. The line counter of chapter 14 is the proof: it uses what chapters 6 through 11 taught, plus the input handling chapter 14 introduces, and it is a tool a person could actually use.

The programs are small, and they are meant to be. Everything in this volume fits in one file, uses standard output and standard input for its conversation with the machine, and stays inside the primitive types, arrays, and structs it taught. That is what "writes small working programs" means, and it is exactly the exit state the title page promised.

What you cannot do yet

The other side deserves the same plainness. The volume deliberately stopped before the parts of the language that make larger programs possible. You have not met pointers, so a function cannot reach back into the caller's data except by value. You have met the !T return type only in its simplest form, !void: the error sets behind it, and the try, catch, and errdefer that work with them, are still ahead. You have not met optionals, so "a value that might be absent" has to be written as a sentinel value and remembered by you. You have not met the arena or any other way to obtain memory while the program runs. You have not met enums, unions, packed structs, tuples as declared aggregate types, arbitrary-width integers, defer, or coroutines, and you have not built a program out of more than one file. String handling beyond one byte at a time, the wider standard library, and every interaction with the operating system beyond reading and printing are still ahead.

That list is not a defect of the volume; it is the volume's scope. A beginner needs a small language first and the full one second. What matters now is that the missing features have names, so that nothing in the preceding chapters reads as the whole of Z98.

Honest note. If you came here to learn programming in general, Z98 is a fine teacher, but you should know that modern languages exist and do more with less effort. They manage memory for you, give you strings and lists that grow, carry richer error information, and ship with libraries this manual will never mention. This volume is about a specific discipline, not about programming as such: writing for a machine whose memory is counted in megabytes, where every allocation and every failure is written down where you can see it. Learn that discipline here if the target interests you. Learn it here and also learn a modern language if what you want is to build software with the least friction. Neither choice is wrong, and the manual is not offended by either.

The discipline

One idea ran under every chapter, and the last page is the right place to name it. Z98 is small because the machine it aims at is small: a Pentium-class computer with tens of megabytes of memory, where memory and not processor speed is the binding constraint. A language that compiles to C89, that asks you to choose every width, to start every variable with a value, and to read every diagnostic, is a language that keeps the cost of the program visible. That visibility is the discipline this manual has been teaching. It is also why the manual refused to oversell: on a modern machine, tools that hide these costs are the better choice, and chapter 2 and the honesty note above say so.

Where to go next

The next volume is Volume II — Learning Z98. It is written for a reader who already programs in some language, and after this volume that is you. It assumes you know what a variable is and does not explain the machine again; its pages go to the parts of Z98 that differ from the languages you will meet elsewhere: the full type system, pointers, the aggregates, error unions, optionals, the arena, the builtins, and the idioms that hold them together. Its own final chapter is another "what you have learned", at a larger scale.

If your goal was programming itself rather than this language and this era, Volume II is still the honest second step: it shows what a small language asks of you and what it gives back. And when you can write Z98 fluently, the contents page shows the rest of the set: Volume III for shipping software on 1998 hardware, Volume IV for looking things up, Volume V for solving a specific task, and Volume VI for the compiler's own internals. The read me page repeats the reading paths if you want to choose a different one.

One last thing before the questions. You built the compiler from a seed, wrote and ran real programs, and read real diagnostics without panic. That is not nothing: it is the whole first leg of the path printed at the front of this volume. Turn the page and start the second.

Check yourself

Answer these before moving on. They need no code and no machine; every answer is somewhere in this volume.

  1. What three parts does chapter 1 say every program has, and where did the line counter put each of them?
  2. Name the five primitive types of chapter 6 and one job each is good for. Why does Z98 make you choose a width instead of offering a single number type?
  3. Chapter 7 gave two behaviours for an addition that leaves the range of its type. Name both, say which is the default, and describe what each one does.
  4. For an array of N items, why is [0..N] not the same as [0..N-1]? What does the two-dot range keep, and what does it leave out?
  5. The compiler reports error[3002] on an assignment to a parameter. What is the rule, and what is the fix?
  6. The line counter stops when readByte answers 255. Why would testing for a zero byte be wrong twice over?
  7. Name three things this volume did not teach, and the volume that takes them up.
  8. The honesty note says modern languages do more with less effort. What does the manual say it is about instead? Answer in one sentence, in your own words.
