The Type System

Volume I's sixth chapter gave you the names a C programmer already knows. This chapter gives you the whole map. Z98 takes C89's types and adds one idea: an integer type can carry an exact compile-time width, anywhere from one bit to sixty-four. Everything else here follows from that idea and from a second, less glamorous fact: what the compiler lets you convert without saying so.

Two rules carry the chapter, and both are measured on the compiler this manual ships with, not remembered from a language specification. The width rule: for an arbitrary-width integer, @sizeOf reports the C carrier the value is stored in, and @bitSizeOf reports the width you declared. The conversion rule: integer-to-integer conversions are implicit today — a declaration or an assignment warns and converts, a call site converts silently — and @intCast is the explicit, warning-free form. The example at the end of the page prints the evidence for both.

That second rule is written the way it is on purpose. A manual is allowed to wish the compiler rejected something; it is not allowed to say it does when it does not. On this compiler the conversions happen, and the page teaches the measured behavior.

The fixed-width primitives

The names below are shorthand for exact C89 types. They are the vocabulary of most Z98 code, and their sizes are the same on every target this manual supports: a 32-bit machine where int is four bytes.

Z98 type C89 equivalent Size
i8, i16, i32, i64 signed char, short, int, __int64 1, 2, 4, 8 bytes
u8, u16, u32, u64 unsigned char, short, int, unsigned __int64 1, 2, 4, 8 bytes
isize, usize int, unsigned int 4 bytes (platform-sized)
f32, f64 float, double 4, 8 bytes
c_char char (signedness is implementation-defined) 1 byte
bool unsigned char, holding 1 or 0 1 byte
void void 0 bytes
noreturn void (see the note below) no storage of its own

The signed fixed names stop at i64; there is no i128 and no wide integer arithmetic. The unsigned fixed names stop at u64. That is not as narrow a set as it sounds, because the interesting part is the widths in between.

Arbitrary widths: u1 through u64

Z98 integer types can be declared at an exact width: unsigned u1 through u64, signed i1 through i63 (the fixed i64 owns the 64-bit signed slot). A u3 holds 0 through 7; an i7 holds -64 through 63. Widths outside those ranges do not exist, and spelling one is an ordinary name error: 

error[20]: identifier 'u65' is not declared or imported in this module
error[3000]: unknown type in variable declaration

The example program declares a u1, a u3, an i7, an i63, a u9, and a u33, prints a value from the first four, and then asks the compiler what storage each one got. Here is that part of the run: 

u1  value=1 @sizeOf=1 @bitSizeOf=1
u3  value=5 @sizeOf=1 @bitSizeOf=3
i7  value=-3 @sizeOf=1 @bitSizeOf=7
i63 value=-5 @sizeOf=8 @bitSizeOf=63
u9 @sizeOf=2 @bitSizeOf=9 u33 @sizeOf=8 @bitSizeOf=33
u3 max=7 i7 min=-64

Read the last line first: the extremes fit their declared widths exactly, and the compiler is the one enforcing it. Then read the @sizeOf column against the @bitSizeOf column. They are different numbers, and the rest of the chapter is about why.

The width rule: carrier and declared width

An arbitrary-width integer is stored in the smallest power-of-two C integer that can hold its value: one, two, four, or eight bytes. The declared width is a compile-time contract about which values are legal, not a storage layout. So @sizeOf answers "how many bytes does a value of this type occupy in the emitted C?" and @bitSizeOf answers "how many bits did the source declare?". For u3 the answers are one byte and three bits; for i63 they are eight bytes and sixty-three bits.

Declared type @sizeOf (carrier) @bitSizeOf (width)
u1 1 1
u3 1 3
i7 1 7
u9 2 9
u33 8 33
i63 8 63
Honest note. The widths will surprise you if you expect width and size to be the same number. A u9 takes two bytes; a u33 takes eight; an i63 takes eight. The carrier is what the C89 compiler can move in one register, and Z98 does not hide the cost of the smaller widths behind bit-packing. If you need fields that actually occupy three bits side by side, that is the packed struct's job, and chapter 5 is where it lives. An arbitrary-width integer keeps one value inside the smallest whole carrier.

The emitted C makes the same point without the builtins. This chapter's program declares a u3; the C that comes out of the compiler holds it in an unsigned char and masks writes back to the declared width: 

unsigned char small_unsigned;
...
zT_5 = (unsigned char)(zT_5 & 7);
small_unsigned = zT_5;

The mask is not decoration. It is how a one-byte carrier keeps three-bit semantics, and it is why the compiler can promise that a u3 never holds 8. A signed width gets the mirror treatment; the i7 in the same program is a signed char whose writes are sign-extended back to seven bits. The temporary names are the compiler's; the mask is the point.

isize and usize

usize and isize are the platform-sized integers: four bytes on the 32-bit target this manual supports, the same size as a pointer. They are the C unsigned int and int, and they are the types the standard library reaches for when it counts things: slice.len is a usize, arena capacities are usize, and loop indexes over arrays are usize. The example prints their sizes on their own line: 

usize=4 isize=4

Because they are ordinary integers to the compiler, usize values convert to and from i32 under the conversion rule in the next section. Sharing a size does not make them interchangeable in a signature; the fix for a mismatch is @intCast, not a cast through a pointer.

bool, void, c_char, and noreturn

Four types with no arithmetic in them round out the set.

bool is one byte holding true or false. It is a distinct type, not a small integer: it is what comparisons and logical operators return, and the compiler does not let you pass it where an integer is expected. Print it with {} and it prints true or false.

void is the empty type. It has no values and no size (@sizeOf(void) is 0, as the example's f32=4 f64=8 bool=1 cchar=1 void=0 line shows). A function returning void returns nothing, and a function whose body falls off the end returns void implicitly.

c_char is C's char, one byte, with the C implementation deciding whether it is signed. Reach for it when an extern declaration or a string's bytes ask for it; reach for u8 when you mean an unsigned byte.

noreturn is in the type table because the language specification lists it, and a function signature may spell it. Here the honesty is in the detail: the spelling is accepted and degrades to void, and the compiler does not enforce that the function never returns. The thing that actually stops a program is @panic, which writes its message to stderr and traps. This compiles, and calling it ends the program: 

fn stop() noreturn {
    @panic("stop");
}

before
panic: stop

The first line is stdout; the panic: stop line is stderr; the process dies on a trap, not on a return. Treat noreturn as a name the signature may carry, not as a promise the compiler checks.

Integer conversions: implicit today, explicit with @intCast

This is the section a C programmer needs most, because the rule is neither C's rule nor the rule the language was designed around. It is the rule the compiler has, measured:

Where the conversion happens What the compiler does today
var a: usize = v; (declaration) warning[3000], then converts; the program builds and runs
a = v; (assignment) warning[3000], then converts; the program builds and runs
takesUsize(v); (call argument) converts silently; no diagnostic
const c = @intCast(usize, v); converts silently; explicit, checked

So integer-to-integer conversion is implicit, and the compiler asks you to notice it at the two sites where a mistake is easy to make. The program at the end of this page writes both warned forms on purpose; here is the compiler's own output for them, from the build transcript: 

docs/sf/manuals/src/vol2/types2.z98:27:4: warning[3000]: type mismatch in variable declaration -- initialization type may not be compatible with declared type
    var a: usize = v;
    ^^^^^^^^^^^^^^^^^
note: source: i32
note: target: type
docs/sf/manuals/src/vol2/types2.z98:28:6: warning[3000]: type mismatch in assignment -- internal type representations differ; generated code may be incorrect
    a = v;
      ^
note: source: i32
note: target: type

The warning names the source and the target and lets the conversion run. It is the compiler saying "these two integers do not have the same representation, so read what you wrote" — not an error, and not a rejection. Both forms print 3 in the run.

@intCast is how you say the same thing with intent. It takes the target type as its first argument, works in both directions (@intCast(usize, v) widens on a 32-bit target, @intCast(i32, c) narrows back), and emits nothing. It is also the form that is checked: in the default safe mode an @intCast whose value does not fit the target traps instead of wrapping. A u8 cast of the value 300 stops the program with: 

panic: integer cast overflow in @intCast

The lesson is the chapter's shape in miniature. The compiler accepts the implicit conversion for the code that exists, and the version you write on purpose is the version with the check attached.

Floats: literals are double-precision

f32 is four bytes and f64 is eight. A float literal — and a literal-only float expression — is carried as a double-precision value, and at an f32 site the compiler narrows it by value, silently, whether or not the value is exactly representable: 

const exact: f32 = 1.5;
const inexact: f32 = 0.1;

Both of those compile with no diagnostic, and the program prints f32 exact=1.5 inexact=0.1. The rounding of 0.1 happens where the literal meets the type, and the same rule applies when the literal is bound to an unannotated const first (const x = 0.1; const f: f32 = x;).

The rule narrows with the value's provenance. A const that is explicitly typed f64 narrows to f32 only when the value is exactly representable. const d: f64 = 0.5; const e: f32 = d; is silent; const d: f64 = 0.1; const e: f32 = d; is rejected: 

error[3000]: type mismatch in variable declaration -- initialization type may not be compatible with declared type
note: source: f64
note: target: f32

And a value that is only known at run time does not narrow implicitly. A runtime f64 at an f32 site is the same rejection; the explicit form is @floatCast, which the example uses to make the narrowing say what it means: 

var rd: f64 = 0.5;
const fromruntime: f32 = @floatCast(f32, rd);

Read against C, the difference is the point. C narrows double to float wherever the assignment is, silently, whether the value is a literal or a variable. Z98 keeps the friendly case — a literal whose value the compiler can see — and makes the runtime narrowing an explicit, greppable operation.

The example

The whole chapter in one program. It declares the widths, prints their carriers and declared sizes, exercises both warned conversions and the explicit @intCast, and narrows two float literals. It is docs/sf/manuals/src/vol2/types2.z98: 

const std = @import("std");

fn takesUsize(n: usize) void {
    std.io.print("call site: {}\n", .{n});
}

pub fn main() void {
    const one_bit: u1 = 1;
    const small_unsigned: u3 = 5;
    const small_signed: i7 = -3;
    const wide_signed: i63 = -5;
    const u3_max: u3 = 7;
    const i7_min: i7 = -64;

    std.io.print("u1  value={} @sizeOf={} @bitSizeOf={}\n", .{ one_bit, @sizeOf(u1), @bitSizeOf(u1) });
    std.io.print("u3  value={} @sizeOf={} @bitSizeOf={}\n", .{ small_unsigned, @sizeOf(u3), @bitSizeOf(u3) });
    std.io.print("i7  value={} @sizeOf={} @bitSizeOf={}\n", .{ small_signed, @sizeOf(i7), @bitSizeOf(i7) });
    std.io.print("i63 value={} @sizeOf={} @bitSizeOf={}\n", .{ wide_signed, @sizeOf(i63), @bitSizeOf(i63) });
    std.io.print("u9 @sizeOf={} @bitSizeOf={} u33 @sizeOf={} @bitSizeOf={}\n", .{ @sizeOf(u9), @bitSizeOf(u9), @sizeOf(u33), @bitSizeOf(u33) });
    std.io.print("u3 max={} i7 min={}\n", .{ u3_max, i7_min });

    std.io.print("i32={} i64={} u32={} u64={}\n", .{ @sizeOf(i32), @sizeOf(i64), @sizeOf(u32), @sizeOf(u64) });
    std.io.print("f32={} f64={} bool={} c_char={} void={}\n", .{ @sizeOf(f32), @sizeOf(f64), @sizeOf(bool), @sizeOf(c_char), @sizeOf(void) });
    std.io.print("usize={} isize={}\n", .{ @sizeOf(usize), @sizeOf(isize) });

    var v: i32 = 3;
    var a: usize = v;
    a = v;
    takesUsize(v);
    const c = @intCast(usize, v);
    const back = @intCast(i32, c);
    std.io.print("declared={} cast={} back={}\n", .{ a, c, back });

    const exact: f32 = 1.5;
    const inexact: f32 = 0.1;
    std.io.print("f32 exact={} inexact={}\n", .{ exact, inexact });
}

Common mistakes

The mistakes below are the ones a C programmer makes first with this type set. Each has a corrected shape, and the conversion one is the reason the earlier sections are worded so carefully.

Assuming C's implicit integer conversions. In C, assigning an int to a size_t is usually silent, and Z98 converts too — but not silently at the declaration. That form emits warning[3000]; at a call site it emits nothing. The corrected shape is not "write more casts"; it is "use @intCast when you mean the conversion". The explicit form is warning-free and checked, and it is what the compiler's own source uses. Do not come away from this chapter believing that Z98 rejects these conversions; it does not, as the transcript above shows.

Expecting @sizeOf to equal the declared width. u3 is one byte and three bits; i63 is eight bytes and sixty-three bits. @sizeOf answers the storage question, @bitSizeOf answers the width question, and both are compile-time constants. If you need the storage to shrink to the width, you want a packed struct, not a narrower integer.

Assuming a 1.5 literal is f32. A float literal is a double-precision value; it narrows at an f32 site by value, silently. That works for literals. It does not extend to a typed f64 value that is not exactly representable, and it never extends to a runtime f64: both of those reject with error[3000], and @floatCast is the explicit form. In C the same code truncates without a word.

Spelling a width that does not exist. There is no u0, no u65, and no i65. The compiler reports them as unresolved names (error[20]) plus an unknown type in variable declaration. Unsigned runs u1 to u64; signed runs i1 to i63, with the fixed i64 as the 64-bit signed name.

Trusting noreturn to keep a function from returning. The signature spelling is accepted, but it degrades to void and the compiler does not enforce it. The enforcement you get is @panic's trap, which is what the example's stop actually does.
