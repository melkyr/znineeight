WinSock under Z98

A network program for this machine is a WinSock program. Windows 95 and 98 do not ship a BSD socket layer with the full modern surface; they ship Winsock, the Windows Sockets API, and everything that talks to the network — a browser, a mail client, a game's lobby, a small server on the LAN — goes through it. This chapter is how Z98 reaches that API, what the library actually gives you, and the one complete socket program the volume ships.

The good news is that you already know the shape. Chapter 11 showed that a Z98 module is a C translation unit and that a C API is reached with extern declarations. Winsock is exactly that kind of API: a set of C functions from a system library (the 32-bit import library wsock32), declared with the Win32 stdcall convention, and compiled against the system header winsock.h. Z98 does not add a socket feature to the language for this. The standard library wraps the C functions, and you call the wrapper.

That distinction matters more here than anywhere else in the volume, because the blueprint for this manual assumed something that is no longer true. It described emitter-level socket builtins — magic names like @socketCreate that the compiler itself lowered to Winsock calls. Those were removed. Sockets in Z98 are the ordinary std.net extern surface, which means the rules of chapter 11 apply unchanged: declarations, calling conventions, and the C ABI. This chapter documents what the compiler and the library actually do, not what the blueprint promised.

What is measured here. Every Z98 and library statement on this page was checked against sf/src/std_net.zig, the Language Spec, and the compiler source, and every transcript is a real run of the seed-built zig1. The sample, http-mini.z98, is compiled and run on Linux and then cross-built with i686-w64-mingw32-gcc and run under a dedicated 32-bit wine prefix; its Windows transcript below is that run, and the wine capture matched the Linux capture byte for byte. The OpenWatcom build_owc.bat path is emitted and not run here, exactly as chapter 8 states; the real-machine screenshot stays the figure. The Winsock revision Z98 binds is 1.1 (wsock32, initialized with WSAStartup(1,1)), not Winsock 2, and this page never claims otherwise.

One library, two operating systems

std.net is one module, sf/src/std_net.zig, re-exported by the standard library as std.net. It presents one small Z98 API and selects its implementation at compile time from the target. On Linux and the other Unix hosts it binds the C library's socket functions. On the Windows target it binds wsock32, the Winsock 1.1 import library, through winsock.h. The selection is not a runtime check and not a build flag you set: the emitter knows the target, and the module's @isWindows() guards prune the branch that does not apply before the C is written.

The mechanism is worth seeing, because it is the same target-selection pattern the rest of the volume uses. The module's first line pulls in a small target-neutral include file: 

@cInclude("<net_prelude.h>");

net_prelude.h opens with a platform switch. On Windows it includes the Win32 and Winsock headers and names the import library: 

#ifdef _WIN32
#define WIN32_LEAN_AND_MEAN
#include <windows.h>
#include <winsock.h>
#pragma comment(lib, "wsock32.lib")
#else
#include <sys/socket.h>
#include <netinet/in.h>
#include <arpa/inet.h>
#include <sys/select.h>
#include <sys/time.h>
#include <unistd.h>
#include <netdb.h>
#include <fcntl.h>
#endif

Whichever compiler builds the emitted C — gcc -m32 on the host, i686-w64-mingw32-gcc or OpenWatcom's wcc386 for the target — selects the branch, so the single declaration source for every Winsock function is the system header itself. That is the same rule as chapter 11's prototype rule: the header declares the function, the Z98 extern names it, and both compilers check the same text.

The names are the only wrinkle. std.net owns the words accept, connect, send, recv, close, and select for its own public functions, so the raw externs are declared with an _os suffix and net_prelude.h maps them back to the real OS symbols: 

#define accept_os accept
#define connect_os connect
#define send_os send
#define recv_os recv
#define close_os close
#define select_os select

The aliases are declared after the includes, so they never rewrite the system headers; only the emitted std.net call sites — which compile into the same translation unit — are affected. The result is that the Z98 source never names a Winsock symbol directly. You call a Z98 function, and the compiler emits a C call to the OS function. The next section is those functions.

The surface the standard library exposes

std.net is deliberately small. It is the subset a client or a small server needs, plus the readiness and UDP helpers the volume's examples use. Its public API is the following, and it is the same source for both targets.

Function Returns What it does
init() i32 WSAStartup(1,1) on Windows; 0 elsewhere
cleanup() void WSACleanup() on Windows; nothing elsewhere
createTcpServer(port) i32 socket + bind; returns the listening handle or -1
createTcpClient(port) i32 socket + connect to 127.0.0.1; handle or -1
bindListen(fd, backlog) i32 listen; returns 0 or -1
accept(fd) i32 accept a pending connection; handle or -1
connect(fd, port) i32 connect an existing handle; 0 or -1
send(fd, buf, len) i32 send up to len bytes; count or -1
recv(fd, buf, len) i32 receive up to len bytes; count or -1
close(fd) void closesocket on Windows; close elsewhere
select(nfds, r, w, e, ms) i32 wait for readiness; ready count, 0 on timeout, -1 on error
fdZero(s), fdSet(fd, s), fdIsset(fd, s) void / void / bool clear, set, and test a socket in an fd_set

There is a UDP surface as well — udpBind, udpSendTo, udpRecvFrom, and udpSetTimeout, each returning a NetError!T — and a non-blocking surface for the cooperative style of chapter 10: setNonBlocking, recvNonBlocking, and sendNonBlocking. This chapter stays with the TCP surface because it is what the sample uses and what a first network program needs. The point is the shape: a handle is an i32, a transfer returns a byte count, and failure is a negative number.

The externs underneath

Under those public functions are the raw Winsock declarations, and reading them is the clearest statement of what Z98 is really calling. The socket calls and the _os-suffixed wrappers are all stdcall: 

extern "stdcall" fn socket(af: i32, typ: i32, proto: i32) i32;
extern "stdcall" fn bind(s: i32, name: *const void, namelen: i32) i32;
extern "stdcall" fn listen(s: i32, backlog: i32) i32;
extern "stdcall" fn accept_os(s: i32, addr: *void, addrlen: *void) i32;
extern "stdcall" fn recv_os(s: i32, buf: [*]u8, len: i32, flags: i32) i32;
extern "stdcall" fn send_os(s: i32, buf: [*]const u8, len: i32, flags: i32) i32;
extern "stdcall" fn select_os(nfds: i32, readfds: *void, writefds: *void, exceptfds: *void, timeout: *const void) i32;
extern "stdcall" fn closesocket(s: i32) i32;
extern "stdcall" fn WSAStartup(wVersion: u16, lpWSAData: *void) i32;

That is the Winsock 1.1 entry set the blueprint named — socket, bind, listen, accept, recv, send, select, closesocket, WSAStartup — declared in Z98 with the types the C header uses. The convention is not optional here: the 32-bit Windows API cleans its own stack, and chapter 11 showed that an unknown convention string stops the build with error[3045] while a wrong but accepted one corrupts the stack at the call. std_net.zig declares every Winsock entry stdcall, and its two POSIX-only helpers, __errno_location and fcntl, cdecl.

Starting Winsock: init and cleanup

WinSock has a rule that no other library in this volume has: you must call WSAStartup before you call anything else. A program that calls socket, bind, or send first does not get a handle, it gets a failure. WinSock documents that failure as WSANOTINITIALISED (10093), read back with WSAGetLastError. It is the first mistake a WinSock program makes, and it is why std.net has an explicit init instead of doing the work lazily.

std.net.init() runs the startup call on Windows and returns its result; on the Unix targets it is a no-op that returns 0: 

pub fn init() i32 {
    if (@isWindows()) {
        var wsa: WSAData = undefined;
        const rc = WSAStartup(@intCast(u16, 0x0101), @ptrCast(*void, &wsa));
        return rc;
    } else {
        return 0;
    }
}

0x0101 is the "1.1" the manual keeps repeating, and the emitted call shows the version word as the compiler wrote it: 

zT_8 = ((zT_290557A7_FS_int_unsigned_sho)WSAStartup)((unsigned short)(257), (void*)((void*)zT_6));

The program's job is one line: check init() before creating a socket, and call cleanup() on the way out so WSACleanup releases the Winsock state. The sample does exactly that. cleanup is a no-op on the Unix targets, so the same source runs on both. If you skip init on Windows, the first socket call fails and the program's own error path runs instead of the network path — a failure that looks like "the network is down" but is really "the library was never started."

The handle is a signed i32

This is the one place where the blueprint's description is actively wrong, and the correction is worth stating plainly. A WinSock socket is a SOCKET, which in C is an unsigned 32-bit integer, and the blueprint said Z98 had an "unsigned SOCKET comparison rule." It does not. std.net defines its handle as a plain signed integer: 

pub const Socket = i32;

Every public function returns that i32, and failure is the value -1. The reason this is safe is the value WinSock itself uses for a bad handle. INVALID_SOCKET is (SOCKET)(~0), all thirty-two bits set, which is exactly -1 when the same bits are read as a signed i32. A real socket is a small positive index, so the failure value is distinct and the comparison is an ordinary signed comparison. There is no cast to unsigned and no all-ones literal to remember; the check is < 0 or == -1. The listening path shows both spellings in the same module, because the Windows and Unix branches are written separately: 

const s = socket(@intCast(i32, 2), @intCast(i32, 1), @intCast(i32, 0));
if (s == -1) return -1;      // Windows branch
...
if (s < 0) return -1;        // Unix branch

The rule for the reader is therefore simple: a handle is signed, a negative return is a failure, and a non-negative return is a usable handle or a byte count. Do not store a handle in an unsigned type, and do not write a check like fd >= 0 as though the value could not be negative; it can, and -1 is the sentinel. Chapter 11 made the same point about the C boundary in general: the sentinel is the library's convention and the Z98 declaration has to match it.

Binding and listening

A TCP server is two calls. createTcpServer(port) makes the socket and binds it to a port; bindListen(handle, backlog) puts it into the listening state. The first function is where the address structure lives: 

pub fn createTcpServer(port: u16) i32 {
    if (@isWindows()) {
        const s = socket(@intCast(i32, 2), @intCast(i32, 1), @intCast(i32, 0));
        if (s == -1) return -1;
        var addr = SockAddrIn{
            .sin_family = @intCast(u16, 2),
            .sin_port = htons(port),
            .sin_addr = htonl(@intCast(u32, 0)),
            .sin_zero = [8]u8{ 0, 0, 0, 0, 0, 0, 0, 0 },
        };
        if (bind(s, @ptrCast(*const void, &addr), @intCast(i32, 16)) == -1) {
            _ = closesocket(s);
            return -1;
        }
        return s;
    }
    ...
}

The constants are the Winsock ones and they match the Unix ones: address family 2 is AF_INET, socket type 1 is SOCK_STREAM, protocol 0 lets the system choose TCP. The address is a sixteen-byte sockaddr_in: a family word, a network-order port, a network-order address, and eight bytes of padding. Setting sin_addr to htonl(0) is INADDR_ANY, which binds every interface on the machine; createTcpClient uses htonl(0x7F000001) instead, the loopback address 127.0.0.1.

The byte order is the classic socket detail. Network byte order is big-endian, and the machine is little-endian, so the port and the address go through htons and htonl. Those are real OS functions here — htons/htonl from wsock32 on Windows, from libc elsewhere — but std.net also carries portable htonsManual/htonlManual byte-swaps for code that wants to be explicit. The address structure itself is the compiler's ordinary aligned struct, laid out by the same 32-bit model chapter 11 pinned, and passed by pointer, so no by-value ABI question arises.

bindListen wraps listen. Its backlog argument is the number of pending connections the system will hold before an accept drains them; a small server uses a small number. The function returns 0 on success and -1 on failure, so the caller composes it with the bind like this: 

const server = std.net.createTcpServer(PORT);
if (server < 0) { ... }
if (std.net.bindListen(server, 1) < 0) { ... }

From that point the port is open and the system is completing handshakes into the backlog even before the program calls accept. That is what makes the sample's loopback design possible; it is also why a listener that is never accepted still holds a connection, briefly, until the backlog fills.

Accepting, sending, receiving, closing

Once a connection is pending, accept(server) returns a new handle for that connection and leaves the listening handle open for the next one. std.net's accept passes null for the peer address: 

const c = accept_os(fd, @ptrCast(*void, @intToPtr(*void, 0)), @ptrCast(*void, @intToPtr(*void, 0)));

It returns -1 on failure and a fresh handle otherwise. The two sockets are independent: the listening handle stays bound to the port, and the accepted handle is the conversation. A server that accepts one connection and then wants another calls accept again on the same listening handle.

send and recv move bytes. The signatures take a raw pointer and a length — the Z98 slice's pointer and length, as chapter 11 taught — and both return the number of bytes transferred, or -1 on error. The detail that catches every first network program is that the count may be short. send is allowed to accept fewer bytes than you offered, and recv is allowed to return less than you asked for; TCP is a byte stream, not a record protocol. The sample therefore loops on send until the whole buffer is gone, and treats one recv as "whatever arrived," which is correct for a request that fits in one segment. A production server keeps reading until it has a complete request. 

fn sendAll(fd: i32, buf: []const u8) bool {
    var sent: usize = 0;
    while (sent < buf.len) {
        const chunk = buf[sent..];
        const n = std.net.send(fd, chunk.ptr, @intCast(i32, chunk.len));
        if (n <= 0) return false;
        sent += @intCast(usize, n);
    }
    return true;
}

close is the polite end. On Windows it calls closesocket; on the Unix targets it calls close. It returns nothing, so there is no result to check; the module hides the one-real-difference between the two worlds. A server closes the accepted handle when the conversation ends, and closes the listening handle at shutdown, then calls cleanup. The order matters on Windows: WSACleanup should follow the last closesocket.

Readiness: select and fd_set

The socket calls above are blocking. accept waits for a connection, recv waits for data, and a program that calls them in the obvious order serves one client at a time and freezes whenever the client is slow. The way out is the readiness call, select: you ask the system which handles have something to do, and you only call the blocking function on a handle that is ready. It is the primitive under every single-threaded server, and it is the one the volume's coroutine chapter pairs with coroutines.

std.net's select takes a count, three optional handle sets, and a timeout in milliseconds: 

pub fn select(nfds: i32, readfds: ?*u8, writefds: ?*u8, exceptfds: ?*u8, timeout_ms: i32) i32

The sets are ?*u8 because the underlying fd_set is an opaque blob — a Z98 type with no C equivalent that both systems agree on: 

pub const fd_set = struct {
    // Opaque fd_set blob (Windows 260B / Linux 128B layouts covered by 512B).
    data: [128]u32,
};

Five-hundred-twelve bytes is large enough for either system's structure, and the [128]u32 member forces the four-byte alignment Winsock's select requires. You never read the blob; you cast its address to *u8 and hand it to the three helpers. fdZero clears it, fdSet adds a handle, and fdIsset tests one after select returns: 

var read_fds: std.net.fd_set = undefined;
std.net.fdZero(@ptrCast(*u8, &read_fds));
std.net.fdSet(server, @ptrCast(*u8, &read_fds));
const ready = std.net.select(server + 1, @ptrCast(*u8, &read_fds), null, null, 1000);
if (ready > 0 and std.net.fdIsset(server, @ptrCast(*u8, &read_fds))) {
    // accept() will not block
}

The opacity is not laziness; the two systems genuinely disagree about what an fd_set is. Windows stores a count in the first word followed by the handles, so fdSet increments the count and writes the handle after it. The Unix layout is a bitmask, so fdSet sets one bit in one word. The helpers branch on @isWindows() and hide the difference, which is exactly the kind of per-OS detail a C89 project usually carries by hand. The nfds argument is the highest handle plus one on Unix; Windows ignores it, and passing server + 1 is correct on both. A negative timeout_ms means "wait forever"; the sample passes 1000 so a missing connection is a timeout it can report rather than a hang.

One honest limit belongs here. Winsock 1.1 offers select and blocking sockets; it does not offer the scalable event interfaces of later Winsock versions. For the machine this manual targets — one program, a handful of connections, 32 MB — that is the right tool, and it is the same tool the Unix side provides, so the source stays one source. The way to serve many connections without threads is the pattern of chapter 10: select says who is ready, and a coroutine per connection is resumed only when its socket is.

What was removed: the socket builtins

If you have seen an older draft or the blueprint, it may mention builtins such as @socketCreate. The compiler had emitter-level socket builtins once, and they were removed in favor of the std.net surface this chapter documents. A program that still calls one does not get a socket; it stops at the builtin: 

$ /tmp/manual_seed/zig1_5_clean -o out sockbuiltin.z98
sockbuiltin.z98:3:4: error[3000]: cannot declare variable of type void
    var s = @socketCreate(2, 1, 0);
    ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
sockbuiltin.z98:3:12: error[3000]: unsupported builtin function
    var s = @socketCreate(2, 1, 0);
            ^^^^^^^^^^^^^^^^^^^^^^

The two diagnostics are the honest picture: the builtin has no implementation, so it resolves to void, and the compiler says both that no such builtin exists and that a variable cannot have that type. The way over is the one this chapter has been building: import std and call std.net functions. There is no socket syntax to learn and no compiler feature to wait for; sockets are ordinary extern calls behind a small Z98 API.

The sample: http-mini.z98

The sample is a complete, if minimal, HTTP server. It binds a port, waits for a connection, reads one HTTP/1.0 request, and writes one fixed response. To make the transcript deterministic and to need no external client, both ends of the connection live in the same process: the program opens a loopback client to its own listener and then serves it. That exercises the whole surface — init, socket, bind, listen, select, fd_set, accept, send, recv, close, cleanup — without a second machine. 

const std = @import("std");

// http-mini: the smallest complete socket program. It binds a listener, opens
// a loopback client, accepts the connection, reads one fixed HTTP/1.0 request,
// and writes one fixed response. Keeping both ends in one process needs no
// external client and makes the transcript the same on every run.
const PORT: u16 = 18088;
const BUF_SIZE: usize = 256;

// The request the loopback client sends. It is fixed so the transcript is
// reproducible.
const REQUEST: []const u8 = "GET /hello HTTP/1.0\r\nHost: localhost\r\n\r\n";

// The document and the response that carries it.
const RESPONSE: []const u8 = "HTTP/1.0 200 OK\r\nContent-Type: text/plain\r\nContent-Length: 15\r\nConnection: close\r\n\r\nhello from Z98\r\n";

// send() may transfer fewer bytes than asked; sendAll loops until the buffer
// is gone. A zero or negative return is the error channel at the C boundary.
fn sendAll(fd: i32, buf: []const u8) bool {
    var sent: usize = 0;
    while (sent < buf.len) {
        const chunk = buf[sent..];
        const n = std.net.send(fd, chunk.ptr, @intCast(i32, chunk.len));
        if (n <= 0) return false;
        sent += @intCast(usize, n);
    }
    return true;
}

// The first line of an HTTP request, up to CR or LF.
fn firstLine(buf: []const u8) []const u8 {
    var i: usize = 0;
    while (i < buf.len) : (i += 1) {
        if (buf[i] == '\r' or buf[i] == '\n') return buf[0..i];
    }
    return buf;
}

pub fn main() void {
    if (std.net.init() != 0) {
        std.io.print("http-mini: socket init failed\n", .{});
        return;
    }

    const server = std.net.createTcpServer(PORT);
    if (server < 0) {
        std.io.print("http-mini: bind failed on port {}\n", .{PORT});
        std.net.cleanup();
        return;
    }
    if (std.net.bindListen(server, 1) < 0) {
        std.io.print("http-mini: listen failed\n", .{});
        std.net.close(server);
        std.net.cleanup();
        return;
    }
    std.io.print("http-mini: listening on port {}\n", .{PORT});

    // The client end, in the same process. connect() completes because the
    // listener is already in listen() and the kernel finishes the handshake
    // into the backlog.
    const client = std.net.createTcpClient(PORT);
    if (client < 0) {
        std.io.print("http-mini: connect failed\n", .{});
        std.net.close(server);
        std.net.cleanup();
        return;
    }

    // Wait for the pending connection with select(). The fd_set is an opaque
    // blob that the std.net helpers fill and test.
    var read_fds: std.net.fd_set = undefined;
    std.net.fdZero(@ptrCast(*u8, &read_fds));
    std.net.fdSet(server, @ptrCast(*u8, &read_fds));
    const ready = std.net.select(server + 1, @ptrCast(*u8, &read_fds), null, null, 1000);
    if (ready <= 0 or !std.net.fdIsset(server, @ptrCast(*u8, &read_fds))) {
        std.io.print("http-mini: no connection ready\n", .{});
        std.net.close(client);
        std.net.close(server);
        std.net.cleanup();
        return;
    }

    const conn = std.net.accept(server);
    if (conn < 0) {
        std.io.print("http-mini: accept failed\n", .{});
        std.net.close(client);
        std.net.close(server);
        std.net.cleanup();
        return;
    }
    std.io.print("http-mini: accepted a connection\n", .{});

    if (!sendAll(client, REQUEST)) {
        std.io.print("http-mini: client send failed\n", .{});
        std.net.close(conn);
        std.net.close(client);
        std.net.close(server);
        std.net.cleanup();
        return;
    }

    var req: [BUF_SIZE]u8 = undefined;
    const got = std.net.recv(conn, &req, @intCast(i32, BUF_SIZE));
    if (got <= 0) {
        std.io.print("http-mini: recv failed\n", .{});
        std.net.close(conn);
        std.net.close(client);
        std.net.close(server);
        std.net.cleanup();
        return;
    }
    const request: []const u8 = req[0..@intCast(usize, got)];
    std.io.print("http-mini: request {s}\n", .{firstLine(request)});

    if (!sendAll(conn, RESPONSE)) {
        std.io.print("http-mini: response send failed\n", .{});
        std.net.close(conn);
        std.net.close(client);
        std.net.close(server);
        std.net.cleanup();
        return;
    }
    std.io.print("http-mini: served {} bytes\n", .{@intCast(i32, RESPONSE.len)});

    var resp: [BUF_SIZE]u8 = undefined;
    const rgot = std.net.recv(client, &resp, @intCast(i32, BUF_SIZE));
    if (rgot <= 0) {
        std.io.print("http-mini: client recv failed\n", .{});
        std.net.close(conn);
        std.net.close(client);
        std.net.close(server);
        std.net.cleanup();
        return;
    }
    std.io.print("http-mini: client received {} bytes\n", .{rgot});

    std.net.close(conn);
    std.net.close(client);
    std.net.close(server);
    std.net.cleanup();
    std.io.print("http-mini: done\n", .{});
}

Walking the sample

The first two calls are the pair every WinSock program opens with: std.net.init() and the check of its result. On Windows that is WSAStartup(1,1); on Linux it returns 0 and the branch never runs. Then createTcpServer(18088) makes the socket and binds it, and bindListen starts listening. If either fails the program prints one line and returns, so a reader never sees a heap of cascading errors from a missing port.

The interesting move is the next one: the program calls createTcpClient(18088) on itself. The listener is already in listen, and the kernel completes the loopback handshake into the backlog, so connect returns a handle even though nothing has called accept yet. That is the ordinary behavior of a listening socket, and it is what lets one process play both roles. The client handle is a real std.net socket on 127.0.0.1; the only thing unusual about it is that its peer is in the same executable.

Before accepting, the program builds an fd_set, adds the listening handle, and calls select with a one-second timeout. This is the readiness check of the previous section: it proves the pending connection is there, so the following accept cannot block forever. The fdIsset test is the positive confirmation. Then accept returns the connection handle.

The transfer is split between the two handles exactly as a real client and server would. The client sends the fixed request with sendAll; the server recvs it, slices off the first line, and prints it — the {s} specifier is the print formatter's string route, and the first line is the part a real server routes on. The server writes the fixed response with sendAll, the client recvs it back, and the program prints the byte count on each side. Finally it closes the connection handle, the client handle, and the listening handle, in that order, and calls std.net.cleanup(). Every failure path closes whatever it opened before returning, which on Windows is more than tidiness: it keeps the socket table from filling during a long run.

Two choices are worth defending because a reader may wonder about them. The request and the response are constants, so the transcript is the same every run and the page can promise byte-for-byte parity; a real server would parse the path and build the response. And the port is a fixed high number, 18088, which is enough for a program that connects to itself and moves on; a server that must coexist with others would make the port a command-line argument.

The trade

The trade for using sockets in Z98 is the same trade as the rest of the C boundary, with one extra edge: you get the real API, and you pay for it in manual bookkeeping. There is no framework, no connection object, and no automatic lifetime. You call init and cleanup; you check every negative return; you close every handle on every path; and you remember that send and recv count bytes rather than deliver records. In exchange, the generated C is a sequence of Winsock calls a 1998 C programmer would recognize instantly, with no runtime to initialize and no glue to debug on the target machine.

For the amount of networking most programs for this machine need — a client, or a small server on a LAN — that is the right side of the trade. The whole TCP surface is a dozen functions and one opaque blob. The cost is real only when the program wants many connections at once, and even then the answer is not a framework but the pattern this volume already gave you: select for readiness and a coroutine per connection.

Honest note. The sockets here are blocking by default, and that is a real limit of the simple reading of this API, not a bug. Call accept with no connection pending, or recv with no data on the socket, and the program waits — which on a single-threaded machine means the whole program waits. The way over is not to pretend it does not happen; it is to make the wait informed. Use select to learn which handles are ready, so the blocking call is only entered when it can complete, and use the non-blocking surface (setNonBlocking, recvNonBlocking, sendNonBlocking) or the coroutine scheduler of chapter 10 when the program has more than one thing to do. WinSock 1.1 gives you exactly select; that is enough for this machine, and it is the same primitive the Unix side gives you, so the source stays one source.

Common mistakes

These are the mistakes a first WinSock program makes, roughly in the order it makes them. Each is paired with the correction.

Calling a socket function before WSAStartup. WinSock requires WSAStartup first; without it socket fails and the handle is -1. std.net.init() is that call, and its non-zero return is the startup failure. Call it before createTcpServer or createTcpClient, and call cleanup() at the end.

Treating the handle as unsigned. There is no unsigned SOCKET rule in std.net; the handle is i32 and failure is -1. Check < 0 (or == -1), and do not store handles in unsigned types or write >= 0 checks as though a negative value could not occur.

Assuming send sends everything. A successful send may transfer fewer bytes than you passed; a short count is not an error. Loop until the buffer is gone, which is what the sample's sendAll does, and treat 0 or a negative return as failure.

Assuming one recv is one message. TCP is a byte stream. A single recv may return part of a request, or two requests at once. For a small fixed request one read can be enough, as in the sample; a real server reads until it has a complete request line and body.

Reading fd_set directly. The type is an opaque blob. Clear it with fdZero, add with fdSet, and test with fdIsset; never index the words yourself. The Windows layout (a count followed by handles) and the Unix layout (a bitmask) are different, and the helpers are the only portable way to touch it.

Forgetting the timeout on a blocking read. A blocking accept or recv waits forever when nothing arrives. Use select with a millisecond timeout to bound the wait, as the sample does before its accept. A negative timeout means "block", which is the opposite of what a first server usually wants.

Forgetting extern "stdcall". Winsock is a stdcall API. Declaring an entry point cdecl links and then corrupts the stack at the call. The standard library is the reference: every Winsock extern in std_net.zig is stdcall, exactly as chapter 11 describes. Do not declare Winsock functions yourself when std.net already has them.

Reaching for the old socket builtins. @socketCreate and its siblings were removed. The compiler reports error[3000]: unsupported builtin function and emits no C. Import std and use std.net.

Closing the listening handle when a connection ends. accept returns a new handle for the connection; the listening handle stays open. Close the accepted handle when the conversation is over, and keep accepting on the listening handle. Confusing the two shuts down the server after one client.
