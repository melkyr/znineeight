Aggregates I: Structs

A struct is a bundle of named fields that travel together. You know the idea from C, and Z98 does not change the idea; it changes the spelling and it adds three builtins that let a program read the layout the compiler chose. This chapter declares structs, builds values, works the field order and the padding rule, reads the offsets with @offsetOf, @sizeOf, and @alignOf, and nests one struct inside another. It is the first of the five aggregate chapters; the zig-zag of parenthesis-free types, positional literals, and codegen-level introspection all start here.

The guiding fact is that a Z98 struct is a C89 struct in all but name. The fields are laid out in the order you declare them, each field is stored at the next offset its alignment allows, and the whole thing is rounded up to the alignment of its most demanding field. The emitted C is a plain struct in that same order, and Z98 pins the computed alignment into it, so the offsets the compiler folds are the offsets the compiled binary uses on every supported 32-bit toolchain. The introspection builtins do not invent a layout; they report the one Z98 and the emitted C both build.

A type is a named constant

Z98 declares a struct the Zig way: const, a name, and the type expression. The name is an ordinary constant that happens to denote a type, and every declaration that uses the struct refers to it by name. 

const Vec2 = struct {
    x: i32,
    y: i32,
};

Vec2 is now a type. It is not a variable and it occupies no storage; it is the recipe. The chapter's other type, Sprite, is built on top of it and shows a nested struct: 

const Sprite = struct {
    id: u8,
    tint: u32,
    width: u16,
    height: u16,
    origin: Vec2,
    scale: i64,
};

The style rule is the one C uses for typedef struct names: a type name starts with a capital, a field name with a lowercase letter. There is no struct Sprite tag to keep separate from Sprite; there is one name and it names the type. A struct type carries no functions. Z98 has no method syntax, so the operations that belong to a type are free functions whose first parameter is the struct (chapter 16 (planned) works the pattern in full).

Building a value

A variable of struct type is declared with a type annotation, and the literal on the right is a brace set with the field names spelled out: 

var s: Sprite = .{
    .id = 7,
    .tint = 0x00ff00,
    .width = 16,
    .height = 32,
    .origin = .{ .x = 1, .y = 2 },
    .scale = -3,
};

The leading dot on each field is required, and the literal is typed by the variable it initializes. A field you leave out is not zero-filled: the literal compiles, but the omitted field holds whatever the memory already contained, so it is usually garbage. This is the opposite of C's aggregate initializer, where the fields you skip are quietly zeroed, and it is the same "undefined is not zero" rule that runs through the whole language. Write every field you intend to read, or write = undefined and fill the value before using it. (A declaration with no initializer at all is rejected: var s: Sprite; reports error[3014]: variable must be initialized; use '= undefined' to opt out.)

Once built, the value is read and written field by field with the ordinary dot. A nested struct reaches its inner field by chaining the dots, and the whole value behaves as one thing: 

s.origin.x = 5;

Struct assignment copies. var copy: Sprite = s; produces an independent value; changing copy afterward leaves s alone. There is no reference semantics hiding in the =.

Field order is declaration order

The compiler lays a struct out with one simple rule. Start a cursor at offset zero. For each field in the order it was declared, round the cursor up to the field's alignment, record that as the field's offset, and advance the cursor by the field's size. When every field is placed, round the total up to the largest alignment any field required; that is the struct's size and alignment. Fields are never reordered, and no field is ever packed against its neighbor unless its alignment allows it. The same rule is what a C compiler applies to a plain struct, with one caveat that the emitted C settles for you: on 32-bit hosts the C compiler's default alignment for a 64-bit type can be 4, not 8, while Z98's model says 8. The emitted C therefore declares its 64-bit carriers with an explicit 8-byte alignment, pinning the binary to the model instead of trusting the host default. That is what keeps the folded offsets and the running program's offsets equal; the example's i64 scale is the field that exercises it.

Worked for Sprite, with the cursor in the last column:

Field Type Size Align Offset Cursor after
id u8 1 1 0 1
tint u32 4 4 4 8
width u16 2 2 8 10
height u16 2 2 10 12
origin Vec2 8 4 12 20
scale i64 8 8 24 32
total 8 32

Two gaps fall out of the arithmetic. The u8 id leaves the cursor at 1, and the u32 tint cannot start there, so bytes 1 through 3 are skipped and tint lands at 4. Later, origin ends at 20 and the i64 scale needs an 8-byte boundary, so bytes 20 through 23 are skipped and scale lands at 24. The struct ends at 32, already a multiple of 8. Those skipped bytes are called padding, and the layout builtins will show you exactly where they are.

The order the fields are written is therefore a real decision, not a cosmetic one. The three fields { a: u8, b: i64, c: u8 } occupy 24 bytes: a at 0, seven bytes of padding, b at 8, c at 16, rounded up to 24. Move the i64 to the front and the same three fields occupy 16: b at 0, a at 8, c at 9, rounded up to 16. C programmers once learned to sort fields widest-first for exactly this reason, and the habit still pays here. (The chapter's own Sprite lands on 32 whichever way its fields are ordered, because 25 bytes of fields cannot round to less than the 8-byte multiple above them; the three-field example is where the effect of the padding rule shows plainly.)

Honest note. The layout is consistent, but it is not a contract. The offsets in this chapter are the ones this compiler produces on this target (32-bit, little-endian, the Win9x-era ABI), and the emitted C pins that same order and alignment, so the model and the compiled binary agree on every supported 32-bit toolchain. Nothing promises the padding bytes hold any particular value, that a future compiler will not widen a field's carrier, or that a struct sent across a wire or a process boundary will be decoded the same way by other software. If the exact byte image is the point, either write the fields out one at a time or use the packed struct of the next chapter, which spells out every bit and removes the padding entirely. A Z98 struct is a memory convenience, not an interface description.

The layout builtins

Three builtins turn that arithmetic into values a program can print, compare, or feed to an allocator. They are compile-time constants, recognized by name, folded before any C is emitted, and they take the type rather than a value:

Builtin Answers Result for Sprite
@sizeOf(T) Bytes one value of T occupies, padding included 32
@alignOf(T) The strictest alignment any field demands 8
@offsetOf(T, "field") Byte offset of one field from the start see below

@offsetOf is the one that takes an argument beyond the type: the field name, and the name must be a string literal. That is the difference from C's offsetof macro, which spells the field as a bare member designator. Passing a name computed at run time is rejected: 

error[3073]: field name must be a string literal

So is an offset request for a name the struct does not have: 

error[3073]: no field named 'zz' in struct 'S'

And @offsetOf insists the target really is a struct. A union, a pointer, or a scalar is rejected rather than folded to zero, because an offset into those types has no meaning: 

error[3072]: expected struct type, found 'U'

The printed offsets for the example's two types are Vec2 x=0 y=4 and Sprite id=0 tint=4 width=8 height=10 origin=12 scale=24. Every one of those numbers is that field's offset in the worked table above; the builtin and the by-hand arithmetic are the same rule, and the run proves it.

Nested structs are stored inline

A field whose type is another struct is not a pointer and not a reference: the inner value lives inside the outer one, occupying its full size at its aligned offset. Sprite.origin is a Vec2 occupying bytes 12 through 19, and @sizeOf(Sprite) includes all eight of them. Reaching a field of the inner struct chains the dots, s.origin.x, and taking the address of the inner value with &s.origin gives a *Vec2 as you would expect.

The inner type's own layout is computed first, by the same rule, so a nested struct's size and alignment are just numbers the outer layout uses like any other field's. Vec2 is two i32 fields, so it is 8 bytes with alignment 4; a nested struct contributes both numbers to the outer layout exactly as a scalar of the same size and alignment would. There is no depth limit worth worrying about, but a struct cannot contain itself by value; a struct that must point at another of its own type stores a pointer (next: *Node), exactly as in C.

The example

The whole chapter in one program. It declares a two-field struct and a six-field struct that nests the first, prints the size and alignment of both, prints every field offset of both, then builds a value, mutates one nested field, and prints the fields back. It is docs/sf/manuals/src/vol2/shapes.z98: 

const std = @import("std");

const Vec2 = struct {
    x: i32,
    y: i32,
};

const Sprite = struct {
    id: u8,
    tint: u32,
    width: u16,
    height: u16,
    origin: Vec2,
    scale: i64,
};

pub fn main() void {
    std.io.print("Vec2 size={} align={}\n", .{ @sizeOf(Vec2), @alignOf(Vec2) });
    std.io.print("Sprite size={} align={}\n", .{ @sizeOf(Sprite), @alignOf(Sprite) });

    std.io.print("Vec2 offsets x={} y={}\n", .{
        @offsetOf(Vec2, "x"),
        @offsetOf(Vec2, "y"),
    });
    std.io.print("Sprite offsets id={} tint={} width={} height={} origin={} scale={}\n", .{
        @offsetOf(Sprite, "id"),
        @offsetOf(Sprite, "tint"),
        @offsetOf(Sprite, "width"),
        @offsetOf(Sprite, "height"),
        @offsetOf(Sprite, "origin"),
        @offsetOf(Sprite, "scale"),
    });

    var s: Sprite = .{
        .id = 7,
        .tint = 0x00ff00,
        .width = 16,
        .height = 32,
        .origin = .{ .x = 1, .y = 2 },
        .scale = -3,
    };
    s.origin.x = 5;
    std.io.print("fields id={} tint={} width={} height={} origin.x={} origin.y={} scale={}\n", .{
        s.id,
        s.tint,
        s.width,
        s.height,
        s.origin.x,
        s.origin.y,
        s.scale,
    });
}

Build the compiler once from the committed seed, then emit and compile the program, exactly as in chapter 3: 

bash scripts/seed/build_from_seed.sh release/seed/zig1-seed.tgz /tmp/manual_seed

The result is /tmp/manual_seed/zig1_5_clean with the standard library beside it in /tmp/manual_seed/lib/. This example compiles with no diagnostics; the program then runs to the end: 

$ mkdir -p /tmp/manual_out
$ /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol2/shapes.z98
$ cd /tmp/manual_out && sh build_target.sh linux shapes
Building for linux...
Built: shapes
$ ./shapes
Vec2 size=8 align=4
Sprite size=32 align=8
Vec2 offsets x=0 y=4
Sprite offsets id=0 tint=4 width=8 height=10 origin=12 scale=24
fields id=7 tint=65280 width=16 height=32 origin.x=5 origin.y=2 scale=-3

Five lines. The first two are the whole-struct facts: Vec2 is 8 bytes aligned to 4, and Sprite is 32 bytes aligned to 8. The next two are the per-field offsets, matching the worked table. The last line proves the value itself: tint prints as 65280 (the decimal form of the 0x00ff00 written in the source), origin.x reads back as 5 after the mutation, and scale keeps its sign as -3. The exit status is 0.

Common mistakes

The mistakes below are the ones a programmer arriving from C makes first with Z98 structs. Each one has a corrected shape, and the corrected shape is the compiler's rule, not a style preference.

Assuming the struct is packed. In C a struct may happen to have no padding for small field sets, and the layout can be forced with #pragma pack or __attribute__((packed)). Z98 structs are naturally aligned, always, and there is no attribute to reach for. The three bytes after id and the four after origin are real, and @sizeOf(Sprite) is 32, not 25. If you are matching a wire format or a hardware register, a plain struct is the wrong tool — the next chapter, packed struct, is the right one, and it is where the bit-exact layout lives.

Writing C's offsetof. The C macro takes the member name as a bare designator, offsetof(Sprite, tint). The Z98 builtin takes the field name as a string literal, @offsetOf(Sprite, "tint"). The unquoted form does not compile, and a name computed at run time is rejected with error[3073]: field name must be a string literal. The name is a compile-time key into the type, not a value.

Using @offsetOf on a union. Offsets are a struct idea. Asking a union for a field offset, or asking a pointer or a scalar, is rejected with error[3072]: expected struct type, found 'U' rather than folded to zero. Unions (chapter 7) overlap their members at offset zero by construction, so there is nothing for an offset to say.

Treating a struct as bytes. Because the padding bytes are indeterminate, copying a struct with a raw byte copy and then sending those bytes somewhere can leak whatever was in the gaps and will not match a decoder that omits padding. Struct assignment in Z98 copies the value; the emitted C is a single struct assignment (copy = s;), which is safe; a hand-rolled @sizeOf-long byte copy is not. If the bytes are the protocol, serialize one field at a time.

Expecting a constructor or a method. There is no Sprite.init() and no s.draw(). A struct is data and nothing else; the code that builds or uses one is a free function that takes the value or a pointer to it. Z98 has no methods, no constructors, and no destructors, so nothing runs behind your back when a struct variable is declared or goes out of scope (chapter 16 (planned) covers the init-function pattern that replaces them).
