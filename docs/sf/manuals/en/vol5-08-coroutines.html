Write and Drive a Coroutine

This guide writes a suspending function, initializes and drives its frame with the four @async* builtins, then registers several tasks with the std.async Context / Task / Scheduler driver — sizing every buffer with @asyncFrameSize so each frame stays 8-aligned.

Prerequisites

  • The compiler rebuilt from the seed at /tmp/manual_seed/zig1_5_clean, with the standard library beside it in /tmp/manual_seed/lib/. If it is not there yet, follow Rebuild the compiler from seed first.
  • A Linux host with a 32-bit-capable gcc (the emitted script uses gcc -m32 -std=c89).
  • The repository checked out, so the shipped samples docs/sf/manuals/src/vol2/builtins/async.z98 and docs/sf/manuals/src/vol3/tasks.z98, and the async fixtures under repro/mi_matrix/stdlib_async_*, are present. Every command runs from the repository root, /workspace/znineeight.
  • For the frame/step ABI and the std.async surface, keep the Volume IV Async and coroutines page open.

The idea

A function is suspending when its body contains @asyncSuspend, or directly calls a function that is suspending. You do not declare it: the compiler computes the property once, program-wide, and rewrites every suspending function into a step machine. The synchronous body is not emitted; instead a generated step runs forward to the next suspension, saves the values it will need, and returns a non-null sentinel while it is suspended (null means finished).

The language gives you four builtins and no scheduler. @asyncFrameSize(fn) is a compile-time constant: the authoritative, conservative byte size of fn's root frame. @asyncInit(ctx, buf, fn, args) initializes a fresh root frame for fn inside the 8-aligned buffer buf, using the per-task pool ctx, and copies the args record positionally into fn's parameters. @asyncSuspend(data) is the explicit suspension point. @asyncResume(frame, arg) loads the step word stored at offset 0 of frame, calls the step, and returns its result: null when the coroutine is done, non-null while it is still suspended. There is no async/await keyword.

Two rules carry the whole mechanism. A direct call from one suspending function to another is an implicit await, and the child frame comes from the per-task Context pool. And every frame is padded up to a multiple of 8 bytes, so consecutive frames in an 8-aligned pool stay 8-aligned and an f64 or pointer inside any frame loads correctly. Back every pool and root frame with an array of u64, never with a bare array of u8: a u8 array is only 1-aligned, and contextInit traps on a misaligned buffer on purpose rather than corrupting every child frame that follows.

Steps

  1. Start at the repository root. 

    $ cd /workspace/znineeight

  2. Create the output folder. The compiler writes its emitted tree there but will not create the folder itself. 

    $ mkdir -p /tmp/manual_out

  3. Translate the builtins sample, which runs one coroutine that suspends three times. 

    $ timeout 120 /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol2/builtins/async.z98

    The command is silent on success. It emits one C89 pair per module, the runtime, and the companion build script.

  4. Build and run it. Run the emitted script from inside the output folder and give it the target linux and the program name async. 

    $ cd /tmp/manual_out && timeout 120 sh build_target.sh linux async
Building for linux...
Built: async
$ timeout 120 ./async
frame=88
n=3 steps=4

    The first line is @asyncFrameSize(worker). The second counts the resumes: the loop resumes until @asyncResume returns null; the first three resumes stop at a suspension point and return non-null, and the fourth runs i to 3, stores the result, and returns null. Four steps, three suspensions. This coroutine has no child calls, so its Context pool is configured but never used. The program exits with status 0.

  5. Now drive several tasks with the library scheduler. The shipped program docs/sf/manuals/src/vol3/tasks.z98 builds a per-task Context pool and root frame, fills a Task, registers it with addTask, and runs waitAll. Translate it. 

    $ timeout 120 /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol3/tasks.z98

  6. Build and run the scheduler program. 

    $ cd /tmp/manual_out && timeout 120 sh build_target.sh linux tasks
Building for linux...
Built: tasks
$ timeout 120 ./tasks
frame size = 168
task 0 step 0
task 1 step 0
task 2 step 0
task 0 step 1
task 1 step 1
task 2 step 1
task 0 done
task 1 done
task 2 done
done = 3

    The order is deterministic, not timing. tick walks the registered tasks in the order they were added, so task 0 runs, suspends, and yields to task 1, which suspends and yields to task 2. On the next tick each resumes at its saved state, prints its second step, and suspends again. On the third tick each falls out of its loop and finishes; waitAll returns and main prints done = 3. The Task record stores no step pointer: when tick resumes a task it calls @asyncResume(t.frame, t.arg), and the step word at offset 0 of the frame supplies the function. That is why one scheduler drives tasks built from completely different suspending functions without generics, and it is why the round-robin order is exactly reproducible.

  7. Check the scheduler against the committed fixture. This one builds hand-made frames whose step word is the only thing the library knows, then verifies addTask, count, a forced suspend, and waitAll through the byte-exact golden. The standard-library gate emits the fixture, links it with build_target.sh, runs it three times, and diffs the result byte-for-byte against the committed expected.txt and expected.rc. 

    $ bash scripts/stdlib/verify_stdlib.sh /tmp/manual_seed/zig1_5_clean repro/mi_matrix/stdlib_async_sched_xmod
== std-lib runtime gate ==
   zig1: /tmp/manual_seed/zig1_5_clean
PASS repro/mi_matrix/stdlib_async_sched_xmod
----------------------------------------
run_fixtures: 1 PASS / 0 FAIL over 1 dirs
STDLIB GATE OK

    Its six-line transcript is 1, 3, 2, 10, 20, 30: the first registration returns true, three tasks are registered, a forced suspend puts task 2 in the suspended state, and waitAll resumes every task to completion, each emitting id * 10.

  8. Verify the 8-align rule directly. The frame layout pads every frame up to a multiple of 8, and the Context header is 16 bytes (not the 12 you might write after seeing three 4-byte fields), so that pool_base = ctx + 16 stays 8-aligned whenever the caller's buffer is. The first fixture allocates a struct holding an f64 from the pool and checks that the returned pointer is 8-aligned and that the f64 round-trips. 

    $ bash scripts/stdlib/verify_stdlib.sh /tmp/manual_seed/zig1_5_clean repro/mi_matrix/stdlib_async_f64align_xmod
== std-lib runtime gate ==
   zig1: /tmp/manual_seed/zig1_5_clean
PASS repro/mi_matrix/stdlib_async_f64align_xmod
----------------------------------------
run_fixtures: 1 PASS / 0 FAIL over 1 dirs
STDLIB GATE OK

    Its three-line transcript is 1, 1, 1: the pointer is 8-aligned ((ptr & 7) == 0), the f64 reads back as 3.5, and the tag survives. The second fixture sizes the buffer to exactly the 16-byte header and checks the capacity = buf.len - 16 boundary: a zero-capacity pool must fail with error.OutOfFrame, set the sticky oom flag, and leave used at zero. 

    $ bash scripts/stdlib/verify_stdlib.sh /tmp/manual_seed/zig1_5_clean repro/mi_matrix/stdlib_async_headerexact_xmod
== std-lib runtime gate ==
   zig1: /tmp/manual_seed/zig1_5_clean
PASS repro/mi_matrix/stdlib_async_headerexact_xmod
----------------------------------------
run_fixtures: 1 PASS / 0 FAIL over 1 dirs
STDLIB GATE OK

    Its four-line transcript is 1, 1, 1, 1: capacity == 0, the first allocation fails, used stays 0, and oom is set. The failure is a named error you can handle, not a corrupt heap.

Verify it worked

The two transcribed runs in Steps 4 and 6 are the recorded measured output of the shipped samples; running the commands in Steps 2–6 reproduces them exactly. Step 4 shows the four builtins driving a single coroutine to completion (frame=88, four resumes, three suspensions). Step 6 shows the Context / Task / Scheduler driver keeping three tasks in deterministic round-robin order until done = 3. Steps 7–8 are the committed goldens: the scheduler fixture passes byte-for-byte, and the two alignment fixtures pin the 8-align frame rule and the 16-byte Context header. A passing STDLIB GATE OK in every case confirms the emitted program matches the committed expected.txt and expected.rc.

Common mistakes

  • Backing a pool or frame with a bare [N]u8. A u8 array is only 1-aligned, and contextInit traps on a misaligned buffer rather than corrupting every child frame that follows. Use an 8-aligned element type such as [K]u64, and let @asyncFrameSize(fn) tell you how much room the frame needs — never a hard-coded byte count.
  • Passing the args record as an optional. @asyncInit wants a plain *const void, written @ptrCast(*const void, &record). A ?*const void is a non-scalar optional in this position and emits invalid C89. The record's fields are the coroutine's parameters, so their number and order must match fn exactly; @asyncInit copies them positionally, with no names involved.
  • Taking the address of a suspending function. It is rejected with error[3017]: taking the address of a suspending function is not allowed.
  • Suspending in the wrong place. @asyncSuspend outside a suspending function is error[3018], and inside a defer/errdefer body it is error[3019]. A coroutine cannot suspend from its cleanup.
  • Asking for the frame size of a non-suspending function. @asyncFrameSize requires a known suspending function; otherwise it is error[3046]: @asyncFrameSize argument must be a known suspending function.
  • Calling awaitTask from main. awaitTask parks the currently running task, so it is legal only inside a coroutine; from main it panics with std.async: awaitTask called from a non-suspending context. A driver with no current task must use waitFor (or waitAll) instead. The two are not interchangeable: waitFor also ticks unrelated ready tasks.
  • Expecting a coroutine to be a thread. The scheduler is cooperative and single-threaded; nothing is preempted, so there are no data races between tasks and no locks, but there is also no parallelism. That is the point on this machine, and it is what makes the order in the Step 6 transcript reproducible.
