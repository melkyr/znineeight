Aggregates II: Packed Structs

A packed struct is a struct written as bits. It declares named fields exactly like the struct of the last chapter. The literal, the dot, the nested access, and the assignment rules are all the same. The difference is the one word in front of the declaration: the compiler does not align the fields, does not insert padding, and does not round the layout to anyone's idea of a machine word. The fields are laid end to end, bit by bit, from the first bit of the first byte, and the byte image that comes out is exactly the one you described.

That is what this type is for. A plain struct is a way to group memory; a packed struct is a way to describe a fixed sequence of bits. When the layout is the point — a hardware register on a nonstandard port, a byte in a file format, the header of a packet on the wire — a plain struct is the wrong tool, because the compiler is free to leave gaps in it. This chapter declares packed structs, works the bit arithmetic by hand, reads the layout with @bitOffsetOf and @bitSizeOf, views the result as bytes, and warns about the limit that keeps the type honest: no field may be wider than 31 bits.

Adding one word to a struct

The syntax is the struct syntax with packed in front. The chapter's wire header is two 4-bit fields and a byte, a shape you will meet in real protocols under names like version, flags, and length: 

const Header = packed struct {
    version: u4,
    flags: u4,
    length: u8,
};

A packed field may be bool (one bit), an integer type whose declared width is at most 31 bits, or a nested packed struct admitted by its inner total width: its own fields obey the same rule, and the nested type as a whole may be wider than 31 bits. u1 through u31 and i1 through i31 are all fair game, and so are the named widths u8, u16, i8, and so on. An integer field of type u32 or wider is rejected, and so is every other type — a float, a pointer, an array, or an ordinary struct has no defined place in a bit sequence. The exact diagnostics are in the honesty note later in the chapter.

The difference from the last chapter's struct shows up immediately. The plain twin of Header — the same three fields without packed — spends a byte on each field, because each field must sit at its own byte offset:

Field Type Width Plain struct Packed struct
version u4 4 byte 0 bits 0–3
flags u4 4 byte 1 bits 4–7
length u8 8 byte 2 bits 8–15
total 3 bytes, align 1 16 bits = 2 bytes, align 1

The plain version measures @sizeOf 3 and @alignOf 1 here, and the packed version measures 2 and 1. The byte saved is real, but it is not the interesting part. The interesting part is that in the packed version every bit has an address you can name, and the two nibbles actually share byte 0.

LSB-first packing

The layout rule is one sentence: fields are placed in declaration order, each one starting at the lowest bit that is still free. That is called LSB-first packing, because the first field owns the least significant bit of the first byte. A field that does not fit in the rest of a byte continues in the next byte, starting at that byte's bit 0; nothing is inserted between fields. The last byte is used from the bottom up, and any bits above the last field are not part of any field.

For Header the cursor is easy to follow: version takes bits 0–3, flags takes the next four bits (4–7), and length needs eight bits, so it starts at bit 8 and fills all of byte 1. The whole type is 16 bits, which is 2 bytes; the run confirms @bitSizeOf(Header) is 16 and @sizeOf(Header) is 2.

The same rule makes multi-byte fields land in little-endian order in the byte image. Take a wider field that straddles bytes: 

const Word = packed struct {
    low: u4,
    high: u12,
};

low is bits 0–3 and high is bits 4–15, so the pair is one 16-bit little-endian number whose low nibble lives in the first field. With low = 13 and high = 2748 (0xABC), the word is 0xABCD: byte 0 is 0xCD = 205 and byte 1 is 0xAB = 171. Both numbers are odd because low is the low nibble, not the high one; the first field is the least significant, always. The control register later in the chapter prints 203 and 171 for exactly the same reason.

The bit builtins

Four builtins read a type's layout without running anything. The last chapter met three of them on plain structs; on a packed struct they change one meaning each, and @bitOffsetOf joins them:

Builtin On a plain struct On a packed struct
@sizeOf(T) padded byte size the total bits rounded up to whole bytes
@alignOf(T) strictest field alignment always 1
@bitSizeOf(T) byte size × 8 the sum of the field widths
@bitOffsetOf(T, "f") byte offset × 8 the field's bit offset
@offsetOf(T, "f") the byte offset the bit offset divided by 8, rounded down

The last row is the trap. @offsetOf is a byte answer, so on a packed struct it can only round; two fields that share a byte both report offset 0, and a field at bit 12 reports byte 1. For Header the program prints version=0 flags=0 length=1: the flags nibble is in byte 0, but the bit offset is 4, and @offsetOf cannot say so. @bitOffsetOf is the builtin that keeps the bit.

On a plain struct the relationship runs the other way: there are no sub-byte fields, so @bitOffsetOf is just the byte offset multiplied by eight. A struct with a u8 at offset 0 and a u32 at offset 4 reports bit offsets 0 and 32. Both builtins are compile-time constants: they fold before any C is emitted, and they take the type and a string-literal field name, with the same field-name and target-type rejections the last chapter described (error[3072] for a non-struct target, error[3073] for a bad field name).

There is one more useful fact about @sizeOf. It is the byte count, not the bit count, so a type of five bits still occupies one byte: a packed struct { a: u2, b: u3 } reports @bitSizeOf 5 and @sizeOf 1. The bits above the last field in that byte are not part of any field and are not written when the fields are written.

Reading the bytes

The point of a packed struct is the byte image, and Z98 makes it visible without a union or a cast to a number: take the address and view it as bytes. @ptrCast([*]const u8, &h) gives a many-item pointer to the first byte, and p[0], p[1], and so on read the image in order. For Header with version = 6, flags = 10, and length = 200, byte 0 is 6 | (10 << 4) = 166 and byte 1 is 200.

Decoding runs the same arithmetic backwards. Read the two bytes as one little-endian 16-bit value, then mask and shift the fields out of it: 

var raw: u16 = @intCast(u16, hp[0]) | (@intCast(u16, hp[1]) << 8);
var back: Header = .{
    .version = @intCast(u4, raw & 15),
    .flags = @intCast(u4, (raw >> 4) & 15),
    .length = @intCast(u8, (raw >> 8) & 255),
};

The decoded fields are 6, 10, and 200 — the values the encoder was given. That round trip is the whole contract of the type: the field access writes and reads the bits, and a decoder that agrees on the packing gets the same values back. Printing a whole packed value with {} shows the named fields (.{ .version = 6, .flags = 10, .length = 200 }), but the bytes on the wire are the two numbers printed above.

Two portability statements follow, and they are different statements. Within a running Z98 program, the layout is fixed by the language, not by the host C compiler: the emitted C for a packed struct is a small array of unsigned char plus shift-and-mask code, so every supported toolchain produces and consumes the same bytes. Across programs that were not compiled from Z98, nothing is guaranteed except the rule itself, which must be written down on both sides: fields in declaration order, LSB-first, little-endian for multi-byte fields. A big-endian receiver, or a C struct with hand-written bitfields, will disagree unless it is told the rule.

A hardware register

The other classic use is a memory-mapped register, where a datasheet draws a 16-bit word as named bits. The control register below is the same shape as the header, but read left to right instead of first-to-last: 

const Ctrl = packed struct {
    enable: u1,
    mode: u3,
    divisor: u12,
};

enable is bit 0, mode takes bits 1–3, and divisor takes the top twelve bits, 4–15. The type is 16 bits, 2 bytes, alignment 1, and the fields behave exactly like the named bits a programmer would otherwise set with constants and shifts:

Field Type Width Bit offset Value
enable u1 1 0 1
mode u3 3 1 5
divisor u12 12 4 2748 (0xABC)
total 16 0xABCB = 43979

The register word is 1 | (5 << 1) | (2748 << 4), which is 0xABCB; its bytes in memory are 0xCB = 203 then 0xAB = 171. That is what the program prints, and it matches the datasheet line for line. In C this shape is usually written with a word and a pile of masks; here the masks are the field widths.

Honest note. The 31-bit cap is not a detail to discover later; it is the price of the type. A packed field can be bool, an integer of at most 31 bits, or a nested packed struct admitted by its inner total width (its own fields obey the same rule, and the nested type as a whole may be wider than 31 bits). A u32, an i64, a float, a pointer, an array, or an ordinary struct cannot appear at all, and the compiler rejects the declaration: error[3000]: packed struct field width must be <= 31 bits (u32/i64 etc. packed fields are not supported yet) for a wide integer, and error[3000]: packed struct fields must be bool or an integer type (uN/iN); this field type is not allowed in a packed struct for anything else. A 32-bit value fits as two 16-bit fields or as u24 plus u8, and the program can define the split itself. What you do not get is one integer field spanning the whole word. The layout is also little-endian and LSB-first by definition; it is not a universal interchange format, and the emitted C does not fall back on the host compiler's bitfield rules. Within Z98 and its supported targets, the byte image is exact; outside that boundary, both sides must agree on the rule.

The example

The whole chapter in one program. It declares the wire header and the control register, prints the size, the bit count, the bit offsets and the byte offsets, views each value as raw bytes, and decodes the header back from its bytes with shifts and masks. It is docs/sf/manuals/src/vol2/wire.z98: 

const std = @import("std");

// A 16-bit wire header: two 4-bit fields packed into the first byte, then
// the payload length in the second byte. LSB-first.
const Header = packed struct {
    version: u4,
    flags: u4,
    length: u8,
};

// A 16-bit control register, read left to right on a datasheet:
// enable (bit 0), mode (bits 1-3), divisor (bits 4-15).
const Ctrl = packed struct {
    enable: u1,
    mode: u3,
    divisor: u12,
};

pub fn main() void {
    var h: Header = .{ .version = 6, .flags = 10, .length = 200 };
    var hp = @ptrCast([*]const u8, &h);

    std.io.print("Header size={} bits={}\n", .{ @sizeOf(Header), @bitSizeOf(Header) });
    std.io.print("Header bit offsets version={} flags={} length={}\n", .{
        @bitOffsetOf(Header, "version"),
        @bitOffsetOf(Header, "flags"),
        @bitOffsetOf(Header, "length"),
    });
    std.io.print("Header byte offsets version={} flags={} length={}\n", .{
        @offsetOf(Header, "version"),
        @offsetOf(Header, "flags"),
        @offsetOf(Header, "length"),
    });
    std.io.print("Header bytes {} {}\n", .{ hp[0], hp[1] });

    var raw: u16 = @intCast(u16, hp[0]) | (@intCast(u16, hp[1]) << 8);
    var back: Header = .{
        .version = @intCast(u4, raw & 15),
        .flags = @intCast(u4, (raw >> 4) & 15),
        .length = @intCast(u8, (raw >> 8) & 255),
    };
    std.io.print("decoded version={} flags={} length={}\n", .{ back.version, back.flags, back.length });

    var c: Ctrl = .{ .enable = 1, .mode = 5, .divisor = 2748 };
    var cp = @ptrCast([*]const u8, &c);
    std.io.print("Ctrl size={} bits={}\n", .{ @sizeOf(Ctrl), @bitSizeOf(Ctrl) });
    std.io.print("Ctrl bit offsets enable={} mode={} divisor={}\n", .{
        @bitOffsetOf(Ctrl, "enable"),
        @bitOffsetOf(Ctrl, "mode"),
        @bitOffsetOf(Ctrl, "divisor"),
    });
    std.io.print("Ctrl bytes {} {}\n", .{ cp[0], cp[1] });
    std.io.print("Ctrl fields enable={} mode={} divisor={}\n", .{ c.enable, c.mode, c.divisor });
}

Nine lines, in three groups. The first four are the header's arithmetic: 16 bits in 2 bytes; the fields' bit offsets 0, 4, and 8; the byte offsets 0, 0, and 1 that show @offsetOf rounding the flags nibble down into byte 0; and the raw bytes 166 and 200. Common mistakes

The mistakes below are the ones a programmer arriving from C makes first with packed structs. Each one has a corrected shape, and the corrected shape is the compiler's rule, not a style preference.

Assuming the platform's packing is the packing. In C the byte image of a struct is the C compiler's business; #pragma pack and __attribute__((packed)) change the rules from compiler to compiler, and hand-written C bitfields have implementation-defined order. Z98's packed layout is not the host compiler's layout: it is the language's rule, applied by the emitted C itself, which stores the value as bytes and moves the bits with explicit shifts. Do not prototype a packed struct by writing a C struct and checking its sizeof; the two agreements are different agreements.

Reaching for a 32-bit field. u32 packed fields do not exist yet, and neither do i32, u64, or any width above 31. The compiler rejects the declaration with error[3000]: packed struct field width must be <= 31 bits. The fix is to split the value at a bit boundary the format already has — low: u16 plus high: u16, or u24 plus u8 — and to define which half is which in the code that reads and writes it.

Assuming a bit order. The fields are LSB-first: the first declared field owns bit 0 of byte 0, and a wider field's low bits come first in the byte stream. That is not what a datasheet drawn left to right implies, and it is not what a big-endian machine would produce. When two programs exchange these bytes, the order has to be part of the agreement, on both sides. The safest summary to remember is the one this chapter verified: declaration order, LSB-first, little-endian for multi-byte fields.

Asking @offsetOf for a bit offset. The C reflex is offsetof, which is bytes only. On a packed struct @offsetOf(Header, "flags") compiles and answers 0, because the flags nibble lives in byte 0; the answer is rounded down, not rounded off. The builtin that takes bits seriously is @bitOffsetOf(Header, "flags"), which answers 4. Use @offsetOf for the byte a field starts in (the header's length is byte 1) and @bitOffsetOf for anything smaller.

Confusing @sizeOf with @bitSizeOf. A packed type of 5 bits still occupies a whole byte, so @sizeOf is 1 while @bitSizeOf is 5. The bits above the last field in the final byte belong to no field, are not written by the field stores, and must not be read as if they were data. When the bit count is what matters, ask for the bit count.

Treating the saved padding as free round-tripping. A packed struct removes alignment padding, but it does not remove the need for a decoder. The bytes are still bytes: reading them requires the address, the length @sizeOf reports, and a reader that knows the format. Struct assignment still copies the value, and a pointer cast still views the live memory — neither one turns the value into a file on disk. If the bytes leave the program, make the format explicit, exactly as the example's decode line does.
