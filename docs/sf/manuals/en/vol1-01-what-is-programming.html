What is a Program

Before you can write a program, you need a plain working idea of what one is. Strip away the language, the editor, and the compiler and what is left is small: a program is a set of instructions that a machine carries out, one after another, exactly as they were written. Everything else in this manual is detail hung on that sentence.

This chapter has no code in it. It is the mental model the rest of the volume builds on. If you have never written a program, read it slowly; if you already have, it is still worth a skim, because the wording used here — input, process, output, and the machine as a very literal assistant — is the wording the later chapters assume.

Note. Throughout this manual, a program is the written instructions, and running or executing a program means the machine carrying them out. Keep the two apart in your head: the instructions sit on the disk and do nothing until the machine is told to run them.

The machine as a very literal assistant

Imagine you hire an assistant who does exactly what you say. Not what you meant, not what you would have said if you had thought about it a little longer — exactly what you said. This assistant is tireless, fast, and completely without judgement. Give it a clear instruction and it carries it out perfectly. Give it an unclear one and it does not stop to ask; it picks an interpretation and commits to it, or it fails, and either way it does not apologize.

A computer is that assistant. This is the single most useful thing to understand about programming, and the thing beginners most often get wrong. The machine does not understand your goal. It does not know that you wanted the report sorted by date, or that you meant the second file and not the first. It has no common sense to fall back on and no way to infer what you left out. It simply does what the instructions say.

Suppose you tell the literal assistant “bring me a chair.” In a room with one chair, that works. In a room with three, the instruction is incomplete, and a literal assistant has no basis for choosing. It might bring the nearest one, it might bring the largest, it might do nothing at all. You cannot blame it. You did not say which chair. The precise instruction — “bring me the blue chair in the corner” — is the one that gets the result you wanted.

Programming is the work of turning what you want into instructions that are literal. It is not a matter of persuading or explaining. It is a matter of saying exactly what you mean, in a form the machine can follow, with no gaps for it to fill in on its own. That is why programmers spend so much time thinking before they type, and why a program that is almost right is usually no better than one that is plainly wrong.

Input, process, output

Almost every program, from the smallest to the largest, can be described in three parts: what it is given, what it does with it, and what it produces. This is the input → process → output model, and it is old enough to predate the personal computer. It fits a pocket calculator, a word processor, and the compiler you will use later in this manual. It fits a program so small it is a single instruction and a program so large it takes a team to write.

The model is not a law of nature. It is a lens. Some programs have no input worth naming, some have no output you can see, and some have several of each. But if you cannot say what goes in, what happens, and what comes out, you do not yet understand the program you are trying to write — and neither will the machine. Learn to reach for the three questions first.

Input: what the program is given

Input is the information a program starts from. Nothing is supplied by magic; input comes from somewhere real, and if it does not come, the program has nothing to work on. The usual sources are the keyboard, a file on the disk, a value typed on the command line when the program is started, another program that runs it, or a piece of hardware that reports what it senses.

Input is not always present. A program that prints a fixed greeting needs nothing from the outside, and that is fine; its input is simply empty. But even then the rule holds: the program can only use information it has been given. A program cannot read your mind, and it cannot reach out and take data you never handed it. If the input is missing, the program will not invent it.

It is worth noticing how much of a program's behaviour is really a statement about its input. “Adds two numbers” says nothing until you know which two numbers, and where they came from. When a program misbehaves, the input is one of the first things to check, because the machine can only be as right as the information it was handed.

Process: the steps

The process is the middle of the model, and it is where the program proper lives: the steps that turn the input into the output. A program is a sequence. The steps are carried out in order, one after another, and the order matters. Move a step earlier or later and you get a different result, or no result at all. The literal assistant does not rearrange your instructions to make them work; it takes them in the order you gave.

Real programs do more than march straight ahead. They make choices and they repeat work, and later chapters are devoted to both. But a choice is still made of steps — one set of steps if a condition holds, another set if it does not — and repetition is the same steps performed more than once. Under all the machinery, the process is a sequence of things to do, and the machine does them in order.

Because the assistant is literal, each step must be complete and unambiguous. A step that assumes the machine will figure something out is a step that will eventually go wrong. The process is where the precision you learned to value in the previous section is spent.

Output: the result

Output is what the program produces: text shown on the screen, a file written to disk, a page sent to a printer, a message sent across a network, or a value handed to another program that called this one. Output is how the world learns what the program did. A program with no output at all is, for practical purposes, unobservable; it may have done something useful, but you have no way to tell.

Output is also how you check your work. You run the program, look at what came out, and compare it with what you expected. When the two match, the program is probably right; when they differ, the difference tells you where to look. Much of the craft of programming is choosing outputs that make it easy to see whether the process did what you intended.

The three parts as a habit

The three questions are worth turning into a habit. Before you write a program — before you even open the editor — describe it in three sentences: what it takes in, what it does, and what it produces. If you can write those three sentences, you are ready to begin. If you cannot, you are not stuck on the language; you are stuck on the design, and no amount of typing will fix that.

This habit scales up. A large program is not one enormous process; it is many small input → process → output pieces joined together, where the output of one piece becomes the input of the next. When a big program is confusing, the cure is usually to find the small pieces and describe each one in three sentences. The confusion is a sign that one of the pieces has not been described yet.

When you write your own programs, describe them this way before you begin: say what the program takes in, what it does, and what it produces. A program whose three sentences you cannot write is a program you are not ready to write yet.

What a program is not

It helps to be just as clear about what a program is not. A program is not magic, and it is not intelligent. It does not know what you meant. It cannot fill in a missing case with a sensible guess, because it has nothing to guess with. If you leave a situation out of your instructions, the machine does not notice and quietly do the reasonable thing; it does whatever the incomplete instructions say, which may be nothing useful at all.

This is not a flaw to be worked around so much as the nature of the tool. A machine is valuable precisely because it has no opinions: it does exactly what it is told, every time, without getting bored or distracted or deciding it knows better. The price of that reliability is that the responsibility for being right is entirely yours. The machine will not meet you halfway.

So when a program does the wrong thing, the useful question is not “why is the machine being difficult?” but “what did I actually tell it to do?” The answer is almost always in the instructions, not in the machine. Learning to ask that question calmly, rather than blaming the computer, is a larger part of becoming a programmer than any single piece of syntax.

Instructions, not intentions

Return once more to the literal assistant. You hand over two instructions: “take the blue chair to the workshop, then paint it.” The assistant takes the chair to the workshop and paints it, and the job is done. Now suppose you hand over only the first: “take the blue chair to the workshop.” The chair arrives unpainted. The assistant has not disobeyed; it did exactly what you said. The paint was never mentioned.

Every program is like this. The machine carries out the instructions you wrote, not the ones you had in mind. If a step is missing, the result is missing a step. This is why writing a program is closer to writing a precise set of directions than to describing an outcome and trusting the reader to work out the rest. You are not asking the machine to achieve a goal. You are telling it, step by step, how.

That shift in thinking — from stating what you want to stating how to get it — is the real beginning of programming. The rest of this volume teaches you the vocabulary for writing those steps. It starts, in the next chapters, with what the language is and what machine you will run it on, and it reaches its first actual instruction in chapter 5, where you will write a program that does nothing but print one line. That is enough to see the whole model at work: a small process, almost no input, and an output you can read.

Check yourself

Answer these before moving on. They need no code and no machine.

  1. Pick a program you use often — a calculator, a text editor, an alarm clock. In one sentence each, say what its input is, what its process does, and what its output is.
  2. You tell a literal assistant “sort these papers.” Give two different ways the instruction could reasonably be carried out, then rewrite it so that only one result is possible.
  3. A program prints a fixed greeting and takes nothing from the outside. Does it still fit the input → process → output model? Explain your answer in a sentence or two.
