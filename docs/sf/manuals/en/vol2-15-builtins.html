Builtins, in Full

Every language has a layer below its own syntax: the operations the compiler performs itself. Z98 calls them builtins. They are written @name(...) and recognized by name, and they are the escape hatch for the things a small, C89-shaped language cannot express as library code: a cast that promises a layout, a question about a type's size or alignment, a byte written to the console, an argument read out of a C variadic list, a coroutine suspended and resumed.

The set is small on purpose. Forty names, in six groups: cast, conversion, and introspection (19), runtime (11), C varargs (3), async (4), declarations (2), and formatted print (1), plus the rule that ties them together — an unknown builtin is error[3000]. This chapter walks all forty. Where a one-line example teaches the builtin, it is in a table; where the behavior needs a program, the group has one. Every example was compiled by the seed-built compiler, every runnable program was run, and every transcript is the real output.

The runnable examples live beside the other chapter samples. The main program is docs/sf/manuals/src/vol2/builtins.z98; the supporting programs are runtime.z98, console.z98, exit.z98, cvarargs.z98, async.z98, and cinclude.z98 in docs/sf/manuals/src/vol2/builtins/.

Honest note. This is the whole builtin surface, and it is smaller than the surface of the Zig you may have used. There is no @typeInfo, no @errorName, no @typeName, no @memcpy, no @memset, no @min; there is no anytype and no comptime. What is here is the set the type system, the runtime, the C bridge, and the coroutines actually need. Two consequences are worth naming at the start. Code that reaches for a modern builtin gets error[3000], and the supported answer is this page. And several builtins come in an old name and a modern alias — @ptrToInt/@intFromPtr, @intToPtr/@ptrFromInt — so two spellings compile where you might expect one to be missing. The missing names are not an oversight to work around; chapter 16 shows what replaces them in practice.

The rule: unknown builtins are error[3000]

Builtins are resolved by name, before any library could be involved. A call to @name(...) whose name is not in the supported set is rejected with the compiler's own error code, error[3000]. There is no runtime lookup, no extension mechanism, and no warning-then-continue: the name is either supported or it stops the build.

Here is the reject, produced by a program whose only statement calls a builtin that does not exist: 

$ mkdir -p /tmp/manual_out
$ /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out bad.z98
bad.z98:4:4: error[3000]: unsupported builtin function
    @frobnicate(5);
    ^^^^^^^^^^^^^^

The message names the rule directly: unsupported builtin function. If the call's result is used, the compiler adds a second diagnostic at the declaration — error[3000]: cannot declare variable of type void — because an unresolved builtin has no type. The first error is the one to read; the second is the cascade.

One more thing before the groups: @ names are not keywords. They are seen only in call position, and the character is not available for ordinary identifiers, which is why library code never collides with a builtin.

Group A: cast, conversion, introspection (19)

This is the largest group, and it splits into four jobs. Pointer casts move between pointer types, or between pointers and integers: @ptrCast, @ptrToInt, @intFromPtr, @intToPtr, @ptrFromInt, @volatileCast. Numeric conversions change width, signedness, or representation: @intCast, @floatCast, @intToFloat, @bitCast. Enum conversions cross between an enum and its integer value: @intToEnum, @enumToInt. Introspection answers layout questions at compile time: @sizeOf, @alignOf, @offsetOf, @bitSizeOf, @bitOffsetOf. Two more fit their own slots: @as is an explicit coercion to a named type, and @fieldParentPtr recovers a containing struct from a pointer to one of its fields.

The table is the reference; the program below it is the proof. Every example column is a line from that program or a direct variant of one.

Call What it does Verified example
@ptrCast(T, expr) Explicit pointer cast. Both the target and the operand must be pointers. const raw: [*]u8 = @ptrCast([*]u8, &v);
@ptrToInt(expr) Pointer to usize. const a: usize = @ptrToInt(p);
@intFromPtr(expr) Modern alias of @ptrToInt; same result. @ptrToInt(p) == @intFromPtr(p) is true
@intToPtr(T, expr) Integer to pointer, result type named explicitly. const p: *i32 = @intToPtr(*i32, addr);
@ptrFromInt(expr) Integer to pointer, result type taken from context. const q: *i32 = @ptrFromInt(addr);
@fieldParentPtr(T, "field", expr) Pointer to the containing T from a pointer to one of its fields. @fieldParentPtr(Vec, "y", py) recovers Vec
@bitCast(T, expr) Same-size bit reinterpretation. const u: u32 = @bitCast(u32, x);
@volatileCast(T, expr) Remove the volatile qualifier; the base type must match. const plain: *i32 = @volatileCast(*i32, vp);
@intCast(T, expr) Checked integer conversion / width change. const b: u8 = @intCast(u8, 200);
@floatCast(T, expr) Float conversion; not runtime-checked, narrowing may lose precision. const h: f32 = @floatCast(f32, d);
@intToFloat(T, expr) Integer to float. const f: f64 = @intToFloat(f64, 3);
@intToEnum(T, expr) Integer to enum. const c: Color = @intToEnum(Color, 1);
@enumToInt(expr) Enum to integer. const n: i32 = @enumToInt(c);
@as(T, expr) Explicit coercion to a named type. const f: i64 = @as(i64, 5);
@sizeOf(T) Byte size of a type (the carrier size). @sizeOf(Vec) is 8
@alignOf(T) Alignment of a type. @alignOf(Vec) is 4
@offsetOf(T, "field") Byte offset of a field; T must be a struct (packed included). @offsetOf(Vec, "y") is 4
@bitSizeOf(T) Declared bit size (not the carrier size). @bitSizeOf(Flags) is 8
@bitOffsetOf(T, "field") Bit offset of a field; struct-only like @offsetOf. @bitOffsetOf(Flags, "b") is 4

A note on the checked casts. @intCast is one of the six runtime checks of the default -fsafe build: a value that does not fit traps instead of truncating. Under -ffast the check is omitted, like the arithmetic checks of Volume I. @floatCast is not checked; narrowing a float may lose precision silently. And @bitCast demands two equal-size types — it reinterprets bits rather than converting values, which is why -1 reads back as ffffffff.

The cast and introspection program

builtins.z98 exercises all nineteen Group A builtins and prints one line per family. Read it as the chapter's engine: each function is a complete, minimal use, and main prints its result. 

const std = @import("std");

const Vec = struct {
    x: i32,
    y: i32,
};

const Flags = packed struct {
    a: u4,
    b: u4,
};

const Color = enum(u8) {
    red = 0,
    green = 1,
    blue = 2,
};

fn castRoundTrip() i32 {
    var v: i32 = 42;
    const raw: [*]u8 = @ptrCast([*]u8, &v);
    const p: *i32 = @ptrCast(*i32, raw);
    return p.*;
}

fn ptrIntEq() bool {
    var v: i32 = 7;
    const p: *i32 = &v;
    return @ptrToInt(p) == @intFromPtr(p);
}

fn ptrRoundTrip() i32 {
    var v: i32 = 42;
    const addr: usize = @intFromPtr(&v);
    const p1: *i32 = @intToPtr(*i32, addr);
    const p2: *i32 = @ptrFromInt(addr);
    if (p1.* != p2.*) return -1;
    return p2.*;
}

fn parentX() i32 {
    var v = Vec{ .x = 11, .y = 22 };
    const py: *i32 = &v.y;
    const pv: *Vec = @fieldParentPtr(Vec, "y", py);
    return pv.x;
}

fn bitPattern() u32 {
    const x: i32 = -1;
    return @bitCast(u32, x);
}

fn volatileRead() i32 {
    var reg: i32 = 9;
    const vp: *volatile i32 = &reg;
    const plain: *i32 = @volatileCast(*i32, vp);
    return plain.*;
}

fn narrow() u8 {
    const wide: i32 = 200;
    return @intCast(u8, wide);
}

fn half() f32 {
    const d: f64 = 1.5;
    return @floatCast(f32, d);
}

fn toFloat() f64 {
    return @intToFloat(f64, 3);
}

fn pick() Color {
    return @intToEnum(Color, 1);
}

fn number(c: Color) i32 {
    return @enumToInt(c);
}

fn five() i64 {
    return @as(i64, 5);
}

pub fn main() void {
    std.io.print("ptrCast {}\n", .{castRoundTrip()});
    std.io.print("ptrToInt eq {}\n", .{ptrIntEq()});
    std.io.print("intToPtr/ptrFromInt {}\n", .{ptrRoundTrip()});
    std.io.print("fieldParentPtr {}\n", .{parentX()});
    std.io.print("bitCast {x}\n", .{bitPattern()});
    std.io.print("volatileCast {}\n", .{volatileRead()});
    std.io.print("intCast {}\n", .{narrow()});
    std.io.print("floatCast {}\n", .{half()});
    std.io.print("intToFloat {}\n", .{toFloat()});
    std.io.print("intToEnum {} enumToInt {d}\n", .{ pick(), number(pick()) });
    std.io.print("as {}\n", .{five()});
    std.io.print("size align bits {d} {d} {d}\n", .{ @sizeOf(Vec), @alignOf(Vec), @bitSizeOf(Flags) });
    std.io.print("offset y bitOffset b {d} {d}\n", .{ @offsetOf(Vec, "y"), @bitOffsetOf(Flags, "b") });
}

$ /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol2/builtins.z98
$ cd /tmp/manual_out && sh build_target.sh linux builtins
Building for linux...
Built: builtins
$ ./builtins
ptrCast 42
ptrToInt eq true
intToPtr/ptrFromInt 42
fieldParentPtr 11
bitCast ffffffff
volatileCast 9
intCast 200
floatCast 1.5
intToFloat 3
intToEnum .green enumToInt 1

size align bits 8 4 8
offset y bitOffset b 4 4

Line by line: the @ptrCast round trip reads the value back through a byte pointer; the two address spellings agree; integer-to-pointer and context-typed pointer-from-integer agree; @fieldParentPtr reaches back from v.y to v and reads x; -1 through @bitCast is the all-ones pattern; @volatileCast removes the qualifier and the read survives; @intCast narrows 200; @floatCast narrows the literal; @intToFloat widens the integer; @intToEnum/@enumToInt round-trip the number 1 and the name .green; @as names the type; and the last two lines are the whole layout family.

One distinction from chapter 2 comes back here: @sizeOf(Vec) is the carrier size in bytes, while @bitSizeOf(Flags) is the declared width in bits. On a plain u3 they disagree — one byte of carrier, three declared bits. Use @sizeOf for memory and @bitSizeOf for wire formats.

Group B: runtime (11)

These builtins talk to the machine. Eight are I/O and console calls, two terminate or delay the program, and one answers a target question at compile time. Each lowers to a call into the platform layer, with no hidden allocation.

Call What it does Verified example
@putChar(c) Writes a single character. @putChar('P');
@stdoutWrite(ptr, len) Writes len bytes to standard output. @stdoutWrite(out.ptr, out.len);
@stderrWrite(ptr, len) Writes len bytes to standard error. @stderrWrite(err.ptr, err.len);
@getChar() Reads a single character; blocks until one arrives. return @getChar(); — compiled, not called
@exit(code) Terminates the process with code. @exit(3);
@sleepMs(ms) Sleeps for ms milliseconds. @sleepMs(5);
@isWindows() Compile-time-folded target predicate: true only for the Windows target. if (@isWindows())
@consoleClear() Clears the console. @consoleClear();
@consoleGotoxy(x, y) Moves the console cursor. Coordinates are zero-based. @consoleGotoxy(0, 0);
@consoleSetColor(fg, bg) Sets the console colors. @consoleSetColor(7, 0);
@panic(msg) Writes panic: <msg> to stderr, then traps. Typed noreturn; it is not a no-op and it cannot be caught. @panic("stop"); — compiled, not called

The runtime program

runtime.z98 runs the non-blocking, non-trapping half of the group: @putChar, both write calls, @isWindows, and @sleepMs. It also declares the two builtins this chapter will not execute: @getChar blocks on input, and @panic traps, so both are exercised in uncalled functions. Compiling the program with them present is the verification; calling them is the reader's business. 

fn getCharOnce() u8 {
    return @getChar();
}

fn die() noreturn {
    @panic("stop");
}

pub fn main() void {
    @putChar('P');
    @putChar('Q');
    @putChar('\n');

    var out: []const u8 = "stdoutWrite\n";
    @stdoutWrite(out.ptr, out.len);

    if (@isWindows()) {
        var win: []const u8 = "isWindows true\n";
        @stdoutWrite(win.ptr, win.len);
    } else {
        var nowin: []const u8 = "isWindows false\n";
        @stdoutWrite(nowin.ptr, nowin.len);
    }

    @sleepMs(5);
    var slept: []const u8 = "slept 5 ms\n";
    @stdoutWrite(slept.ptr, slept.len);

    var err: []const u8 = "stderrWrite\n";
    @stderrWrite(err.ptr, err.len);
}

Run it, then look at the two streams separately. The first command's output is standard output; the second reads back the file the same run left on standard error: 

$ ./runtime 2>err.txt
PQ
stdoutWrite
isWindows false
slept 5 ms
$ cat err.txt
stderrWrite

@putChar and @stdoutWrite travel the same path, so their output keeps call order. On the Linux build @isWindows() folds to false; the Windows build prints isWindows true from the identical source — the predicate is decided while compiling. The final line went to the other stream, which is why the second command is there.

@exit

exit.z98 prints one line and leaves with status 3. There is no cleanup hook and no defer that runs afterward: the process is over. 

const std = @import("std");

pub fn main() void {
    var msg: []const u8 = "before exit\n";
    @stdoutWrite(msg.ptr, msg.len);
    @exit(3);
}

$ ./exit; echo "rc=$?"
before exit
rc=3

The console builtins

console.z98 clears the screen, homes the cursor, sets white on black, and prints one line. On the Linux target the three calls lower to ANSI escape sequences, so the captured bytes need a viewer that shows control characters: cat -v renders the ESC byte as ^[. 

const std = @import("std");

pub fn main() void {
    @consoleClear();
    @consoleGotoxy(0, 0);
    @consoleSetColor(7, 0);
    std.io.print("console ok\n", .{});
}

$ ./console | cat -v
^[[2J^[[H^[[1;1H^[[37;40mconsole ok

Four escape sequences, then the text: clear, home, position, colors. On the Windows target the same builtins lower to the Win32 console API instead (SetConsoleCursorPosition, SetConsoleTextAttribute), which is the right behavior on a real Windows 98 machine. Note the zero-based coordinates: @consoleGotoxy(0, 0) emits the ANSI home sequence.

Group C: C varargs (3)

These three builtins walk a C va_list. va_list is a primitive type in Z98, not a library type, and the functions that use it are ordinary variadic functions declared with .... The working spelling is shown in the program; the @cVaArg call names the type it should read, and the list must be ended with @cVaEnd.

Call What it does Verified example
@cVaStart(ap) Starts traversing the variadic arguments of the enclosing function. @cVaStart(ap);
@cVaArg(ap, T) Reads the next argument as type T. total += @cVaArg(ap, i32);
@cVaEnd(ap) Ends the traversal. @cVaEnd(ap);

The varargs program

cvarargs.z98 sums three integers passed through a C variadic list: 

const std = @import("std");

fn sum(count: i32, ...) i32 {
    var ap: va_list = undefined;
    @cVaStart(ap);
    var total: i32 = 0;
    var i: i32 = 0;
    while (i < count) : (i += 1) {
        total += @cVaArg(ap, i32);
    }
    @cVaEnd(ap);
    return total;
}

pub fn main() void {
    std.io.print("sum={}\n", .{sum(3, 10, 20, 12)});
}

$ ./cvarargs
sum=42

Two details carry the weight. The va_list is declared = undefined because @cVaStart initializes it; it does not zero a buffer for you. And @cVaArg takes the type as its second argument, so the reader's contract — "these arguments are i32" — is written in the code, not inferred. The list is read once; there is no rewind.

Group D: async / coroutines (4)

Z98's coroutines are cooperative and stackless. Four builtins drive them; the scheduler and the task bookkeeping live in std.async, not in the language. The machine model is worth one paragraph. A suspending function is compiled to a step machine; a coroutine owns a root frame in a buffer the caller supplies. Each resume runs from the last suspension point to the next, or to completion. The frame's layout, its step pointer, and the state word are the compiler's business.

Call What it does Verified example
@asyncInit(ctx, buf, fn, args) Initializes a root frame for suspending function fn in buf; returns it as *void. Arguments are copied positionally from the args record. @asyncInit(ctxp, &fbuf, worker, args);
@asyncSuspend(data) An explicit suspension point; valid only inside a suspending function. @asyncSuspend(null);
@asyncResume(frame, arg) Runs one step; returns null when the coroutine has finished, non-null while it is suspended. more = @asyncResume(frame, null);
@asyncFrameSize(fn) Compile-time byte size of fn's root frame. @asyncFrameSize(worker) is 88

The async program

async.z98 runs one coroutine that suspends three times, counts its resumes, and prints the frame size the compiler computed: 

const std = @import("std");

const WArgs = struct { out: *i32 };

fn worker(out: *i32) void {
    var i: i32 = 0;
    while (i < 3) : (i += 1) {
        @asyncSuspend(null);
    }
    out.* = i;
}

pub fn main() void {
    std.io.print("frame={}\n", .{@asyncFrameSize(worker)});
    var result: i32 = 0;
    var cbuf: [64]u8 = undefined;
    var fbuf: [128]u8 = undefined;
    var wa: WArgs = WArgs{ .out = &result };
    var ctxp: *void = @ptrCast(*void, &cbuf);
    var args: *const void = @ptrCast(*const void, &wa);
    var frame: *void = @asyncInit(ctxp, &fbuf, worker, args);
    var more: ?*void = @asyncResume(frame, null);
    var steps: i32 = 1;
    while (more != null) {
        more = @asyncResume(frame, null);
        steps += 1;
    }
    std.io.print("n={} steps={}\n", .{ result, steps });
}

$ ./async
frame=88
n=3 steps=4

Read the counting line first. The loop resumes until @asyncResume returns null; the first three resumes stop at a suspension point and return non-null, and the fourth runs i to 3, stores the result, and returns null. Four steps, three suspensions. The frame size is a compile-time literal, so the frame buffer can be checked against it under the default safe build. The ctx pointer is the per-task child-frame pool; this coroutine has no children, so the pool is configured but never used. Coroutines get their own chapters later: Volume III (planned) and the standard library tour.

Group E: declarations (2)

Two builtins are about code that comes from elsewhere. @import is used by every program in this manual; @cInclude is rarer and has one placement rule.

Call What it does Verified example
@import("file.zig") Includes another module. The standard library is @import("std"); only a module's pub declarations are visible to an importer. const std = @import("std");
@cInclude("header.h") Emits a C header include into the generated C for the module. Module level only. @cInclude("stdio.h");

@import needs no example beyond the chapter's own first line, const std = @import("std");. @cInclude is shown by cinclude.z98, whose include sits above the import: 

@cInclude("stdio.h");

const std = @import("std");

pub fn main() void {
    std.io.print("include ok\n", .{});
}

$ ./cinclude
include ok

The include leaves a mark in the generated C: the emitted module header contains #include "stdio.h" ahead of the module's forward declarations. It makes C declarations available to the generated code, which is why the standard library's own modules use it.

Group F: print (1)

The last entry is not spelled with an @, because it is not a builtin in the compiler's table: it is a compiler special case for calls whose callee is named print. The compiler parses the format string, checks each argument against its placeholder, and emits one print call per argument; the formatting bodies live in std.fmt, imported for you. This chapter has used it on almost every line above.

The full story — the five specifiers, tuple-literal arguments, and the error[3013] rejections — belongs to chapter 18. The one-line version: arguments must be a tuple literal, and the wrapper is std.io.print(fmt: [*]const c_char, ...) void.

Common mistakes

The mistakes below are the ones a reader arriving from modern Zig makes first. Each has a diagnostic or a corrected shape, and every diagnostic is a real capture.

Reaching for a builtin that does not exist here. The modern Zig surface is much larger than Z98's. @errorName, @typeName, @memcpy, @memset, and @min each reject on this compiler with the same message: 

error[3000]: unsupported builtin function

The mistake is not the intent; it is assuming the name carries over. Check the table before writing the call. The byte routines live in std.mem, and the remaining replacements belong to chapters 12, 16, and 18; printing a value's name is a chapter 18 topic.

Declaring anyerror. Modern Zig has a dynamic error type; Z98 does not. A signature that names it stops with: 

error[20]: identifier 'anyerror' is not declared or imported in this module

Write the set you mean, or use an inferred !T return. The same reason is why @errorName cannot exist: with no dynamic error type there is no runtime name table to index.

Putting @cInclude in a function body. The include is a module-level declaration. In statement position the compiler reports an internal diagnostic, and its span even points at line 1 rather than at the call: 

error[3020]: internal error: unhandled node kind in type resolution

Move it to the top of the file, above the imports. The placement rule is the whole fix.

Swapping @getChar and @putChar. The names are a one-letter pair and mean opposite things: @putChar writes a byte, @getChar reads one and blocks until the user types it. A program that calls @getChar in a batch run waits for input that will never come. This chapter never executes it, and neither should a test program that is meant to finish on its own.

Expecting @panic to return, or to be caught. It is typed noreturn: it writes panic: <msg> to stderr, then traps. There is no recovery path and no error tag to catch. If a program needs to end with a chosen status and a predictable transcript, use @exit, as exit.z98 does. And if you want to see a trap for yourself, do it in a program you are willing to lose.

Interleaving std.io.print with @putChar/@stdoutWrite and expecting call-order output. The two paths do not share a buffer: std.io.print writes through immediately, while @putChar and @stdoutWrite go through C's stdio and are flushed at exit. A program that alternates them prints the immediate lines first and the buffered lines last, whatever the source order. Keep one path per program — this chapter's programs do — or flush deliberately.

Forgetting that @intToPtr and @ptrFromInt differ. Both turn an integer into a pointer, but @intToPtr names the result type in the call while @ptrFromInt takes it from context, so the context must be typed. With no declared type the compiler has nothing to resolve against.
