Arrays and Slices

An array is the aggregate with only one thing to say about its elements: they all have the same type. The length is not a property of the value, it is part of the type itself: [5]i32 is five i32 values, no more, no fewer, and the compiler knows it. A slice is the pair that carries a pointer and a length at runtime, so a function can accept an array of any size through one parameter type. It is written []T: the [] is the length you do not know at compile time.

That pair is the reason this chapter exists. Up to now every value in the manual had a size fixed by its type. A slice is the first value whose length is a runtime number, and the rest of the language reacts to that: .len reads the length, .ptr reads the element pointer, slicing produces new slices from old ones, and const has to propagate through all of it so a read-only view cannot be laundered into a writable one.

The chapter's program is docs/sf/manuals/src/vol2/strings.z98. It builds an array, views it through a mutable slice, walks its .ptr, cuts closed and open-ended slices from it, reads a string literal as a byte slice, and hands a const view to a function that only reads: 

array len 5 last 50
slice len 5 first 15
ptr 15 30 50
mid 2 midtail 30 tail 40 none 0
hello z98 rocks len 9 bytes 122 115
view 17 8

Everything else about arrays and slices in this chapter is measured on the compiler shipped with this manual, and every diagnostic quoted below is the one the compiler actually prints.

A fixed-size array

An array type is written [N]T, where N is a compile-time constant and T is the element type. The length is part of the type. An array value is built with a literal; the untyped form infers the element type from the values the way a tuple literal does, and the spelled form writes the type in front: 

var scores: [5]i32 = .{ 10, 20, 30, 40, 50 };
var flags: [3]u8 = [3]u8{ 1, 2, 3 };

Both forms are interchangeable at the declaration. The spelled form [3]u8{ ... } is the one to reach for when the array sits inside a larger initializer — an array field inside a struct literal, for instance, must carry its element type, and the reason is one of the common mistakes below.

.len reads the compile-time length, and indexing goes from 0 to N - 1 with no pointers involved: 

std.io.print("array len {} last {}\n", .{ scores.len, scores[4] });
// array len 5 last 50

An index that is compile-time-known and out of bounds is rejected before any C is emitted, matching official Zig. Past the end: 

error[3062]: index 3 outside array of length 3

The same message is produced by arr[arr.len], because .len folds to the constant. A negative index is rejected by the type the index has to have: 

error[3062]: type 'usize' cannot represent integer value '-1'

A runtime index keeps a bounds check instead of a compile-time diagnostic; that check is a -fsafe feature and is discussed under the checks at the end of the slicing section.

An array bound with var is writable element by element, and an array bound with const is not: 

var scores: [5]i32 = .{ 10, 20, 30, 40, 50 };
scores[0] = 15;

const primes: [4]i32 = .{ 2, 3, 5, 7 };
primes[0] = 1;
// error[3002]: cannot assign to immutable variable

The array as a whole is a value; it is not a pointer, and it does not decay the way a C array decays in every expression. It coerces where a slice or a many-item pointer is expected — the assignments and call arguments measured in this chapter — and nowhere else: there is no arr.ptr, arithmetic on the array value is rejected, and a == b between two arrays is accepted but compares the two storage addresses rather than the contents. A probe's two identically filled arrays compared false. Compare lengths and elements explicitly; the comparison is a trap, not an equality test.

An array may also be a struct field. The field keeps its declared length, and .len works through the field; the program below uses no struct fields, but the chapter's probing did: 

const S = struct { tag: i32, data: [4]i32 };
var st: S = .{ .tag = 7, .data = [4]i32{ 1, 2, 3, 4 } };
std.io.print("field len {} first {}\n", .{ st.data.len, st.data[0] });
// field len 4 first 1

The [4]i32{ ... } spelling is not decoration there. With an untyped .{ ... } field initializer the compiler builds an anonymous tuple and then leaves the array field at zero, without a diagnostic; the measured behavior is in Common mistakes. Whole-field assignment after construction, st.data = [4]i32{ ... }, is a different shape that the probe also failed to emit buildable C for; write the elements or use a slice of the field when a bulk write is needed.

Slices: a pointer plus a length

A slice is written []T, or []const T for a read-only view. It is represented as two words, a pointer and a length; on this compiler @sizeOf([]i32) and @sizeOf([]const u8) are both 8, the 32-bit pointer plus the 32-bit length. Where an array's length is part of its type, a slice's length is a runtime value read through .len.

An array coerces to a slice where a slice is expected — in an assignment or a call argument — and the result points at the array's first element with the length filled in. The program leans on that to write through a mutable view: 

var scores: [5]i32 = .{ 10, 20, 30, 40, 50 };
var s: []i32 = scores;
s[0] = 15;
// slice len 5 first 15

The slice is a view, not a copy: the write at s[0] is the write at scores[0]. A slice is even more directly a cursor than an array, because a function can accept any length through the one type. The chapter's program does exactly that: 

fn total(values: []const i32) i32 {
    var sum: i32 = 0;
    for (values) |v| {
        sum += v;
    }
    return sum;
}

.ptr is the other half. On a []T slice it reads the element pointer, a many-item pointer [*]T, and a many-item pointer is indexed like a C array; on a []const T slice the same field is a [*]const T. The chapter's program prints three elements through it: 

var s: []i32 = scores;
const p: [*]i32 = s.ptr;
std.io.print("ptr {} {} {}\n", .{ p[0], p[2], p[4] });
// ptr 15 30 50

A mutable array can also coerce straight to a many-item pointer, as chapter 3 shows, but the slice is what carries the length with it. And a slice of a const view can never be written through. Indexing a []const T reads; storing reports the element as immutable: 

const view: []const i32 = primes;
view[3] = 9;
// error[3002]: cannot assign to immutable variable

The precise rule for what may coerce to what is the const-propagation table at the end of this chapter. The short version for slices: adding const is always allowed, discarding it is always error[3000]: cannot implicitly discard 'const' qualifier.

Slicing

A slice expression cuts a new slice out of an array or a slice — and, under the special rules below, out of a pointer. The form is base[start..end] with start inclusive and end exclusive, exactly the range notation chapter 8 used for tuple positions but with two runtime-capable bounds instead of one comptime ordinal. The end may be omitted; the start may not: 

const mid: []i32 = scores[1..3];    // two elements: 20 30
const tail: []i32 = scores[3..];    // two elements: 40 50
const none: []i32 = scores[5..5];   // the empty slice

The empty forms are legal: arr[len..] and arr[len..len] are slices of length 0, which makes a "cursor at the end" expressible without a special case. Omitting the start is not supported at all; arr[..2] does not parse: 

error[2000]: expected expression
error[2000]: unexpected token

A slice of a slice is just another slice expression, and the result type carries the original constness: slicing a []const T yields another []const T, and slicing a []T yields []T. Bounds are checked the same way at both levels.

On a pointer to an array, *[N]T, slicing is legal for every comptime or runtime bound. The result is the Z98 slice []T (a documented divergence from Zig's *[M]T), the pointer is the element pointer at start, and the length is end - start. An omitted end runs to the declared length, and pa[N..] is the legal empty slice. The dereferenced array is indexed directly as pa.*[i]: 

const pa: *[4]i32 = &arr;
const s1: []i32 = pa[1..3];
const s2: []i32 = pa[2..];
const s3: []i32 = pa[4..];
pa.*[0] = 11;
// pa slices 2 20 2 30 0
// pa.* 11 11

On a many-item pointer [*]T, the open-ended form mp[start..] is accepted and yields [*]T — the pointer offset by start, still with no length, because a many-item pointer has none. The closed form is a real slice the same way it is for an array: mp[start..end] yields a []T whose length is end - start; only the start <= end half of the runtime check can apply, because there is no length to compare the end against. Pointer offsetting that keeps the many-item type is written with pointer arithmetic, and chapter 3 covers that.

On a bare single-item pointer *T, slicing survives only for Zig compatibility, with three comptime-known shapes: p[0..0], p[0..1], and p[1..1]. The results are pointer-to-array values, and a for loop over them iterates the pointee, exactly as it does over any *[N]T: 

var sum: i32 = 0;
for (p[0..1]) |v| {
    sum += v;
}

const e = p[0..2];
// error[3067]: slice of single-item pointer must have bounds [0..0], [0..1], or [1..1]

const open = p[0..];
// error[3067]: slice of single-item pointer must be bounded

An untyped const binding of a rejected pointer slice also reports the pre-existing error[3000]: cannot declare variable of type void cascade, because the failed expression is typed void; the 3067 line is the slice rule that fired.

Indexing a bare *T is a separate strict reject; only many-item pointers and pointers-to-arrays support ptr[i]: 

const y = p[0];
// error[3066]: type '*i32' does not support indexing

Constant bounds on a fixed-size base are checked at compile time, so the classic off-by-one never reaches the runtime: 

const s = arr[1..5];   // error[3062]: end index 5 out of bounds for array of length 4
const t = arr[3..1];   // error[3062]: start index 3 is larger than end index 1
const u = arr[-1..2];  // error[3062]: type 'usize' cannot represent integer value '-1'

A closed range whose present end is runtime is not compile-checked, and a bound that is runtime keeps a runtime check instead of a diagnostic.

Runtime bounds checks

-fsafe is the default. Under it, a runtime index or a runtime slice range on an array or slice traps when the bound fails; the process dies with exit status 133 and prints no message of its own: 

var arr: [4]i32 = .{ 10, 20, 30, 40 };
var i: usize = 7;
std.io.print("{}\n", .{arr[i]});
// trap: exit status 133 under -fsafe

The same is true of the slice form arr[i..j] when a runtime bound fails either the start <= end check or the end <= len check. -ffast removes all of these guards: the same program runs to completion with whatever the out-of-bounds access produces. The chapter's probe built every binary with -fsafe (the default) and confirmed the 133 exit status on the failing shapes, then emitted -ffast and watched the check disappear.

Strings are byte arrays

A string literal is not a language-level string type. It is a constant array of bytes, typed *const [N]u8, and it coerces to the const forms a constant byte array can: []const u8, [*]const u8, or the legacy single-item pointer *const u8. The chapter's program binds it as a slice, reads its length, and walks its bytes: 

const hello: []const u8 = "z98 rocks";
const bytes: [*]const u8 = hello.ptr;
std.io.print("hello {s} len {} bytes {} {}\n", .{ hello, hello.len, bytes[0], bytes[8] });
// hello z98 rocks len 9 bytes 122 115

122 is the code for z and 115 is the code for s; a byte slice is an array like any other. Two printing forms matter here: {s} prints a byte slice as text, and {c} prints a single byte as its character. A for loop over a byte slice visits the bytes; the program's total function uses the same form over an i32 slice. Neither []u8 nor []const u8 is printable with plain {}.

Because the literal is constant, the mutable coercions are exactly the ones the const rules forbid: 

var s: []u8 = "abc";    // error[3000]: cannot implicitly discard 'const' qualifier
var p: [*]u8 = "abc";   // error[3000]: cannot implicitly discard 'const' qualifier

The third literal form, *const u8, is accepted but produces a level-0 warning from the declaration check: 

const one: *const u8 = "hello";
// warning[3000]: type mismatch in variable declaration -- initialization type
// may not be compatible with declared type
// note: source: pointer
// note: target: pointer

The program builds and runs; the warning is recorded rather than recommended. Bind to []const u8 and take .ptr when a single-item pointer is wanted.

Const propagation

The const qualifier travels with the view, and the coercions above are allowed or rejected by one rule: a conversion may add const, never discard it. The spec's table, measured on the compiler, is:

Conversion Result
[N]T (mutable binding) → []T / [*]T allowed
[]T → []const T / [*]const T allowed
[]T → [*]T allowed
[]const T → [*]const T allowed
[]const T → []T / [*]T error[3000]
const-bound [N]T → []T / [*]T error[3000]
"abc" → []u8 / [*]u8 error[3000]
&arr on a const array → []T / [*]T error[3000]

The reject is always the same level-0 diagnostic, at the site that would discard the qualifier: 

const ca: [3]i32 = .{ 1, 2, 3 };
var s: []i32 = ca;
// error[3000]: cannot implicitly discard 'const' qualifier

var p: [*]i32 = ca;
// error[3000]: cannot implicitly discard 'const' qualifier

Propagation follows the decay through slicing. Slicing a const array or a []const T produces a []const T, and the resulting slice rejects at the ordinary sites if a mutable target is expected: 

var s: []i32 = ca[0..];
// error[3000]: cannot implicitly discard 'const' qualifier

The same guarantee covers an array reached through a field of a const aggregate. A const-bound struct's array field materializes as a const element pointer, so the field, its slice, and its address all carry the qualifier: 

const S = struct { a: [3]i32 };
const cs: S = .{ .a = [3]i32{ 4, 5, 6 } };

const s1: []const i32 = cs.a[0..];   // accepted
const p1: *const [3]i32 = &cs.a;    // accepted

var s2: []i32 = cs.a[0..];
// error[3000]: cannot implicitly discard 'const' qualifier
var p2: [*]i32 = &cs.a;
// error[3000]: cannot implicitly discard 'const' qualifier

A mutable aggregate's field keeps its mutability — the probe wrote through m.a[0..] and read the new value back from the field — so the rule only bites where the storage itself is const-bound. Chapter 4's struct rules and this table together cover the conversion surface, and when a write is forbidden the conversion that would hide the fact is rejected before any C is emitted. The C89 backend still drops const from its output, so this is a frontend guarantee: the emitted C will happily express a write that the frontend rejects.

Honest note. The runtime check story is not uniform, and the exceptions are worth knowing. -fsafe traps runtime index and slice bounds and -ffast removes the guards, but a runtime bound of type i32 is neither rejected nor guarded: the compiler accepts arr[i..j] with negative runtime i32 values, and a probe with i = -1 ran to completion, built a three-element slice, and read before the array. A literal or folded negative bound still rejects with error[3062]; only the runtime signed shape slips through. Do not claim the guards make every runtime bound safe. The compile-time checks are solid, and [..end] is a parse error rather than a silent behavior. An array value has .len but no .ptr: scores.ptr is error[3060]: no field or member function named 'ptr' in array type, and a many-item pointer or a slice is the pointer spelling. Printing is narrow: {} on a slice rejects error[3013]: invalid print format specifier for the argument type, {} on an array rejects error[3063]: print argument type is not supported (no std.fmt printer), and {x} on a []const u8 rejects error[3063] as well; {s} is the byte-slice form. One documented residual survives from before this chapter: the address of an element of a const-bound array, &ca[0], still comes back as a mutable *i32 and a write through it reaches the storage, even though the same write spelled ca[0] = 9 is rejected. The aggregate-field form carries the qualifier correctly; the direct-binding residue is recorded in the language spec and not scheduled. Two shapes this chapter does not teach: a [2][3]i32 initialized and indexed as m[0][1] emitted C that the C compiler refused, and passing or returning a whole array by value did the same. Stay one-dimensional and hand slices across call boundaries until those shapes get their own revision.

The example

The whole chapter in one program. It declares an array, coerces it to a slice and writes through it, reads the element pointer, cuts closed, open-ended, and empty slices, reads a string literal as a byte slice, and passes a const view to a read-only function. It is docs/sf/manuals/src/vol2/strings.z98: 

const std = @import("std");

// A read-only view: the callee may look, but not write.
fn total(values: []const i32) i32 {
    var sum: i32 = 0;
    for (values) |v| {
        sum += v;
    }
    return sum;
}

pub fn main() void {
    // A fixed-size array: the length is part of the type.
    var scores: [5]i32 = .{ 10, 20, 30, 40, 50 };
    std.io.print("array len {} last {}\n", .{ scores.len, scores[4] });

    // An array coerces to a slice: a pointer plus a length.
    var s: []i32 = scores;
    s[0] = 15;
    std.io.print("slice len {} first {}\n", .{ s.len, scores[0] });

    // .ptr is the element pointer, a [*]T; index it directly.
    const p: [*]i32 = s.ptr;
    std.io.print("ptr {} {} {}\n", .{ p[0], p[2], p[4] });

    // Closed and open-ended slices of an array.
    const mid: []i32 = scores[1..3];
    const tail: []i32 = scores[3..];
    const none: []i32 = scores[5..5];
    std.io.print("mid {} midtail {} tail {} none {}\n", .{ mid.len, mid[1], tail[0], none.len });

    // A string literal is a constant byte array; []const u8 is its view.
    const hello: []const u8 = "z98 rocks";
    const bytes: [*]const u8 = hello.ptr;
    std.io.print("hello {s} len {} bytes {} {}\n", .{ hello, hello.len, bytes[0], bytes[8] });

    // A mutable array reads through a const view; slices of slices stay const.
    const primes: [4]i32 = .{ 2, 3, 5, 7 };
    const view: []const i32 = primes;
    std.io.print("view {} {}\n", .{ total(view), total(view[1..3]) });
}

Build the compiler once from the committed seed, then emit and compile the program, exactly as in chapter 3: 

bash scripts/seed/build_from_seed.sh release/seed/zig1-seed.tgz /tmp/manual_seed

The result is /tmp/manual_seed/zig1_5_clean with the standard library beside it in /tmp/manual_seed/lib/. This example compiles with no diagnostics; the program then runs to the end: 

$ mkdir -p /tmp/manual_out
$ /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol2/strings.z98
$ cd /tmp/manual_out && sh build_target.sh linux strings
Building for linux...
Built: strings
$ ./strings
array len 5 last 50
slice len 5 first 15
ptr 15 30 50
mid 2 midtail 30 tail 40 none 0
hello z98 rocks len 9 bytes 122 115
view 17 8

Six lines. The first reads the compile-time length and the last element of scores. The second writes 15 through the mutable slice and reads it back from the array, which is the same storage. The third walks the element pointer. The fourth mixes a closed slice (mid, two elements) and an open-ended one (tail, two elements) and confirms the empty scores[5..5] has length 0. The fifth treats the string literal as a byte slice: 9 bytes, first and last printed as numbers. The sixth sums the whole const view (17) and a const sub-slice (8) through a function that takes []const i32. The exit status is 0.

Common mistakes

The mistakes below are the ones a programmer arriving from C (or from a newer Zig) makes first with arrays and slices. Each one has a corrected shape, and the corrected shape is the compiler's rule, not a style preference.

Expecting C's decaying array pointer. In C an array name is a pointer in every expression; here it is a value. scores is not a [*]i32 unless the context asks for one, there is no scores.ptr (error[3060]: no field or member function named 'ptr' in array type), and the coercions are confined to assignment and call arguments. When a cursor is wanted, say so with a type: var p: [*]i32 = scores; or take a slice's .ptr. And use .len where C reaches for sizeof ... / sizeof ...; the count is already in the type. One C similarity is a trap rather than a feature: a == b on two arrays is accepted and compares addresses, so two identically filled arrays compare false. Compare .len and the elements.

Off-by-one slicing. The end index is exclusive. arr[1..3] is two elements; arr[3..] runs to the end; arr[len..] and arr[len..len] are the empty slice. Omitting the start does not parse at all (arr[..3] is error[2000]: expected expression), and constant bounds that cross a line are diagnosed rather than silently clamped: end index 5 out of bounds for array of length 4 and start index 3 is larger than end index 1, both error[3062].

Expecting mutation through []const T. A const view is a promise the frontend enforces: binding a const array or slice to a mutable target is error[3000]: cannot implicitly discard 'const' qualifier, and writing an element through a []const T is error[3002]: cannot assign to immutable variable. String literals are const arrays, so var s: []u8 = "abc"; is the same 3000. To write, own the storage: declare the array with var, write through it or through a mutable slice, and hand out []const T views when the callee should not write.

Writing .{ ... } for a struct's array field. The untyped literal is a tuple, and at a struct-field position the tuple is not copied into the array: the field compiles and is then left at zero. A probe printed field len 4 0 0 for a field initialized with .data = .{ 1, 2, 3, 4 }. Spell the element type — .data = [4]i32{ 1, 2, 3, 4 } — and the same probe prints 1 2 3 4. The typed spelling is the rule inside a larger initializer, such as a struct literal; whole-field assignment after construction is a separate shape the compiler does not yet emit correctly, so write the elements or assign through a slice.

Indexing a string literal directly. The literal itself is a pointer-to-array spelling, and the compiler's emitted C for indexing one does not build. const lit = "abc"; lit[0] and "abc"[0] both produce C that gcc rejects. Bind the literal to a slice first — const s: []const u8 = "abc"; s[0] — or slice it as "abc"[0..]; both are verified shapes.

Assuming {} prints an aggregate. It does not print an array or a slice: {} on a slice is error[3013]: invalid print format specifier for the argument type, {} on an array is error[3063]: print argument type is not supported (no std.fmt printer), and {x} on a byte slice is 3063 as well. Use {s} for a []u8/[]const u8 and index for the rest.
