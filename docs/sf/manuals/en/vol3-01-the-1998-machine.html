The 1998 Machine

The honesty spine of this volume is the six chapters from chapter 2 to chapter 7. This chapter stands in front of them, and it is an honesty chapter in form though not in subject. Where chapter 2 inventories what the language gives and withholds, this chapter inventories the machine the language is pointed at. It draws the envelope: the baseline 1998 PC, what you may assume about it, what you may not, and the one number that decides more designs than any other — its memory. Chapter 6, what you cannot do on a Pentium II, is the list of hard limits the envelope imposes. This chapter is the envelope itself.

Volume II measured the language on the seed-built compiler and pinned the target model it emits for. Volume III points that model at 1998 hardware. Before any of the era's discipline makes sense, you need a concrete picture of the machine on the other end: not “an old PC,” but a named processor, a named amount of memory, a named operating system, a named disk, and a named display. A design is measured against that picture, and a picture borrowed from the development host measures the wrong machine.

Era framing. Statements here about the era's processors, memory, display hardware, storage, and operating system are era context, and where a statement is an opinion the text says so. This host has no Pentium II and no Windows 95/98, so an era hardware claim cannot be run here; the text marks those as the era's facts and readings rather than measurements. Statements about Z98 are a different kind, and those are checked against docs/reference/Language_Spec_Z98.md, the compiler source, and the compiler built from the committed seed: the target model, the memory budget, and the measurement tool named below are the compiler's own.

What you expect

Two expectations arrive with a reader from a modern machine, and both need setting aside before the envelope can be read.

The first is that the target is vague: “an old PC,” defined by being slower than the machine in front of you. If the target is vague, the design responds to nothing in particular, and the first thing the era punishes is a design made for hardware no one named. The second expectation is subtler, and it is the one this chapter exists to correct. A reader assumes the constraint is the processor: a 233 MHz Pentium II is slow, so the work is to write code that does fewer operations. That reading is intuitive and it is wrong for this class of program. The processor is fast enough for the logic, the parsing, and the protocol work that the era's software is made of. What runs out first is memory.

The confusion is understandable, because on a modern machine memory is cheap and invisible: you ask for storage, the allocator finds it, and the cost shows up as a number in a profile rather than as a design constraint. On the baseline machine, storage is the constraint everything is measured against. Picture a program as a working set — code, static data, a framebuffer, buffers, and whatever the program allocates — and picture the machine as a fixed pool of bytes that the operating system also draws from. The program fits or it does not. Processor speed decides how fast a fitting program runs; memory decides whether it runs at all. That is the sentence this chapter is built to make true, and the sections below carry its arithmetic.

The baseline machine

The Pentium II is a 32-bit processor, little-endian, with a single execution core. The 233 MHz part was the entry model of the line introduced in 1997, and it is the processor the volume names; faster parts existed, and the baseline is the slower end on purpose. A program designed for the floor runs on everything above it, which is the only safe direction to design in when you do not know the exact machine a reader has. This is a marked opinion, and it is the manual's: target the baseline, and treat a faster processor as headroom rather than a requirement.

The operating system is Windows 95 or Windows 98. Both are 32-bit Windows systems with the Win32 API and a graphical shell, and the emitted C89 targets them in the same way the era's compilers did. The distinction between 95 and 98 matters less than the distinction from everything after them: the API surface is the one the emitted code is written against, the memory the OS leaves to a program is what the program actually gets, and the filesystem, the socket library, and the console are the era's versions. Chapter 8, Building for Win9x (planned) walks a program onto exactly this target.

The disk is IDE — the ATA interface the era shipped — and the phrase “IDE drives” in the blueprint is doing real work. It means the program's storage is a rotating magnetic disk with millisecond-scale seeks, not a solid-state device with microsecond ones, and it means the disk is the slowest thing in the machine by a wide margin. A design that reads from disk inside a frame, or scatters small reads across a file, spends its time waiting. The era's answer was to read in large sequential blocks, cache in memory, and keep the disk out of the hot path — which is the same argument as the memory budget, seen from the other side: memory is what buys you the freedom not to touch the disk.

The display is 640×480. The arithmetic of a framebuffer at that size is the cleanest way to feel the envelope. At 8 bits per pixel, 640×480 is 307,200 bytes — about 300 KB. At 16 bits per pixel it is 614,400 bytes — about 600 KB. Both fit comfortably in a 32 MB machine, which is exactly why 8-bit and 16-bit color were the era's working modes and why a modern 32-bit 1024×768 framebuffer (about 3 MB) was not. The resolution is not a preference to be raised when the design allows it; it is part of the envelope, and chapter 6 develops what fitting inside it costs.

What you can assume

These are the assumptions a program may make about the baseline. Each is either an era fact about the hardware or a Z98 fact about the emitted code, and each is safe to build on.

  • A 32-bit, little-endian, single-core processor. The width of a pointer is four bytes, and the target's integer and floating-point work is done by the processor itself.
  • Z98's target model matches the machine. The compiler emits for a 32-bit little-endian target with an 8-byte alignment model, pinned so the compiler's folded offsets and the running program's offsets agree. That is the model Volume II, chapter 4 worked through, and it is the Win9x-era ABI this machine uses.
  • An era C89 compiler exists on the far side. Z98 emits C89 deliberately, so the emitted code is compiled by the tools that actually ran on the machine — OpenWatcom, MSVC 6, or Borland — not by a modern toolchain that cannot be built there.
  • The Win32 API and its C89 runtime. Console, files, and networking are the era's versions, reached through extern declarations and @cInclude (chapter 11, planned; chapter 12, planned).
  • Integer and floating-point arithmetic at the era's cost. The processor does the work; floating point may be software-assisted on the cheapest parts, but the baseline can compute.
  • A 640×480 display at 8 or 16 bits per pixel. A software framebuffer at that size is a few hundred kilobytes, which the budget can carry.
  • One execution core. Concurrency on the baseline is cooperative, because two instruction streams on one core take turns (chapter 9, planned).

What you cannot assume

These are the assumptions that break a design when it makes them. They are the other half of the envelope, and they are the subject chapter 6 develops as hard limits with their ways over.

  • More memory than the baseline. The volume plans against 32 MB, shared with the operating system. A program that is comfortable on the development host can still be over the era's budget, because the host is not the target.
  • A modern display or 3D hardware. The baseline has no hardware 3D and a 640×480 screen. A design that requires the modern resolution, the modern texture, or the accelerator does not run on the floor machine.
  • Parallel speedup from threads. On one core, threads interleave rather than compute in parallel, so the work is the same plus the cost of switching and the locks. Cooperative coroutines are the era's model.
  • Modern operating-system services. There is no dynamic linking to modern shared libraries, no ready-made HTTP or TLS client, no package manager, and no debugger UI. Each has an era answer, and the answers are the rest of this volume.
  • Fast storage and fast network. The disk seeks in milliseconds and the network, when there is one, is thin. The program's I/O is designed around those latencies, not around the host's.
  • That the development host is the target. The compiler runs on Linux here and emits for the era machine; the two are not the same computer, and a measurement taken here is a hint, not a proof.

Why memory, not the processor, is the binding constraint

This is the load-bearing claim of the chapter, and the arithmetic makes it plain. A Pentium II at 233 MHz executes hundreds of millions of instructions per second. The era's programs — a game loop, a text protocol, a file converter, a small server — are logic-bound, not compute-bound: they make decisions and move small amounts of data, and the processor carries that work without strain. The reason a 1998 project failed to ship was almost never that the processor was too slow. It was that the program did not fit.

The bytes are the constraint because every part of the program draws from the same fixed pool. A 16-bit 640×480 framebuffer is about 600 KB. A single 32-bit 1024×1024 texture is 4 MB, and four of them are 16 MB — before the framebuffer, the working set, or a line of logic. A per-connection state block, a coroutine frame, a level's worth of map data: each is a line item, and the line items sum against 32 MB minus what the operating system holds. The processor's speed does not appear anywhere in that sum. You can add clock cycles; you cannot add bytes.

The failure modes confirm it. When memory runs out, an allocation fails: in Z98 that is a caught error.OutOfMemory from the arena (Volume II, chapter 14), not a silent null. On the era's operating system, a program that pushes past physical memory swaps to disk, and a swap to an IDE disk whose seeks take milliseconds turns a fast program into an unusable one. Either way the limit is memory, and the recovery is to fit — smaller resolution, smaller texture, shallower cache, fewer live objects — not to make the processor do more work per second.

Z98's angle here is structural, and it is why this chapter can call memory a design constraint rather than a warning. Storage in Z98 comes from an arena: one buffer the program declares, a bump cursor over it, and a single reset that reclaims everything. The amount of memory a phase can use is therefore a number in the program, not an emergent property of scattered allocations, and the compiler is held to the same discipline it asks of you: it operates within a 16 MB peak budget. The tool to see the number is built in. Run the compiler with --markers --track-memory and it reports the arena peaks it used: 

$ /tmp/manual_seed/zig1_5_clean --markers --track-memory -o /tmp/out docs/sf/manuals/src/vol2/arena.z98
track-memory: perm=61K mod=365K scr=254K pool=2475K type_db=31K total=680K

That transcript is from the compiler built from the committed seed on this host, and it is the concrete form of the claim. The arena example from Volume II measured a peak of 680 KB on this compiler; the compiler itself, self-hosting, is held to a 16 MB peak budget. The point for the 1998 machine is the one the whole chapter is making: memory is something you can see, size, and spend deliberately, because the language gives you the buffer and the tool rather than an allocator that finds bytes somewhere. Chapter 16, Memory budgets (planned) does the arithmetic in full.

Honest note. The single most useful number on this page is 32 MB, and it is the number a modern reflex treats as a detail. On the baseline machine it is the whole design. Processor speed decides how fast a program that fits will run; memory decides whether it runs at all. If a design is in trouble, the first question is not “can this be made faster?” but “what is this spending, and on what?” — and the arena and --track-memory are how the era answers it.

The trade

Read the assumptions and the arithmetic together and one trade appears. The machine is a fixed envelope, and designing inside it buys two things: the program runs on the machine the project set out to serve, and it stays small enough to understand. The era's software was shaped by this discipline, and the programs that are remembered are largely the ones designed to the machine rather than against it. A 300 KB framebuffer and a few megabytes of working set force a design that a machine with a gigabyte never has to make, and the forced design is usually the clearer one.

The paying side is that the envelope does not move. The resolution you wanted, the texture you wanted, the parallel speedup you wanted: none of them are available, and no choice of language conjures them back, because they are properties of the machine and not of the compiler. That is the honesty of this chapter. The reward for respecting the envelope is that the program ships; the cost is that some ambitions are cut at design time rather than discovered later, on the target, as a failure.

Where the machine's limit is genuinely a language's job, Z98 does something about it — the arena bounds storage, the coroutine replaces the thread, std.net provides the socket. Where the limit is the hardware, no language helps, and the chapters on C89, C++98, and assembly say so plainly: the other tools run on the same processor, use the same memory, and write to the same display. Swapping the language does not raise the envelope.

The way over it

The way over the machine's limits is a habit, not a library, and it starts before the first line of code. Stated as rules:

  • Write the envelope down. Resolution and color depth, a memory ceiling for the whole program, the processor, and the operating system. Every later decision is measured against those terms. This is the page you just read.
  • Choose content to the envelope. Textures, audio, geometry, entity counts, and connection counts are chosen against the ceiling at design time, where a small texture is an artistic decision rather than a late optimization.
  • Make storage explicit. Declare the buffer, hand an arena over it, and size it deliberately. A phase's memory is a line item you can read, not an emergent total you discover in a crash.
  • Measure in the target's terms. --track-memory reports the arena peaks; measure before the envelope is breached, not after. Chapter 16 (planned) is the full method.
  • Keep the disk out of the hot path. Read in large blocks, cache in memory, and let the memory budget pay for the caching. The disk is the slowest part of the machine.
  • When the limit is the hardware, cut the feature — never the checks. A bounds check or an error path traded for a kilobyte is a bug purchased with a design decision. When something does not fit, the feature goes.

Six rules, and the first one is the subject of this chapter. The rest are the volume: chapter 8 builds for the operating system, chapter 9 brings the cooperative model, chapter 16 budgets the memory, and chapter 6 names the limits each rule answers.

Common mistakes

The chapter has no code sample, because the envelope is not fixed by code. The mistakes below are the ones a reader makes when the machine is treated as a detail rather than as the target.

Defining the machine by its processor. “An old PC” is not a target. The baseline is a named processor, a named memory size, a named operating system, a named disk, and a named display, and each one changes the design. A program written for the processor and not the memory is written for the wrong constraint.

Optimizing cycles before bytes. A faster algorithm helps only after the program fits. A 4 MB texture is 4 MB no matter how clever the loop around it; the first question is what the program spends on storage, not how many instructions it executes.

Trusting the development host. This host is not the target. A program that is comfortable here can still be over the era's memory budget, and an I/O pattern that is instant here can stall there. Measure the program the way the target would, with the budget in front of you.

Designing to an accelerator instead of the floor. The baseline machine may or may not have a 3D card. A program that requires one does not ship to the baseline; target the small software path and treat the accelerator as an optional improvement, which is what the era's own dual-path games did.

Spending memory without naming it. On the baseline, storage that is not a declared buffer is storage you cannot size, measure, or reset. Reach for the arena and --track-memory, not for a habit of allocation that assumes bytes are free.

Reading from disk inside the frame. The IDE disk is the slowest part of the machine. A design that touches it in the hot path spends its time waiting; read in blocks, cache in memory, and keep the disk where it belongs.
