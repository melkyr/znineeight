Memory Budgets

Chapter 1 made the claim this chapter has to pay for: on the 1998 machine, memory — not the processor — is the binding constraint. A Pentium II at 233 MHz has cycles to spare for the logic a program is made of; what it does not have is bytes. The number to design against is therefore a memory number, and the discipline of this volume is the discipline of staying inside it.

There are two budgets in that sentence, and they are not the same budget. There is the compiler's budget: the tool that turns your Z98 into C89 is itself held to a peak-memory target, and it ships the instrument to measure that. And there is your program's budget: the number of bytes you, the author, decide the program may spend when it runs on the target. This chapter is the accounting for both. It shows how the compiler's budget is stated, how to read the peaks it reports, how the arena is organized into tiers, how the compiler trades disk for RAM when you ask it to, and when — and only when — loosening the compiler's memory gate is the right answer.

The blueprint gives this chapter no sample program, and none is needed. The subject is a discipline, and the evidence is the compiler's own measurements. Every transcript below is a real run on this host: the seed-built compiler (v89, fixed point 8216fedc…) profiling the Volume II arena example, then compiling itself. The numbers reproduce; the addresses and timings do not, which is why none of them appear.

What is measured here. The compiler under test is the seed build /tmp/manual_seed/zig1_5_clean, fixed point 8216fedc8dd69db084d453be80f3c010. The two workloads profiled are the Volume II arena example (docs/sf/manuals/src/vol2/arena.z98, a program whose whole point is a declared byte buffer) and the compiler's own source (sf/src/main.zig, the heaviest workload the toolchain has). All peaks are the compiler's allocator high-water marks, printed by --track-memory; the live in-use figures are copied from the same runs. If a number here and a number you measure differ in the kilobyte, the compiler or the source has moved, and the method — not the constant — is what to keep.

Two budgets, one of them a policy

Start with the compiler's budget, because it is the one written down in the source and the one a reader is most likely to misread. The compiler carries two constants named for the peak memory it is designed to run within on the target machine: 

pub const DEV_MAX_MEM: usize = 16 * 1024 * 1024;
pub const RELEASE_MAX_MEM: usize = 16 * 1024 * 1024;

That is the 16 MB target-build policy: sixteen mebibytes (16 × 1024 × 1024 bytes) is the peak the compiler is built to hold when it runs on the 1998 machine, the same machine your compiled program runs on. It is a policy, not a promise the host gate enforces by default, and that distinction is the whole of this section.

The host binary you run on the development machine defaults to a different number: 64 MB. The command-line gate — -mm<N>, N in decimal megabytes — is initialized from a constant named DEFAULT_MAX_MEM_KB, and its value is 64 × 1024. So when you run the compiler without thinking about memory, the limit it actually checks against is four times the target policy. The two numbers answer two different questions:

Number Where it lives What it is for
16 MB DEV_MAX_MEM / RELEASE_MAX_MEM, sf/src/allocator.zig The target-build policy: the peak the compiler is designed to hold on the 1998 machine. A design statement about the era, not the default of a host run.
64 MB DEFAULT_MAX_MEM_KB, applied to cli.max_mem The host default gate: the ceiling a development-host compile is stopped at unless you pass -mm<N>. Generous on purpose, because the host is not the target.

Why the gap? Because the target policy is a statement about live memory on a machine the compiler must share with Windows, and the host gate is a tripwire on a coarser number — the whole bump-pool high-water, which we will see is several times larger than the live figure. Setting the host gate at the target's live budget would make the compiler refuse to build itself on this host, where the pool high-water is legitimately above 16 MB. The honest reading is the one this chapter keeps: 16 MB is the policy for the machine; 64 MB is the default for the host; they are not interchangeable. If you set -mm16 on the host because “the target is 16 MB,” you will trip the gate on a normal self-compile, and the next section shows exactly that.

Profiling with --track-memory

The instrument is built in. The compiler carries a memory profiler that reports the peak of each arena tier at the end of a compile, and it is turned on with two flags, not one. The rule is the one chapter 15 stated in its note: --track-memory emits through the same channel as --markers, so it only shows anything when --markers is on as well. Both flags, or nothing. Here is the arena example, profiled: 

$ /tmp/manual_seed/zig1_5_clean --markers --track-memory -o /tmp/manual_out \
      docs/sf/manuals/src/vol2/arena.z98
track-memory: perm=61K mod=365K scr=254K pool=2475K type_db=31K total=680K

One line, six fields, and every field a peak in kilobytes rather than a running total. Drop --markers and the profiler is silent — the compile still succeeds, it simply says nothing about memory: 

$ /tmp/manual_seed/zig1_5_clean --track-memory -o /tmp/manual_out \
      docs/sf/manuals/src/vol2/arena.z98
$ echo $?
0

That is a deliberate design, not a bug: the profiler shares the marker channel so that a diagnostic build pays for one output path, and the marker channel is off unless asked for. The pairs are the whole memory toolkit: --markers --track-memory for the peaks, and --markers alone for the running commentary behind them. Read the profiler's numbers as belonging to the compiler at the moment it emitted that program. They are not your program's runtime memory; they are the memory the compiler spent turning your source into C. The two are related only through the size and shape of what you wrote.

Read the arena line field by field, because the field names are the compiler's own and they recur everywhere the memory model is discussed:

Field Tracks Arena example
perm The permanent tier: data that lives for the whole compile — interned strings, the module registry, types that survive every phase. 61K
mod The module tier: per-module and per-phase data that is reset between phases, the AST and the lowering structures included. 365K
scr The scratch tier: short-lived working memory, reset aggressively during analysis so the peak is dominated by the largest single function, not by their sum. 254K
type_db The type registry's own table — the store that gives every type its stable id. 31K
pool The high-water of the single byte pool the tiers are carved from. It includes growth slack and the tiers not named above, so it is larger than total. 2475K
total The sum of the three headline tiers, perm + mod + scr — the live in-use figure the target policy is really about. 680K

The arithmetic checks: 61 + 365 + 254 = 680, so total is exactly the three-arena sum. And pool (2475K) is larger than total because it is a different measurement: the raw high-water of the one pool the compiler allocates all of its growable tiers from, which carries the growth slack each tier asked for and the tiers the line does not name. Keep the two apart and the line is unambiguous: the tiers are where the bytes went; pool is how far the underlying pool was pushed.

The arena tiers, and the ones the line does not show

The three headline tiers are the compiler's own instance of the arena discipline: a small permanent tier for what never dies, a module tier for what dies with a phase, a scratch tier for what dies with a function. It is the dual-arena pattern of Volume II chapter 14, extended to three, because a compiler has two natural lifetimes to reclaim at rather than one. The reasoning is the same as the chapter that introduced it: data with different lifetimes should not share a fill level, or you can never reset the short-lived tier without losing the long-lived one.

The --track-memory line reports the peaks of the three headline tiers, the type registry, and the pool. It does not report every internal tier, and the reason is worth knowing because it is the same reason the debugger chapter gave: the compiler's internals are visible through --markers if you ask, and the tier names are in that stream. Filter the markers to the arena reports and the fuller set appears: 

$ /tmp/manual_seed/zig1_5_clean --markers -o /tmp/manual_out \
      docs/sf/manuals/src/vol2/arena.z98 2> markers.txt
$ grep -a '^arena ' markers.txt | sort -u
arena diag_read: grew ...
arena import_scratch: grew ...
arena module: grew ...
arena perm: grew ...
arena scratch: grew ...
arena type_db: grew ...

Those are the tiers that announce their growth: perm, module, scratch, and type_db as before, plus import_scratch (module-resolution working memory) and diag_read (the diagnostics store). The line each one writes is its growth, not its peak — the profiler prints the peak at the end, the markers narrate the journey. Between them you have the compiler's memory model in two views: where the bytes went, and when each tier asked for more.

The design that makes the tiers pay off is the reset. On this compiler the scratch tier and the module tier are reset at phase boundaries, which is why the self-compile's live figure stays small even though the total work is large. The same lever in your own program is std.arena.reset, and it is the subject of the last section of this chapter. The principle is uniform: a tier with a lifetime should be reset at the boundary of that lifetime, and the permanent tier should never be reset at all.

The 16 MB claim, measured

Now the claim itself. The compiler's heaviest workload is compiling its own source. Run it with the profiler and read the live figure and the pool figure together. At the default spill level (-s0, all spills on disk — the next section explains that flag), a full self-compile reports: 

$ /tmp/manual_seed/zig1_5_clean --markers --track-memory -s0 \
      -o /tmp/manual_out sf/src/main.zig
track-memory: perm=981K mod=1022K scr=1024K pool=20644K type_db=346K total=3027K

Read the two last numbers as the two halves of the claim. The live in-use total is 3027K, a little under 3 MB — comfortably inside the 16 MB target-build policy, and that is the claim that reproduces: the compiler's three live arena tiers self-host in single-digit megabytes. The pool high-water is 20644K, a little over 20 MB, which is larger than the target policy — and that is the claim that does not reproduce, because pool is not the live figure. The pool carries the growth slack and the unnamed tiers, which is exactly why the host gate defaults to 64 MB and not to 16.

The distinction is not a dodge; it is testable in one command. Force the host gate down to the target policy and watch it stop the build on the pool number, not the live number: 

$ /tmp/manual_seed/zig1_5_clean --markers --track-memory -s0 -mm16 \
      -o /tmp/manual_out sf/src/main.zig
memory limit exceeded: pool limit=16384K pool=20644K
$ echo $?
3

The gate compares the pool high-water to the limit and aborts the compile with status 3 when it is over. At -mm16 the pool figure (20644K) exceeds the limit (16384K) and the compile stops, even though the live figure is 3 MB. That is the mechanism, and it is honest about what it measures: a conservative host tripwire on the pool, standing in for the live budget it cannot cheaply observe. The compiler's own budget policy lives in the constants; the runtime gate is a coarser instrument that defaults high so it does not fire on ordinary host work.

Two smaller points settle the rest of the claim. First, the user-program case reproduces trivially: compiling the arena example, whose entire runtime working set is a 32-byte and a 64-byte buffer, costs the compiler 680K of live arena and a 2475K pool high-water. Whatever your program spends at run time, the compiler's cost to emit it is in this range unless the program is very large. Second, the live total at the default spill level is dominated by the three tiers in roughly equal measure — about a megabyte each on the self-compile — which is the shape the three-arena design predicts. There is no single tier hoarding the budget.

Disk or RAM: the -s spill ladder

The compiler's memory does not only depend on the input. It has a switch that trades disk for RAM, and the switch is the reason the host gate defaults to 64 MB. During a compile the compiler keeps six spill stores — intermediate structures it would rather write to a temporary file than hold in memory. The -s<N> flag chooses how many of those six live in RAM instead of on disk, from -s0 (all on disk) to -s6 (all in RAM). Higher levels are faster and larger; emission is identical in every mode, because the same data is merely stored differently. Measured on the self-compile:

Level Spills in RAM pool total At the 64 MB default
-s0 none — all on disk 20644K 3027K rc 0
-s1 AST 57433K 18389K rc 0
-s2 AST, LIR 127641K 18389K rc 3 — needs -mm128
-s6 all six 133785K 18389K rc 3 — needs -mm0

The table tells the story that makes the 16 MB policy concrete. At the default -s0, the compiler keeps the spills on disk and the live arena total is 3027K — the fit-the-target setting. Move the first spill into RAM and the live total jumps to 18389K, a little over 18 MB, because the AST spill alone is a 16 MB module-tier allocation. The pool high-water climbs from 20 MB to 57 MB at -s1, then past the default gate at -s2. So the default is the target setting: all spills on disk, live total in low single-digit megabytes, and the disk pays the price in temporary-file I/O. The higher levels are a host convenience — trade I/O for speed — and they cost memory in exactly the way the target cannot afford.

The switch is strict about its input. The valid range is 0 to 6; a bare -s, a non-digit, or an out-of-range level is a clean command-line error with status 1, not a silent fallback: 

$ /tmp/manual_seed/zig1_5_clean -s7 -o /tmp/manual_out docs/sf/manuals/src/vol2/arena.z98
error: -s<N> spill level out of range (0..6: 0 = all on disk, 6 = all in RAM)
$ /tmp/manual_seed/zig1_5_clean -s -o /tmp/manual_out docs/sf/manuals/src/vol2/arena.z98
error: -s<N> requires a decimal level 0..6 (e.g. -s0 all on disk, -s6 all in RAM)

The per-level smoke test is the spill-file ladder: the temporary file for a spill disappears from the working directory once that spill is promoted to RAM. -s1 leaves no AST spill file, -s2 also leaves no LIR spill file, and so on to -s6, where the compiler writes no spill files at all. If you ever need to confirm which mode actually ran, the files on disk are the evidence.

When -mm0 is the right answer

The -mm<N> gate was built to stop a runaway allocation before it eats the host. There is a case where the right move is not a bigger number but the removal of the ceiling altogether, and that case is -mm0. Zero is not “zero megabytes”; it is the switch that tells checkCombinedPeak to fall back to the static pool's own size as the limit. The pool is a fixed 256 MiB reservation, so -mm0 means “the only limit is the pool itself” — effectively no gate. The source says it in one line: 

return mb * @intCast(u32, 1024); // -mm0 -> 0 (checkCombinedPeak's max_mem==0 relax path)

That is why -mm0, not -mm128, is the call for the heaviest host run. The all-RAM self-compile peaks at 133785K, above 128 MB, so even -mm128 is too small for it; -mm0 lets it finish: 

$ /tmp/manual_seed/zig1_5_clean --markers --track-memory -s6 -mm0 \
      -o /tmp/manual_out sf/src/main.zig
track-memory: perm=981K mod=16384K scr=1024K pool=133785K type_db=562K total=18389K
$ echo $?
0

So when is -mm0 right? When you are deliberately running the compiler at a heavy setting on the development host — the all-RAM -s6 above, or a workload whose pool high-water you have decided the host can carry — and the gate is standing between you and the run rather than protecting anything. It is a host tool: it says nothing about the target. Never reach for -mm0 to make a build “fit a 1998 machine”; the pool ceiling is a property of the host binary, not of the era hardware, and the number that matters for the target is the live figure the same command prints.

Prefer the smallest switch that works. -mm0 is the blunt instrument; -mm128 is the scalpel when 128 MB is genuinely enough. And note that a small gate is useful, not hostile: run the arena example at -mm2 and the compiler stops on the pool figure it exceeds, which is exactly the early warning the flag exists to give: 

$ /tmp/manual_seed/zig1_5_clean -mm2 -o /tmp/manual_out docs/sf/manuals/src/vol2/arena.z98
memory limit exceeded: pool limit=2048K pool=2475K
$ echo $?
3

The rule of thumb: leave the default alone for ordinary work, raise it to the measured need with a named -mm<N> when you know it, and use -mm0 only when you have decided no gate is wanted for that run on that host.

Your own budget: the arena tiers at scale

The compiler's discipline is the pattern; your program is where you apply it. On the target, Volume II chapter 14 gave you the arena — one declared buffer, a bump cursor, a reset — and the dual-arena rule: a permanent arena for what lives for the whole run, never reset, and a scratch arena for per-phase work, reset at every phase boundary. At scale, the pattern is the same rule with more tiers, and the accounting is the compiler's own accounting applied to your buffers.

The arithmetic is the point, so do it in bytes before the code exists. On the baseline machine the pool is 32 MB shared with the operating system, which leaves far less than 32 MB for the program. Every byte the program asks for — the framebuffer, the level data, the per-connection state, the coroutine frames — comes out of that share. The three-arena shape turns "how much memory does this program use?" from a discovery into a sum: the permanent buffer plus the largest scratch buffer plus whatever the other tiers hold, all numbers you wrote down. The total field of the compiler's profile is the same arithmetic, one tier per line.

At scale the second tier is not enough for every program, and the honest answer is to add a third rather than enlarge the first. A server that handles many connections wants a per-connection tier whose lifetime is one connection, sitting between the permanent tier and the per-phase scratch: a connection's buffers come from its own arena, and when the connection closes that arena resets and the bytes return at once, without touching the permanent data or waiting for a phase boundary. The coroutine chapter already uses exactly this shape for its child frames: a per-task pool whose Context occupies the first 16 bytes of a caller-supplied buffer, with the frames drawn from the bytes after it, each frame rounded to 8 bytes. That is a tier with a lifetime, backed by a buffer you declared, reset when the task ends — the same move as the compiler's module tier, at connection scale.

The sizing rule follows from the lifetimes. Ask three questions of every buffer: how long does it live, who resets it, and what is the largest single phase or connection it must hold. A buffer whose answer is “the whole run” goes in the permanent arena and is sized once. A buffer whose answer is “one phase” or “one connection” goes in a tier that resets at that boundary, and is sized for the peak of a single phase — not the sum of all phases, because the reset means they never coexist. That last phrase is the memory the dual-arena pattern pays for: sizing the scratch tier for one phase instead of all of them is the whole return on the discipline.

Two habits keep the accounting honest. First, keep the disk out of the hot path by spending memory deliberately — the same trade the compiler makes with -s0, seen from the other side: bytes held in RAM are I/O not paid. Second, measure with the instrument, not by feel. There is no --track-memory for your own program — the profiler reports the compiler's arenas, not yours — but your program is an arena, and arena.used and arena.capacity are public fields you can print at any boundary, exactly as the Volume II example does. The compiler's line is the pattern; arena.used is yours.

Honest note. The 16 MB target is a policy, and the honest reading of the measurements is narrower than the slogan. The compiler's live arena tiers self-host in about 3 MB at the default spill level, well inside the target; its raw pool high-water is about 20 MB, which is why the host gate defaults to 64 MB, and setting the gate to 16 MB on the host stops the build. Neither number is a lie and neither is the whole truth: the policy is what the compiler is designed to hold on the 1998 machine, the gate is a coarser host tripwire, and the only way to know which you are looking at is to run --markers --track-memory and read total beside pool. On the target, the number that decides whether your program ships is the same discipline at the scale of your own buffers: size each tier to its lifetime, reset it at the boundary, and spend the ceiling deliberately rather than discovering it in a failed allocation.

Common mistakes

The chapter has no sample program, but the memory discipline has a small set of failures that account for most of the confusion. They are listed in the order they are usually made.

Running --track-memory without --markers. The profiler emits through the marker channel, so the pair is required. Without --markers the compile succeeds and prints nothing, and the natural conclusion — “the numbers are unavailable” — is wrong. Pass both flags.

Confusing the 16 MB target policy with the 64 MB host default. The policy is what the compiler is designed to hold on the 1998 machine; the default is the tripwire a host run uses. They are different numbers on purpose, and setting -mm16 on the host because the target is 16 MB makes ordinary host work fail. Keep the two apart.

Reading pool as live memory. pool is the raw high-water of the underlying byte pool, growth slack included; total is the live sum of the three headline tiers. The target budget is about live memory, so total is the figure to compare against 16 MB, and pool is the figure the host gate checks. They are not interchangeable.

Assuming the compiler's profile is your program's memory. --track-memory reports what the compiler spent emitting your program, not what your program spends when it runs. A program with a tiny source and a huge runtime buffer compiles cheaply and runs expensively; the profile will not show you the runtime cost. Track that with your own arena.used.

Leaving the spills in RAM on the machine that cannot afford them. The default -s0 keeps all six spills on disk and the live total small. Raising -s trades disk for speed and moves the AST spill — a 16 MB allocation — into RAM, pushing the live total over the target policy. Use the higher levels on the host, not when measuring the target.

Reaching for -mm0 to “make it fit.” Zero lifts the gate to the static pool ceiling. It is a host convenience for a run you have decided the host can carry, not a way to fit a program onto the era machine. Prefer the smallest -mm<N> that works.

Treating a small -mm gate as the enemy. A gate that stops a compile is doing its job. Run a large program at -mm2 and the compiler names the pool figure it exceeded and exits with status 3; that is the early warning, not a defect.

Forgetting to reset the scratch tier. An arena never reclaims on its own. A per-phase tier that is never reset climbs to its capacity and every later allocation fails with error.OutOfMemory even though the phase data is long dead. Reset at the boundary, not when the arena is full — the lesson of Volume II chapter 14, restated here because memory budgets are where it stops being hygiene and starts being arithmetic.
