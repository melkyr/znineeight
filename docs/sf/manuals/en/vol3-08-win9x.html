Building for Win9x

The first seven chapters of this volume were about the machine and about the language. This chapter is about the step in between them: taking a program you have already written and turning it into something the 1998 machine can run. There is exactly one flag for that, -osw, and the chapter is mostly about what the flag writes into the output directory, what those files mean, and what the program does when it starts on Windows.

The good news is the same fact this volume keeps returning to. The source does not change. A Z98 program is a Z98 program; -osw chooses the emitted build scripts and the emitted target header, not a second dialect. The sample for this chapter is Volume I's hello, adapted by one line, and it compiles and prints on the Linux host and on a 32-bit Windows target from the same text. What changes is everything around the source: the scripts, the runtime, and the machine you finally run it on.

That last machine is the one thing this chapter cannot put in front of you directly. There is no Pentium II on the development host. So the chapter is explicit about the evidence at every step. The Linux run is real. The Windows run is real, but it is the program under wine on a 32-bit cross-build, not Windows 98. The OpenWatcom build script is real, and it is emitted but not run here. The screenshot will be captured on the real machine, and it is the figure at the foot of the page. Keeping those three kinds of evidence separate is the whole honesty of a chapter like this one.

What -osw writes

Start with the command and its output directory, because the scripts are the subject. The compiler emits C89 plus a small set of runtime and platform files, and it writes a build script beside them so you do not have to remember the flags. Emitting a program for the Windows target is one command: 

$ mkdir -p out
$ /tmp/manual_seed/zig1_5_clean -osw -o out hello.z98

-osl is the Linux target and it is the default; -osw is the Windows target. The flag is target selection, not code generation: the C89 emitted for a given program is the same shape in both cases, and the guard macros discussed below are what the target adds. In the output directory you now find the emitted translation units and headers, the runtime pair, and three build scripts, one per era toolchain:

Script Toolchain What it does
build_target.sh gcc (Linux) or mingw (Windows) one script, two targets; the default is the Linux host, and sh build_target.sh mingw cross-compiles the Windows binary
build_target.bat MSVC cl the Windows command-prompt build, compiled with cl and linked with link
build_owc.bat OpenWatcom wcc386/wlink the OpenWatcom 32-bit build, the classic era toolchain

The mingw branch is the one this host can actually run, and the flags matter because they are the contract between the emitted C and the compiler that builds it. The branch reads: 

  mingw)
    CC=i686-w64-mingw32-gcc
    CFLAGS="-m32 -std=c89 -O0 -Wall -Wno-long-long -Wno-pointer-sign -Wno-implicit-function-declaration -I ."
    LDFLAGS="-m32"
    LIBS="-lwsock32"
    [ -n "$OUT" ] || OUT=prog.exe
    ;;

Read the flags as the era story. -m32 pins the 32-bit ABI. -std=c89 -O0 asks for the C89 dialect with no optimization, which is what the emitted code targets. The three -Wno- switches turn off warnings the emitted C89 would otherwise raise under a modern gcc: long long (not in C89), pointer-sign mismatches, and implicit function declarations. The -Wno-implicit-function-declaration is the one that corresponds to the interop rule from chapter 5: a bare non-variadic extern gets no emitted prototype, so the generated call is technically an implicit declaration. The header fix is the correct code; the switch keeps the supported build quiet. The mingw branch here carries -lwsock32 because this dump emitted the std_net module (you can see std_net_A15200CC.c in the output directory), and that module references Winsock even though the program never opens a socket. A program whose emitted set omits std_net needs no socket library.

The MSVC and OpenWatcom scripts encode the same idea with the era's own flags. The MSVC script compiles with cl /c /Za /W3 /WX /DZIG_WIN32 /I . and links with link /subsystem:console kernel32.lib … wsock32.lib. The OpenWatcom script uses wcc386 /za /we /dZIG_WIN32 /i=. and wlink system console op q opt stack=65536 … library wsock32. /Za and /za are the two compilers' "strict ANSI" switches, the counterparts of -std=c89; /WX and /we are their warnings-as-errors switches, and both scripts say so in a comment so a warning can be downgraded without giving up the build. The /DZIG_WIN32 and /dZIG_WIN32 are the target guard, which is the next section. The MSVC link line and the OpenWatcom wlink line both pull wsock32.lib for the same reason the mingw branch carries -lwsock32.

One more thing about the script set is worth saying plainly, because it is the boundary of everything that follows. The emitted scripts are the interface to three toolchains. On this development host, exactly one of those toolchains is installed. i686-w64-mingw32-gcc is present and is used below; cl is not runnable here, and neither is wcc386. The two Windows-only scripts are therefore emitted and documented, not executed in this chapter's evidence. The chapter shows their exact text and their flags so you can run them on the era machine; it does not pretend it ran them.

The source, and the same source twice

Here is the whole sample. It is Volume I's hello with a second and third line added, so the transcript has enough shape to prove it ran: 

const std = @import("std");

// The same source builds for the Linux host and for the 32-bit Windows 9x
// target. Nothing here is conditional: -osw chooses the emitted build scripts,
// not the source, and the program prints the same text on both machines.
pub fn main() void {
    std.io.print("Hello from Z98!\n");
    std.io.print("this is Volume III, chapter 8\n");
    std.io.print("built for the 1998 machine\n");
}

There is no #ifdef in it, no platform import, and no call to a Windows-only function. That is deliberate. A program that uses nothing but std.io.print should build unchanged on both targets, and the first proof of the chapter is that it does. The Linux baseline is captured first, because it is the parity target for the Windows run: 

$ mkdir -p out && /tmp/manual_seed/zig1_5_clean -o out hello.z98
$ cd out && sh build_target.sh linux hello
Building for linux...
Built: hello
$ ./hello
Hello from Z98!
this is Volume III, chapter 8
built for the 1998 machine

The build prints a page of -Wunused-function warnings from the shared runtime header — the runtime carries helpers a given program may not use, and gcc notices. They are omitted above for length; they are warnings, not errors, which is why the script's policy is warnings-not-errors. The three output lines are the baseline that the Windows transcript must match.

What the emitted C looks like

Before the Windows run, read the emitted C, because the guards live there and not in the source. Every Z98 function is mangled and every call is an ordinary C call. The sample's whole main translation unit is short enough to quote: 

#include "hello_9C12B390.h"
/* main */
void zF_EA90E208_main(void) {
    char* zT_0;
    unsigned char* zT_1;
    char* zT_2;
    unsigned char* zT_3;
    char* zT_4;
    unsigned char* zT_5;
    zT_1 = "Hello from Z98!\n";
    zT_0 = zT_1;
    zF_16378A88_print(zT_0);
    zT_3 = "this is Volume III, chapter 8\n";
    zT_2 = zT_3;
    zF_16378A88_print(zT_2);
    zT_5 = "built for the 1998 machine\n";
    zT_4 = zT_5;
    zF_16378A88_print(zT_4);
    return;
}

int main(void) {
    zF_780653D2___module_init();
    zF_780653D2___module_init_1();
    zF_EA90E208_main();
    return 0;
}

The zF_ prefix and the hash are the identifier mangling chapter 3 introduced and chapter 5 used to warn you not to try to override a function by its source name. The main at the bottom is the one plain name the linker needs, and it calls the module initializers and then your main. This is C89 a 1998 compiler can read: no // comments, declarations at the top of the block, no C99 features.

The target guard is in the shared headers, not in the sample. The emitted zig_compat.h defines the calling-convention macro from the guard, so the same emitted C gets the right convention on each compiler — and gets an empty macro off Windows, which is what keeps the Linux emission byte-identical: 

#if !defined(_WIN32)
#define Z98_STDCALL
#elif defined(_MSC_VER) || defined(__WATCOMC__)
#define Z98_STDCALL __stdcall
#else
#define Z98_STDCALL __attribute__((stdcall))
#endif

The emitted net_prelude.h selects the socket headers the same way: the _WIN32 branch includes <windows.h> and <winsock.h>, the other branch includes the POSIX socket headers, and the _os aliases that map std_net's public names to the real OS symbols are declared after the include so they never rewrite an OS header. Both headers show the same principle: _WIN32 is a macro the toolchain sets, and the emitted C is written to be correct under it. It is not a Z98 keyword, and the source never sees it.

The ZIG_WIN32 guard and WINVER

There are two guards in the picture and it helps to keep them apart. _WIN32 is the C toolchain's own macro, and the emitted headers use it to pick a branch, as shown above. ZIG_WIN32 is the guard the emitted Windows build scripts define on the command line — /DZIG_WIN32 for cl, /dZIG_WIN32 for wcc386, and it is the marker that says "this build is the Windows target". The bootstrap-era platform_win98.h header and its _MBCS define are gone: they belonged to an older tree, and they are not in this compiler's source and not in the emitted C. What the current target emits instead is the ZIG_WIN32 guard in the scripts, plus the _WIN32 branches in the headers.

There is one place where the emitted C does define Windows version macros, and it is worth naming because a reader coming from the bootstrap era will ask about it. For a module that uses the @console* builtins, the emitter writes a version block ahead of <windows.h>. Here is the head of the emitted translation unit for docs/sf/manuals/src/vol2/builtins/console.z98: 

#include "console_B29CA079.h"
#ifdef _WIN32
#define WINVER 0x0410
#define _WIN32_WINDOWS 0x0410
#define _WIN32_WINNT 0x0400
#define NTDDI_VERSION 0x04000000
#define WIN32_LEAN_AND_MEAN
#include 
#else
#include 
#endif
extern void std_print_len(const char* s, unsigned int len);

So the measured reality is narrower than the old bootstrap story and wider than "no version macros at all". The bootstrap's platform_win98.h and _MBCS are gone; WINVER 0x0410 is emitted, together with _WIN32_WINDOWS, _WIN32_WINNT, NTDDI_VERSION, WIN32_LEAN_AND_MEAN, and <windows.h>, but only for modules that use @console*. 0x0410 is Windows 98. The definition is guarded by #ifdef _WIN32 so the Linux branch is unaffected, and it is at sf/src/c89_emit.zig:2816 in the compiler source. A plain std.io program like this chapter's sample does not trigger it; the block appears only when a console builtin is used.

Z98 can also ask the target question in source, with the compile-time builtin @isWindows(), which the Language Spec defines as a folded predicate that is true only for the Windows target. It is not needed in the sample, but it is the source-level counterpart of the emitted guard, so it is worth showing it verified. The probe is a single if: 

const std = @import("std");

pub fn main() void {
    if (@isWindows()) {
        std.io.print("this build targets Windows\n");
    } else {
        std.io.print("this build targets the host\n");
    }
}

Built for the Linux target, it prints the host line; built with -osw and cross-compiled, the same source prints the Windows line. Both are real runs on the seed compiler: 

$ /tmp/manual_seed/zig1_5_clean -o out win.z98
$ cd out && sh build_target.sh linux win && ./win
this build targets the host

$ /tmp/manual_seed/zig1_5_clean -osw -o out win.z98
$ cd out && sh build_target.sh mingw win && wine win.exe
this build targets Windows

The predicate folds at compile time, so it costs nothing at run time and the unused branch is not emitted. This is the honest way to write the rare program that must differ by target: put the difference behind @isWindows() in the source. What you should not reach for is a ZIG_WIN32 test in Z98 source; ZIG_WIN32 is a build-script define, and the language-level question is @isWindows().

The Windows cross-build and run

Now the run that proves the program survives the trip. This host has i686-w64-mingw32-gcc and a 32-bit wine prefix at /tmp/wine32, and the committed harness scripts/win32_cross/ composes the whole pipeline: it dumps the C89 with -osw, cross-compiles every emitted translation unit with mingw, links the executable, runs it under wine, and compares the captured stdout with the Linux baseline. The entry is given repo-relative because module resolution is relative to the working directory: 

$ ZIG1=/tmp/manual_seed/zig1_5_clean PARITY_STRIP_CR=1 \
    WINEPREFIX=/tmp/wine32 WINEARCH=win32 \
    bash scripts/win32_cross/cross_parity.sh \
    docs/sf/manuals/src/vol3/hello.z98 /dev/null \
    /tmp/manual_win/hello.linuxstdout /tmp/manual_win/hello
XRUNRC=0
WINE_RC=0
PARITY=OK

Three verdict lines, and each one is a distinct claim. XRUNRC=0 means the dump and the mingw compile and link all succeeded. WINE_RC=0 means the Windows executable ran to completion under wine. PARITY=OK means the captured stdout matches the Linux baseline. That is the whole of the Windows verification on this host, and it is the strongest statement the chapter can make without the era machine.

One detail of the comparison is worth understanding rather than trusting. This program writes through the C runtime's text mode, so Windows translates each \n into \r\n. The raw captured stdout has carriage returns; with PARITY_STRIP_CR=1 the harness strips them from a copy and compares the LF-normalized bytes, while keeping the raw file as evidence. The raw Windows stdout for this run is exactly: 

Hello from Z98!^M
this is Volume III, chapter 8^M
built for the 1998 machine^M

where ^M is the carriage return. Stripped of those, it is byte-for-byte the Linux output above. This is the normal result for a CRT-path program, and the harness records whether the comparison was normalized so there is no ambiguity later.

Era framing. The Windows run above is wine on a 32-bit mingw cross-build, not Windows 98. It proves the emitted C89 compiles with a Windows toolchain and that the program logic runs when executed, which is what the harness can prove on this host. It does not prove behavior under the era kernel, and the chapter does not claim it does. Statements here about the era's toolchains and machine are era context; statements about Z98 are checked against docs/reference/Language_Spec_Z98.md, the compiler source, and the compiler built from the committed seed.

OpenWatcom, cl, and the era toolchains

The reason there are three build scripts instead of one is that the era had more than one C compiler, and the one you used depended on what you already owned. MSVC cl came with Visual C++; Borland had its own; and OpenWatcom's wcc386/wlink pair was the tool many people reached for because it was cheap, fast, and produced tight 32-bit code. Z98 emits a script for each so the program can be built on whichever toolchain is on the machine. The OpenWatcom script is the one the volume's later chapters lean on, so read it in full: 

@echo off
REM build_owc.bat - generated by zig1 (OpenWatcom wcc386/wlink)
setlocal
if "%~1"=="" (set OUT=prog.exe) else (set OUT=%~1)
echo Compiling...
wcc386 /za /we /dZIG_WIN32 /i=. hello_9C12B390.c
wcc386 /za /we /dZIG_WIN32 /i=. std_io_59DB29D9.c
wcc386 /za /we /dZIG_WIN32 /i=. std_net_A15200CC.c
wcc386 /za /we /dZIG_WIN32 /i=. zig_runtime.c
wcc386 /za /we /dZIG_WIN32 /i=. zig_pal.c
wcc386 /za /we /dZIG_WIN32 /i=. c_exit.c
echo Linking...
wlink system console op q opt stack=65536 file hello_9C12B390.obj,std_io_59DB29D9.obj,std_net_A15200CC.obj,zig_runtime.obj,zig_pal.obj,c_exit.obj library wsock32 name %OUT%
echo Built: %OUT%

/za is strict ANSI, /we turns warnings into errors, /dZIG_WIN32 is the target guard, and /i=. makes the current directory the include root. The link asks for a console subsystem, a 64 KB stack, and wsock32. For an OpenWatcom user this is the build, start to finish, and it is the script the socket-using samples in chapter 10 and chapter 12 (planned) are built with on the real machine.

And here is where the chapter has to be exact about its own evidence. wcc386 is not installed on this development host. The script above is emitted by the compiler, quoted from the actual output directory, and verified as text; it is not executed. Nothing in this manual should be read as saying OpenWatcom was run. The same applies to MSVC's cl: the build_target.bat is emitted and quoted, and it is not executed here. Only the mingw cross-build and the wine run above were executed. This is the honest split the whole volume uses: the mechanism is verified on the host, the era toolchain is documented and deferred to the machine.

It is also why the OpenWatcom dialect is named as friction in chapter 7. wcc386 accepts C89, not gcc's dialect, and the emitted C89 is written to the intersection so a strict C89 compiler can read it. That is the same reason the flags include /Za and -std=c89: the target is the strict dialect, not the convenient one.

Running it on the era machine

The last step is the one the host cannot take. Move the output directory to the 1998 machine, run the script that matches the toolchain installed there, and execute the binary. The chapter's figure is that moment: a Windows 98 command prompt showing hello.exe run from its build directory, printing the three lines. Everything before it — the same source, the mangled C, the guard, the cross-build, the parity — is what makes that moment unremarkable, which is the point.

Most readers will not have a Pentium II either, and the honest alternative is an emulator. 86Box is the usual choice: it emulates a period-correct 32-bit PC, including the BIOS, the IDE disk, and the VGA card, and it can run Windows 95 or 98 closely enough for a console program. It is a different kind of evidence from wine: wine reimplements the Win32 API on Linux, while 86Box runs the real operating system on emulated hardware, so it exercises the era's own command.com and CRT. This chapter names 86Box as the practical path to the figure and does not claim to have run it here; the emulator, the era OS image, and the screenshot are all part of the figure's capture, on the figure's machine. The wine run above is the host-side proof that the program itself is correct.

Honest note. A cross-build under wine is not Windows 98, and an emulator is not the era's hardware either. This chapter is careful to say which one each claim rests on: the emitted C89 compiling with a Windows toolchain and the program logic running are proven here by mingw and wine; the build scripts for MSVC and OpenWatcom are emitted and quoted but not run here; and the real machine is the figure. When you ship, the machine that matters is yours. Build with the script that matches your toolchain, run it there, and let the screenshot be the proof rather than this page.

Common mistakes

The mistakes below are the ones that come from a modern build habit rather than from Z98 itself.

Looking for a Windows header in the source. There is nothing to include. The sample has no #ifdef and no platform import; -osw adds the target's headers and guards to the emitted C. If you reach for a Windows type in Z98 source, you are in chapter 11's territory (planned) — that is interop, and it comes with its own rules.

Claiming OpenWatcom or MSVC was run because the script exists. The compiler emits all three scripts on every -osw emit, whether or not the toolchain is installed. On a Linux host only the mingw branch is runnable. Quote the scripts as documentation; do not describe them as executed.

Testing ZIG_WIN32 in portable code. ZIG_WIN32 is a command-line define the build script passes to the C compiler, not a Z98 symbol. The source-level target predicate is @isWindows(). Using the script define in the wrong place is the mistake the two-guard section above exists to prevent.

Expecting the Windows stdout to be byte-identical without normalization. The CRT text mode turns \n into \r\n on Windows. For a program on the std.io.print path the comparison is LF-normalized, and the raw file is kept. A program that writes through the PAL WriteFile path keeps strict byte parity; know which path your program is on before you call a parity mismatch a bug in the emission.

Moving one file instead of the output directory. The emitted program is not a single .c. It is a directory of translation units, the runtime pair, the platform files, and the build script, and the script compiles all of them with -I .. Copy the whole directory to the era machine; carrying one file loses the runtime and the build fails at link time.

Assuming -osw changes the language. It changes the target's build scripts and emitted headers, not the parser or the type checker. A program that compiles for Linux compiles for Windows unless it uses a platform-specific extern or builtin. If a change is needed, it is in the source and it should be behind @isWindows(); the flag alone will not paper over it.
