Optionals

Chapter 12 gave failure a place in the type: an error union is "a value, or an error". This chapter gives absence a place in the type. An optional is "a value of type T, or null", written ?T. It is the language's answer to the question C answers with a sentinel: the search that did not find the key, the list whose end is marked by a special pointer, the number that is "not set".

An optional is not an error channel, and chapter 12's note about orelse said why: orelse belongs here, and catch belongs there. This chapter makes that separation concrete. It shows the three ways an optional is consumed — with orelse, with an if capture, and with a while capture — and it measures what an optional costs: every ?T is a two-field C struct, even when T is a pointer. The chapter's program is docs/sf/manuals/src/vol2/lookup.z98, a small linked list of key/value entries; its lookup returns ?*Entry, and the program consumes that result every way the language allows.

Honest note. You will reach for a sentinel pointer; here is the Z98 way. The C habit is to return NULL, or -1, or a pointer to a static "empty" object, and to trust every caller to recognise the value. Z98 moves the absence into the type: ?T says "a T, or null", and the compiler makes you unwrap before you use it. The two unwraps name the two intents directly — orelse supplies the value to use instead, and a capture binds the value that is actually there. The cost is measured and real: the representation is a payload plus a flag for every optional, including ?*T, so on the 32-bit target an optional pointer is twice the size of the pointer it wraps. That is the trade: a uniform shape and a four-byte flag in exchange for absence the compiler can see.

?T, null, and the implicit wrap

An optional type is written with a question mark in front of the payload type: ?i32 is "an i32 or nothing"; ?*Entry is "a pointer to Entry or nothing". The one literal is null. A plain value of type T coerces to ?T automatically, so the only time a value needs a special spelling is when it is absent: 

var x: ?i32 = null;
if (x == null) {
    std.io.print("x is absent\n", .{});
}
x = 42;
std.io.print("x now {}\n", .{x orelse -1});
x = null;
if (x == null) {
    std.io.print("x is absent again\n", .{});
}
const y: ?i32 = 7;
std.io.print("y {}\n", .{y orelse -1});
// x is absent
// x now 42
// x is absent again
// y 7

The comparison forms are == null and != null; both are ordinary boolean conditions, measured above and in the chapter's example. There is no separate "has value" operator and no way to ask for the value without naming what happens when it is missing. Assigning null to an optional that already holds a value is legal and returns it to the absent state, which the probe shows as x is absent again.

The wrap is one-way and cheap; the unwrap is where the interesting forms live. orelse is the next section, and the capture forms are chapter 10's subject, revisited below with the optional type in view.

The representation: one struct, pointers included

The compiler represents an optional as a C struct with two fields: the payload and an int flag that says whether the payload is live. The chapter's program prints the sizes first, and this is its first line: 

sizes: ?i32=8 ?u8=8 ?*Entry=8 *Entry=4

Two things are visible there. First, the size does not track the payload width: ?u8, whose payload is a single byte, is 8 bytes, because the C struct is the payload plus padding plus the four-byte flag. Second, and the point of this section, ?*Entry is 8 bytes while *Entry is 4: an optional pointer is not a pointer. It is the same two-field struct as every other optional, with a pointer in the value field. The emitted definitions for the chapter's types: 

typedef struct { int value; int has_value; } zT_45E16F0B_Opt_6;
typedef struct { zT_9CBFED33_Entry* value; int has_value; } zT_3BE2184E_Opt_61;

The mangled names are irrelevant; the shapes are the claim. There is no special case for pointers: no reserved null value, no sentinel, no tag packed into the low bit. The compiler has exactly one optional representation, and ?*T uses it like everything else.

That is a deliberate difference from official Zig 0.15.2, where an optional pointer is the same size as the raw pointer because the all-zero address doubles as null. Measured side by side for the same type: the sample's ?*Entry=8 *Entry=4 above, against ?*Entry=8 *Entry=8 from the official compiler on the development host. Z98 trades the extra bytes for one uniform rule that a C89 emitter can render without per-type decisions. On the 1998 target, where a pointer is four bytes, this is the difference between a free absence and one that costs two words.

The safe build does not let a bad unwrap slip through at run time either. In the emitted C for the chapter's lookup, each payload read is guarded: 

if (!(cur.has_value)) { pal_trap(); }
e = cur.value;

The guard is part of the -fsafe null-unwrap check; it compiles away under -ffast, where a null optional read is undefined instead. The next sections are about writing code that never needs the guard to fire.

orelse: the fallback operator

expr orelse fallback yields the payload when expr is present, and evaluates fallback when it is null. The value form supplies a value of the payload type directly. The chapter's program uses the same lookup twice, once with a hit and once with a miss, and the fallback entry shows which branch produced the printed value: 

const found = lookup(head, 10) orelse &fallback;
std.io.print("orelse hit: {}\n", .{found.value});
const missing = lookup(head, 99) orelse &fallback;
std.io.print("orelse miss: {}\n", .{missing.value});
// orelse hit: 1
// orelse miss: -1

The fallback can also be a block, which is the form to use when the absent case is an exit rather than a substitute value. The chapter's valueOrZero returns zero from the block when the lookup misses: 

fn valueOrZero(head: ?*Entry, key: i32) i32 {
    const e = lookup(head, key) orelse {
        return 0;
    };
    return e.value;
}

A block that falls off its end is not the shape to design around: a labeled block that breaks with a value is not implemented in Z98 (chapter 10 documents the value-less labeled block), so use the value expression when a value is what you have, and the block when the fallback is a return or a loop exit.

orelse requires an optional operand, and the compiler keeps it apart from catch. Applied to an error union it rejects, exactly as chapter 12 documented: 

error[3016]: orelse requires an optional operand; use 'catch' for error unions

The rule is one line: ?T takes orelse; E!T takes catch. If an operation can fail, the failure belongs in an error union; if it can be absent, the absence belongs in an optional.

Unwrapping with if and while

The capture is the second unwrap. Chapter 10 introduced the syntax; here is the optional's half of it. An if on an optional binds a payload only on the branch where the value exists, and the else arm handles the absent case. The chapter's program captures a lookup result: 

if (lookup(head, 20)) |e| {
    std.io.print("if: key 20 value {}\n", .{e.value});
} else {
    std.io.print("if: key 20 missing\n", .{});
}
// if: key 20 value 2

The capture is also an expression, with the else arm required when the value is used in a value position. The binding is an immutable copy, as chapter 10's capture section showed (error[3002] for an assignment through it), and it is an ordinary value of the payload type, so field access on it works because the optional is gone by then.

A while capture loops as long as the optional has a value. That is the shape for walking a chain whose end is null. The chapter's lookup walks the linked entries that way, and the program repeats the form at the call site: 

fn lookup(head: ?*Entry, key: i32) ?*Entry {
    var cur = head;
    while (cur) |e| {
        if (e.key == key) return e;
        cur = e.next;
    }
    return null;
}

var walk = head;
while (walk) |e| {
    std.io.print("walk {} {}\n", .{ e.key, e.value });
    walk = e.next;
}
// walk 10 1
// walk 20 2
// walk 30 3

The loop variable is reassigned through e.next each iteration, and the loop ends when the variable becomes null; the copy bound in |e| stays immutable. The ?*T chain type is the replacement for the sentinel-terminated list: the tail is a value the type system knows about, not a pointer that happens to be special.

There is no .? unwrap operator and no field access through an optional. Both shapes are rejected, and the two diagnostics measure the boundary: 

std.io.print("{}\n", .{p.value});
// error[3000]: cannot access field on optional type; use .? to unwrap first

std.io.print("{}\n", .{p.?.value});
// error[2000]: expected field name or index after '.'

The first message is the type checker pointing at the right concept, and the second is the parser saying the spelling does not exist. The two live unwraps are the capture and orelse; a program that wants the payload has to choose one of them.

The example

The whole chapter in one program. Three entries form a short linked list whose tail is null; lookup returns ?*Entry; valueOrZero uses the orelse block; main consumes the lookup with an if capture, a value and a block orelse, the two null comparisons, and a while capture that prints the chain. The size line at the top is the representation section's evidence. It is docs/sf/manuals/src/vol2/lookup.z98: 

const std = @import("std");

const Entry = struct {
    key: i32,
    value: i32,
    next: ?*Entry,
};

fn lookup(head: ?*Entry, key: i32) ?*Entry {
    var cur = head;
    while (cur) |e| {
        if (e.key == key) return e;
        cur = e.next;
    }
    return null;
}

fn valueOrZero(head: ?*Entry, key: i32) i32 {
    const e = lookup(head, key) orelse {
        return 0;
    };
    return e.value;
}

pub fn main() void {
    var third = Entry{ .key = 30, .value = 3, .next = null };
    var second = Entry{ .key = 20, .value = 2, .next = &third };
    var first = Entry{ .key = 10, .value = 1, .next = &second };
    var fallback = Entry{ .key = 0, .value = -1, .next = null };
    var head: ?*Entry = &first;

    std.io.print("sizes: ?i32={} ?u8={} ?*Entry={} *Entry={}\n", .{ @sizeOf(?i32), @sizeOf(?u8), @sizeOf(?*Entry), @sizeOf(*Entry) });

    if (lookup(head, 20)) |e| {
        std.io.print("if: key 20 value {}\n", .{e.value});
    } else {
        std.io.print("if: key 20 missing\n", .{});
    }

    const found = lookup(head, 10) orelse &fallback;
    std.io.print("orelse hit: {}\n", .{found.value});
    const missing = lookup(head, 99) orelse &fallback;
    std.io.print("orelse miss: {}\n", .{missing.value});

    std.io.print("block: 30 -> {} 99 -> {}\n", .{ valueOrZero(head, 30), valueOrZero(head, 99) });

    const absent = lookup(head, 99);
    if (absent == null) {
        std.io.print("absent == null\n", .{});
    }
    const present = lookup(head, 30);
    if (present != null) {
        std.io.print("present != null\n", .{});
    }

    var walk = head;
    while (walk) |e| {
        std.io.print("walk {} {}\n", .{ e.key, e.value });
        walk = e.next;
    }

    head = null;
    if (head == null) {
        std.io.print("head nulled\n", .{});
    }
}

Eleven lines. The size line is the representation claim in numbers. The if capture finds key 20. The two orelse lines show the present and absent branches of the same expression; the block form answers 30 -> 3 and 99 -> 0 through valueOrZero. The null comparisons report both directions. The three walk lines are the while capture following the next pointers until the tail's null. The exit status is 0.

Common mistakes

The mistakes below are the ones a programmer arriving from C makes first with absent values. Each has a measured diagnostic or a corrected shape, and each corrected shape is the compiler's rule, not a style preference.

Reaching for a sentinel pointer. The C version of the chapter's program ends its list with a magic pointer, returns NULL from the search, and maybe documents that -1 means "not found" in some other function. Every caller has to know all of the conventions, and the compiler knows none of them. In Z98 the absence has one spelling, null, and one type, ?T. The chain's tail is a null the type system sees, the lookup returns ?*Entry, and the caller cannot use the result without choosing orelse or a capture. There is no sentinel value to collide with, because there is no sentinel.

Using orelse on an error union. orelse is the optional's operator, and E!T is a different type. The compiler rejects the confusion and names the right tool: 

error[3016]: orelse requires an optional operand; use 'catch' for error unions

When the operation can fail, write catch; when it can be absent, write orelse. Chapter 12 is the other half of the rule.

Dereferencing a null optional. There is no direct path: field access on an optional is rejected before any code is emitted, with error[3000]: cannot access field on optional type; use .? to unwrap first. The bypass a C programmer reaches for is to assert the value is there — p orelse unreachable — and the compiler takes that at its word. A measured probe declared a null ?*Node, unwrapped it that way, compiled cleanly, and then trapped when it ran: Trace/breakpoint trap, exit status 133, no message, under both -fsafe and -ffast. The absent case is not free, it is just moved to where you chose to ignore it. Capture it or supply a fallback instead.

Expecting .? to work because the error suggests it. The error[3000] message above says "use .? to unwrap first", but .? does not parse: 

error[2000]: expected field name or index after '.'

The message names the right idea and the wrong spelling. The unwraps the language actually has are orelse, if (opt) |v|, and while (opt) |v|; use one of those, and the message never comes back.

Assigning through a capture. The capture is an immutable copy of the payload, not a handle back into the optional. Writing to it is rejected with error[3002]: cannot assign to immutable variable, the same rule as chapter 10's other captures. To advance a loop, assign the loop variable itself — walk = e.next; in the example — not the binding inside the bars.
