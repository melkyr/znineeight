I/O and HTTP

The I/O modules are imported by path: @import("std_file.zig"), @import("std_stream.zig"), and their companions. They are not part of the thirteen-name std re-export list. std_file owns an OS handle and is binary-safe; std_stdin reads lines and all input from process stdin; std_stream composes line and frame readers over file and socket sources; and std_http is a small HTTP/1.1 client.

The file, stdin, and stream layers never allocate behind the caller's back: std_file allocates only for readAll and directory names, std_stream never allocates at all, and std_http allocates its parsed result from a caller arena. The OS-specific work lives in the std-side PAL support files, not in the compiler PAL.

std_file

std_file is a binary-safe file layer built on OS handles. On Win32 it opens through CreateFileA, sizes and seeks with the profile-aware helpers, and uses the Win9x FindFirstFileA/FindNextFileA backend for directory iteration. On POSIX it uses open, read, write, fsync, close, unlink, and rename, with 64-bit seeking. read returns zero at end of file, not an error; write may write fewer bytes than requested, so writeAll loops.

Directory names are copied into the caller's arena on each readDir and are not NUL-terminated. The source does not filter . or ..; callers that do not want them must skip those names themselves. On Linux a DT_UNKNOWN entry falls back to a stat of the joined path to decide is_dir. openDir also copies the path into the arena on the POSIX path so that fallback can use it.

Use readAll for a whole small file, and bounded read plus seek for large media instead of materializing the whole payload. The mtime result is intended for resume sidecars. A worked introduction is on Volume V, Read, write, exists.

std_stdin

std_stdin wraps process stdin as a std_file.File and reads through the file layer. readLine reads one byte at a time so it never consumes past the line terminator. It strips the terminating \n, and the \r of a \r\n pair, and returns a slice into the caller's buffer. At EOF with no partial line it returns null. A line longer than the buffer returns a full buffer and leaves the rest of the line for the next call; the module carries boundary state so an exact-multiple long line does not produce a spurious empty line. A zero-length buffer is a panic.

Name Signature / declaration Returns / error Purpose
StdinError pub const StdinError = error{OutOfMemory, Io}; error set The module's one error set; Io is a read failure.
readLine pub fn readLine(buf: []u8) StdinError!?[]u8 StdinError!?[]u8; null at EOF with no partial line Read one line into buf, stripping its terminator.
readAll pub fn readAll(arena: *arena_mod.Arena) StdinError![]u8 StdinError![]u8 Read all of stdin into one arena allocation grown by doubling.

readLine allocates nothing and returns a view into the caller's buffer. readAll is the only allocating function, and it uses the caller's arena. Both propagate a read failure as error.Io.

std_stream

std_stream composes line and frame readers over caller-owned resources. It never allocates: the caller supplies the accumulation buffer, and a returned line or frame aliases that buffer until the next call. Each source has a blocking sync function and a cooperative async function. The async path yields with @asyncSuspend(null) when a read is incomplete or would block, and the caller re-drives it on the next scheduler tick. The module does not own or run a scheduler.

The line readers strip \n and the \r of \r\n, return the final unterminated line at EOF, and return an overlong line as a full-buffer prefix without creating a spurious empty line. MsgReader reads a big-endian u32 length prefix, then that many bytes. A declared length larger than buf.len is error.FrameTooLarge. A zero-length frame is valid and returns an empty slice, not null. EOF in the prefix or body returns null. For the coroutine setting, see Volume III, A coroutine program.

std_http

std_http is a minimal HTTP/1.1 client with no TLS. The source supports Content-Length and close-delimited bodies; chunked transfer encoding and keep-alive are not implemented and a chunked response is rejected. The header block is capped at 8 KB and the body at 1 MB. The pure functions are parseUrl, percentEncode, and parseResponse; get is the network entry point. The module is the tracker client behind z9torr.

parseUrl allocates nothing: its four slices point into the caller's input. percentEncode, parseResponse, and get allocate from the supplied arena. In a parsed response the header name and value slices point into the raw response, while the header array and the body are copied into the arena. get passes timeout_ms to the connect and select paths and follows a 301, 302, 303, or 307 redirect once if a location header is present. The socket layer it uses is std.net.
