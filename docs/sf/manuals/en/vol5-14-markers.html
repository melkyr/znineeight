Trace with Markers

This guide turns on the compiler's marker channel with --markers, captures the stream to a file, and reads it to see what the compiler did while it built a program.

Prerequisites

  • The compiler rebuilt from the seed at /tmp/manual_seed/zig1_5_clean, with the standard library beside it in /tmp/manual_seed/lib/. If it is not there yet, follow Rebuild the compiler from seed first.
  • The repository checked out, so the sample docs/sf/manuals/src/vol2/arena.z98 is present. Every command runs from the repository root, /workspace/znineeight.
  • A POSIX shell with grep. The marker channel is text on standard error, so the only other tool needed is a way to filter it.
  • No prior guide is required. This is the compiler-side half of Debug the generated C, which debugs the binary; markers debug the build that produced it.

Steps

  1. Turn on the channel. --markers is the only switch; without it the compiler writes nothing to the marker channel. Redirect standard error to a file, because the stream is longer than a terminal should show. The compiler creates files but not the output directory, so create it first: 

    $ cd /workspace/znineeight
$ rm -rf /tmp/manual_markers
$ mkdir -p /tmp/manual_markers
$ timeout 120 /tmp/manual_seed/zig1_5_clean --markers -o /tmp/manual_markers docs/sf/manuals/src/vol2/arena.z98 2> /tmp/markers.txt
$ wc -l /tmp/markers.txt
2206 /tmp/markers.txt

    Two thousand lines from one small compile. The same compile without the flag is silent on that channel: 

    $ rm -rf /tmp/manual_plain
$ mkdir -p /tmp/manual_plain
$ timeout 120 /tmp/manual_seed/zig1_5_clean -o /tmp/manual_plain docs/sf/manuals/src/vol2/arena.z98 2> /tmp/plain_err.txt
$ wc -l /tmp/plain_err.txt
0 /tmp/plain_err.txt

    The flag is parsed in sf/src/main.zig:149, where it calls pal.markersEnabled(1). The markers and the compiler's diagnostics both go to standard error, so always redirect the stream when a compile might also emit an error.

  2. Read the top of the stream. It shows the pipeline phases in order: allocation, then the type registry, then the string interner. 

    $ head -28 /tmp/markers.txt
arena perm: grew 4096 -> 16384
arena perm: grew 16384 -> 32768
arena perm: grew 32768 -> 65536
DC:k0n0t0
DC:k1n0t1
DC:k2n0t2
DC:k3n0t3
DC:k4n0t4
DC:k5n0t5
DC:k6n0t6
DC:k7n0t7
DC:k8n0t8
DC:k9n0t9
DC:k10n0t10
DC:k11n0t11
DC:k12n0t12
DC:k13n0t13
DC:k14n0t14
DC:k15n0t15
DC:k16n0t16
DC:k33n0t17
DC:k34n0t18
DC:k35n0t19
DC:k31n0t20
DC:k40n0t21
INT:new1
INT:new2
INT:new3

    arena <name>: grew <old> -> <new> is an allocator bucket growth; the named arenas — perm, module, scratch, type_db, import_scratch, diag_read — are the compiler's own memory tiers. DC:k<kind>n<name>t<id> is the type registry announcing a new type, carrying its kind, the id of its name string, and the new type id.

  3. Filter the stream. Every marker begins on its own line, so grep is the whole query language. Count the phases to see the shape of a compile: 

    $ wc -l /tmp/markers.txt
2206 /tmp/markers.txt
$ grep -a -c '^INT:new' /tmp/markers.txt
1259
$ grep -a -c '^DC:' /tmp/markers.txt
401
$ grep -a -c '^arena ' /tmp/markers.txt
29
$ grep -a -c '^FWD:' /tmp/markers.txt
66

    INT:new<id> is the string interner adding a string. Its reuse partner INT:dup<id> belongs to the compiled-off debug channel (step 4), so it never appears in this capture; INT:new is the only interner marker the live stream emits. For the tail of the stream, where the emitter writes forward declarations and function bodies, filter those prefixes: 

    $ grep -a '^DC:' /tmp/markers.txt | head -5
DC:k0n0t0
DC:k1n0t1
DC:k2n0t2
DC:k3n0t3
DC:k4n0t4
$ grep -a '^arena ' /tmp/markers.txt | tail -3
arena scratch: grew 65536 -> 131072
arena scratch: grew 131072 -> 262144
arena scratch: grew 262144 -> 524288
$ grep -a -A2 'FWD:n=613 m=9' /tmp/markers.txt
FWD:n=613 m=9
P0:lc=0
FE:p0

    FWD:n=<name> m=<mod> is a function signature emitted, P0:lc=<n> opens a function body with n locals, and FE:p0 is the output buffer flushed. The 613 is an interned name id, not a line number. Read the capture with grep -a, never strings: the marker channel can carry bytes that strings silently drops.

  4. Know which API produces what you are reading. The live stream comes from the measureMarkerWrite* family in sf/src/pal.zig: 

    pub fn measureMarkerWrite(msg: []const u8) void {
    if (g_markers_enabled != @intCast(u32, 0)) {
        stderr_write(msg);
    }
}

    That is the whole gate (sf/src/pal.zig:252–256): measureMarkerWrite, measureMarkerWriteInt, and measureMarkerWriteInt64 test isMarkersEnabled() and write straight to standard error. The flag that turns them on is the g_markers_enabled word set by markersEnabled(on: u32) (sf/src/pal.zig:197–205).

    The older markerWrite, markerWriteInt, and markerWriteInt64 (sf/src/pal.zig:214–250) sit behind a second gate, g_markers_debug (sf/src/pal.zig:210), which is 0 in the shipped compiler: 

    pub const g_markers_debug: u32 = 0;

pub fn markerWrite(msg: []const u8) void {
    if (g_markers_debug != @intCast(u32, 0)) {
        if (g_markers_enabled != @intCast(u32, 0)) {
            stderr_write(msg);
        }
    }
}

    Because g_markers_debug is 0, those three functions are compiled off and emit nothing, with or without --markers. They are the source-level debug channel; the letter-code pipeline markers (I, S, T, L, C) and the per-node traces (INT:dup, IRD:, IRV:) are the same kind of compile-time instrumentation and are not live output either. Only the measureMarkerWrite* sites produce the stream you just captured.

  5. The same channel carries the memory report. --track-memory writes its one-line peak-memory summary through measureMarkerWrite, so it also needs --markers on: 

    $ rm -rf /tmp/manual_tm
$ mkdir -p /tmp/manual_tm
$ timeout 120 /tmp/manual_seed/zig1_5_clean --markers --track-memory -o /tmp/manual_tm docs/sf/manuals/src/vol2/arena.z98 2> /tmp/markers_tm.txt
$ grep -a 'track-memory' /tmp/markers_tm.txt
track-memory: perm=61K mod=365K scr=254K pool=2475K type_db=31K total=680K

    The figures are kilobytes of peak use per arena, with total the sum of perm, mod, and scr. Without --markers the report is silent too, because the memory line rides the marker gate. This is the same budget instrument described in Volume IV — Memory and the arena and Volume III — Memory budgets.

  6. Two things about markers are worth saying plainly. First, they are diagnostic text, not a contract: the prefixes live in the compiler's source and can change with the compiler, so a script that depends on one prefix is a script that may break at the next rebuild. Read them the way you read a compiler's internal comments. Second, they trace the compiler, not your program. By the time your binary runs, the markers are gone. If a value is wrong at run time, markers will not show it — use gdb on the generated C, as Debug the generated C shows. Markers answer compiler questions: which type was created, how many strings were interned, which arena grew, which function was emitted.

Verify it worked

The transcripts above are the captured output of those commands against a compiler installed at /tmp/manual_seed. Four things together prove the channel is wired. Step 1 shows one compile producing 2206 marker lines and the same compile without --markers producing 0. Step 2 shows the phases in order: arena growth, then DC: type-registry lines, then INT: interner lines. Step 3's counts — 1259 INT:new, 401 DC:, 29 arena, 66 FWD: — are all present in the 2206-line file. Step 5's track-memory line appears only because --markers is on, which confirms that the report and the stream share one gate. If you see those, the compiler trace is one flag away.

Common mistakes

  • Forgetting to redirect standard error. Markers and diagnostics share standard error, so an unredirected --markers compile floods the terminal with two thousand lines and buries any real error. Always add 2> /tmp/markers.txt.
  • Filtering with strings. The marker channel can carry bytes that strings drops, silently losing entries. Use grep -a on the raw capture.
  • Expecting the flag to trace your program. Markers trace the compiler as it builds your program. They are gone by run time; use gdb for the binary.
  • Looking for markerWrite output. The shipped compiler has g_markers_debug = 0, so markerWrite, markerWriteInt, and markerWriteInt64 are compiled off. The live stream comes from measureMarkerWrite*; read that API when you extend the instrumentation.
  • Expecting --track-memory on its own. The memory summary is written through the marker channel, so it needs --markers too.
  • Mixing the marker tree with the plain tree. --markers emits an instrumented tree: the generated C carries extra /*==MARKER_…==*/ and /*==LF:…==*/ comment lines, so its line numbers no longer match a plain build. In the run above the same module is 413 lines in /tmp/manual_plain/arena_F3DC0DA4.c and 462 lines in /tmp/manual_markers/arena_F3DC0DA4.c. Keep the marker tree and the tree you debug with gdb apart, or the breakpoint lands on the wrong line.
  • Treating a marker prefix as an interface. The prefixes are diagnostic text that can change with the compiler. Script them only with that caveat in mind.
