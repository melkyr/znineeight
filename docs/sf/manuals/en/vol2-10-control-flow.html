Control Flow, in Full

Volume I showed the four shapes a program is built from — if, while, for, and switch — in their everyday forms. This chapter is the full surface, as the compiler actually accepts it: the value forms, the captures, the ranges, and the labels, each with the diagnostic it produces when it is used wrongly.

Three rules are worth carrying in from the start, because they explain almost every difference from the C you already write. First, a switch must have an else prong, always, even when the cases cover the whole type. Second, a capture (if (x) |v|, for (arr) |v, i|) is an immutable copy of one element, not a reference. Third, the control-flow statements are also expressions where Zig makes them expressions: an if or a switch can compute a value, and its arms are ordinary expressions.

The chapter's program is docs/sf/manuals/src/vol2/control.z98. It walks every construct family once, in one runnable program, and ends with the exhaustive enum switch that still writes its mandatory else: 

ifstmt 8
ifexpr 1
classify -1 0 1
capture 5
capture expr -1
while step i 6 sum 13
while true 3
while opt 6
for values 100 weighted 200
for range 6
for explicit 110 6
switch range 66
switch const 7
switch value 2
labeled 2
block true
enum switch 3

Everything below is measured on the compiler shipped with this manual, and every diagnostic quoted is the one the compiler actually prints. Where the rule differs from official Zig 0.15.2, the difference is called out at the point where it bites.

if and if expressions

An if statement takes a condition that must be a bool. Braces are optional around a single statement; the condition is not an expression that can carry an assignment, so the C idiom if (a = 3) does not parse. An if without else is a statement; an if used as a value must have both arms: 

var n: i32 = 7;
if (n > 5) n = 8 else n = 9;

const kind: i32 = if (n == 8) 1 else 2;
// ifstmt 8
// ifexpr 1

The brace-less form has one trap: a semicolon may not sit between the first body and the else. The compiler names the fix: 

if (x > 0) return 1; else return 0;
// error[2000]: ';' not allowed before 'else' - use braces: if (cond) { ... } else { ... }

Write the braces, or omit the semicolon as in if (x > 0) return 1 else return 0;. A condition of the wrong type is rejected before any C is emitted: 

if (5) { ... }
// error[3058]: condition must be of type 'bool'

while (5) { break; }
// error[3058]: condition must be of type 'bool'

A value if with only one arm is the other half of the rule. The missing arm would leave the value undefined, and the compiler refuses it rather than inventing a zero: 

const x: i32 = if (c) 1;
// error[3059]: if expression without 'else' cannot be used as a value (its type is 'void')

An assignment is a statement, not an expression, so if (a = 3) is a parse error (error[2000]: expected ')' but found token). Use == for comparison.

The arms may be if expressions themselves, and an arm may return; a function written as an if/else chain is the ordinary style: 

fn classify(value: i32) i32 {
    if (value < 0) return -1;
    if (value == 0) return 0;
    return 1;
}
// classify -1 0 1

Capturing a payload: if (x) |v|

When the condition is an optional, the if can unwrap it with a capture. The capture binds the payload only on the branch where it exists, and it is an immutable copy: 

var maybe: ?i32 = 5;
if (maybe) |v| {
    std.io.print("capture {}\n", .{v});
} else {
    std.io.print("capture none\n", .{});
}
// capture 5

The same form works in expression position, with the else arm standing in when the value is absent: 

maybe = null;
const fallback: i32 = if (maybe) |v| v else -1;
// capture expr -1

The capture is not a handle back to the optional. Assigning through it reports the binding as immutable: 

for (arr) |v| {
    v = 9;
}
// error[3002]: cannot assign to immutable variable

A capture on a condition that is not an optional is rejected at the condition, with a message that says what the capture needs: 

if (true) |v| { ... }
// error[3058]: capture condition must be an optional or error union type

There is no else |err| spelling for the error case; it does not parse. Error unions, try, and catch are chapter 12's territory: 

} else |err| {
// error[2000]: expected expression

while and the continue-expression

A while loop takes a condition and a body; when the loop has a continue-expression after the colon, the expression runs after the body and before the condition is tested again: 

var i: i32 = 0;
var sum: i32 = 0;
while (i < 6) : (i += 1) {
    if (i == 2) continue;
    sum += i;
}
// while step i 6 sum 13

That output is the important measurement of this section. i ends at 6, not 5: the continue at i == 2 jumps to the continue-expression i += 1 before the next condition test, so it does not skip the increment and does not spin. In a hand-written C loop that puts i++ at the bottom of the body, the same continue would skip the increment; here the step is part of the loop header, and continue cannot reach it wrongly.

while (true) plus an early break is the do ... while replacement the language documents (there is no do statement): 

var count: i32 = 0;
while (true) {
    if (count == 3) break;
    count += 1;
}
// while true 3

When the condition is an optional, the capture form loops as long as the optional has a value. The loop variable can be reassigned to move toward the exit; the capture itself stays immutable: 

var down: ?i32 = 3;
var total: i32 = 0;
while (down) |v| {
    total += v;
    down = if (v > 1) v - 1 else null;
}
// while opt 6

for over collections and ranges

The iteration statement has two halves: the iterable and the capture list. A collection — an array, a slice, a pointer to an array — hands out its elements, optionally with a second capture for the index: 

var scores: [4]i32 = .{ 10, 20, 30, 40 };
var values: i32 = 0;
for (scores) |v| {
    values += v;
}
var weighted: i32 = 0;
for (scores) |v, idx| {
    weighted += v * @intCast(i32, idx);
}
// for values 100 weighted 200

The index is a usize. Conversions between usize and i32 are implicit on this compiler: a declaration or assignment reports warning[3000], a call argument is silent, and the value is converted unchecked, so a large index can wrap (a probe's 4000000000 became -294967296 under both -fsafe and -ffast). @intCast is the explicit, warning-free form, and it is what the chapter's program uses. Both captures are immutable copies.

A range is an iterable too. for (0..n) walks 0 through n - 1, and the item already is the number, so the one-capture form is the range form: 

var rsum: i32 = 0;
for (0..4) |x| {
    rsum += @intCast(i32, x);
}
// for range 6

The explicit index range, for (arr, start..end), is the Zig 0.15.2 form for looping over a collection while numbering the captures from start. It iterates every element of the iterable — end does not cut the iteration short. The index is start plus the iteration count, is not clamped to the iterable, and the form requires the index capture. When end is present it must satisfy end - start == arr.len; the open form start.. has no length to check: 

var tail: i32 = 0;
for (scores, 1..) |v, idx| {
    tail += v + @intCast(i32, idx);
}
var spanned: i32 = 0;
for (scores, 0..scores.len) |v, idx| {
    spanned += @intCast(i32, idx);
}
// for explicit 110 6

tail prints 110: the four elements are numbered 1, 2, 3, 4 (10+1, 20+2, 30+3, 40+4) and all four are visited. The end expression may read .len, as spanned shows, and the compiler folds it. A length that is wrong at compile time is a rejection rather than a wrong loop: 

for (arr, 0..3) |v, i| { ... }   // arr has four elements
// error[3000]: non-matching for loop lengths: the index range and the iterable differ in length

When the end is a runtime value, the same check becomes a trap under -fsafe (exit status 133) and disappears under -ffast; the honesty note states the split. The older Zig shape with two iterables in one loop, and its cousin with an explicit range over a range iterable, are parse errors: 

for (a, b) |v| { ... }
// error[2000]: expected token but found ')'

for (0..5, 0..) |x, i| { ... }
// error[2000]: expected ')' but found ','

One iterable per loop. When two collections have to move together, index one of them with the other's index capture.

switch, ranges, and the mandatory else

switch compares one value against items and ranges. Items may be listed with commas, ranges come in two spellings — start...end includes both ends, start..end excludes the end — and the prongs may compute a value in statement position or be the value of a switch expression: 

var grade: i32 = 87;
var letter: i32 = 0;
switch (grade) {
    90...100 => letter = 65,
    80..90 => letter = 66,
    70..80 => letter = 67,
    else => letter = 70,
}
// switch range 66

const band: i32 = switch (grade) {
    90...100 => 1,
    80..90 => 2,
    else => 3,
};
// switch value 2

The else prong is not optional, not even when the items obviously cover the whole type. This is a deliberate divergence from official Zig, which accepts an exhaustive switch without one. The compiler's rule is strict and uniform; there is no exhaustive-switch exception: 

switch (x) {
    1 => r = 1,
}
// error[3068]: switch must have an 'else' prong

switch (c) {         // c: Color, an enum with three members
    .Red => r = 1,
    .Green => r = 2,
    .Blue => r = 3,
}
// error[3068]: switch must have an 'else' prong

Case items resolve to compile-time values. Integer and character literals work directly; module-level consts work as items and as range bounds: 

const LO: i32 = 100;
const HI: i32 = 102;
...
switch (pick) {
    LO...HI => slot = 7,
    else => slot = 8,
}
// switch const 7

The constant must be declared at module scope. A const declared inside a function is not resolved by lowering, so a prong naming it matches nothing and the value silently takes else; the honesty note records the measured behavior. Enum members work in both the shorthand and qualified spellings, and enum ranges expand to the members' underlying values, so enum(uN) gaps stay exact.

Every prong that can run must produce a value when the switch is a value, and a divergent prong — return, break, continue, unreachable — is a legal arm with type noreturn. else still has to be written. The exhaustive enum switch in the chapter's program ends this way, and the reason carries a warning: unreachable is a live trap, not an optimization hint. If control reaches it, the program dies with the trap exit status (133) under -fsafe and under -ffast alike. Write it only where the branch is provably dead: 

switch (color) {
    .Red => rgb = 1,
    .Green => rgb = 2,
    .Blue => rgb = 3,
    else => unreachable,
}
// enum switch 3

Labels: loops and blocks

Loops can be labeled, and break or continue can name a label to leave or advance an outer loop rather than the innermost one. Keep labels unique within a function by convention: the compiler does not reject a duplicate today, and a continue :outer then binds the nearest label with that name (a probe's nested duplicate continued the inner loop): 

var pairs: i32 = 0;
outer: for (0..4) |a| {
    var b: i32 = 0;
    while (b < 3) : (b += 1) {
        if (b == 1) continue :outer;
        if (a == 2) break :outer;
        pairs += 1;
    }
}
// labeled 2

At a == 0 the inner b == 1 continues the outer loop, which runs its step and moves to a == 1; at a == 2 the labeled break leaves both loops. Two increments run in total, which is what pairs 2 reports. The unlabeled forms stay where they always were: the innermost loop.

A block can carry a label too, and a value-less break :label leaves it early. This is control flow, not a value producer: a labeled block has no value of its own, and trying to give one back is a parse error. 

var found: bool = false;
lookup: {
    if (grade < 0) break :lookup;
    found = true;
}
// block true

The value-producing spelling does not parse: 

const x: i32 = blk: {
    break :blk 1;
};
// error[2000]: expected ';' but found integer literal

When a value has to come out of a block, use an if expression, a switch expression, or a function call. A labeled block is for early exit only.

Honesty: the edges of the measured rules

Honest note. The mandatory else is a Z98 divergence: official Zig 0.15.2 accepts an exhaustive switch with no else, and Z98 rejects it with error[3068]. The escape hatch for a genuinely impossible fall-through is else => unreachable, but it is a live trap: the chapter's probes reached it and the process died with exit status 133 under both -fsafe and -ffast. It is not a "this cannot happen" annotation that costs nothing; it is the compiler placing a trap on the prong.

The explicit-index-range length check follows the same safe/fast split as the other runtime checks. A compile-time-known mismatch rejects before C is emitted (error[3000]); a runtime mismatch traps under the default -fsafe; under -ffast the check is gone and the loop walks the whole iterable with the wrong index labels, because the end value is only checked, never used to bound the iteration. A probe with a four-element array and a runtime end of three printed the full sum under -ffast instead of trapping.

Named case items and range bounds resolve at module scope. A function-local const is not resolved by lowering — a probe's local LO...HI range matched nothing and the value silently took the else prong, while the same constants declared at module scope matched. Keep switch constants where the module can see them, and prefer a real fallback over an unreachable one when a local constant is the only thing standing between the else and a trap.

Captures are immutable copies. The loop variable is a fresh binding per iteration; there is no way to write back through it, and assignment rejects with error[3002]. The capture condition must be an optional; anything else rejects at the condition with error[3058]. The error half of the capture, else |err|, does not parse at all (error[2000]: expected expression); error unions are chapter 12.

Switch ranges are compile-time: both endpoints must be literals, module constants, or enum members of the condition's type, and the range is expanded into sequential case labels before any C is emitted. That is why ranges cost nothing at runtime, and why a range whose endpoints are not constant has no case to emit.

The example

The whole chapter in one program. It exercises the brace-less if/else, an if expression, optional captures in statement and expression position, the continue-expression with a continue, while (true), while (opt) |v|, collection loops with and without an index, a range loop, explicit index ranges with an open and a .len end, an integer switch over inclusive and exclusive ranges, module-constant items, a value switch, labeled continue/break, a labeled block, and an exhaustive enum switch with else => unreachable. It is docs/sf/manuals/src/vol2/control.z98: 

const std = @import("std");

// Named constants can be switch items and range bounds.
const LO: i32 = 100;
const HI: i32 = 102;

fn classify(value: i32) i32 {
    // Brace-less if/else; the condition is a bool.
    if (value < 0) return -1;
    if (value == 0) return 0;
    return 1;
}

pub fn main() void {
    // 1. if statements and if expressions.
    var n: i32 = 7;
    if (n > 5) n = 8 else n = 9;
    std.io.print("ifstmt {}\n", .{n});

    const kind: i32 = if (n == 8) 1 else 2;
    std.io.print("ifexpr {}\n", .{kind});
    std.io.print("classify {} {} {}\n", .{ classify(-4), classify(0), classify(4) });

    // 2. Optional capture, statement and expression.
    var maybe: ?i32 = 5;
    if (maybe) |v| {
        std.io.print("capture {}\n", .{v});
    } else {
        std.io.print("capture none\n", .{});
    }
    maybe = null;
    const fallback: i32 = if (maybe) |v| v else -1;
    std.io.print("capture expr {}\n", .{fallback});

    // 3. while, the continue-expression, and continue.
    var i: i32 = 0;
    var sum: i32 = 0;
    while (i < 6) : (i += 1) {
        if (i == 2) continue;
        sum += i;
    }
    std.io.print("while step i {} sum {}\n", .{ i, sum });

    // while (true) plus break is the do/while replacement.
    var count: i32 = 0;
    while (true) {
        if (count == 3) break;
        count += 1;
    }
    std.io.print("while true {}\n", .{count});

    // while (opt) |v| loops while the optional has a value.
    var down: ?i32 = 3;
    var total: i32 = 0;
    while (down) |v| {
        total += v;
        down = if (v > 1) v - 1 else null;
    }
    std.io.print("while opt {}\n", .{total});

    // 4. for over a collection, with and without the index.
    var scores: [4]i32 = .{ 10, 20, 30, 40 };
    var values: i32 = 0;
    for (scores) |v| {
        values += v;
    }
    var weighted: i32 = 0;
    for (scores) |v, idx| {
        weighted += v * @intCast(i32, idx);
    }
    std.io.print("for values {} weighted {}\n", .{ values, weighted });

    // 5. for over a range: the item is the number itself.
    var rsum: i32 = 0;
    for (0..4) |x| {
        rsum += @intCast(i32, x);
    }
    std.io.print("for range {}\n", .{rsum});

    // 6. Explicit index ranges keep the iterable whole.
    var tail: i32 = 0;
    for (scores, 1..) |v, idx| {
        tail += v + @intCast(i32, idx);
    }
    var spanned: i32 = 0;
    for (scores, 0..scores.len) |v, idx| {
        spanned += @intCast(i32, idx);
    }
    std.io.print("for explicit {} {}\n", .{ tail, spanned });

    // 7. switch over inclusive and exclusive ranges.
    var grade: i32 = 87;
    var letter: i32 = 0;
    switch (grade) {
        90...100 => letter = 65,
        80..90 => letter = 66,
        70..80 => letter = 67,
        else => letter = 70,
    }
    std.io.print("switch range {}\n", .{letter});

    // Named constants as items and bounds.
    var pick: i32 = 101;
    var slot: i32 = 0;
    switch (pick) {
        LO...HI => slot = 7,
        else => slot = 8,
    }
    std.io.print("switch const {}\n", .{slot});

    // A switch is also a value expression.
    const band: i32 = switch (grade) {
        90...100 => 1,
        80..90 => 2,
        else => 3,
    };
    std.io.print("switch value {}\n", .{band});

    // 8. Labeled loops: break and continue reach the named loop.
    var pairs: i32 = 0;
    outer: for (0..4) |a| {
        var b: i32 = 0;
        while (b < 3) : (b += 1) {
            if (b == 1) continue :outer;
            if (a == 2) break :outer;
            pairs += 1;
        }
    }
    std.io.print("labeled {}\n", .{pairs});

    // A labeled block is exited with a value-less break.
    var found: bool = false;
    lookup: {
        if (grade < 0) break :lookup;
        found = true;
    }
    std.io.print("block {}\n", .{found});

    // Exhaustive enum switch still carries the mandatory else;
    // unreachable is a live trap, not a no-op, so only write it
    // where the branch really cannot run.
    const Color = enum { Red, Green, Blue };
    const color: Color = .Blue;
    var rgb: i32 = 0;
    switch (color) {
        .Red => rgb = 1,
        .Green => rgb = 2,
        .Blue => rgb = 3,
        else => unreachable,
    }
    std.io.print("enum switch {}\n", .{rgb});
}

Common mistakes

The mistakes below are the ones a programmer arriving from C (or from a newer Zig) makes first with control flow. Each corrected shape is the compiler's rule, not a style preference.

Writing C's for (;;). Z98 has no three-clause for. The counter loop is either a range loop — for (0..n) |i| — or while (true) with a break, which is also the documented replacement for do ... while. A loop that needs an increment between iterations and a condition on top puts the increment in the continue-expression: while (i < n) : (i += 1). Do not keep state in the body and rely on continue to skip it: continue jumps to the step, so the step always runs.

Leaving the else prong off a switch. Every switch needs one, and the compiler enforces it with error[3068]: switch must have an 'else' prong even when the items cover every member of an enum or both values of a bool. Official Zig accepts the exhaustive form, so code carried over from Zig needs the prong added. When the fall-through really cannot happen, else => unreachable is the last prong — but remember it traps when reached, under both -fsafe and -ffast, so prefer an empty block or a real fallback until the branch is proved dead.

Writing a value-labeled block. The label on a block is for early exit, not for values: break :blk 1; does not parse (error[2000]: expected ';' but found integer literal). Use an if, a switch, or a function when a value has to come out. The value-less break :blk; is the supported form, and it is the right tool for bailing out of a block early.

Expecting continue to skip a for's increment. In a C loop with the increment at the bottom of the body, continue skips it and can spin. In Z98 the increment is the continue-expression or the loop's own step, and continue runs it before the next condition test — that is what makes the while ... : (step) and the range for safe with continue. What continue does skip is the rest of the body: any accumulation after the continue is skipped, which is the actual intent in most cases.

Assigning to a capture. The capture is an immutable copy: for (arr) |v| { v = 9; } is error[3002]: cannot assign to immutable variable, and the array is untouched. Accumulate into a var declared outside the loop, or index the array itself when the element has to change.

Assuming a capture condition can be any expression. A capture needs an optional; if (true) |v| rejects with error[3058]: capture condition must be an optional or error union type. And the whole condition must be a bool (or optional): a numeric condition is error[3058]: condition must be of type 'bool', unlike C, where any non-zero number is true.

Putting a semicolon before else. The brace-less form does not allow it: error[2000]: ';' not allowed before 'else' - use braces: if (cond) { ... } else { ... }. Write the braces or drop the semicolon. And do not reach for if (a = 3) as an assignment: assignments are statements, so the parser stops at the =.
