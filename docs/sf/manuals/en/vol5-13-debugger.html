Debug the Generated C

This guide emits a Z98 program to C89, rebuilds that C with debug information, and debugs it with gdb; when the defect is in the compiler rather than in the program, it shows how to read the compiler's --markers trace instead.

Prerequisites

  • The compiler rebuilt from the seed at /tmp/manual_seed/zig1_5_clean, with the standard library beside it in /tmp/manual_seed/lib/. If it is not there yet, follow Rebuild the compiler from seed first.
  • A Linux host with a 32-bit-capable gcc and gdb. The transcripts below were captured with GNU gdb 13.1.
  • The repository checked out, so the sample docs/sf/manuals/src/vol2/arena.z98 is present. Every command runs from the repository root, /workspace/znineeight, except where a step says to enter the emitted directory.
  • No prior guide is strictly required: any program that compiles can be debugged this way. The emitted tree and its build script are explained in Build a single file and Target Linux.

There is no Z98 debugger, and there is no .z98dbg sidecar format anywhere in the toolchain. What the compiler ships is a program in C89; that C is the debugging surface.

The instrument: the generated C

A modern toolchain ships the debugger with the language, and the two agree on file names, line numbers, and variable names. Z98 breaks that assumption on purpose. It does not ship a debugger; it ships the generated C. The generated C is the C a 1998 programmer would have written by hand: one plain function per Z98 function, a struct per struct, a file per module. It carries no #line directives, so gdb reports the generated file names and line numbers directly, and those are stable across builds. You debug a language you can read, with a debugger that has existed for decades.

The only genuinely different part is the names. Every Z98 function becomes a C function named zF_<hash>_<name>, where the hash is derived from the module and the trailing piece is your function's own name. You never guess it: the name is written in a comment above each definition, one grep away.

Steps

  1. Emit the tree. Create the output directory first: the compiler creates files but not the directory that holds them. The command is silent on success. 

    $ cd /workspace/znineeight
$ rm -rf /tmp/manual_out
$ timeout 120 /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol2/arena.z98
error: output directory does not exist: /tmp/manual_out
$ mkdir -p /tmp/manual_out
$ timeout 120 /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol2/arena.z98
$ ls /tmp/manual_out
arena_F3DC0DA4.c      arena_F3DC0DA4.h      build_target.sh
c_exit.c              net_prelude.h
std_arena_7156573C.c  std_arena_7156573C.h
std_fmt_5E28752C.c    std_fmt_5E28752C.h
std_io_59DB29D9.c     std_io_59DB29D9.h
std_net_A15200CC.c    std_net_A15200CC.h
zig_compat.h          zig_pal.c
zig_runtime.c         zig_runtime.h
zig_special_types.h

    Your module, arena.z98, became arena_F3DC0DA4.c; each standard module it pulled in got its own hashed file. The hash suffix is derived from the module's path, so your own module is stable for a given source path. The std_… hashes track the compiler's install path, so the names above belong to a compiler installed at /tmp/manual_seed; a compiler installed elsewhere emits different std_… suffixes for the same program. Read the hashes in a transcript as belonging to the run that produced it, and grep the directory in front of you for the real one.

  2. Build the tree once the ordinary way, so you know the program runs before you attach a debugger. The emitted build_target.sh carries the exact flags and link order for the target. 

    $ cd /tmp/manual_out
$ timeout 120 sh build_target.sh linux arena
Building for linux...
…
Built: arena
$ timeout 120 ./arena
cap=32 used=0
p=3 4 used=8
used after reset=0
p2=9 8 reused p.x=9
caught: error.OutOfMemory
perm=3 4 scratch=5 6
perm used=8 scratch used=8
scratch used after reset=0 perm used=8

    The script prints a long list of warnings from the emitted runtime (unused static helpers); that is why the supported flags include -Wno-… and the script does not pass -Werror. They are not errors, and the binary runs. If you only want to read the C without building it, --dump-c89 remains the alias: with -o it writes the per-module .c/.h files, and without -o it writes a single file to standard output.

  3. Compile from inside the emitted directory, and if you cannot, name the include path absolutely. This is the first wall a reader hits. The emitted C includes its own headers by angle brackets — #include <net_prelude.h> — and an angle-bracket include is searched on the include path, not next to the including file. A relative -I . run from somewhere else points at that somewhere else: 

    $ cd /workspace/znineeight
$ timeout 120 gcc -m32 -std=c89 -I . -c /tmp/manual_out/arena_F3DC0DA4.c -o /tmp/manual_out/arena.o
In file included from /tmp/manual_out/arena_F3DC0DA4.h:9,
                 from /tmp/manual_out/arena_F3DC0DA4.c:1:
/tmp/manual_out/std_net_A15200CC.h:6:10: fatal error: net_prelude.h: No such file or directory
    6 | #include <net_prelude.h>
      |          ^~~~~~~~~~~~~~~
compilation terminated.

    The header is sitting in /tmp/manual_out, but the include path never reached it. The fix is either to run from inside the directory, exactly as the build script does, or to name the directory absolutely: 

    $ timeout 120 gcc -m32 -std=c89 -I /tmp/manual_out -c /tmp/manual_out/arena_F3DC0DA4.c -o /tmp/manual_out/arena.o

    Both work; the absolute -I is the one to reach for when a script or a Makefile invokes gcc from a different working directory. The second half of the same trap is the object files: gcc -c DIR/*.c run from outside writes the .o files into the caller's directory, not into DIR, so a later link of DIR/*.o finds nothing. Compile inside DIR, or give every output an absolute path.

  4. Rebuild with debug information. The emitted script intentionally omits -g, because a shipping build should not carry debug info. For debugging, rebuild the C by hand with -g added and -O0 kept, from inside the emitted directory: 

    $ cd /tmp/manual_out
$ timeout 120 gcc -m32 -std=c89 -O0 -g -Wall -Wno-long-long -Wno-pointer-sign \
      -Wno-implicit-function-declaration -I . -c *.c
$ timeout 120 gcc -m32 -O0 *.o -o arena_g

    Nothing Z98-specific happens here. -g is ordinary gcc debug information, and the layout it records is the Z98 layout, because the generated C is the Z98 layout. Keep -O0: optimization reorders statements and can make a source line step in an order that does not match the code you are reading. If you forget -g, gdb still runs the binary but a breakpoint on main resolves to a bare address with no file and no line. The error is silent, so add -g the first time.

  5. Start a session at the C entry point. This is a real batch session against the arena binary: 

    $ gdb -batch -ex 'set pagination off' -ex 'break main' -ex run \
      -ex 'bt' -ex 'info line' --args ./arena_g
Breakpoint 1 at 0x31e5: file arena_F3DC0DA4.c, line 406.

Breakpoint 1, main () at arena_F3DC0DA4.c:406
406	    zF_780653D2___module_init();
#0  main () at arena_F3DC0DA4.c:406
Line 406 of "arena_F3DC0DA4.c" starts at address 0x… <main+29> and ends at 0x… <main+34>.

    You asked for main and got a main, but not yours. The emitted tree has two: the C entry point, which initializes the modules and then calls your Z98 pub fn main, and that Z98 main, defined as zF_EA90E208_main. break main stops in the module initializers. Some environments print a thread-library or address-space-randomization preamble before the first prompt; it is harmless and can be ignored.

  6. Find your function and break on it. The mangled name is printed above each definition, so one grep on the plain name finds it: 

    $ grep -n 'Point_init' arena_F3DC0DA4.c
30:/* Point_init */
31:zT_D17889A1_EU_47 zF_3439BCE0_Point_init(zT_F22A6288_Arena* arena, int x, int y) {
144:    zT_22 = zF_3439BCE0_Point_init(zT_14, (int)((int)zT_18), (int)((int)zT_20));
176:    zT_42 = zF_3439BCE0_Point_init(zT_34, (int)((int)zT_38), (int)((int)zT_40));
312:    zT_31 = zF_3439BCE0_Point_init(zT_23, (int)((int)zT_27), (int)((int)zT_29));
328:    zT_45 = zF_3439BCE0_Point_init(zT_37, (int)((int)zT_41), (int)((int)zT_43));

    $ gdb -batch -ex 'set pagination off' \
      -ex 'break zF_3439BCE0_Point_init' -ex run \
      -ex 'print x' -ex 'print y' -ex 'bt' --args ./arena_g
Breakpoint 1 at 0x2548: file arena_F3DC0DA4.c, line 40.
cap=32 used=0

Breakpoint 1, zF_3439BCE0_Point_init (arena=0x…, x=3, y=4) at arena_F3DC0DA4.c:40
40	    zig_poison_fill((void*)&zT_8, (unsigned int)sizeof zT_8);
$1 = 3
$2 = 4
#0  zF_3439BCE0_Point_init (arena=0x…, x=3, y=4) at arena_F3DC0DA4.c:40
#1  0x… in zF_7F2346E9_single () at arena_F3DC0DA4.c:144
#2  0x… in zF_EA90E208_main () at arena_F3DC0DA4.c:384
#3  0x… in main () at arena_F3DC0DA4.c:409

    That is the whole technique. The breakpoint resolved to a generated file and line; the arguments are the arguments your Z98 function declared; the backtrace is the call chain, with the Z98 functions in the middle and the C entry point at the bottom. cap=32 used=0 is the program's own output that ran before the breakpoint. Everything after the break is ordinary gdb — next, step, print, finish, watchpoints, conditional breakpoints — and none of it is Z98-specific. Two smaller habits help: gdb completes, so typing zF_ and pressing tab lists the mangled functions; and a file:line breakpoint such as break arena_F3DC0DA4.c:40 is the same breakpoint as the named one. The name is stable across builds; a line number shifts when you edit the source, so use the name when you can.

  7. When the suspicion falls on the compiler rather than the program, use the compiler's own trace. --markers turns on the marker channel: the compiler writes a line to standard error as it walks the pipeline. Emit the marker build into its own directory: --markers writes a marker-instrumented tree whose extra comment lines shift the generated line numbers, so keep it apart from the plain build you debug with gdb. Capture the stream to a file, because it is larger than a terminal should show: 

    $ cd /workspace/znineeight
$ rm -rf /tmp/manual_markers
$ mkdir -p /tmp/manual_markers
$ timeout 120 /tmp/manual_seed/zig1_5_clean --markers -o /tmp/manual_markers docs/sf/manuals/src/vol2/arena.z98 2> markers.txt
$ head -11 markers.txt
arena perm: grew 4096 -> 16384
arena perm: grew 16384 -> 32768
arena perm: grew 32768 -> 65536
DC:k0n0t0
DC:k1n0t1
DC:k2n0t2
DC:k3n0t3
DC:k4n0t4
DC:k5n0t5
DC:k6n0t6
DC:k7n0t7

    and near the end, as the emitter writes forward declarations and bodies: 

    $ grep -a -A2 'FWD:n=400 m=9' markers.txt
FWD:n=400 m=9
P0:lc=2
FE:p0

    Then filter it. DC:k<kind>n<name>t<id> comes from the type registry and announces a new type; INT:new<id> is the string interner adding a string, and INT:dup<id> is it reusing one. arena <name>: grew old -> new is the allocator reporting a bucket growth, and the names — perm, module, scratch — are the compiler's own memory tiers. 

    $ grep -a -c '^INT:new' markers.txt
1259
$ grep -a '^DC:' markers.txt | head -5
DC:k0n0t0
DC:k1n0t1
DC:k2n0t2
DC:k3n0t3
DC:k4n0t4
$ grep -a '^arena ' markers.txt | tail -3
arena scratch: grew 65536 -> 131072
arena scratch: grew 131072 -> 262144
arena scratch: grew 262144 -> 524288

    Read the raw capture with grep -a, never strings: the marker channel can carry bytes that strings silently drops. Two cautions. The labels are diagnostic text, not a contract; they live in the compiler's source and can change, so read them as internal comments, not as a command-line interface. And they trace the compiler, not your program: by the time your binary runs, the markers are gone. That division is the whole reason this guide has two halves — gdb for the binary, --markers for the build that made it.

Verify it worked

The transcripts in the steps are the captured output of those commands against a compiler installed at /tmp/manual_seed; the generated line numbers and symbols reproduce, while pointer and stack addresses vary from run to run. Three things together prove the workflow is wired. Step 6 stops in arena_F3DC0DA4.c at a generated line, not at a bare address, which shows the -g build recorded the generated source. The same step prints $1 = 3 and $2 = 4, the arguments the Z98 Point_init declared, and walks a backtrace through zF_3439BCE0_Point_init, zF_7F2346E9_single, zF_EA90E208_main, and the C main; the grep line for that caller is 144, the same number the backtrace prints. Step 7's --markers stream shows the type registry, the string interner, and the arena tiers during a compile. If you see those, the debugging surface is the generated C and the compiler trace is one flag away.

Common mistakes

  • Running the compile from the wrong directory. The emitted headers are included by angle brackets and found on the include path, so a relative -I . only works from inside the emitted directory. The symptom is fatal error: net_prelude.h: No such file or directory even though the header is plainly there. Run the build script, or pass the directory absolutely.
  • Forgetting that gcc -c DIR/*.c writes into the caller's directory. Compiling from outside DIR scatters the .o files next to you, not in DIR, and the link cannot find them. Do the compile inside DIR.
  • Building without -g. The emitted script omits debug information on purpose. Add -g and keep -O0; then a breakpoint resolves to the generated file and line and print knows your variable names.
  • Breaking on main and expecting your program. The plain C main is the runtime entry point that initializes the modules before it calls your Z98 main. Break on the mangled zF_…_main instead.
  • Searching for a source file that is not there. gdb reports the generated names — arena_F3DC0DA4.c, not arena.z98. There are no #line directives, so the debugger never pretends otherwise.
  • Hunting for .z98dbg. The blueprint once imagined a sidecar debugger format; it does not exist. No file, no format, no tool. The debugging surface is the generated C.
  • Using --markers to find a bug in the program. The markers trace the compiler as it builds your program; by the time the program runs they are long gone. They answer compiler questions, not program questions.
  • Extracting markers with strings. The marker channel can carry bytes that strings drops, silently losing entries. Use grep -a on the raw capture.
  • Debugging optimized C. Build with -O0. Optimization reorders statements and can make a source line step in an order that does not match the code you are reading.
