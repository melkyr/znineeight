Building Multiple Modules

This guide emits a program split across @import modules, reads the per-module C89 files and the shared header it produces, then builds and links the multi-module executable.

Prerequisites

  • The compiler rebuilt from the seed at /tmp/manual_seed/zig1_5_clean, with the standard library beside it in /tmp/manual_seed/lib/. If it is not there yet, follow Rebuild the compiler from seed first.
  • A Linux host with a 32-bit-capable gcc (the emitted script uses gcc -m32 -std=c89).
  • The repository checked out, so the committed cross-module program repro/mi_matrix/stdlib_print_tuple_fwd_ok_xmod/ is present. Every command runs from the repository root, /workspace/znineeight.

The sample

In Z98 one source file is one module. A module names the other modules it uses with @import at file scope, and a module member marked pub is visible to importers. The example is the committed multi-module program repro/mi_matrix/stdlib_print_tuple_fwd_ok_xmod/, which has three source modules. Its entry module main.zig begins with three imports: 

const std = @import("std");
const colors = @import("colors.zig");
const aux = @import("aux.zig");

The two helper modules are small. colors.zig exports two constants: 

pub const C = 5;
pub const C2: i32 = 5 + 7;

and aux.zig (comment lines omitted) imports colors.zig and re-exports one of its constants, so the import graph is main → {colors, aux} and aux → colors: 

const colors = @import("colors.zig");

pub const A: i32 = colors.C2;

The rest of main.zig is the fixture's own test body (it pins a batch of forward-reference cases); this guide does not need it. An import path is resolved relative to the importing file's directory, so @import("colors.zig") finds the file that sits beside the importer. A bare name such as @import("std") is resolved by the compiler from the lib/ folder beside the compiler binary, not from the current directory.

Steps

  1. Start at the repository root. 

    $ cd /workspace/znineeight

  2. Create the output folder. The compiler writes its emitted tree there but will not create the folder itself. 

    $ mkdir -p /tmp/manual_out

  3. Translate the entry module to C89. -o names the output folder; the last argument is the entry source file (the module with the program entry point). 

    $ timeout 120 /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out repro/mi_matrix/stdlib_print_tuple_fwd_ok_xmod/main.zig

    The command is silent on success. The compiler walks the import graph and emits one C89 pair for every module it reaches, plus the runtime and a build script.

  4. Look at what it emitted. There is a paired .c and .h for each module, a self-contained runtime, the shared headers, and the companion script: 

    $ cd /tmp/manual_out && ls -1

    Each module file is named <source-basename>_<hash>.c and .h; the hash is derived from the module's resolved path, so it changes if you move the tree, and you should not hard-code it. The three program modules are main, aux, and colors; std_io, std_fmt, and std_net are the standard-library modules the program actually reaches, emitted the same way. Every module header includes the shared zig_compat.h and zig_special_types.h, and main_*.h includes the headers of the modules that main imports (including colors_*.h and aux_*.h). zig_runtime.c, zig_pal.c, and c_exit.c are the runtime and PAL sources; net_prelude.h is present because the standard library emits its network module. build_target.sh is the generated build script.

  5. Build the executable. Run the emitted script from inside the output folder and give it the target linux and a program name. 

    $ timeout 120 sh build_target.sh linux prog
Building for linux...
Built: prog

    The script compiles every emitted module and runtime .c with gcc -m32 -std=c89, then links the object files in an intentional modules-then-runtime order (the module objects first, the runtime objects last), which is deterministic rather than an alphabetical glob. The Building for linux... and Built: prog lines are its own report. The generated C draws a long list of gcc warnings; they are expected and do not stop the build, because the script does not pass -Werror.

  6. Run it. 

    $ timeout 120 ./prog

    The lines xmod, imp, and chain are the cross-module ones: xmod and imp read colors and chain reaches colors.C2 through aux.

Verify it worked

The committed fixture pins both the program's standard output and its exit code. The standard-library gate emits the fixture, compiles every emitted .c, links it through build_target.sh, runs it three times, and diffs the result byte-for-byte against the committed expected.txt and expected.rc: 

$ cd /workspace/znineeight
$ bash scripts/stdlib/verify_stdlib.sh /tmp/manual_seed/zig1_5_clean repro/mi_matrix/stdlib_print_tuple_fwd_ok_xmod
== std-lib runtime gate ==
   zig1: /tmp/manual_seed/zig1_5_clean
PASS repro/mi_matrix/stdlib_print_tuple_fwd_ok_xmod
----------------------------------------
run_fixtures: 1 PASS / 0 FAIL over 1 dirs
STDLIB GATE OK

PASS means the 22-line transcript above and the exit code 0 matched the goldens on all three runs; STDLIB GATE OK is the wrapper's overall verdict.

Common mistakes

  • Forgetting to create the output folder. The compiler requires the folder to exist and fails with error: output directory does not exist: /tmp/manual_out (exit code 1). Run mkdir -p first.
  • Naming a helper module as the entry. The last argument must be the module with pub fn main. Pointing -o at aux.zig emits a tree without the program entry point, and the final link has no main.
  • Assuming imports are relative to the current directory. An @import("colors.zig") path is resolved relative to the file that contains it; keep the modules together, or fix the path in the importing file.
  • Running the build script from the wrong folder. build_target.sh uses relative paths to the generated files, so cd into the output folder before running it.
  • Editing the emitted .c/.h files. They are regenerated on every emit, along with the path-derived name hashes. Edit the source modules and re-emit.
  • Reading the gcc warnings as failure. The build prints hundreds of warnings but succeeds; look for Built: prog, not for an empty error stream.

Where to go next

Return to the HOWTO index for the other jobs, or go back to One .z98 to an executable for the single-file case. Larger real multi-module programs are built the same way: examples/z98/lzw (five modules) and examples/z98/json_parser (four) both emit with zig1 -o DIR main.zig and build with sh build_target.sh from the output folder. For the rules behind the flags the recipe runs, see the Volume IV command-line page (-o, --output-dir, and --dump-c89); for the grammar of imports and items, see The Full Grammar.
