Honesty: When C++98 Is the Better Choice

Chapter 3 said plainly when C89 is the better choice and ended on the fact that makes the whole volume work: Z98 emits C89, so the two mix freely. This chapter is the next row of the inventory, and it is the harder one. C++98 is not a lower-level tool than Z98; it is a higher-level one. It gives abstract types with constructors and destructors, generic containers, exceptions that unwind the stack, and run-time type information — all things Z98 deliberately withholds. The question is not whether those are real features. They are. The question is what they cost on a 32 MB machine, and whether the module in front of you needs them.

The verdict is plain, and it has two halves. There are projects, and parts of projects, where C++98 is the better choice, and the honest move is to say so and use it. And for most of the cases a reader brings to this chapter, the older C++98 machinery is heavier than the job, and Z98's manual-vtable idiom is the better trade. Both halves are true, and the chapter owes you both.

Era framing. Statements here about the era's machines, toolchains, and compilers are era context, and where a statement is an opinion the text says so. Statements about Z98 are checked against docs/reference/Language_Spec_Z98.md, the compiler source, and the compiler built from the committed seed. The C++98 figures on this page were measured on this host with g++ -m32 -std=c++98; the exact commands and output are quoted verbatim. The era's own C++ compilers — MSVC 6 and Borland C++ 5.02 — do not run on this host, and nothing here claims they were run.

What you expect

After the previous chapter, a reader may expect this one to be symmetrical: it will name three or four C++98 cases and hand them back. That is half of it. But there is a trap in arriving at this chapter from either direction. Arriving from modern C++, a reader expects templates and classes to be the default and Z98 to be the thing you fall back to. Arriving from the previous chapter, a reader may expect C++98 to be a strictly richer tool that simply costs more, and therefore to be chosen whenever the budget allows. Neither reading is the one this chapter uses.

The right frame is the one the volume keeps returning to. Both compilers produce 32-bit native code for the same machine, and both link against the same objects. C++98 gives you abstraction the compiler implements with run-time machinery; Z98 withholds that abstraction and emits C89 with no machinery behind it. What C++98 adds is not free and it is not decoration: an object with virtual functions carries a hidden pointer, a class emits a table and its type information, a throw needs a runtime to unwind, and a template emits a copy per type. Those costs are affordable on this machine in bounded amounts and fragile when they spread. So the chapter's question, like the previous one, is per module: which abstraction does this module actually need, and is it worth the machinery it brings?

There is one expectation this chapter has to set aside up front, because it is where the honest answer is least comfortable. A reader often assumes that because Z98 emits C89, mixing C++98 into a project is as seamless as mixing C89. It is not. C89 is the emission's own language, so the seam is invisible; C++98 name-mangles and has its own object conventions, so the seam has to be a declared extern "C" boundary. That difference is shown in The way over it, and it is part of the trade rather than a footnote to it.

What you get

Four cases where C++98 is genuinely the better choice. The first decides most era projects, because it is the least arguable: a library that is C++98 and nothing else. The next two are feature cases, and they are where the cost shows up. The last is a toolchain case: the project already builds with MSVC 6 or Borland 5.02 and wants their idioms. Each case says plainly that C++98 wins it, and each is followed by the seam or the Z98 pattern that keeps the rest of the project in Z98 if only part of it is in question.

A library that ships as C++98

This is the case that decides most era projects, and it is the direct analogue of the C89 library case in the previous chapter. A great deal of 1998 software ships as a C++98 header set plus a library. Its interface is classes; its generic parts are templates; and its header may be a maze of template definitions, inline functions, and default arguments that a C compiler cannot even parse. There is no C89 header to call through and no prospect of one being written before the project ships.

The honest answer is to write the part that speaks to the library in C++98, or to call a wrapper the library already exposes. Both work, and both require the same boundary: because C++98 mangles names and C89 does not, a C++98 module that Z98 or C89 is to call must expose plain extern "C" entry points that do not throw across the boundary. Where the library already publishes such an interface, calling it from Z98 is a declaration and a link, and the seam is ordinary. Where it does not, you write a thin C++98 wrapper with extern "C" functions that translate status codes and out parameters — the same shape the era's C++ projects used to expose themselves to C callers. That wrapper is a real cost, and it is the price of the library's abstraction.

This is an era fact, not an opinion: the libraries exist in C++98, and calling them from C++98 is the direct path. The seam that lets the rest of the project stay in Z98 is shown in The way over it, below.

Templates, and the era's incomplete implementations

Templates are the feature Z98 most deliberately lacks, and the one C++98 gives cleanly: one container written once, instantiated for every element type. The shape is the same one Volume II chapter 1 sketched, and it is what a C++98 reader would write for a bounded stack: 

template <typename T>
class Stack {
public:
    Stack() : count(0) {}
    void push(const T& v) { if (count < 8) data[count++] = v; }
    bool pop(T& out) {
        if (count == 0) return false;
        out = data[--count];
        return true;
    }
    int count;
private:
    T data[8];
};

That fragment compiles under the era's C++98 dialect and runs. The transcript below is a real run on this host with g++ -m32 -std=c++98, which is the modern compiler that stands in for the era tools here: 

$ g++ -m32 -std=c++98 -O0 stack.cpp -o stack
$ ./stack
out=3

The abstraction is real and the syntax is short, which is exactly why C++98 is the era-appropriate tool when a type genuinely must stay open. The cost is equally real, and it is easiest to see in the emitted objects: each instantiation is its own function. Compiling a small function template for int, long, and double and reading the symbols shows three separate bodies, one per type: 

$ nm -C tmpl | grep ' twice'
0000121c W double twice<double>(double)
000011f4 W int twice<int>(int)
00001208 W long twice<long>(long)

That is the trade in miniature. A generic container written once on the page becomes one copy of its code in the binary for each type it is used with, and the copies multiply with the number of types and the size of the template. On a machine where every kilobyte is budgeted, a template used across a wide set of types is not weightless; it is a deliberate expense.

There is a second, era-specific cost, and the blueprint names it: the era's implementations were incomplete. MSVC 6 and Borland C++ 5.02 shipped around the time the 1998 standard was ratified, and neither implemented all of it. Member templates, partial specialization, and parts of the standard library were missing or buggy, and code that compiles cleanly on a modern compiler may need workarounds there. This is era context, and it is marked as opinion: the manual states it because it is the reason the blueprint says “tolerate” the implementations rather than simply use them. A template written for the era machine is a template written to that machine's dialect, not to the standard's full text. On this host, only modern g++ and the mingw cross-compiler are available; the era compilers' specific gaps are theirs, not measured here.

The way over, when you do not actually need the type to stay open, is the concrete container. Where a C++98 program writes Stack<T> once, a Z98 program writes IntStack, and a second, separate container for the next element type. The repetition is real, and it is the design: Volume II chapter 16 measures it, and the compiler's own source uses the same pattern for the concrete hash maps it needs. When a type must genuinely stay open and the memory can carry the expansions, C++98 is the better choice, and this case says so.

Classes, virtual dispatch, and the runtime cost

Classes are the second feature, and the one whose cost is easiest to quantify. A C++98 class gives constructors and destructors, so cleanup runs automatically on every exit path; it gives virtual functions, so a call dispatches on the object's dynamic type; and it gives operator overloading, so a library can read naturally. Z98 has none of these at the language level; it has the manual vtable, the init function, and defer/errdefer instead. The question is what the compiler adds to make C++98's version work, and the answer is measurable. This program prints the size of three shapes of object — plain, polymorphic, and a hand-built interface — all for the 32-bit target: 

struct PlainOne { int a; };
struct PlainTwo { int a; int b; };
struct VOne { virtual int f() const { return 1; } int a; };
struct VTwo {
    virtual int f() const { return 1; }
    virtual int g() const { return 2; }
    int a;
};
struct ManualOne { int (*f)(const void*); const void* data; };
struct ManualTwo { int (*f)(const void*); int (*g)(const void*); const void* data; };

The measured sizes are the argument: 

$ g++ -m32 -std=c++98 -O0 cost.cpp -o cost
$ ./cost
PlainOne=4 PlainTwo=8 VOne=8 VTwo=8 ManualOne=8 ManualTwo=12

Read the line carefully. A plain object with one integer is four bytes. The same object made polymorphic is eight: the compiler adds one hidden pointer, the vtable pointer, and it adds it once per object regardless of how many virtual functions the class has — VOne and VTwo are both eight bytes, so a second and third virtual cost no more per object than the first. That is the per-object price. The per-class price is higher: each polymorphic class also emits its vtable, and with RTTI enabled its type information. The symbols are in the binary as soon as the class is: 

$ nm -C rtti | grep -E ' (vtable|typeinfo) for '
00003ee0 V typeinfo for Base
00003ed4 V typeinfo for Derived
00003ec8 V vtable for Base
00003ebc V vtable for Derived

Those tables are emitted once per class, not per object, and for a program with a few dozen classes that is a few dozen small tables. The manual interface sits differently. A Z98 interface value is a data pointer plus one function pointer per operation: eight bytes for one operation, twelve for two, measured here as ManualOne=8 ManualTwo=12, and measured on the seed compiler in Volume II chapter 16 as the two-operation Shape at size=12 align=4 fn=4. The concrete object carries no hidden pointer of its own, no per-class table is emitted, and there is no type information. The cost moves from the object and the class onto the interface value, and the interface value is exactly as big as the operations you put in it.

Exceptions are the third cost, and they are the heaviest. The language does not merely branch on failure; throw hands the failure to a runtime that walks the stack and runs destructors at each frame. Z98 has no such runtime because failure is a value in the return type. The references the linker has to satisfy for a program that throws are visible in its symbols: 

$ nm exc | grep -E '__cxa_(throw|begin_catch|end_catch)|_Unwind_Resume'
         U _Unwind_Resume@GCC_3.0
         U __cxa_begin_catch@CXXABI_1.3
         U __cxa_end_catch@CXXABI_1.3
         U __cxa_throw@CXXABI_1.3

The unwinder (_Unwind_Resume) and the exception runtime (__cxa_throw and the catch entry points) are not free; they are code the toolchain links and tables it lays out per function that can unwind. On this host the unwinder lives in a shared library, so the visible size delta is modest — under a kilobyte of extra code and tables at -O0 — but the era's static link puts the machinery in the binary, and the tables exist whether or not a throw ever runs. dynamic_cast has the same shape: it pulls in the type information tables above, which is the cost of having the run-time type oracle at all. This is a marked opinion, but it is the manual's: on a 32 MB machine, exception handling is affordable for a bounded, exceptional path and expensive as a general control-flow habit.

So the runtime cost of C++98's abstraction is the sum of four things: one hidden pointer per polymorphic object, one table plus type information per polymorphic class, a template body per instantiation, and the unwinder and its tables if exceptions are used. None is large on its own. Together, spread across a large program, they are the difference between a binary that fits the era machine comfortably and one that does not.

MSVC 6 and Borland C++ 5.02

The fourth case is the toolchain itself, and it is the one the manual can only state as era context. MSVC 6 shipped cl; Borland C++ 5.02 shipped bcc32. Both compile C++98 for this machine, both came with their own class libraries, their own extensions (__declspec and Borland's own dialects among them), their own project files, and their own debuggers. A project that already builds with one of them has a coherent world: the build script, the class library, and the debugger all agree.

This is marked as opinion, because the manual does not run those compilers and will not pretend to. The case is not that MSVC or Borland is technically superior; it is that if a module must live inside a project whose build is one of them, matching that project's idioms is the smaller decision. Porting the module to Z98 buys the checks and costs a new build step and a new dialect for the people who maintain the project. Whether that is worth it is the same judgment the previous chapter made about maintaining C89, and it points the same way: keep the established module where it is, write the new module in Z98, and let the two link across the C ABI.

The trade

Choosing C++98 in any of these cases buys abstraction, and the bill is the machinery that makes the abstraction work. That is the whole trade, and both sides of it are real. On the buying side, a template is written once and serves every element type; a constructor and destructor run without being called, on every exit path including the one where an exception leaves the scope; a virtual call dispatches on the object's real type; an exception carries a failure up through frames that never named it; dynamic_cast answers what a value really is. Those are powerful things, and a program that needs them is better for having them. On the paying side, every polymorphic object is one word larger, every polymorphic class brings its table and type information, every template brings a body per type, and an exception path brings an unwinder and per-function tables. On a 32 MB machine, with a 16 MB peak budget, all of that competes with the program's own data.

The honest verdict is the blueprint's, and it is not a dodge: on this machine, C++98 is possible but fragile. Possible, because a bounded use costs bounded memory, and the era shipped real C++98 programs on hardware like this. Fragile, because the costs are per object, per class, per type, and per potentially-unwinding function, so a design that leans on the abstraction multiplies them, and the failure mode is a binary that no longer fits the machine rather than a single mistake at a single line. The way to use C++98 well on the era machine is to use it where the abstraction is the point — a generic container over a handful of types, a class whose destructor is the only correct cleanup, a library whose interface is C++98 — and not as the default shape for every value.

And this is where the chapter says the second half plainly: for a great many modules that reach for C++98's machinery, Z98's manual-vtable idiom is the better trade. If the module needs “an object with behavior,” a struct of function pointers plus an init function gives the same dispatch with no hidden pointer, no per-class table, and no type information, and Volume II chapter 16 measures it. If the module needs “a container for the two element types we have,” two concrete containers are the same code the template would have generated, written by hand and visible. If the module needs cleanup on every exit, the arena plus defer/errdefer gives it without an unwinder. C++98 is the better choice when its abstraction is genuinely needed; it is the heavier choice when the abstraction is a habit.

Honest note. The sharpest thing to say about C++98 on this machine is that its abstraction and its bill arrive together. A template, a class, and a throw each bring run-time machinery that Z98 was built to avoid, and the machinery is what makes the 32 MB budget tight. The chapter does not say the abstraction is false or the price is unfair — it says both are real, and that the manual-vtable idiom is often the better trade because most era modules want the shape of the abstraction without the machinery behind it. Where the abstraction is the point, the previous paragraphs said so, and this page has not one word against using C++98 there.

The way over it

There are two ways over, and they answer different questions. The first is how to use C++98 in a project that is otherwise Z98 or C89. The second is how to get the same job done in Z98 when the abstraction turns out not to be needed.

Using C++98 across the seam. Z98 emits C89, so the seam to C89 is invisible: both sides are plain C symbols. The seam to C++98 is real, because C++98 mangles names and C89 does not. The compiler's own name mangling is most of the story, and a two-line probe shows it. A C++ function gets an encoded symbol; the same function declared extern "C" keeps its plain name: 

$ nm mangle | grep add
0000117d T _Z11mangled_addii
00001194 T unmangled_add

So a C++98 module that Z98 is to call must expose extern "C" entry points, and those entry points must be written not to let an exception cross the boundary: a C++98 throw reaching a frame with no C++ unwinder is undefined behavior. The era's convention was exactly this: wrap the C++ implementation in a small extern "C" surface that translates failures to status codes and out parameters. That surface is the C++ equivalent of the C89 header in the previous chapter, and chapter 11, Talking to C (planned), gives the full interop detail — the calling conventions, the @cInclude rule, and the mangling of Z98's own names. The honest difference from the C89 case is that this wrapper is work you have to do, where the C89 seam was work you did not.

Getting the job done in Z98. For each thing a module reaches for C++98 to get, the volume has already named the Z98 shape that does it without the machinery, and each is available on the seed compiler:

  • A generic container? Write the concrete container, one per element type. It is the same code the template would generate, written by hand and readable in the source. Volume II chapter 16 is the measurement; the compiler's own concrete hash maps are the proof.
  • An object with behavior? A struct of function pointers plus one erased data pointer, built by an init function. That is the manual vtable, and it dispatches exactly as a virtual call does, with no hidden pointer and nothing to look up at run time.
  • Cleanup on every exit? defer and errdefer run cleanup as the scope exits, including the failure path, and the arena reclaims the whole region in one call. There is no destructor, and there is nothing to unwind.
  • Failure across frames? An error union carries the failure in the return type, try propagates it, catch handles it, and errdefer rolls back partial work. It is the checked path rather than the unwinding one, and it costs a branch, not a runtime.
  • A type open across unknown element types at run time? This is the one case with no Z98 shape that matches C++98's, because Z98 has no run-time type oracle and no open generics. When a program genuinely needs either, C++98 is the era tool, and the seam above is how it joins the project.

Put together, the rule is the previous chapter's rule with C++98 in the other slot. Choose C++98 where its abstraction is the point and the 32 MB budget carries the machinery; choose Z98 where the shape is wanted but the machinery is not; connect the two at the C ABI, with an extern "C" wrapper on the C++98 side. The decision is per module, and it is reversible, because both sides end up as object files the same linker accepts.

The load-bearing fact of the previous chapter is unchanged and it is worth repeating here, because it is what makes the whole comparison usable: Z98 emits C89, so it links with the era's objects directly. The only addition C++98 makes is that its side of the seam has to be declared rather than assumed. That is the whole difference, and it is a difference in the wrapper, not in the machine.

Common mistakes

The mistakes below are the ones a reader makes when C++98 is treated as free, or when the seam to it is assumed to be as quiet as the seam to C89.

Treating C++98's abstraction as free. It is not decoration. Every polymorphic object is one word larger, every polymorphic class brings a table and its type information, every template instantiation is a body in the binary, and exceptions bring an unwinder and per-function tables. None is large; all of them together, spread across a large program, are what makes the 32 MB budget tight. The measure before the choice is the size of the objects and the number of types, and both are visible before you commit.

Expecting to call a C++98 method directly from Z98. C++98 mangles names, so a call from C or Z98 cannot name the symbol. The way over is the extern "C" wrapper shown above. This is the one place the C++98 seam is materially more work than the C89 seam, and it is the answer to the first mistake a reader makes after the previous chapter.

Letting an exception cross the extern "C" boundary. A throw that leaves a C++98 translation unit into a frame compiled as C has no unwinder to catch it, and the behavior is undefined. The wrapper's job is to catch the exception inside C++98 and return a status or an out parameter that the C side can check. If that feels like reinventing error unions, it is: it is the C++ side doing by hand what Z98 does in the type.

Using exceptions for ordinary control flow. A throw/catch pair for a condition the code expects is the most expensive way to write a branch on this machine, because it drags in the unwinder's tables for a path that is not exceptional. The Z98 shape is the error union, and the C++98 shape for a failure the caller expects is a return value it can check. Reserve exceptions for what they are for: a failure the local code cannot handle.

Assuming every era C++ compiler implements the whole standard. MSVC 6 and Borland 5.02 predate or partly implement the 1998 standard, and a template that builds on a modern compiler may need workarounds there. This is era context and it is marked as opinion, but it is the reason a C++98 module for this machine is written to the machine's dialect rather than to the standard's full text, and it is why the blueprint says the era's implementations must be tolerated.

Rewriting a working C++98 module “for purity.” The mirror of the previous chapter's Common mistakes and the same error: a stable, tested module is not improved by being moved to another language. If it is about to be reworked and its abstraction turns out not to be needed, that is the moment to move it. Until then, the module's job is to work, and the seam lets the new code be written in Z98 beside it.
