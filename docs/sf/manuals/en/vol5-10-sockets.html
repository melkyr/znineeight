Sockets under Z98

This guide starts WinSock with WSAStartup, runs the TCP socket lifecycle through the std.net surface, builds a complete loopback sample on Linux and under wine, and links the Windows build with -lwsock32.

Prerequisites

  • The compiler rebuilt from the seed at /tmp/manual_seed/zig1_5_clean, with the standard library beside it in /tmp/manual_seed/lib/. If it is not there yet, follow Rebuild the compiler from seed first.
  • A Linux host with a 32-bit-capable gcc and bash (the sample uses the loopback device, so no network is needed).
  • For the Win9x step, the committed cross harness under scripts/win32_cross/ plus i686-w64-mingw32-gcc and 32-bit wine. On a real Windows 9x machine use the emitted build_target.bat instead; the OpenWatcom build_owc.bat path is emitted but not run on this host.
  • The repository checked out, so the sample docs/sf/manuals/src/vol3/http-mini.z98, the server example examples/z98/mud_server, and the portable fixtures under repro/mi_matrix/stdlib_net_*_xmod are present. Every command runs from the repository root, /workspace/znineeight.
  • For the surface and the platform layer beneath it, keep the Volume IV Standard library and The PAL pages open.

The idea

std.net is not a protocol framework; it is a set of target-selected extern bindings, one module, sf/src/std_net.zig, re-exported by the standard library. On the Windows target it binds wsock32, the Winsock 1.1 import library, through winsock.h; on Linux it binds the C library's socket functions. The target is chosen at compile time: the module's @isWindows() guards prune the branch that does not apply before any C is written, so one source serves both.

The first line of the module pulls in a small target-neutral header, net_prelude.h, which opens with a platform switch: windows.h and winsock.h plus #pragma comment(lib, "wsock32.lib") on Windows, the POSIX socket headers otherwise. The system header is the single declaration source for every entry point. Because std.net owns the words accept, connect, send, recv, close, and select, the raw externs are declared with an _os suffix that net_prelude.h maps back to the real OS symbol.

std.net declares 19 extern "stdcall" functions in all. The blocking TCP and startup core is these fifteen: 

pub extern "stdcall" fn htons(x: u16) u16;
pub extern "stdcall" fn htonl(x: u32) u32;
extern "stdcall" fn socket(af: i32, typ: i32, proto: i32) i32;
extern "stdcall" fn bind(s: i32, name: *const void, namelen: i32) i32;
extern "stdcall" fn listen(s: i32, backlog: i32) i32;
extern "stdcall" fn setsockopt(s: i32, level: i32, optname: i32, optval: *const void, optlen: i32) i32;
extern "stdcall" fn accept_os(s: i32, addr: *void, addrlen: *void) i32;
extern "stdcall" fn connect_os(s: i32, name: *const void, namelen: i32) i32;
extern "stdcall" fn send_os(s: i32, buf: [*]const u8, len: i32, flags: i32) i32;
extern "stdcall" fn recv_os(s: i32, buf: [*]u8, len: i32, flags: i32) i32;
extern "stdcall" fn select_os(nfds: i32, readfds: *void, writefds: *void, exceptfds: *void, timeout: *const void) i32;
extern "stdcall" fn close_os(fd: i32) i32;
extern "stdcall" fn closesocket(s: i32) i32;
extern "stdcall" fn WSAStartup(wVersion: u16, lpWSAData: *void) i32;
extern "stdcall" fn WSACleanup() i32;

Four more — sendto, recvfrom, WSAGetLastError, and ioctlsocket — back the UDP and non-blocking surfaces. The convention is not optional: Winsock cleans its own stack, and declaring an entry point cdecl links and then corrupts the stack at the call. Every Winsock entry in std_net.zig is stdcall.

The public API is the small surface those externs wrap. A socket is an i32 and failure is -1; a transfer returns a byte count and a negative number is the error channel.

Function Returns What it does
init() i32 WSAStartup(1,1) on Windows; 0 elsewhere
cleanup() void WSACleanup() on Windows; nothing elsewhere
createTcpServer(port) i32 socket + bind; listening handle or -1
createTcpClient(port) i32 socket + connect to 127.0.0.1; handle or -1
bindListen(fd, backlog) i32 listen; 0 or -1
accept(fd) i32 accept a pending connection; handle or -1
connect(fd, port) i32 connect an existing handle; 0 or -1
send(fd, buf, len) / recv(fd, buf, len) i32 transfer up to len bytes; count or -1
close(fd) void closesocket on Windows; close elsewhere
select(nfds, r, w, e, ms) i32 wait for readiness; ready count, 0 on timeout, -1 on error
fdZero(s), fdSet(fd, s), fdIsset(fd, s) void / void / bool clear, set, and test a socket in an fd_set

WinSock adds one rule no other library here has: call WSAStartup before anything else. A program that calls socket, bind, or send first does not get a handle, it gets a failure. The driver is std.net.init(), which is that call on Windows and a 0-returning no-op elsewhere; cleanup() releases it. The lifecycle in between is the same list whatever the program: create, bind, listen, select for readiness, accept, transfer, close — and close every handle on every path.

Steps

  1. Start at the repository root. 

    $ cd /workspace/znineeight

  2. Run the committed portable net fixtures through the standard-library gate. The stdlib_net_*_xmod fixtures exercise the UDP surface (udpBind, udpSendTo, udpRecvFrom) and the non-blocking surface over real loopback sockets; each fixture declares its port in a ports.txt. The gate emits each fixture, links it with the gcc -m32 -std=c89 flag set, runs it, and diffs stdout and the exit code against the committed goldens.

  3. Build and run the complete sample on Linux. http-mini.z98 binds a listener, opens a loopback client to its own port, waits with select, accepts, reads one fixed HTTP/1.0 request, and writes one fixed response. Emit it, run the emitted Linux build script, and run the program. 

    $ rm -rf /tmp/manual_out16 && mkdir -p /tmp/manual_out16
$ timeout 120 /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out16 docs/sf/manuals/src/vol3/http-mini.z98
$ cd /tmp/manual_out16 && timeout 120 sh build_target.sh linux http-mini
Building for linux...
Built: http-mini
$ timeout 120 ./http-mini | tee /tmp/manual_out16/http-mini.linuxstdout
http-mini: listening on port 18088
http-mini: accepted a connection
http-mini: request GET /hello HTTP/1.0
http-mini: served 100 bytes
http-mini: client received 100 bytes
http-mini: done

    Six lines, one per part of the lifecycle: bind and listen, accept, the parsed request line, the response write, the client read, and the shutdown. The two 100s are the same response counted at both ends — the server sending it and the client receiving it — the simplest proof that the bytes made the round trip. On Linux init() returned 0 and the WSAStartup branch never ran.

  4. Cross-build the same sample for Win9x and run it under wine. The committed harness emits with -osw, compiles the C89 with i686-w64-mingw32-gcc, links the Windows import library -lwsock32, runs the .exe under a dedicated 32-bit wine prefix, and compares the captured stdout byte-for-byte against the Linux baseline. Save the Linux output from Step 3 as the parity base first. 

    $ cd /workspace/znineeight
$ timeout 120 env ZIG1=/tmp/manual_seed/zig1_5_clean PARITY_STRIP_CR=1 \
    WINEPREFIX=/tmp/wine32 WINEARCH=win32 \
    bash scripts/win32_cross/cross_parity.sh \
    docs/sf/manuals/src/vol3/http-mini.z98 /dev/null \
    /tmp/manual_out16/http-mini.linuxstdout /tmp/manual_win16/http-mini
XRUNRC=0
WINE_RC=0
PARITY=OK

    XRUNRC=0 is the cross-build (dump, compile, link), WINE_RC=0 is the wine process, and PARITY=OK means the Windows stdout matched the Linux baseline byte-for-byte. This host measured the Windows run as wine-8.0; the bind succeeds because std.net now calls WSAStartup first. The one thing this host cannot claim is OpenWatcom: -osw also writes build_owc.bat for wcc386/wlink, carrying library wsock32, and that script is emitted and documented, not run. The figure is the real-machine proof.

    -lwsock32 is not optional on the Windows side. Every @import("std") program emits the network module std_net_*.c, even a stdio-only one, so the mingw link needs the winsock import library. The emitted build_target.sh sets LIBS="-lwsock32" in its mingw branch for exactly this reason; a hand-rolled link without it fails with undefined reference to '_imp__recv@16' or '_imp__WSAStartup@8'.

Verify it worked

Each step above is a recorded run of a committed artifact, so re-running the commands reproduces it. Step 2's gate must end in STDLIB GATE OK and 0 FAIL: the five loopback and non-blocking fixtures matched their committed stdout and exit code. Step 3 must print the six lines with the two 100s. Step 4 must print XRUNRC=0, WINE_RC=0, and PARITY=OK — the Win9x build bound its socket under wine-8.0 and matched the Linux baseline byte-for-byte, which is the measured wine bind class. Step 5 must end with the two md5s 66c8f0abb926cca7baf9a0d1692ab318 and 93147d0f0bbd983a9d844fea8b7a6fa7 and the three server lines.

Common mistakes

  • Calling a socket function before WSAStartup. WinSock requires it first; without it socket fails and the handle is -1, with WSANOTINITIALISED (10093) from WSAGetLastError. Call std.net.init() before createTcpServer or createTcpClient, and call cleanup() at the end.
  • Treating the handle as unsigned. There is no unsigned socket rule in std.net: the handle is i32 and failure is -1. Check < 0 or == -1; do not store handles in unsigned types.
  • Assuming send sends everything. A successful send may transfer fewer bytes than you passed; a short count is not an error. Loop until the buffer is gone, and treat 0 or a negative return as failure. The sample's sendAll is that loop.
  • Assuming one recv is one message. TCP is a byte stream: a single recv may return part of a request or two requests at once. For the sample's fixed request one read is enough; a real server reads until it has a complete request line and body.
  • Reading fd_set directly. The type is an opaque blob. Clear it with fdZero, add with fdSet, and test with fdIsset. The Windows layout (a count followed by handles) and the POSIX layout (a bitmask) differ, and the helpers are the portable way to touch it.
  • Forgetting the timeout on a blocking read. A blocking accept or recv waits forever when nothing arrives. Use select with a millisecond timeout before the blocking call, as the sample does; a negative timeout means block, the opposite of what a first server wants.
  • Forgetting extern "stdcall". Winsock is a stdcall API. Declaring an entry point cdecl links and then corrupts the stack at the call. Do not declare the Winsock functions yourself: std.net already has them with the right convention.
  • Reaching for the old socket builtins. @socketCreate and its siblings were removed; the compiler stops with error[3000]: unsupported builtin function and emits no C. Import std and use std.net.
  • Closing the listening handle when a connection ends. accept returns a new handle for the connection; the listening handle stays open. Close the accepted handle when the conversation is over and keep accepting on the listening handle, or the server shuts down after one client.
  • Dropping -lwsock32 in a hand-rolled Windows link. Every std importer emits std_net, so the mingw link needs the winsock library even for a program that never opens a socket. Prefer the emitted build_target.sh, whose mingw branch already adds it.
