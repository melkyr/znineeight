Structs

A struct is a named bundle of fields laid out in declaration order. Z98 spells the type const S = struct { field: T, ... };; a variable of that type is built with a brace literal .{ .field = value, ... } and read with the ordinary dot. This page is the lookup for the declaration syntax, the literal and field-access rules (including the uninitialized-field behavior), the 32-bit layout model (declaration order, per-field alignUp, total rounded to the maximum alignment, and the align-8 model for i64, u64, f64), the layout builtins and their rejects, and the packed struct bit rules.

The authority is the parser (parserParseStructType at sf/src/parser.zig:1318-1385), the layout math (layoutCompute at sf/src/type_resolver.zig:275-401, with alignUp at sf/src/type_registry.zig:336), the packed layout (typeRegistryComputePackedLayout at sf/src/type_registry.zig:1052-1087), the packed-field gate (semanticAnalyzerGatePackedFields at sf/src/semantic_analyzer.zig:1996-2034 and semanticAnalyzerPackedFieldTypeAllowed at sf/src/semantic_analyzer.zig:1980-1994), and the introspection check (semanticAnalyzerCheckIntrospectionBuiltin at sf/src/semantic_analyzer.zig:1390-1463). Every rule and reject below was reproduced on seed v90; the reused fixture or sample is named where one exists.

Declaration syntax

A struct declaration is an ordinary const whose value happens to denote a type. The name occupies no storage; it is the recipe. Fields are written name: Type, comma-separated, in the order they will occupy memory. 

const Vec2 = struct {
    x: i32,
    y: i32,
};
Form Spelling Notes
named struct const S = struct { name: T, ... }; The form this page documents. A trailing comma is optional.
tuple type struct { T1, T2, ... } Positional elements; documented on the tuples page (planned). The emitted C fields are _0, _1, …
packed struct const P = packed struct { name: uN, ... }; Bit-packed; see Packed structs below.

The parser requires a struct to be all named or all positional. A mix is error[2000] struct fields must be all named or all positional (tuple), and a positional field inside a packed struct is error[2000] packed structs cannot have positional tuple fields (both measured; each specific message is followed by a generic error[2000] unexpected token at the same span).

A struct type carries no functions. There is no method syntax and no field named by a call; an operation that belongs to a type is a free function whose first parameter is the value or a pointer to it. See Types for the type-kind list and Pointers for ptr.field auto-dereference.

Literals and field access

A struct value is built from a brace literal with the field names spelled after a leading dot. The literal has no type of its own; it is typed by the destination (the variable's annotation, an assignment target, or a call parameter). 

var s: Sprite = .{
    .id = 7,
    .origin = .{ .x = 1, .y = 2 },
    .scale = -3,
};
Rule Behavior (measured on seed v90)
Field names Each field is written .name = value; the leading dot is required.
Typing The literal is typed by its context. A nested struct field takes its own brace literal.
Omitted fields Not zero-filled. A literal that omits a field compiles, and the omitted field holds whatever the memory already contained. Write every field you intend to read, or write = undefined and fill the value before use.
No initializer var s: S; with no initializer rejects error[3014] variable must be initialized; use '= undefined' to opt out. Writing var s: S = undefined; is accepted.
Read / write s.f reads or (in assignment position) writes the field. Nested access chains the dots: s.origin.x = 5;.
Pointer base p.f on a single-level pointer to struct auto-dereferences (emitted as p->f); a **S needs pp.*.f.
Address of a field &s.f is a pointer to the field type (&s.origin is a *Vec2).
Assignment Struct assignment copies the value: var copy: Sprite = s; is independent of s afterward.
void field A void field is legal and readable. It receives the current offset and adds no size and no alignment; measured, struct { v: void, a: i32, w: void, b: u8 } is size 8, alignment 4, with a at 0 and b at 4.

The uninitialized-field rule is the language-wide “undefined is not zero” rule. This program sets only the named fields and reads them back; a field left out of the literal would carry indeterminate bytes: 

var s: Sprite = .{ .id = 7, .origin = .{ .x = 1, .y = 2 } };
std.io.print("{} {} {}\n", .{ s.id, s.origin.x, s.origin.y });
// 7 1 2

The reuse source is the Volume II sample src/vol2/shapes.z98, which builds a nested two-struct value and prints every field; its measured output is reproduced in the layout section below.

Layout model

The layout rule is one sentence. Start a cursor at offset 0. For each field in declaration order, round the cursor up to the field's alignment, record that as the field's offset, and advance the cursor by the field's size. When every field is placed, round the total up to the largest alignment any field required; that is the struct's size and alignment. Fields are never reordered. This is exactly layoutCompute (sf/src/type_resolver.zig:285-303) with alignUp(v, a) = (v + a - 1) & ~(a - 1) (sf/src/type_registry.zig:336).

Type Size Align Notes
void 0 0 A field of this type adds nothing to the cursor.
bool 1 1 Also u8, i8, c_char.
u16 / i16 2 2  
u32 / i32 / usize / isize / pointer 4 4 The 32-bit model makes all pointers 4/4.
u64 / i64 / f64 8 8 See the align-8 model below.

An arbitrary-width integer uses the smallest power-of-two carrier that holds the width, so @sizeOf/@alignOf report the carrier (1/2/4/8) while @bitSizeOf reports the declared width; this matches Types. A nested struct contributes its own size and alignment to the outer layout like any other field.

An empty struct struct {} has no fields, so the cursor stays at 0 and the min-1 rule gives it size 1 / align 1 (@bitSizeOf is 8); the emitted C body is unsigned char _[1]; so the built binary's layout agrees with the folded one. Nesting an empty struct as a field therefore advances the outer cursor by one byte.

Worked for the two three-field examples and for the Volume II Sprite:

Type Size / Align Offsets (measured)
struct { a: u8, b: i64, c: u8 } 24 / 8 a 0, b 8, c 16
struct { b: i64, a: u8, c: u8 } 16 / 8 b 0, a 8, c 9
Vec2 { x: i32, y: i32 } 8 / 4 x 0, y 4
Sprite { id: u8, tint: u32, width: u16, height: u16, origin: Vec2, scale: i64 } 32 / 8 id 0, tint 4, width 8, height 10, origin 12, scale 24

Field order is therefore a real decision. The same three fields { a: u8, b: i64, c: u8 } occupy 24 bytes, but moving the i64 first drops the total to 16. Measured output for the layout probe on seed v90: 

S 24/8/0 8 16
Sbit 0 64 128
R 16/8 0 8 9
Vec2 8/4 0 4
Sprite 32/8 0 4 8 10 12 24

The Sbit row is the byte offset times eight: on a plain struct, @bitOffsetOf is @offsetOf × 8.

Frozen align-8 model (FX14)

The compiler is single-target 32-bit and its layout model is the contract: i64, u64, and f64 are size 8 / alignment 8, and every composite that contains one inherits the maximum member alignment. So struct { a: u8, b: i64, c: u8 } is 24 bytes, alignment 8, with b at 8 and c at 16. The emitted C pins that model on every supported host compiler: each program's 64-bit declarations route through per-program carrier typedefs 

typedef long long <carrier> Z98_ALIGN8;
typedef unsigned long long <carrier> Z98_ALIGN8;
typedef double <carrier> Z98_ALIGN8;

and the shared zig_compat.h typedefs z64/zu64/f64 carry the same Z98_ALIGN8. On gcc/clang/mingw that macro is __attribute__((aligned(8))); on MSVC/OpenWatcom it is empty because their 32-bit defaults (/Zp8, -zp8) already align 64-bit scalars to 8. A packing override such as /Zp4 or -zp4 breaks the pin and is not supported. Packed aggregates are exempt (they are bit-packed byte arrays; a 64-bit packed field rejects error[3000]).

The reused fixture repro/mi_matrix/stdlib_layout_align8_xmod pins both sides of the model: it prints the folded @sizeOf/@alignOf/ @offsetOf values and then measures the real emitted-C layout in the built binary with @ptrToInt field offsets and array strides. Its 22 real-layout rows all report -ok, including the cross-module helper.HS { a: u8, b: i64, c: u8 } row. The Volume II sample src/vol2/shapes.z98 exercises the same model for Vec2 and Sprite.

Layout builtins

Five builtins read a type's layout at compile time. They are recognized by name, folded before any C is emitted, and take the type rather than a value.

Form Plain struct Packed struct
@sizeOf(T) padded byte size (total_bits + 7) / 8, minimum 1
@alignOf(T) strictest field alignment 1
@bitSizeOf(T) byte size × 8 sum of the field widths
@offsetOf(T, "f") the byte offset the field's bit offset divided by 8 (rounded down)
@bitOffsetOf(T, "f") byte offset × 8 the field's bit offset

@offsetOf and @bitOffsetOf are struct-only (packed structs included). Every union kind, and every scalar, pointer, enum, array, slice, optional, or error-union target, rejects error[3072] expected struct type, found 'X' rather than folding to zero. The field name must be a string literal naming an existing field:

Construct Code Message (measured)
@offsetOf(U, "x") on a union error[3072] expected struct type, found 'U'
@bitOffsetOf(U, "x") on a union error[3072] expected struct type, found 'U'
@offsetOf(S, name) non-literal name error[3073] field name must be a string literal
@offsetOf(S, "zz") unknown field error[3073] no field named 'zz' in struct 'S'
@offsetOf(S) wrong argument count error[3074] expected 2 argument(s), found 1

The reused fixtures repro/mi_matrix/builtin_offsetof_xmod and repro/mi_matrix/builtin_bitoffsetof_xmod pin the plain-struct forms: for struct { c: u8, b: u32, d: u16 } the byte offsets are 0 4 8 and the bit offsets are 0 32 64. The corrected rule here supersedes any older text that allowed a union target with offset 0; the printed reference for these builtins is Builtins.

Packed structs

A packed struct is a struct written as bits. The fields are placed in declaration order, each starting at the lowest bit still free (LSB-first), with no padding between fields. A field that does not fit in the rest of a byte continues at bit 0 of the next byte. 

const Header = packed struct {
    version: u4,
    flags: u4,
    length: u8,
};
Rule Detail
Admitted fields bool (one bit) or an integer type whose declared width is at most 31 bits (u1…u31, i1…i31, and the named widths). A nested packed struct is admitted by its inner total width, even when that exceeds 31 bits; its own fields obey the same rule.
Bit order Declaration order, LSB-first; multi-byte fields land little-endian in the byte image.
Size / align @sizeOf is (total_bits + 7) / 8, minimum 1; @alignOf is 1. The emitted C is a byte array plus shift-and-mask code, not the host's bitfields.
@bitSizeOf The sum of the field widths. Bits above the last field belong to no field and are not written by the field stores.
Access Field reads and writes lower to generated bitfield load/store code. Whole-value moves of a nested packed sub-container (a literal element, a whole-field assignment, a whole-value read, or through a packed union member) lower per leaf: one bitfield load/store per leaf with composed offsets.

Two clean rejects remain, both level-0 error[3000]:

Shape Message (measured)
A whole-sub-container store whose access chain crosses a byte-aligned (natural) container field below the packed edge — no addressable-lvalue model for the bit slice. The symmetric whole-value read of the same chain works. cannot write a packed-struct leaf through a byte-aligned container field in a nested packed struct (unsupported store path)
A whole-value move of a type nested deeper than 32 packed levels (the per-leaf copy recursion is bounded), on either the store or the read site. cannot assign a whole packed-struct value to a nested packed-struct field (bit-slice store not supported) / cannot read a whole packed-struct value out of a nested packed-struct field (bit-slice load not supported)

A wide bool/integer field is rejected by the declaration gate before any layout runs:

Construct Code Message (measured)
packed struct { a: u32 } error[3000] packed struct field width must be <= 31 bits (u32/i64 etc. packed fields are not supported yet)
packed struct { a: f32 } error[3000] packed struct fields must be bool or an integer type (uN/iN); this field type is not allowed in a packed struct
packed struct { u1, u1 } positional error[2000] packed structs cannot have positional tuple fields

Measured layout and behavior on seed v90: 

Outer { head: u2, inner: Inner, tail: u2 }, Inner { a: u3, b: u3 }
Outer 2/1 bits=10 offbits_inner=2 offbyte_inner=0 3 5 6 3
Mix { x: u1, y: u3, z: u4 } 1/1 bits=8 byte=155 1 5 9
P { a: u12, b: u4 } 2/1 bits=16 b bit=12 byte=1
Q { a: u2, b: u3 } 1/1 bits=5
OuterBig { head: u1, inner: Big { a: u31, b: u31 }, tail: u1 } 8/1 bits=64

The OuterBig row is the nested-member rule: the inner type is 62 bits, wider than 31, and is still admitted as a member because a packed struct is admitted by its inner total width. The reused fixture repro/mi_matrix/packed_l3_nested_xmod pins the nested read-back (2 5 6 3 3), and repro/mi_matrix/packed_nested_wholeliteral_xmod pins the per-leaf whole-value moves. The boundary fixtures are repro/mi_matrix/packed_nested_whole_chain_reject_xmod (chain store reject), repro/mi_matrix/packed_nested_whole_depth_ok_xmod (a chain 33 packed levels deep still lowers per leaf and runs), and repro/mi_matrix/packed_nested_whole_depth_reject_xmod (one level deeper clean-rejects).

Padding bits are not data. A packed struct whose total bits are not a multiple of 8 leaves the high bits of the last byte outside every field; they are not written by the field stores and must not be read as if they were. Read the declared fields; the reused Volume II sample src/vol2/wire.z98 shows the field-wise encode/decode.

Measured gcc -m32 layout

The folded model values and the real layout of the built binary agree on gcc -m32, which is the transcript recipe's compiler. The emitted C keeps declaration order and routes the 64-bit fields through the aligned carriers, so the host's own 32-bit default (which would align a bare long long to 4) does not decide the layout:

Type Model = real (gcc -m32) Offsets
struct { a: u8, b: i64, c: u8 } size 24, align 8 a 0, b 8, c 16
struct { b: i64, a: u8, c: u8 } size 16, align 8 b 0, a 8, c 9

The check is the stdlib_layout_align8_xmod fixture: each row measures the running binary's real offset with @ptrToInt and compares it with the compiler's folded value, and every row is -ok. This is a layout-consistency pin, not a wire-format or cross-compiler ABI contract; if the exact byte image is the point, serialize fields one at a time or use a packed struct.
