Call C from Z98

This guide declares a C function with extern fn, brings in its real header with @cInclude, selects the right calling convention, and lets a struct cross the boundary by value.

Prerequisites

  • The compiler rebuilt from the seed at /tmp/manual_seed/zig1_5_clean, with the standard library beside it in /tmp/manual_seed/lib/. If it is not there yet, follow Rebuild the compiler from seed first.
  • A Linux host with a 32-bit-capable gcc (the emitted script uses gcc -m32 -std=c89).
  • The repository checked out, so the shipped samples docs/sf/manuals/src/vol2/builtins/cinclude.z98 and docs/sf/manuals/src/vol3/getenv.z98 are present. Every command runs from the repository root, /workspace/znineeight.
  • For the full contract beneath this procedure, keep Volume III — Talking to C open.

The idea

There is no marshalling layer to learn. Z98 emits C89, so a Z98 module is a C translation unit and a Z98 function is a C function by the time the linker sees it. The seam between your module and a C library is the ordinary C ABI, and the only thing you write is the declaration. Two directives cover it: extern fn borrows a C symbol, and @cInclude pulls the library's own header into the generated translation unit so both compilers check the same text.

The declaration is the whole contract, and the compiler cannot verify it against the library for you. The Z98 type checker checks your call sites against the signature you wrote; the C compiler checks your call against the header when you include it. Include the real header and both checks are real.

Steps

  1. Start at the repository root and make an output directory. The compiler requires the output directory to exist. 

    $ cd /workspace/znineeight
$ mkdir -p /tmp/manual_out

  2. Bring a C header in with @cInclude. The shipped sample docs/sf/manuals/src/vol2/builtins/cinclude.z98 puts one module-level include above its declarations, then prints a line: 

    @cInclude("stdio.h");

const std = @import("std");

pub fn main() void {
    std.io.print("include ok\n", .{});
}

    Emit, link, and run it: 

    $ /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol2/builtins/cinclude.z98
$ cd /tmp/manual_out && sh build_target.sh linux cinclude
Building for linux...
Built: cinclude
$ ./cinclude
include ok

    The include is emitted into the sample's generated header, verbatim and in the order written, right after the compiler's own runtime headers: 

    #include "zig_compat.h"
#include "zig_special_types.h"
#include "stdio.h"
#include "std_io_59DB29D9.h"

    That placement matters: every translation unit that includes this module's header sees the C declaration too. Note the quotes — @cInclude("stdio.h") emits #include "stdio.h", not angle brackets. A quoted include still finds system headers, so this is invisible until a header of the same name sits beside your module, which is when you want the local one anyway.

  3. Declare and call C functions with extern fn. The shipped sample docs/sf/manuals/src/vol3/getenv.z98 declares two C run-time functions, calls them, and translates the one C result that can be null: 

    @cInclude("stdlib.h");
@cInclude("string.h");

const std = @import("std");

extern "c" fn getenv(name: [*]const u8) [*]u8;
extern "c" fn strlen(s: [*]const u8) usize;

// Look up one environment variable. getenv returns a C `char *`: the address
// of the value, or a null pointer when the name is not set.
fn find(name: []const u8) [*]u8 {
    return getenv(name.ptr);
}

pub fn main() void {
    var present: []const u8 = "PATH";
    var missing: []const u8 = "Z98_CH11_NOT_SET";

    var p: [*]u8 = find(present);
    if (@intFromPtr(p) != 0) {
        std.io.print("PATH: set\n", .{});
    } else {
        std.io.print("PATH: unset\n", .{});
    }

    var q: [*]u8 = find(missing);
    if (@intFromPtr(q) != 0) {
        std.io.print("Z98_CH11_NOT_SET: set\n", .{});
    } else {
        std.io.print("Z98_CH11_NOT_SET: unset\n", .{});
    }

    var msg: []const u8 = "talking to C";
    std.io.print("strlen: {}\n", .{strlen(msg.ptr)});
}

    Emit, link, and run it: 

    $ /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol3/getenv.z98
$ cd /tmp/manual_out && sh build_target.sh linux getenv
Building for linux...
Built: getenv
$ ./getenv
PATH: set
Z98_CH11_NOT_SET: unset
strlen: 12

    The type mapping is direct. A C char * is [*]const u8 when Z98 only reads through it and [*]u8 when it may write; a C size_t is usize, four bytes on this 32-bit target. A slice does not cross, because there is no C type for one: pass s.ptr and s.len as the two C parameters the library expects, exactly as a C caller would. getenv signals “not set” with a null pointer, and the sample translates that C fact into a Z98 decision once, at the call, with @intFromPtr(p) != 0. Error unions and optionals have no C representation; keep them on the Z98 side of the seam.

  4. Choose the calling convention. It is a string after extern, and the default is cdecl: extern fn f() and extern "c" fn f() declare the same thing. The other convention on this target is "stdcall", the one the 32-bit Win32 API uses: 

    extern "stdcall" fn MessageBoxA(hwnd: ?*void, text: [*]const u8, cap: [*]const u8, typ: u32) i32;

    The accepted spellings are "c" (or "cdecl") and "stdcall". Anything else is rejected at the string, before any C is emitted. The Volume III Talking to C page measured a one-line probe with extern "watcom", and it stops like this: 

    $ /tmp/manual_seed/zig1_5_clean -o out callconv_bad.z98
callconv_bad.z98:1:7: error[3045]: unknown calling convention in `extern`
extern "watcom" fn foo(x: i32) i32;
       ^^^^^^^^

    There is no silent fallback to cdecl, which is the safe choice: a stdcall function mis-declared as cdecl would link and then corrupt the stack. The emitted C carries the convention as a macro so one source builds for every toolchain. The compiler writes this into zig_compat.h: 

    #if !defined(_WIN32)
#define Z98_STDCALL
#elif defined(_MSC_VER) || defined(__WATCOMC__)
#define Z98_STDCALL __stdcall
#else
#define Z98_STDCALL __attribute__((stdcall))
#endif

    Off Windows the macro is empty, so a Linux default-cdecl build is unchanged. On Windows it becomes the toolchain's own spelling. A function pointer's type includes its convention, so a stdcall function value may not be assigned to a cdecl slot; that mismatch is rejected with the level-0 error[3000].

  5. Pass a struct by value. A Z98 struct is a C struct with the same layout, so the declaration is direct. Define both shapes and declare one extern for each, as the Volume III sample does: 

    const Point = struct { x: i32, y: i32 };
const Boxed = struct { tag: u8, value: i64 };

extern "c" fn c_point_sum(p: Point) i32;
extern "c" fn c_boxed_take(b: Boxed) i32;

    The emission is recorded on the Talking to C page. The generated C contains the C structs you would have written by hand, and the call is an ordinary by-value C call, with the value copied into a temporary: 

    struct zT_EAA8EF31_Point {
	int x;
	int y;
};
struct zT_2E48BFE3_Boxed {
	unsigned char tag;
	zT_C69B2266_i64 value;
};
...
zT_12 = p;
zT_13 = c_point_sum(zT_12);

    The layout is fixed by the compiler's frozen 32-bit model. On this target i64, u64, and f64 are size 8 and alignment 8, and any composite containing one inherits that alignment. Boxed above is the example: a one-byte tag, seven bytes of padding, then the 64-bit value — size 16, alignment 8. Every 64-bit declaration is routed through an aligned carrier typedef so gcc, mingw, MSVC, and OpenWatcom all produce the same bytes. Define a boundary struct the way the header declares it and do not override the packing.

Verify it worked

The transcripts in Steps 2–3 are the recorded output of the committed samples; re-running those commands reproduces them. Step 2 shows a module-level @cInclude emitting include ok. Step 3 shows two extern "c" calls returning across the seam: PATH is set, the deliberately absent name is unset, and C's strlen answers 12 for "talking to C". Step 4 documents the accepted spellings (cdecl and stdcall) and shows the parser rejecting an unknown convention with error[3045]; that reject, and the include-in-function reject in Common mistakes, are the measured rejects recorded on the Volume III Talking to C page rather than fresh runs here. Step 5 is likewise the struct emission recorded on that page, cited rather than re-emitted. If your include ok and your three getenv lines match, the C seam is wired correctly.

Common mistakes

  • Putting @cInclude inside a function. The builtin is module level only. In statement position it parses but the type resolver has no case for it, and the compiler reports an internal error rather than a designed diagnostic. This is the reject measured in Volume III: 
    $ /tmp/manual_seed/zig1_5_clean -o out cinclude_stmt.z98
cinclude_stmt.z98:1:2: error[3020]: internal error: unhandled node kind in type resolution
pub fn main() void {
  ^
    Move the include to the top of the file, beside the declarations. It emits no .c and returns a non-zero status, so the misplaced build cannot ship.
  • Expecting a bare extern to emit a prototype. A non-variadic extern declaration does not write a prototype into the generated C; only a variadic one does. The call then compiles as an implicit declaration, which is a warning under the supported build and wrong for any return type other than int. Put the prototype in a header and @cInclude it.
  • Letting the declaration drift from the header. The Z98 type checker checks your call sites against your declaration, not against the library. Write i32 where the header says u32, or omit a parameter, and the Z98 side is clean while the C side is an ABI bug. Write the declaration from the header, line for line, not from memory.
  • Forgetting extern "stdcall" on a Win32 entry point. The 32-bit Windows API pops its own stack; declaring an API function as cdecl links and then corrupts the stack at the call. An unknown convention string stops the build with error[3045]; a wrong but accepted convention does not.
  • Passing a rich optional or an error union through the seam. Neither has an agreed C spelling, and a non-scalar optional in a boundary position can emit invalid C89. Pass C-shaped values — a pointer, a length, an integer code — and translate the result once, at the call.
  • Trying to use @cImport. It is not implemented. The supported pattern is a bare extern declaration for each function you call, plus @cInclude for the header that declares it. A program that writes @cImport stops at error[3000]: unsupported builtin function.
  • Overriding the struct packing. The 32-bit layout is pinned by the compiler's default alignment (8 for 64-bit scalars). A /Zp4 or -zp4 override changes the bytes a boundary struct occupies, so a struct that must match an operating system structure should leave the default alone and declare no 64-bit field the header does not have. Z98 has no extern struct, opaque, or vector type: define a boundary struct as an ordinary struct, and use *void where C uses an opaque handle.
  • Calling a Z98 function from C without export. Z98 mangles every name it defines, so a function written as helper has the symbol zF_<hash>_helper and C cannot find it by its source name. An export fn writes the plain, unmangled name and a prototype instead. An extern, by contrast, is never mangled: it is a promise about an existing C symbol and is emitted exactly as declared.

Where to go next

The exact contract behind every step here — the prototype rule, the include placement, the convention macro, struct-by-value layout, reserved identifiers, and name mangling — is Volume III, Talking to C. @cInclude is catalogued with the other builtins in Volume IV — Builtins, the extern grammar in Grammar, and the Platform Abstraction Layer that the standard library's own externs resolve against in The PAL; the Limits page lists extern struct/opaque/vector among the forms Z98 does not accept.
