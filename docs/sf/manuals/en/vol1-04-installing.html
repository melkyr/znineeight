Installing the Toolchain

The last chapter asked which machine you are on. This chapter installs the toolchain on it and proves the result: it unpacks the compiler's seed, confirms that the compiler runs, and builds the bundled example. There is still no code to write. When this chapter is done, your machine is ready and the first real program is one chapter away.

What installing means here

There is no installer, no package manager, and no network fetch. The disk carries the compiler's seed, a small archive named release/seed/zig1-seed.tgz that holds the compiler's own source, its runtime, and the standard library. Installing means turning that archive into a working compiler in a folder of your choosing.

What you end up with is a compiler binary and a standard library folder beside it. The compiler looks for that folder beside itself, so no extra option is needed to find it; a library kept somewhere else can be named with -I <dir>, but the manual always keeps it beside the compiler. Nothing is placed on the system PATH and nothing is registered with the operating system. You run the compiler by naming its path. That is deliberate: this manual is a disk you carry, not a system you modify.

The two machines are the ones from the last chapter. On Linux you build the compiler from the seed with gcc. On Windows 95 or 98 you use the compiler built for Windows. Either one is enough to follow this volume.

Path one: build the compiler on Linux

On Linux, one script does the whole job. Run it from the repository root, because it reads the compiler's source by a relative path: 

$ bash scripts/seed/build_from_seed.sh release/seed/zig1-seed.tgz /tmp/manual_seed

The first argument is the seed archive on the disk. The second is the folder to build into; the manual's examples use /tmp/manual_seed, but any folder you can write to will do. The script unpacks the seed, uses it to compile the current compiler source, and links the result with gcc. It then builds itself a second time and checks that the two builds are identical, so a successful run ends like this: 

...
[seed] two-hop closure OK: hop1 == hop2 == cd38f3167ca3e39982cc2d817b16dc70
=== [seed] Done: /tmp/manual_seed ===

When it prints Done, the toolchain is in place. The compiler is the file zig1_5_clean in the output folder, and the standard library it needs is the lib folder beside it. The name is the seed script's own; the manual's later commands name it by its full path, /tmp/manual_seed/zig1_5_clean.

Confirm the compiler runs

Before building anything, prove that the compiler is a working program. Run it by path, with no arguments: 

$ /tmp/manual_seed/zig1_5_clean
zig1 - Z98 self-hosted compiler - usage: zig1 [options] <input.zig>
  -mm<N>    hard pool budget in MB (default 64; pool.peak over budget -> ICE rc=3)
  -s<N>     spill level 0..6 (default 0 = all spills on disk; -s1..-s6 deactivate the
            first N spills to RAM in order AST,LIR,HASH,RES,SIDE,EXTRA: higher -s = more RAM,
            less disk I/O (pool= rises; -s6 = all in RAM -> pair with -mm128)
  -osl       compile target = linux (default); -osw = windows
  --target <linux|windows>  long-form target alias for -osl/-osw

That is the compiler's own usage message, and seeing it means the binary runs. You can also run it from inside its folder instead of by full path: 

$ cd /tmp/manual_seed
$ ./zig1_5_clean

Both forms say the same thing: the compiler is not on PATH, so you name it. Putting a program on PATH is a job for your shell's own documentation, and this manual does not set it up for you.

Build the bundled example

Now prove the whole pipeline. The disk carries a small example, hello.z98. The compiler reads it and writes a self-contained tree of C89 files into an output folder, and that tree carries its own build script. Run the three steps: 

$ mkdir -p /tmp/manual_out
$ /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol1/hello.z98
$ cd /tmp/manual_out && sh build_target.sh linux hello
Building for linux...
Built: hello
$ ./hello
Hello from Z98!

The first line creates the output folder, which the compiler requires to exist. The second translates hello.z98 into C89 and writes it, with the runtime and a build_target.sh, into /tmp/manual_out. The third compiles that C with gcc -m32 and links the program hello. The last one runs it, and it prints a single line. The compiler is installed and the pipeline works.

Path two: the compiler on Windows 95 or 98

On the target machine there is no bash and no gcc, so you do not run the seed script there. The seed archive also carries the compiler's own C89 source and the runtime it needs, and that source is the same for every target. On Windows 95 or 98 you build the compiler from it: unpack the archive, compile that C89 with OpenWatcom's wcc386, and link a console zig1.exe with wlink, following the conventions the companion src/build_owc.bat uses for programs. Keep the standard library in a lib folder beside zig1.exe; that is the compiler's default library location. As on Linux, nothing is installed system-wide and nothing is placed on PATH. Run the compiler from inside its folder, or give its full path.

The confirmation is the same test as on Linux: run zig1.exe with no arguments and it prints its usage. As on Linux, the compiler finds the standard library in the lib folder beside it, so a program that imports std builds with no extra option. The companion src/build_owc.bat, run from inside the emitted tree, then compiles the Windows-target C89 and links a console program. The bundled example builds there the same way and prints the same line as on Linux.

If you want to run the compiler from anywhere without giving its path, that is the system's own business: WinHelp on Windows 95 or 98 explains how. This manual keeps the toolchain in its own folder and names it when it runs it.

What you have now

A compiler in a folder, the standard library beside it, and a demonstrated build of the bundled example. That is the whole toolchain this volume needs. You will not install anything again: every later chapter reuses this compiler, and the command you have just run — emit, build, run — is the same shape every program in the volume follows.

One thing is worth saying plainly before you move on. The compiler you built is the current one; it is the only compiler this manual documents, and the commands and transcripts on this page were run against it before they were printed. If a command in a later chapter does not match what you see, the page is wrong, not your machine.
