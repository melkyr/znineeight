A Coroutine Program

Chapter 9 gave you the mechanism: a suspending function, a frame the compiler lays out, and a scheduler in std.async that drives it. This chapter spends that mechanism. It builds one small, complete program — a line echo server — and walks every line of it. The point is not the echo; the point is that the loop you would have written as a switch over a state variable is now an ordinary while loop that yields, and a network server is the shape where that trade pays for itself.

The program is called echo.z98 and it lives beside the other Volume III examples. It listens on a local port, accepts a connection, and runs one coroutine for that connection: read a line, echo it back, yield, repeat. To keep the chapter self-contained — and to make the program able to prove itself — a second coroutine in the same process plays the client. It sends three lines, waits for each echo, prints it, and closes. The scheduler drives both.

What is measured here. Which of the blueprint's two permitted shapes this chapter uses was not chosen by taste. Task 0 measured the transport on this host: after the WSAStartup fix, a Z98 server built with -osw binds, accepts, and serves under wine. The network shape is therefore the ruled one, and the alternate permitted shape — a cooperative task demo with N tasks suspending in a known order — was not needed. The program in this chapter is compiled with the seed-built compiler, run on Linux, and cross-built and run under the committed Windows harness. The transcript is that run, not a sketch.

What the program is

An echo server is the smallest server that exercises the parts that matter. It does not parse a protocol or hold a conversation; it reads a line from a socket and writes the same line back. What makes it interesting is that the work for one connection is spread across time. A line may not be fully arrived when you look; the client may send the next line before you have finished the last; the connection may close between two reads. A C programmer answers all of that with a state machine: a state field, a switch, and a buffer whose position is part of the connection's persistent state. Chapter 9 asked you to stop writing that. This chapter shows the replacement.

The replacement is a function that looks synchronous. The connection handler loops: read a line, echo it, repeat. There is no state field in the handler and no switch you maintain. When a line is not there yet, the handler suspends; the scheduler parks it and runs somebody else; when the socket has data, the scheduler resumes the handler exactly where it stopped. The compiler, not you, wrote the state machine.

That last sentence is the whole point, and the network is where it stops being an academic exercise. A single-threaded server is a program made of many half-finished tasks. Without coroutines you must encode each task's progress into data by hand. With coroutines you write each task as ordinary code and the compiler keeps the bookkeeping in a frame. The cost is one frame per task; the benefit is that the task reads like the algorithm it is.

The shape: one coroutine per connection

The blueprint names the shape directly: one coroutine per connection. It is a promise about how a real server is built, and it is worth stating honestly what the sample does and does not demonstrate.

The sample accepts exactly one connection. A production server would loop: accept a socket, initialize a fresh task with @asyncInit, register it with the scheduler, and go back to accept. Each accepted connection gets its own coroutine, its own child-frame pool, and its own buffer; the tasks are independent because the scheduler interleaves them cooperatively, and there are no data races because nothing preempts anything. Chapter 9's tasks.z98 showed three tasks round-robin; here the tasks happen to come from sockets instead of a loop counter. The addTask/@asyncInit pair is the same.

The sample limits itself to one connection for two reasons. The first is determinism: a single connection produces a transcript whose every line and every interleaving is fixed, so the chapter can promise that what is printed below is what the program prints. The second is self-containment: a server that waits for a client cannot be run by itself. Every Unix programmer knows the answer to that — open a second terminal — but a manual example has to build and run in one command to be verification rather than a story. So the program carries a client coroutine that connects to its own listener over loopback (127.0.0.1), and the two coroutines then talk to each other through the real socket path. It is the same bytes a remote client would send. The client coroutine exists to be the test; the server coroutine is the program.

That decision has one visible consequence worth naming, because it is a real constraint and not a convenience. Because the client is in the same process, the program must not wait for a connection that no one will make. The connection is established before the scheduler starts: the program creates the listening socket, connects the client socket to it, and only then accepts. The client's connect completes against the listener's backlog, so the subsequent accept returns immediately. On a real deployment the accept blocks in an outer loop and each accepted socket is handed to its own task; here the accept is already done by the time the tasks run.

The scheduler, driven from main

Nothing in the program happens because of a hidden runtime. main owns everything: the sockets, the line readers, the buffers, the context pools, the root frames, and the scheduler. The tasks run only when main ticks the scheduler, and main ticks it in waitAll until both tasks have finished. That is the Volume III model of concurrency in one sentence: the machine is single-threaded and cooperative, and the program decides when work runs.

Two details make this concrete. First, each task has a root frame, a fixed-size buffer that holds the coroutine's whole memory for its whole life, and a child-frame pool, the per-task arena that implicit awaits draw from. Both must be 8-aligned and both live in main, because the coroutine may be resumed on any tick and must never point at a buffer that has gone away. Second, the sockets are switched to non-blocking mode. A blocking recv inside a cooperative task would stall the scheduler and every other task with it; a non-blocking read that has no data returns a would-block, the task yields, and the scheduler moves on. This is exactly what makes the loop in the connection handler safe to write as a loop.

The line reading itself is handled by std.stream, the standard library's stream module. Its SocketLineReader wraps a caller-owned socket and a caller-owned buffer and enforces the line contract you want: strip the terminating \n (and the \r of a \r\n), return the final unterminated line at end of input, and return null at end of file. Two entry points exist over that contract. readSocketLineSync blocks; it is for a blocking socket and a plain (non-suspending) caller. readSocketLineAsync is the one this program uses: it calls the same non-blocking read, and when the read would block it does @asyncSuspend and resumes on the next tick. That single fact is why the connection handler can be a loop instead of a state machine — the suspend-and-retry lives in the reader, and the handler just calls it.

Piece Owned by Role

There are two coroutines here and each is suspending for a different reason, which is worth seeing. echoConnection contains no @asyncSuspend at all in its body. It becomes suspending because it calls readSocketLineAsync, which is suspending; the property propagates up the call graph exactly as chapter 9 described. echoClient is suspending for the same reason. Neither function says "I am a coroutine"; the compiler works it out from the calls they make.

The program

Here is echo.z98 in full. It is a little longer than tasks.z98 because a socket program has setup to do, but the coroutine half is small: two functions, and the loop in each looks like straight-line code. 

const std = @import("std");
const std_stream = @import("std_stream");

const PORT: u16 = 18080;
const BUF_SIZE: usize = 128;
const POOL_WORDS: usize = 512;

// The connection coroutine's parameters. The line reader and its buffer live
// in `main` for the whole run, so each coroutine holds only a pointer to them.
const ConnArgs = struct {
    sock: i32,
    lr: *std_stream.SocketLineReader,
    echoed: *i32,
};
const ConnRec = struct { ca: *ConnArgs };

const ClientArgs = struct {
    sock: i32,
    lr: *std_stream.SocketLineReader,
};
const ClientRec = struct { ca: *ClientArgs };

fn sendLine(sock: i32, msg: []const u8) void {
    _ = std.net.send(sock, msg.ptr, @intCast(i32, msg.len));
}

// One coroutine per connection: read a line, echo it back, yield.
fn echoConnection(ca: *ConnArgs) void {
    const nl: []const u8 = "\n";
    while (true) {
        const maybe = std_stream.readSocketLineAsync(ca.lr) catch return;
        if (maybe) |line| {
            _ = std.net.send(ca.sock, line.ptr, @intCast(i32, line.len));
            _ = std.net.send(ca.sock, nl.ptr, @intCast(i32, nl.len));
            ca.echoed.* += 1;
        } else {
            break;
        }
    }
    std.net.close(ca.sock);
}

// A tiny client coroutine, so the program is its own test driver.
fn echoClient(ca: *ClientArgs) void {
    const m0: []const u8 = "hello, echo\n";
    const m1: []const u8 = "coroutines are cooperative\n";
    const m2: []const u8 = "goodbye\n";

    sendLine(ca.sock, m0);
    const e0 = std_stream.readSocketLineAsync(ca.lr) catch return;
    if (e0) |line| {
        std.io.print("client got: {s}\n", .{line});
    }

    sendLine(ca.sock, m1);
    const e1 = std_stream.readSocketLineAsync(ca.lr) catch return;
    if (e1) |line| {
        std.io.print("client got: {s}\n", .{line});
    }

    sendLine(ca.sock, m2);
    const e2 = std_stream.readSocketLineAsync(ca.lr) catch return;
    if (e2) |line| {
        std.io.print("client got: {s}\n", .{line});
    }

    std.net.close(ca.sock);
}

pub fn main() void {
    if (std.net.init() != 0) {
        std.io.print("socket init failed\n", .{});
        return;
    }

    const server = std.net.createTcpServer(PORT);
    if (server < 0) {
        std.io.print("could not create server\n", .{});
        return;
    }
    if (std.net.bindListen(server, 5) < 0) {
        std.io.print("could not listen\n", .{});
        return;
    }

    var client = std.net.createTcpClient(PORT);
    if (client < 0) {
        std.io.print("could not connect\n", .{});
        return;
    }

    var conn: i32 = -1;
    var tries: usize = 0;
    while (conn < 0 and tries < 100000) : (tries += 1) {
        conn = std.net.accept(server);
    }
    if (conn < 0) {
        std.io.print("could not accept\n", .{});
        return;
    }

    std.net.setNonBlocking(&conn) catch return;
    std.net.setNonBlocking(&client) catch return;

    // Reader and buffer live in main for the whole run.
    var conn_buf: [BUF_SIZE]u8 = undefined;
    var client_buf: [BUF_SIZE]u8 = undefined;
    var conn_lr = std_stream.initSocketLineReader(&conn, conn_buf[0..]);
    var client_lr = std_stream.initSocketLineReader(&client, client_buf[0..]);

    var echoed: i32 = 0;
    var ca = ConnArgs{ .sock = conn, .lr = &conn_lr, .echoed = &echoed };
    var crec = ConnRec{ .ca = &ca };
    var cla = ClientArgs{ .sock = client, .lr = &client_lr };
    var clrec = ClientRec{ .ca = &cla };

    var conn_pool: [POOL_WORDS]u64 = undefined;
    var conn_frame: [POOL_WORDS]u64 = undefined;
    var client_pool: [POOL_WORDS]u64 = undefined;
    var client_frame: [POOL_WORDS]u64 = undefined;
    var tasks: [2]std.async.Task = undefined;
    var task_ptrs: [2]*std.async.Task = undefined;
    var sched_tasks: [2]*std.async.Task = undefined;
    var sched = std.async.schedulerInit(sched_tasks[0..]);

    // Client first: its first action sends a line, so the connection task
    // always has data waiting when it runs.
    task_ptrs[0] = &tasks[0];
    task_ptrs[0].ctx = std.async.contextInit(@ptrCast([*]u8, &client_pool)[0 .. POOL_WORDS * 8]);
    task_ptrs[0].frame = @asyncInit(task_ptrs[0].ctx, @ptrCast([*]u8, &client_frame), echoClient, @ptrCast(*const void, &clrec));
    task_ptrs[0].state = .ready;
    task_ptrs[0].cancel_requested = false;
    task_ptrs[0].result = @ptrCast(*void, &echoed);
    task_ptrs[0].arg = @ptrCast(*void, &clrec);
    task_ptrs[0].waiting_on = task_ptrs[0];
    task_ptrs[0].has_waiting_on = false;
    _ = std.async.addTask(&sched, task_ptrs[0]);

    task_ptrs[1] = &tasks[1];
    task_ptrs[1].ctx = std.async.contextInit(@ptrCast([*]u8, &conn_pool)[0 .. POOL_WORDS * 8]);
    task_ptrs[1].frame = @asyncInit(task_ptrs[1].ctx, @ptrCast([*]u8, &conn_frame), echoConnection, @ptrCast(*const void, &crec));
    task_ptrs[1].state = .ready;
    task_ptrs[1].cancel_requested = false;
    task_ptrs[1].result = @ptrCast(*void, &echoed);
    task_ptrs[1].arg = @ptrCast(*void, &crec);
    task_ptrs[1].waiting_on = task_ptrs[1];
    task_ptrs[1].has_waiting_on = false;
    _ = std.async.addTask(&sched, task_ptrs[1]);

    std.async.waitAll(&sched) catch {
        std.io.print("frame pool exhausted\n", .{});
    };

    std.net.close(server);
    std.net.cleanup();
    std.io.print("echoed {} lines\n", .{echoed});
}

Walking the program

The listing divides into four movements, and each is worth reading on its own: the two coroutines, the argument records they are initialized from, the setup in main, and the drive.

The connection coroutine

echoConnection is the server. It takes one argument, a pointer to a ConnArgs that carries the socket, a pointer to the line reader, and a pointer to the shared count of echoed lines. The body is the loop from chapter 9's argument, made real: 

while (true) {
    const maybe = std_stream.readSocketLineAsync(ca.lr) catch return;
    if (maybe) |line| {
        _ = std.net.send(ca.sock, line.ptr, @intCast(i32, line.len));
        _ = std.net.send(ca.sock, nl.ptr, @intCast(i32, nl.len));
        ca.echoed.* += 1;
    } else {
        break;
    }
}
std.net.close(ca.sock);

readSocketLineAsync returns an optional slice: a line when one is available, null at end of file. Under the covers it reads in non-blocking chunks; when a chunk would block it suspends, and the scheduler resumes the task on a later tick. The handler does not know or care how many ticks that takes. When a line comes back, the handler writes it to the socket with std.net.send, writes a newline after it, and counts it. Because the reader strips the newline, echoing the line means re-adding one explicitly. When the reader finally returns null — the peer closed — the loop breaks and the handler closes its own socket.

Compare that to the C89 version. In C89 you would own a state field on the connection, a buffer and a pos, and a switch that resumes mid-line. Every early return when the data was not ready is a jump out of a function whose local variables then have to be fields, because they must survive. The Z98 handler keeps those locals — maybe, line, the constants — as locals, and the compiler hoists the ones that are live across a suspension into the frame. That hoisting is the whole trade: the compiler writes the state machine so that you do not.

One detail is load-bearing and easy to miss. The reader and its buffer do not live in the coroutine's frame; the coroutine holds a pointer (ca.lr) to a reader that lives in main. This is deliberate. A reader is a fairly large struct, and keeping it in a caller-owned buffer rather than in the frame removes a whole class of "is this local still alive across the suspension?" questions. The rule the examples follow is general: the things a coroutine must not lose — frames, pools, readers, buffers that outlive a suspension — live in main or in a dedicated arena, and the coroutine holds pointers to them. What lives in the frame are the small locals the compiler is good at tracking.

The client coroutine

echoClient is the program's test driver, and it is deliberately dumb. It sends a line, then reads the echo, then prints it; it does that three times and closes. Each iteration is a send, an awaited read, and a print: 

sendLine(ca.sock, m0);
const e0 = std_stream.readSocketLineAsync(ca.lr) catch return;
if (e0) |line| {
    std.io.print("client got: {s}\n", .{line});
}

The read after the send is what makes the interleaving deterministic. The client sends, then immediately asks for the echo. There is no echo yet, so the reader suspends the client task and returns control to the scheduler. The scheduler runs the connection task, which finds the line waiting and echoes it. On the next tick the client resumes, gets its echo, prints it, and sends the next line. The two coroutines hand the ball back and forth without either one blocking, and the transcript below is the exact order that produces.

The three messages are ordinary constants: "hello, echo\n", "coroutines are cooperative\n", and "goodbye\n". The newline matters: the line reader returns at a newline, so sending a line means sending the terminator with it. The echo returned to the client has no newline — the reader stripped it — so the print adds its own. That asymmetry is the reader's contract stated once, and the program relies on it in exactly one place on each side.

The argument records

@asyncInit copies an argument record positionally into the coroutine's parameters: the record's fields are the parameters, in order. So a one-parameter coroutine is initialized from a one-field record. That is why ConnRec is a record with one field, ca, matching echoConnection's one parameter: 

const ConnRec = struct { ca: *ConnArgs };
...
var crec = ConnRec{ .ca = &ca };
task_ptrs[1].frame = @asyncInit(task_ptrs[1].ctx, @ptrCast([*]u8, &conn_frame), echoConnection, @ptrCast(*const void, &crec));

The record is passed as a plain *const void. As chapter 9 warned, a ?*const void is a non-scalar optional in this position and emits invalid C89, so the cast is always to the non-optional *const void. The record must also outlive the coroutine, because @asyncInit stores it as the task's arg and the scheduler re-passes it on every resume. Both records here (crec and clrec) are locals in main, which is alive for the entire run.

The setup in main

The setup is the part a modern runtime would hide, and reading it is how you learn what a coroutine actually costs. In order:

Bring up the network. std.net.init() runs WSAStartup(1,1) on Windows and is a no-op elsewhere; a non-zero return means the socket stack did not initialize. Then createTcpServer(PORT) makes and binds the listening socket, bindListen starts it listening, and createTcpClient(PORT) connects the client socket over loopback. On Windows the sockets are wsock32 handles; the API is the same on both targets.

Accept the connection. The accept loop retries until accept returns a socket. In a production server this is the outer loop; here it runs once, because the single connection is already in the listener's backlog.

Switch both sockets to non-blocking. std.net.setNonBlocking is what makes the async reader safe. On a blocking socket a read with no data would stall the whole cooperative scheduler; on a non-blocking socket it returns would-block and the reader suspends. That is the contract the reader documents and this program depends on.

Build the readers and buffers. Each socket gets a SocketLineReader and a 128-byte buffer, both in main. The buffers are ordinary byte arrays here rather than aligned u64 arrays, because the reader is not a coroutine frame and does not carry the coroutine alignment requirement; the frame buffers are a different story.

Allocate the coroutine storage. For each task there is a pool and a root frame, backed by [POOL_WORDS]u64 arrays. The u64 backing is not decoration: contextInit traps on a buffer that is not 8-aligned, and a bare [N]u8 is only 1-aligned. The cast to []u8 gives the pool interface the byte view it wants. Each buffer is 512 u64 words, 4 KiB, which is far more than these shallow call chains need and a reminder that a pool is cheap when its size is fixed at compile time.

Initialize the tasks. For each task: make the Context from the pool, initialize the root frame with @asyncInit, fill the remaining Task fields, and addTask it. The Task struct is the one from chapter 9 — frame, ctx, state, cancel_requested, result, arg, waiting_on, has_waiting_on — and it stores no step pointer. The step is inside the frame, written by @asyncInit; the scheduler loads it through @asyncResume. That is why the same scheduler can drive a connection task and a client task whose functions have different types: the type is erased into the frame.

The one ordering choice in the setup is that the client task is added first. tick walks tasks in registration order, so on the first tick the client runs first: it sends its first line and suspends waiting for the echo. Then the connection task runs and finds that line waiting. If the order were reversed the program would still be correct, just one tick later — the reader would suspend the connection task until the client's next turn — but "client first" makes the first tick do useful work and keeps the transcript easy to read.

The drive

The last movement is one call: 

std.async.waitAll(&sched) catch {
    std.io.print("frame pool exhausted\n", .{});
};

waitAll ticks the scheduler until every registered task is done or cancelled. Each tick resumes every runnable task — ready or suspended — once, in order; a task that suspends is parked until the next tick. The two tasks take turns, the client finishes after its third echo and closes its socket, the connection task then reads end-of-file and finishes, and waitAll returns. The only error it can surface is error.OutOfFrame from a child-frame pool overflow, which the program reports rather than ignores. After the drive, main closes the listening socket, cleans up the socket stack, and prints the count.

The transcript

Compiled with the seed-built compiler, linked with the standard Linux build script, and run: 

client got: hello, echo
client got: coroutines are cooperative
client got: goodbye
echoed 3 lines

The three client got: lines are the client coroutine printing the echoes it received; the last line is main printing the counter that the connection coroutine incremented. The lines arrive in the order the messages were sent because the client waits for each echo before sending the next. No timing is involved. Because the scheduler is cooperative and single-threaded, the run is exactly reproducible, which is what makes a coroutine program testable in the first place.

Running under Windows 98

This is a network program, so it is also the first sample in the volume that proves the Windows socket path rather than just the console path. The committed harness cross-compiles the emitted C with i686-w64-mingw32-gcc directly and links wsock32 unconditionally, then runs the resulting echo.exe under a dedicated 32-bit wine prefix. On this host the Windows run returned XRUNRC=0 and WINE_RC=0, and its stdout was byte-identical to the Linux transcript above: the parity check reported PARITY=OK. The raw Windows stdout was already LF-terminated and matched the Linux baseline exactly, so the compare was an exact byte-match, not merely a normalized one.

That is a stronger statement than chapter 9 could make. Chapter 9 proved that coroutine execution runs under Windows. This chapter proves that coroutines plus the Windows socket stack run together: the server binds, accepts a loopback connection, reads non-blocking, suspends, resumes, and echoes, with the scheduler driving all of it. The trade

A coroutine per connection is not free, and the cost is easiest to see in a program this small. Four limits are worth naming, each with what you do instead.

A frame per connection is permanent memory. Each task owns a root frame and a child-frame pool for its whole life. A server with a thousand connections owns a thousand frames and a thousand pools. The way over is to size them, not to fear them: @asyncFrameSize gives the exact root-frame size at compile time, the pool is yours to size, and both are fixed. A connection that is idle still costs its frame, so a server that must hold many idle connections budgets for them up front — which is the same arithmetic the era forces on every other kind of buffer.

Nothing preempts anything. A connection coroutine that never suspends starves the rest. The way over is the same as chapter 9's: suspend where the work genuinely pauses. Here every read suspends on would-block, so a task that is waiting for a client yields naturally and the scheduler runs another connection. A task doing a long computation between reads should be written to suspend at chunk boundaries, or split.

The scheduler is driven by you. There is no event loop behind your back, and waitAll ticks every registered task. That is fine when every task is non-blocking, as here. It is not fine if a task blocks, because a tick would stall on it. The way over is the model this program already follows: make every socket non-blocking and let the async reader suspend instead of block. If you mix a blocking task into the scheduler, drive only the tasks you mean to, as the larger mud_server example does with select.

One root pool in a suspending main is fixed at 256 bytes. A suspending pub fn main has a synthesized driver with a fixed pool, so its implicit awaits can overflow. This program sidesteps it the recommended way: main does not suspend. It sets up an explicit pool per task and drives them from outside, so the only pool that matters is the one it sized itself.

None of those limits falls on the common case, and all of them are visible. You give up the machine's ability to schedule for you, and in exchange you own a program whose concurrency is a list of tasks and a tick, with no locks and no races.

Honest note. The client coroutine in this sample exists so the program can prove itself; a real client is another machine. Do not read the sample as a template for putting the client in the server. Read it as two things: the connection handler is the program, and the client is the test. The part that scales — accepting in a loop and initializing a task per socket — is exactly the part the sample does once, and the @asyncInit/addTask pair is the same whether you call it once or in a loop. The rest of the volume's network chapter (chapter 6's promised way over the no-threads limit) is this pattern applied to more connections.

Common mistakes

These are the mistakes a reader makes first when turning the mechanism into a program. Each has a corrected shape.

Leaving the socket blocking. The async reader assumes a non-blocking socket; on a blocking one, a read with no data does not yield, it waits. The scheduler then stalls on that one task and the other coroutines never run. The fix is one call per socket, std.net.setNonBlocking(&sock), before the task that reads it is registered.

Putting the reader and buffer in the coroutine frame. A reader holds a slice into its buffer and the buffer must stay put across suspensions. Keeping both as locals in the suspending function works against the frame layout; the safe and idiomatic shape is to own them in main (or an arena) and give the coroutine a pointer, which is what ConnArgs.lr is.

Forgetting the newline. The line reader stops at, and strips, the terminator. If you echo the returned slice with no terminator, the peer's next read never sees a complete line and the conversation hangs. The connection handler sends the line and then a newline, and the client prints the stripped echo with a freshline of its own. Watch both sides of any line protocol.

Sending the arg record as an optional. The fourth argument to @asyncInit is @ptrCast(*const void, &record). A ?*const void emits invalid C89 here. The record's field count must also match the coroutine's parameter count, because the copy is positional; ConnRec and ClientRec each have exactly one field for exactly one parameter.

Backing a pool or frame with [N]u8. The pool and root frame must be 8-aligned, and a u8 array is only 1-aligned; contextInit traps otherwise. Back both with [K]u64 and cast a slice to []u8. The readers' buffers are a different type and do not need this, but the coroutine storage does.

Expecting the program to work if you call it twice. The fixed port makes a second concurrent run fail to bind. The error paths in main report each failure and return instead of crashing, which is the Z98 error-union habit; read them as the program telling you the port is in use, not as the socket stack being broken.

Where to go next

The mechanism was chapter 9, Coroutines — the third big shift; this chapter is what the third shift is for. The coroutine-converted multi-connection server in the examples tree, examples/z98/mud_server, is this pattern with more connections and a readiness-gated drive, and it is the proof that the shape scales.

The socket API behind this program is the std.net extern surface, and the harness that verified it under Windows is the same one the WinSock chapter will use; the detailed socket story is (planned) for chapter 12. The line reader itself, std.stream's SocketLineReader, is defined in sf/src/std_stream.zig; its async reader is the shipped implementation, and the format string in the client's print is chapter 18. The scheduling primitives are catalogued in Volume IV — Builtins.

If the frame-and-pool model still feels unfamiliar, the two earlier shifts are Volume II chapter 12, Error unions and chapter 14, The arena; a coroutine's pool is an arena that happens to hold frames. The volume's inventory, chapter 2, lists coroutines among the things Z98 gives you, and chapter 6 states the limit this chapter is the way over. Chapter 7 warns that OpenWatcom is emitted-only on the development host; the Windows section above is the measured boundary.
