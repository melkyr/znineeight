DirectX 7/8 under CINTERFACE

DirectX is the part of the era machine that draws and plays sound. It is not a language feature and it is not a library that Z98 ships; it is a set of Microsoft COM objects that the operating system exposes, and the way a C program reaches them is the way it reaches any COM object: through a virtual function table you walk by hand. This chapter is about that table — what it looks like in C89, how a call through it is written, what the IUnknown base is for, and why the three creation functions that begin every DirectX program are the easy part while the headers that declare them are the hard part.

It is also the one Win32 chapter in this volume with no sample. The blueprint's ddraw-mini.z98 was dropped by the program's own Phase 0 ruling, and the reason is stated plainly here rather than hidden in a footnote: no DirectX SDK or DirectX header ships with Z98, and the graphical and audio paths this chapter describes are not something the volume's verifier can run on the development host. What is left is what can be said truthfully — era context about COM in C89 and about the header pain, mapped onto the manual-vtable idiom of Volume II chapter 16 and chapter 11. The boundary is stated in full at the end of the chapter.

What is measured here, and what is not. There is no code sample on this page and there is no figure: the ddraw-mini.z98 program was dropped by ruling, and no DirectX SDK, header, or src/vol3/ program for this chapter exists. The COM and DirectX statements below are era context about the SDK and the operating system, stated as facts about 1998–2001 Windows and marked as opinion where they are opinion; they cannot be compiled or run on this host. The Z98-side claims were checked on the seed-built compiler (v89): a struct of function pointers with an lpVtbl interface pointer lays out as the C headers do, a call through lpVtbl compiles and runs, *void and **void carry the interface and out-parameter, and a function-pointer type can name the stdcall convention. Those are measured; the DirectX API surface behind them is documented, not run.

Why this chapter has no sample

The rest of Volume III tries to end every Win32 chapter with something that really ran: chapter 12 binds a socket under wine, chapter 13 drives the real debug loop. This chapter cannot, and the honest move is to say why once and then get on with the useful part.

Three things are true at the same time. First, DirectX is a runtime capability, not a header file: to compile a DirectX program you need the SDK's headers and import libraries, and none of them are in the repository or on this host. Second, the interesting behavior of DirectX — a display mode changes, a surface is blitted, a buffer plays — is device and driver behavior. Wine has built-in replacements for some of it, but the volume does not rely on them, does not test against them, and will not stake a claim on them; the verifier here is the mingw-plus-wine harness for ordinary Win32 calls, and a graphics stack is outside what that harness establishes. Third, even a program that compiled would be testing the development host's idea of 1998 graphics, not a Pentium II with an era driver. So the sample was dropped, and this page keeps only the parts that are about the interface: the COM ABI in C89, which is real and stable, and the Z98 mapping, which is measurable.

That is a deliberate limit and not a hole. The chapter still earns its place because the COM-in-C89 material is exactly what a reader needs before touching any DirectX (or DirectShow, or any other COM) header, and because the header pain is real work that the rest of the volume's rules already tell you how to do.

DirectX on the 1998 machine

DirectX is an umbrella over several APIs that share one calling model:

  • DirectDraw, the 2D layer: create surfaces in video or system memory, blit, flip, and take over the display. It is the heart of a 2D game or a full-screen demo.
  • Direct3D, the 3D layer, which began as a retained-mode API bolted onto DirectDraw and became immediate-mode. On a Pentium II the practical use is a software or simple hardware rasterizer at low resolution — the limits of chapter 6 apply with full force.
  • DirectSound, the audio layer: a mixer and a set of playing buffers.
  • DirectInput, the input layer: keyboard, mouse, and joystick as devices, with force feedback in the later versions.

The versions matter for the SDK but not for the C interface. The chapter's title names DirectX 7 and DirectX 8 because those are the generations whose C form this material is drawn from; the interface model below did not change between them, and it did not change from the earlier DirectX 5 that shipped with Windows 98. Era opinion: for the manual's 1998 target the reader will most often link whatever DirectX runtime the machine already has, and the binding is source-compatible across those versions for the calls named here. Treat the version numbers as a floor, not a feature list.

The one fact that governs everything else is that DirectX is COM. An IDirectDraw is not a struct full of fields; it is a COM interface pointer. An IDirectSoundBuffer is another one. You do not call functions on them the C way — there are no exported DirectDrawFlip symbols — you call through the object's virtual function table. The three exports that do exist, the ones that create the objects, are named DirectDrawCreate, DirectSoundCreate, and DirectInput8Create, and they are the only ordinary functions in the story. Everything after them is lpVtbl.

COM in C89

COM was designed to be usable from C, which is a large part of why it is shaped the way it is. The model has exactly three pieces:

An interface is a pointer to a struct whose only member is a pointer to a table of function pointers. In C, that second struct is called the vtable and the member is called lpVtbl. A call is two dereferences and a function call: take the object pointer, follow lpVtbl to the table, take the function pointer out of the table, and call it.

Every interface begins with the same three methods. They are QueryInterface, AddRef, and Release, and together they make up an interface named IUnknown. Because every vtable starts with those three in that order, a pointer to any interface can be treated as a pointer to IUnknown; that is what lets COM pass objects around without knowing their concrete type.

Objects are reference-counted. AddRef raises a counter, Release lowers it, and when it reaches zero the object destroys itself. There is no garbage collector and no free — the last Release is the deallocation. This is the single most important discipline of COM and the one a C programmer is most likely to get wrong.

The reason this is called CINTERFACE is that the DirectX headers are written for both C and C++. In C++ an interface is a class with pure virtual methods and the compiler generates the vtable; the call p->Flip(...) hides the lpVtbl walk and passes the this pointer for you. Define the macro CINTERFACE before including the headers and they expose the C form instead: a struct of function pointers and an explicit This first argument. Z98 is not C++, so the C form is the one that matters here. Era fact: the DirectX SDK documentation of the period is written around this split, and every sample in it comes in a C and a C++ version that compile to the same calls.

The IUnknown base

Here is the base interface as the C headers present it. This is the shape every DirectX interface inherits by repeating these three entries at the front of its own vtable: 

typedef struct IUnknownVtbl {
    HRESULT (STDMETHODCALLTYPE *QueryInterface)(IUnknown *This,
                                                REFIID riid,
                                                void **ppvObject);
    ULONG   (STDMETHODCALLTYPE *AddRef)(IUnknown *This);
    ULONG   (STDMETHODCALLTYPE *Release)(IUnknown *This);
} IUnknownVtbl;

typedef struct IUnknown {
    IUnknownVtbl *lpVtbl;
} IUnknown;

Read it slowly, because all three of COM's ideas are in those ten lines. The interface is a one-member struct holding lpVtbl. The vtable is a struct of function pointers, not an array, so a compiler can give each method a name and a stable offset. Every method takes This as its first parameter: in C that is explicit, and it is the object pointer itself, passed back to the object so the method can find its data. The calling convention is STDMETHODCALLTYPE, which on 32-bit Windows is stdcall.

QueryInterface is the type-safe cast of COM. You hand it the interface identifier you want (a REFIID, a pointer to a GUID) and it either returns that interface through the void ** out-parameter or returns a failure code. AddRef and Release return the new reference count. A return type of HRESULT is the other COM habit: success is the specific value S_OK (zero), and the macros SUCCEEDED(hr) and FAILED(hr) test the sign bit. Comparing an HRESULT to true or false is one of the mistakes at the bottom of this page.

lpVtbl calls

A call through the table is the whole technique. In C, setting the cooperative level on a DirectDraw object — the call that tells DirectDraw whether you want a window or the full screen — is written with three explicit steps: 

IDirectDraw *dd = /* an interface pointer */;
HRESULT hr;

hr = dd->lpVtbl->SetCooperativeLevel(dd, hwnd, DDSCL_NORMAL);
if (FAILED(hr)) {
    /* handle it */
}

The first argument is dd itself. That is not a formality: because C has no implicit this, the object pointer is just an ordinary argument, and the headers declare every method to take it. The compiler does not check that the dd you pass is the same object whose table you called through; the object's method assumes it, and a program that passes the wrong pointer gets nonsense. This is the price C pays for the convenience C++ hides.

Now put the same shape in Z98. The declaration is a struct with a function-pointer member per method, and the interface is a struct whose only field is a pointer to the vtable: 

const IUnknownVtbl = struct {
    QueryInterface: extern "stdcall" fn (*void, *const u8, **void) i32,
    AddRef:         extern "stdcall" fn (*void) u32,
    Release:        extern "stdcall" fn (*void) u32,
};

const IUnknown = struct {
    lpVtbl: *IUnknownVtbl,
};

This is Volume II chapter 16's manual-vtable idiom with the COM names on it, and it was compile-checked on the seed compiler as a scratch fragment. Three facts came back from that check and they are the ones worth keeping:

  • A function pointer is four bytes on the 32-bit target, so the three-entry IUnknownVtbl is 12 bytes.
  • The interface struct is exactly one pointer: @sizeOf(IUnknown) is 4 bytes, and lpVtbl sits at offset zero.
  • A call through the field — iu.lpVtbl.AddRef(self) with the object pointer passed by hand — compiles and runs, and the emitted C is a plain function-pointer call, which is precisely what the CINTERFACE macro produces from the header.

There is no receiver magic in Z98, so the call reads lpVtbl.Method(self, ...) rather than the C++ p->Method(...) or the C p->lpVtbl->Method(p, ...). The semantics are the C ones: the object pointer is an ordinary first argument. That is the direct translation, and it is why the manual vtable is not a workaround here so much as a restatement of what COM already is. The type checker sees the function signature and the fact that the interface is a pointer; it cannot see that the table's This will be cast back to a concrete object inside the method, because that is a contract between the implementation and its callers, not between types.

The calling convention is part of the type

COM methods are stdcall, and a vtable whose entries are declared cdecl would corrupt the stack on the target even though it might compile. Z98 carries the convention on the function-pointer type, spelled after extern, so the declaration above is ABI-correct. On the Windows target the compiler emits the convention through a macro, Z98_STDCALL; at this writing it expands to __stdcall for MSVC and for OpenWatcom (which defines __WATCOMC__) and to __attribute__((stdcall)) for gcc and mingw. On the Linux host the macro is empty, which is why a Linux probe of the same declaration is not a test of the Windows ABI — it is a test of the type-level shape only.

The convention also has teeth at the type level. Chapter 11 introduced the rule that a function-pointer value may be assigned only to a target whose signature matches exactly, calling convention included. A plain (cdecl) Z98 function assigned into a stdcall vtable field is therefore rejected with error[3000], before any C is emitted; the way to place such a function deliberately is an explicit @ptrCast, which is legal. This was measured on the seed compiler: the direct initializer failed with the type-mismatch error and the @ptrCast form emitted cleanly and ran. The rule is a feature here. A COM table with the wrong convention compiles to code that looks fine and falls apart at the call, and a diagnostic is a much better outcome than that.

Creating the objects

Nothing in the previous section creates anything. A COM object is created by a function exported from a DLL, and DirectX exports exactly one such function per API. The three that begin the three common programs are these, quoted from the era headers: 

HRESULT DirectDrawCreate(GUID *lpGUID,
                         LPDIRECTDRAW *lplpDD,
                         IUnknown *pUnkOuter);

HRESULT DirectSoundCreate(LPCGUID pcGuidDevice,
                          LPDIRECTSOUND *ppDS,
                          LPUNKNOWN pUnkOuter);

HRESULT DirectInput8Create(HINSTANCE hinst,
                           DWORD dwVersion,
                           REFIID riidltf,
                           LPVOID *ppvOut,
                           LPUNKNOWN punkOuter);

The pattern is the same in all three, and it is the pattern to learn. The function takes a way to choose the device, a pointer to an interface pointer that it fills in, and an outer object for COM aggregation that is always NULL in ordinary use. It returns an HRESULT. The out-parameter is the creation's product: you declare a variable of the interface pointer type, pass its address, check the HRESULT, and from then on call through lpVtbl. In C the address-of a pointer is a **, and in Z98 the corresponding parameter type is **void — the double pointer verified in the scratch probe above.

The differences between the three are worth naming because they trip people up. DirectDrawCreate takes a GUID * where NULL means the default display adapter; it returns an IDirectDraw, and the later DirectDrawCreateEx returns an IDirectDraw7 instead. DirectSoundCreate takes an LPCGUID device identifier where NULL means the default playback device; it returns an IDirectSound, with DirectSoundCreate8 for the IDirectSound8 of the later SDK. DirectInput8Create is the odd one: it takes the instance handle, the DirectInput version word (DIRECTINPUT_VERSION), and the interface identifier IID_IDirectInput8, and creates the one DirectInput object the later SDK offers. The identifier argument is the same GUID mechanism QueryInterface uses, which is not a coincidence: DirectInput8Create is in effect a create-then-query folded into one call.

The DLL names follow the API names: ddraw.dll, dsound.dll, dinput8.dll. Linking is against the SDK's import libraries (ddraw.lib, dsound.lib, dinput8.lib under Microsoft tools), and the GUID identifiers the later calls need are supplied either by including initguid.h once in one translation unit or by linking uuid.lib. None of that is Z98-specific; it is the ordinary Win32 link story of chapter 8, and it is the first place the header pain below turns into build-system pain.

The object behind the table

Once created, a DirectDraw program is a sequence of lpVtbl calls, and the order of the entries in the table is a version-specific fact that matters. The IDirectDraw vtable begins with QueryInterface, AddRef, and Release, and continues with the 2D operations: Compact, CreateClipper, CreatePalette, CreateSurface, DuplicateSurface, EnumDisplayModes, EnumSurfaces, FlipToGDISurface, GetCaps, GetDisplayMode, GetFourCCCodes, GetGDISurface, GetMonitorFrequency, GetScanLine, GetVerticalBlankStatus, Initialize, RestoreDisplayMode, SetCooperativeLevel, SetDisplayMode, and WaitForVerticalBlank. IDirectDraw7 repeats that prefix and adds more entries after it, which is why a vtable pointer to one is not a vtable pointer to the other.

This is the concrete meaning of an interface version in COM. A method is not looked up by name at run time; it is a fixed slot in a table, and the slot numbers are the ABI. Calling an IDirectDraw7 method through an IDirectDraw vtable type does not fail cleanly — it calls whatever function happens to occupy that slot, with whatever arguments the wrong signature implies. The safe rules are the ones COM already gives you: request the interface version you actually need with QueryInterface, name the vtable type that matches it, and never retype an interface pointer with a cast.

The 2D idiom itself is short and old: set the cooperative level to say whether you own the screen, set a display mode if you are going full-screen, create one or more surfaces, and then loop on Flip or a blit to present a frame. The details — pixel formats, the DDSCL_ flags, whether a surface is in video or system memory — are the SDK documentation's business, and they change with the hardware. What is true across all of it is the call mechanism this chapter is about.

Header pain under OpenWatcom

Here is the friction the blueprint names, and it is worth being precise about what kind of problem it is. The DirectX SDK headers are not portable C89 headers. They are Microsoft headers written to be consumed by Microsoft tools, and they lean on the compiler in ways a plain C89 compiler does not provide.

  • They are written for two languages at once. Without CINTERFACE they expand to C++ classes with virtual methods; with it they expand to the C struct form. The macro interface, the DECLSPEC_UUID and __declspec(uuid(...)) annotations, the STDMETHOD and STDMETHODCALLTYPE macros, and the PURE marker all exist to let one header serve both compilers.
  • They assume the Windows headers and the SDK are on the include path in the right order, with the SDK's GUID, REFIID, HRESULT, LPVOID, and HINSTANCE types already defined by windows.h and the platform headers. Get the order wrong and the errors are type-name errors hundreds of lines from the cause.
  • They define GUID values, which pulls in the initguid.h / uuid.lib convention above, and they use #pragma pack to pin struct layouts — a detail that matters because the same packing must be in force in every translation unit that touches a DirectX struct.

OpenWatcom is a capable C compiler, but it is not the compiler the SDK was written for, and it has no DirectX headers of its own: you point its include path at the SDK's include directory and its linker at the SDK's import libraries. The emitted OpenWatcom script that chapter 8 describes, build_owc.bat, calls wcc386 with the language extensions turned off (/za) and warnings promoted to errors (/we) — both good defaults for the compiler's own output, and both unfriendly to headers that rely on extensions. Era opinion, marked as such: the combination is where most of the "DirectX under Watcom" frustration comes from. It is not that DirectX cannot be used from OpenWatcom; it is that the header path is a negotiation.

The way over it is the one this volume has been teaching since chapter 11 and used again in chapter 13: declare the slice of the header you actually use, rather than compiling the whole header under a compiler it was not written for. A DirectX program touches a handful of interfaces and perhaps a dozen methods each, and every one of them is a shape this chapter has already shown. The creation functions become extern "stdcall" fn declarations in the vol3-11 style. The interfaces become vtable structs and one-member interface structs, laid out in the header's order. The GUID constants you need you define by hand or request with QueryInterface. This is more typing than an @cInclude would be — and Z98 has no @cImport, as chapters 11 and 13 measured — but it is honest about the boundary, it compiles under whatever era compiler you have, and it does not depend on the SDK's headers surviving a compiler they were not written for.

The trade

The trade for reaching DirectX from Z98 is the trade this whole volume keeps describing, with the graphics stack added. What you get is the real operating system service, at full speed, with no wrapper and no runtime; the generated C is the CINTERFACE C a 1998 programmer would have written, and the calls are the same calls. What you pay is that all of COM's bookkeeping is now yours: the lpVtbl walk is explicit, This is passed by hand, every AddRef has to be matched by a Release, every creation call's HRESULT has to be checked, and every interface has to be named at the right version. There is no destructor to run at scope exit and no smart pointer to save you; the compiler checks types but not lifetimes.

For a program of the size this machine supports, that is the right side of the trade. A 2D game or a demo is a few thousand lines and a small number of objects, and the reference-counting discipline is easy to hold in your head once it is written down. The place it stops being the right trade is a large object graph where ownership is genuinely tangled; there, the C++ form of the same headers exists for a reason, and chapter 4's honest rules about C++98 on a 32 MB machine are the ones to apply. Z98 does not pretend to make that easier; it makes the C path exact.

Honest note. This chapter describes an interface and a set of era facts; it does not ship a DirectX program and it does not claim to have run one. No DirectX SDK or header exists in this tree, and the graphical and audio stacks are not part of what the volume's Windows verifier establishes. Every COM statement here is a fact about the C ABI and the era SDKs; every Z98 statement was checked on the seed compiler; and the place a DirectX claim would become real is a Pentium II with a period driver, which is the reader's machine and not this host.

The boundary, stated plainly

Two boundaries are about the toolchain rather than the API. The second is the verifier itself: the volume's Windows oracle runs ordinary Win32 and CRT programs under wine, and the DirectDraw and DirectSound paths are outside the capability it establishes, so the boundary is "described, not run" and not a claim about what wine can or cannot do. That is the honest classification, and it is the reason the sample was dropped rather than shipped with a caveat.

Common mistakes

These are the mistakes that cost a C programmer the most time in COM and DirectX, in roughly the order they are made. The chapter has no runnable sample, but the declarations above are real, so the corrections are concrete.

Forgetting CINTERFACE. Include the DirectX headers without defining CINTERFACE first and you get the C++ classes, which a C89 source file cannot use; the errors are about unknown types and missing -> members. Define CINTERFACE before the first SDK include, in every translation unit that touches a DirectX type.

Forgetting to pass This. In C there is no hidden receiver, so dd->lpVtbl->SetCooperativeLevel(hwnd, flags) is missing its first argument and passes the wrong values in the wrong registers. The object pointer is always the first argument: dd->lpVtbl->SetCooperativeLevel(dd, hwnd, flags). In Z98, where there is no this and no method syntax, the same rule reads iface.lpVtbl.SetCooperativeLevel(self, hwnd, flags).

Using method syntax in Z98. Z98 has no methods, so iface.SetCooperativeLevel(...) does not exist. The call goes through the table member and passes the object pointer by hand. This is not a limitation to work around; it is the CINTERFACE call written out in full, which is what the rest of this chapter has been building toward.

Declaring the vtable cdecl when the API is stdcall. The entries must be extern "stdcall" fn on the 32-bit Windows target. A cdecl declaration may compile and then corrupt the stack on the first call, because the callee and the caller disagree about who cleans up. Z98 helps here: the convention is part of the function-pointer type and a cross-convention assignment is error[3000], so a vtable built from mismatched Z98 functions is stopped before emission.

Not checking the HRESULT. DirectX creation and most methods return HRESULT. Ignoring it and using the out-parameter anyway means driving an uninitialized pointer; the failure surfaces later as a crash far from the call. Test with SUCCEEDED(hr) / FAILED(hr), and never compare an HRESULT to true or false — success is the specific value S_OK, which is zero.

Leaking references. Every object you create or QueryInterface for arrives with a reference you own, and the last Release destroys it. Forgetting a Release leaks the object and, for DirectDraw and DirectSound, often the underlying device; releasing twice corrupts the count and crashes. Decide on one owner per interface pointer and match every acquisition with exactly one release.

Retyping an interface pointer. Casting an IDirectDraw7 to an IDirectDraw, or naming the wrong vtable type, calls the wrong slot with the wrong signature. Interfaces are versioned through QueryInterface; ask for the version you need and use the matching vtable type rather than casting between them.

Mixing uninitialized storage with an out-parameter. The creation functions take a pointer to an interface pointer; initialize the variable to a known value before the call so a failure cannot leave you reading an old pointer, and check the HRESULT before using whatever it wrote. The same care applies to **void out-parameters in Z98.

Wrestling the whole SDK header instead of declaring the slice. Trying to make the complete DirectX headers compile under a compiler they were not written for can consume a day and leave the build dependent on a header negotiation. Declare the interfaces and methods you use, in the header's order, the way chapters 11 and 13 declare windows.h; the layout model guarantees the result and the build stops depending on the SDK's compiler assumptions.
