Data and containers

These modules ship with the compiler but are imported by path, not re-exported from std. A program names the source file directly: @import("std_map.zig"), @import("std_sort.zig"), and so on. sf/src/std.zig remains the thirteen-name re-export list described on The standard library. The by-path modules use the same concrete, no-generics rules as the re-exported surface: each container has a fixed key and value type, and each function names its element width in its own name where that matters.

The modules on this page divide into three groups: the arena-backed containers (std_map, std_heap), the in-place ordering helpers (std_sort, std_rle), and the text and wire-format helpers (std_parse, std_bencode). None of them changes std.zig.

std_map

std_map is three concrete open-addressed hash tables, all using Robin Hood insertion and backward-shift deletion. There is no generic map and no allocator object: each init takes a caller arena and a capacity, and the table is one arena allocation made at init. The capacity is the maximum number of entries; the slot array is sized to the next power of two that keeps the load factor at or below 0.75. A full table reports error.OutOfMemory on a new key, while a put of an existing key replaces the value in place.

The control byte is 0x80 for empty, 0xFE for reserved (not observed in a steady-state table), and 0x00..0x7F for the low seven bits of the hash of a used slot. Probe distance is a u32, which is exact for any 32-bit table. Deletion shifts following entries backward while their probe distance stays positive, so no tombstones remain. The maps never free: reset the arena to reclaim them. Slot order and lookup are deterministic; no address, clock, or process id enters the hash.

The three families share the same probe and deletion rules but do not share a generic implementation. Use std_heap when the job is repeatedly taking the smallest key, std_sort when a batch needs ordering, and std_map when lookup by key is the operation that matters.

std_sort

std_sort is an in-place introsort over a caller-supplied vtable. The vtable exposes length, less-than, and swap callbacks over a *void data pointer. Introsort uses median-of-three pivot selection, a recursion-depth limit of twice the floor of the base-two logarithm of the element count, and heapsort once that limit is exhausted. Ranges of sixteen elements or fewer finish with insertion sort. The sort is in place, allocates nothing, and is not stable.

binarySearchU32 assumes the array is sorted in non-decreasing order, for example by sortU32; on unsorted input the result is unspecified. A duplicate key may return any one of its positions. The concrete wrappers are not stable, so a caller that needs stability must sort on a total order such as a composite key.

std_heap

std_heap is a binary min-heap over (i64 key, *void value) entries. It orders first by key and then by a monotonically increasing insertion sequence number, so equal keys pop in insertion order. The backing table is allocated from the caller arena at init; a push that fills it grows the table by doubling. Growth allocates and copies before changing the heap, so a failed growth leaves the heap and the arena untouched. heapPop, heapPeek, and heapLen never allocate.

The heap is the open set behind std_pathfind. Use std_map for key lookup rather than an exhaustive heap walk, and std_sort when the whole set must be ordered once.

std_rle

std_rle is a byte-oriented run-length encoder. A stream starts with a four-byte little-endian u32 decoded-length prefix, followed by tokens. A token byte below 0x80 is a literal and emits itself. A token byte with the high bit set is a run control: the low seven bits plus one give the run length in the range 1 to 128, and the next byte is the repeated value. A run longer than 128 is split into several run tokens. A single byte whose value is below 0x80 is a literal; every other run, including a one-byte run of a value with the high bit set, uses a run token.

Function Signature Returns / error Purpose

The length helpers allocate nothing. encode and decode allocate only their output, and their error set is exactly error.OutOfMemory. decode trusts a well-formed stream: a truncated stream yields a zero-filled tail, and an overlong run is clamped to the declared decoded length. It never reads out of bounds.

std_parse

std_parse is pure and imports nothing. Parsing rejects whitespace, a leading +, and underscores; malformed input and overflow return null rather than trapping. Overflow is detected in u64 before narrowing. The integer formatting functions write backwards from the end of the caller's buffer and return a slice into that buffer.

ftoa rounds half up, uses at most seventeen fraction digits (a larger precision is clamped), and never emits exponent notation. It renders NaN as nan, positive infinity as inf, and negative infinity as -inf. A finite value needs at most 328 bytes for sign, 309 integer digits, the decimal point, and 17 fraction digits. If the buffer cannot hold the rendered text, ftoa writes nothing and returns an empty slice.

std_bencode

std_bencode is the BitTorrent bencode reader and writer. The decoded form is a Value tagged union, with lists as []Value and dictionaries as []Entry. Every list, dictionary, and Value array is allocated from the caller's arena; a caller resets that arena to reclaim the whole tree. The encoder also writes through the arena, using the buffer module. The module is used by z9torr for torrent metadata, DHT messages, and PEX.

The decoder limits nesting to 100 levels, 1024 keys per dictionary, 32 MB per value, and 64 MB total input. It rejects i04e, i-0e, leading zeros, i64 overflow, duplicate dictionary keys, and a string length larger than the remaining input. encode writes dictionary keys in their stored order, not sorted order, so a caller that wants a canonical dictionary must sort the entries before encoding. For the HTTP side of torrent work, see std_http.
