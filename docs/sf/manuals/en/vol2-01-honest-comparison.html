The Honest Comparison

You already program, so this volume does not owe you "what is a variable". It owes you the harder answer: what is Z98, why does it exist, and why would you choose it? The answer this volume defends is the framing of the whole book: Z98 is a higher-level C89, not a smaller modern Zig.

That second half is not an apology, and this chapter is going to be clear about why. Z98 exists for one job: writing software that runs on the 1998 machine and is built by the 1998 toolchain. On that machine, a modern language is not on the menu. The honest comparison is not "Z98 versus the language you use today"; it is Z98 versus C89, C++98, and assembly — the tools that were actually there. Set against those, Z98 is not a consolation prize. It is a deliberate step up: checked errors, an arena, coroutines, and compile-time introspection on top of the same C89 output, with no runtime the machine cannot carry.

Honest note. This chapter compares languages, and comparison is opinion. The statements about C89, C++98, modern C, and modern Zig are era framing: context, not claims this manual's tooling verifies. Only the Z98 column is checked, claim by claim, against the language reference and the compiler. When the two disagree, the Z98 column wins; when a sentence about another language ages badly, the Z98 column is still true.

The machine decides

A 1998 machine is a 32-bit x86 PC on Windows 95, 98, or NT, with tens of megabytes of RAM and no modern toolchain. You do not install today's compiler on it, and no current language runtime lives there. So when this chapter names modern Zig or modern C, it is naming Z98's lineage and its contrast — not a candidate for the target. A modern Zig toolchain cannot be built for or run on the target machine. Neither can today's C or C++ compilers. The candidates on that machine are the era's C89 toolchain, the era's C++98 compilers, and assembly.

That changes what "worse than modern Zig" means. Of course a language from a newer world has more features; it targets a newer world. The question that actually decides a 1998 project is narrower: does this give me more safety and less manual bookkeeping than the C89 I would otherwise write, without adding a runtime the machine cannot afford? For Z98 the answer is yes, and the rest of the chapter shows the receipts.

The comparison set

The table is the map. The rows are languages; the columns are the four questions that decide most projects: where memory comes from, how failure is reported, what you can build types out of, and what concurrency looks like.

Read the Z98 row against the C89 row underneath it: the same machine, the same C89 output, but the failure story, the allocation story, and the concurrency story are all checked. Read the modern rows as context: they are where Z98's syntax comes from and what a newer machine would use, not what this one can run.

What each language brings

One paragraph each. This is the era-framing part: it is the author's summary of the five languages, not a set of verified claims about the four that are not Z98.

C89 — the baseline

C89 is the language Z98 emits and the language it improves on. Its virtues are the era's virtues: a small language, a small runtime, compilers almost everywhere, and output a 1998 machine runs comfortably. Its costs are also the era's: memory is malloc/free pairs you must match correctly, failure is a return code you must remember to check, and the language itself has no generics, no classes, and no exceptions. Everything is a function and a struct, and the discipline is entirely yours.

C++98 — power with a runtime bill

C++98 adds what C89 lacks: classes and virtual dispatch, templates, exceptions, namespaces, operator overloading, and the beginnings of the standard library. On a 32 MB machine those are not free — exception machinery, vtables, RTTI, and template expansions all cost memory and code size, and the era's compiler support was uneven. C++98 is the right tool when you need its abstractions and can pay for them.

Z98 — C89 with the sharp edges filed

Z98 speaks Zig's syntax (a strict subset of it) and emits C89. Its additions are the four in the next section: error unions, coroutines, the arena, and the compile-time introspection builtins. Everything else is deliberately C89-shaped: structs, enums, unions, packed structs, arrays, slices, and free functions. There are no classes to pay for at runtime and no hidden allocations; when the compiler adds something, you can read the C89 it produces. That is the whole design in one sentence: keep the machine's cost model, raise the programmer's safety.

modern C — the same model, more facilities

C99 and later made C easier without changing its model: declarations anywhere, // comments, fixed-width integer types, variadic macros. C11 added atomics and an optional threads library. Memory is still malloc/free, failure is still error codes, and there are still no classes and no exceptions. None of it is a target option in 1998.

modern Zig — the syntax ancestor

Modern Zig shares Z98's taste: explicit errors, explicit allocators, no hidden control flow, no exceptions. It is also far larger, and it is not available on the target. Full comptime, generics, anytype, @Type, @typeInfo, anyerror, and std.Thread are part of it, and a 1998 machine cannot host any of them. Z98 borrows Zig's syntax and its discipline; it does not pretend to be the same tool for the same machines.

What Z98 gives you that C89 does not

Four additions. Each one removes a class of bug or a pile of bookkeeping that C89 leaves to you, and each one lowers to plain C89 with no hidden runtime.

Error unions

In C89, failure is a convention. In Z98, failure is part of a function's type: error{Foo, Bar}!i32 means "an i32, or one of these errors", and the compiler holds both sides of the contract. A caller propagates with try, handles with catch |err|, and undoes partial work with errdefer. A call whose result is an error union cannot be silently dropped; the compiler rejects it. Neither is try allowed in a function that never promised to carry an error on. In C89 the compiler will not notice a forgotten return code; in Z98 it will.

Two absences define the design. There is no anyerror type and no @errorName builtin: an error is always a declared tag in a declared set, and the function signature is where a caller can read it. This is the first big shift, and chapter 12 is devoted to it.

Coroutines

C89 has no concurrency in the language at all. Z98 has cooperative, stackless coroutines: four builtins — @asyncInit, @asyncSuspend, @asyncResume, @asyncFrameSize — plus a scheduler and a per-task frame pool in std.async. The frame lives in a buffer you provide; the coroutine's state is type-erased to *void; a suspension happens only where the code says @asyncSuspend; the driver resumes it with @asyncResume. There is no async/await keyword and no future type, and the scheduler is ordinary library code you can read.

That shape is a promise, and on a single-core era machine it is a gift. Because nothing preempts a running coroutine, it keeps the machine until it reaches a suspension point, and shared state never changes under it at an arbitrary instruction boundary. There are no locks to buy, because there is nothing to lock against.

The arena

There is no malloc/free pair in Z98's memory model. You give std.arena.init a byte buffer; std.arena.alloc bumps within it and returns ArenaError![*]u8, or error.OutOfMemory; std.arena.reset reclaims everything at once. Allocation is fallible and it is an error union, so the same try/catch machinery from the previous section applies — orelse is the wrong operator for it and is rejected. Typed allocation goes through an init function that casts the raw block. There is no deinit: the reset is the whole lifetime story.

The other half of the pattern is knowing when memory dies. Long-lived state and short-lived scratch work get separate arenas, so the scratch arena can be reset on a schedule without touching anything permanent. On a machine where fragmentation and leaks are the failure mode, a single reset is both simpler and safer than a free per object. This is the second big shift, and chapter 14 carries it.

Comptime-introspection builtins

C89 gives you sizeof and offsetof. Z98 adds a family of compile-time questions about types and representation: @sizeOf, @alignOf, @offsetOf, @bitSizeOf, @bitOffsetOf, and checked conversions such as @intCast. The interesting pair is @sizeOf/@bitSizeOf, because integer types can be declared at exact widths — unsigned u1 through u64, signed i1 through i63: @sizeOf reports the C carrier the value is stored in, and @bitSizeOf reports the width you declared. A u3 occupies one byte and knows it is three bits wide.

What Z98 does not have is the general comptime system those builtins live beside in modern Zig. The answers are compile-time constants, not a metaprogramming language. The builtins are the replacement for most of what comptime is used for at this scale.

Around those four additions sits the rest of the language: optionals (?T, null, orelse), defer and errdefer, fixed-size arrays and slices with .ptr and .len, packed structs, tagged unions, and enums with explicit backing widths. All of it lowers to C89, and none of it needs a garbage collector or an unwinder.

What Z98 does not give you — and what stands in for it

The limits are real, and this chapter will not pretend otherwise. They are also the limits of what the target machine can host, not a shortfall against a language that machine cannot run. Each one has an era-practical answer, and for most projects the answer is enough.

Generics, templates, and comptime

There are no generics: no type parameters, no anytype, no @Type, no @typeInfo, and no comptime beyond constant folding and the specific builtins. A comptime parameter does not parse; the compiler reports error[2000]: expected ':' but found identifier. A generic function is written as one function per concrete type, and container types are written out concretely. C89 had exactly the same hole, and C programmers solved it the same way for decades; where a type really needs to be open, C++98 templates are the alternative, at their known runtime and compile-time cost.

Classes and methods

There are no classes and no method syntax. Aggregate types cannot contain function declarations, so s.bar() is not a method call with a different spelling; it is rejected with error[3060]: no field or member function named 'bar' in struct type. The Z98 idiom is the C idiom made explicit and type-checked: free functions take the struct as their first parameter, and polymorphism is a struct holding a function pointer plus the data pointer — a manual vtable. If you wrote C89, you already wrote this pattern by hand; Z98 only stops you from getting the function-pointer type wrong.

Exceptions

There are no exceptions and no stack unwinding. The keywords try and catch are error-union operators, not exception handlers: nothing is thrown, nothing unwinds, and an error is a value that travels through return types until someone handles it. There is no throw statement (it does not parse), no anyerror to erase tags into, and no @errorName to recover their names. C++98 has exceptions; C89 does not. Z98 chooses the C89 answer and then makes it checked — which is an upgrade over unchecked error codes, not a downgrade from C++.

Threads and preemption

There is no thread API in the language and none in the shipped standard library. The era's machines mostly ran one thread and juggled, and the coroutines do not change that: they are cooperative and round-robin, resumed by a scheduler at explicit suspension points, never preempted. Nothing runs in parallel; nothing interrupts a running function at an arbitrary instruction. If a program needs real parallelism, it comes from an operating-system API reached through extern declarations — the same door C89 uses — or from another tool. On 16 MB, cooperative coroutines are usually the cheaper answer anyway.

Honest note. The right way to read that list is not "Z98 is missing things". It is: if a modern language is available to you, use it, and use it happily. On the target machine it is not available. Judged against what does run there — hand-checked C89, heavyweight C++98, or assembly — Z98 is the option that checks the most and surprises the least. The limits are the price of that; the next sections show what the price buys.

Syntax ergonomics: the same evaluator in C89 and Z98

Abstract comparisons are cheap. Here is the same small task written twice. The task is a Lisp-style evaluator: a tree of expressions, a recursive eval, and one real failure mode (division by zero). It is a good probe because it forces every hard part of a system language: tagged data, allocation, recursion, dispatch, and error plumbing. C89 and Z98 solve all of it; the difference is how much of it you write and how much the compiler checks.

C89: tag it, allocate it, plumb it, dispatch it

The C89 shape is an enum tag, a union payload, a malloc/free per node, and a status int threaded through every call. This is era framing, the same pattern every C programmer of the period wrote: 

typedef enum { E_NUM, E_NEG, E_ADD, E_SUB, E_MUL, E_DIV } EKind;

typedef struct Expr {
    EKind kind;
    union {
        int num;
        struct Expr *neg;
        struct { struct Expr *l, *r; } bin;
    } u;
} Expr;

/* 0 = success, -1 = divide by zero; the result comes back through *out */
static int eval(const Expr *e, int *out)
{
    int l, r;
    switch (e->kind) {
    case E_NUM: *out = e->u.num; return 0;
    case E_NEG:
        if (eval(e->u.neg, &l) != 0) return -1;
        *out = -l; return 0;
    case E_ADD:
        if (eval(e->u.bin.l, &l) != 0) return -1;
        if (eval(e->u.bin.r, &r) != 0) return -1;
        *out = l + r; return 0;
    case E_DIV:
        if (eval(e->u.bin.l, &l) != 0) return -1;
        if (eval(e->u.bin.r, &r) != 0) return -1;
        if (r == 0) return -1;
        *out = l / r; return 0;
    default: return -1;
    }
}

Count what the compiler cannot see. The tag and the union are separate declarations, and nothing stops a node from being built with the wrong tag for its payload. Every call site must declare a result variable, check the status, and have a cleanup path for the failure; a caller that forgets the check compiles and ships. Every node is a separate allocation and a matching free on every exit path, including the error paths. The default prong is needed because the compiler cannot prove the switch is exhaustive.

Z98: one type, one switch, an error in the signature

The Z98 shape makes the tag and the payload one type, makes the switch exhaustive and payload-binding, and puts the failure in the return type: 

const Bin = struct { l: u32, r: u32 };

const Expr = union(enum) {
    num: i32,
    neg: u32,
    add: Bin,
    sub: Bin,
    mul: Bin,
    div: Bin,
};

fn eval(nodes: []Expr, i: u32) error{DivideByZero}!i32 {
    switch (nodes[@intCast(usize, i)]) {
        .num => |v| return v,
        .neg => |j| return -(try eval(nodes, j)),
        .add => |b| return (try eval(nodes, b.l)) + (try eval(nodes, b.r)),
        .sub => |b| return (try eval(nodes, b.l)) - (try eval(nodes, b.r)),
        .mul => |b| return (try eval(nodes, b.l)) * (try eval(nodes, b.r)),
        .div => |b| {
            const rhs = try eval(nodes, b.r);
            if (rhs == 0) return error.DivideByZero;
            return (try eval(nodes, b.l)) / rhs;
        },
        else => unreachable,
    }
}

The tag is not a field you can desynchronise from its payload; it is the type. The switch binds the payload to a name, so b.l is a u32 and not a blind union read. The failure is written into the signature as error{DivideByZero}!i32, so try can propagate it and the compiler refuses to let it be dropped. Nodes come from one arena slice instead of a malloc per node, so there is no free to match and no leak path. Indexing goes through a length-carrying slice, and under the default safety mode it is bounds-checked. The else => unreachable prong is the one piece of ceremony Z98 insists on: every switch names its fallback, and unreachable here means the compiler can see the prong can never run.

The example: lisp_eval.z98

The chapter's first runnable program is that evaluator, complete: docs/sf/manuals/src/vol2/lisp_eval.z98. It builds a node pool over an arena, constructs (2+3)*(10-4)/2, evaluates it, then evaluates 10/(10-10) and catches the error. 

const std = @import("std");

const Bin = struct { l: u32, r: u32 };

const Expr = union(enum) {
    num: i32,
    neg: u32,
    add: Bin,
    sub: Bin,
    mul: Bin,
    div: Bin,
};

const Pool = struct { nodes: []Expr, used: u32 };

fn make(pool: *Pool, e: Expr) u32 {
    const i = pool.used;
    pool.nodes[@intCast(usize, i)] = e;
    pool.used = i + 1;
    return i;
}

fn eval(nodes: []Expr, i: u32) error{DivideByZero}!i32 {
    switch (nodes[@intCast(usize, i)]) {
        .num => |v| return v,
        .neg => |j| return -(try eval(nodes, j)),
        .add => |b| return (try eval(nodes, b.l)) + (try eval(nodes, b.r)),
        .sub => |b| return (try eval(nodes, b.l)) - (try eval(nodes, b.r)),
        .mul => |b| return (try eval(nodes, b.l)) * (try eval(nodes, b.r)),
        .div => |b| {
            const rhs = try eval(nodes, b.r);
            if (rhs == 0) return error.DivideByZero;
            return (try eval(nodes, b.l)) / rhs;
        },
        else => unreachable,
    }
}

pub fn main() !void {
    var buf: [8192]u8 = undefined;
    var arena = std.arena.init(buf[0..]);
    const raw = try std.arena.alloc(&arena, @sizeOf(Expr) * 64);
    var pool = Pool{ .nodes = @ptrCast([*]Expr, raw)[0..64], .used = 0 };

    const two = make(&pool, .{ .num = 2 });
    const three = make(&pool, .{ .num = 3 });
    const ten = make(&pool, .{ .num = 10 });
    const four = make(&pool, .{ .num = 4 });

    const sum = make(&pool, .{ .add = .{ .l = two, .r = three } });
    const diff = make(&pool, .{ .sub = .{ .l = ten, .r = four } });
    const product = make(&pool, .{ .mul = .{ .l = sum, .r = diff } });
    const answer = make(&pool, .{ .div = .{ .l = product, .r = two } });

    std.io.print("eval((2+3)*(10-4)/2) = {}\n", .{ try eval(pool.nodes, answer) });

    const zero = make(&pool, .{ .sub = .{ .l = ten, .r = ten } });
    const bad = make(&pool, .{ .div = .{ .l = ten, .r = zero } });
    _ = eval(pool.nodes, bad) catch {
        std.io.print("eval(10/(10-10)) caught DivideByZero\n", .{});
        return;
    };
    std.io.print("unreachable\n", .{});
}

Build the compiler once from the committed seed, then emit and compile the program, exactly as in chapter 2: 

$ mkdir -p /tmp/manual_out
$ /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol2/lisp_eval.z98
$ cd /tmp/manual_out && sh build_target.sh linux lisp_eval

Built: lisp_eval
$ ./lisp_eval

eval(10/(10-10)) caught DivideByZero

The first line is the successful evaluation: (2+3) is 5, (10-4) is 6, the product is 30, and 30/2 is 15. The second line is the error path: the evaluator reaches a zero divisor, returns error.DivideByZero, and the catch at the call site handles it. The program exits 0. The compile is clean: no warnings, no casts to paper over, no free.

What replaces what in the era's game code

An evaluator is a compiler-shaped example. The same ergonomics show up in the two pieces of every era game: moving entities and loading a tilemap. Both are mostly C89 bookkeeping in C89, and both shrink in Z98.

The entity update loop

C89 passes a bare pointer and a separate count, and trusts the loop bound. This is era framing: 

typedef struct { int x, y, vx, vy; } Entity;

void update(Entity *e, int dt) {
    e->x += e->vx * dt;
    e->y += e->vy * dt;
    if (e->x < 0)   { e->x = 0;   e->vx = -e->vx; }
    if (e->x > 100) { e->x = 100; e->vx = -e->vx; }
    if (e->y < 0)   { e->y = 0;   e->vy = -e->vy; }
    if (e->y > 60)  { e->y = 60;  e->vy = -e->vy; }
}

void step(Entity *world, int n, int dt) {
    int i;
    for (i = 0; i < n; i++) update(&world[i], dt);
}

The Z98 shape is the same arithmetic with the array length attached to the data and an index that is checked: 

const Entity = struct { x: i32, y: i32, vx: i32, vy: i32 };

fn update(e: *Entity, dt: i32) void {
    e.x += e.vx * dt;
    e.y += e.vy * dt;
    if (e.x < 0) { e.x = 0; e.vx = -e.vx; }
    if (e.x > 100) { e.x = 100; e.vx = -e.vx; }
    if (e.y < 0) { e.y = 0; e.vy = -e.vy; }
    if (e.y > 60) { e.y = 60; e.vy = -e.vy; }
}

fn step(world: []Entity, dt: i32) void {
    for (world) |_, i| {
        update(&world[i], dt);
    }
}

The arithmetic is deliberately identical, because the win here is not shorter code. The win is that world carries its own length, so there is no separate n to pass or to get wrong, and under the default safety mode the index is checked at runtime. A bounds bug that would corrupt memory in C89 traps and tells you where.

The tilemap loader

Loading a w×h grid in C89 means allocating, checking the allocation, filling with a manually computed index, checking the fill status, and freeing every path out. Length is a variable the caller keeps beside the pointer: 

static int load_map(unsigned char *map, int w, int h)
{
    int r, c;
    if (map == NULL) return -1;
    for (r = 0; r < h; r++)
        for (c = 0; c < w; c++)
            map[r * w + c] = (unsigned char)((r + c) % 4);
    return 0;
}

unsigned char *map = malloc((size_t)w * (size_t)h);
if (map == NULL) { cleanup(); return -1; }
if (load_map(map, w, h) != 0) { free(map); return -1; }
/* ... use map ... */
free(map);

In Z98 the loader returns either a slice or an error, and the slice carries its length. The allocation failure is in the type, and there is no free: 

fn loadMap(arena: *std.arena.Arena, w: usize, h: usize) ![]u8 {
    const raw = try std.arena.alloc(arena, w * h);
    const map = @ptrCast([*]u8, raw)[0..w * h];
    var r: usize = 0;
    while (r < h) : (r += 1) {
        var c: usize = 0;
        while (c < w) : (c += 1) {
            map[r * w + c] = @intCast(u8, (r + c) % 4);
        }
    }
    return map;
}

Three things are gone from the call site: the malloc result check (try replaces it), the separate width and height bookkeeping (map.len is the slice's own), and the free and its error paths (the arena reset reclaims the map). The fill still writes through a manually computed index, and @intCast makes the narrowing to u8 explicit and checked — but the failure and lifetime plumbing that made the C89 version long is in the type system now, not in your head.

The example: game_loop.z98

The second runnable program puts both together and adds a coroutine: docs/sf/manuals/src/vol2/game_loop.z98. It updates two entities, loads and checksums a tilemap, then runs a four-step patrol coroutine over the first entity. 

const std = @import("std");

const Entity = struct { x: i32, y: i32, vx: i32, vy: i32 };

fn update(e: *Entity, dt: i32) void {
    e.x += e.vx * dt;
    e.y += e.vy * dt;
    if (e.x < 0) { e.x = 0; e.vx = -e.vx; }
    if (e.x > 100) { e.x = 100; e.vx = -e.vx; }
    if (e.y < 0) { e.y = 0; e.vy = -e.vy; }
    if (e.y > 60) { e.y = 60; e.vy = -e.vy; }
}

fn step(world: []Entity, dt: i32) void {
    for (world) |_, i| {
        update(&world[i], dt);
    }
}

fn loadMap(arena: *std.arena.Arena, w: usize, h: usize) ![]u8 {
    const raw = try std.arena.alloc(arena, w * h);
    const map = @ptrCast([*]u8, raw)[0..w * h];
    var r: usize = 0;
    while (r < h) : (r += 1) {
        var c: usize = 0;
        while (c < w) : (c += 1) {
            map[r * w + c] = @intCast(u8, (r + c) % 4);
        }
    }
    return map;
}

const MoveArgs = struct { e: *Entity };

var g_pool: [1024]u64 = undefined;
var g_frame: [256]u8 = undefined;

fn patrol(e: *Entity) void {
    var i: i32 = 0;
    while (i < 4) : (i += 1) {
        e.x += e.vx;
        _ = @asyncSuspend(null);
    }
}

pub fn main() void {
    var world = [2]Entity{
        .{ .x = 10, .y = 10, .vx = 7, .vy = -3 },
        .{ .x = 90, .y = 50, .vx = -9, .vy = 4 },
    };
    step(world[0..], 1);
    std.io.print("entity 0 after update: {},{} v={},{}\n", .{ world[0].x, world[0].y, world[0].vx, world[0].vy });
    std.io.print("entity 1 after update: {},{} v={},{}\n", .{ world[1].x, world[1].y, world[1].vx, world[1].vy });

    var buf: [8192]u8 = undefined;
    var arena = std.arena.init(buf[0..]);
    const map = loadMap(&arena, 8, 4) catch {
        std.io.print("map load failed\n", .{});
        return;
    };
    var tsum: usize = 0;
    for (map) |t| {
        tsum = tsum + @intCast(usize, t);
    }
    std.io.print("tilemap 8x4 checksum={}\n", .{tsum});

    var args = MoveArgs{ .e = &world[0] };
    const ctx = std.async.contextInit(@ptrCast([*]u8, &g_pool)[0..8192]);
    const frame = @asyncInit(ctx, @ptrCast([*]u8, &g_frame), patrol, @ptrCast(*const void, &args));
    var r = @asyncResume(frame, null);
    while (r != null) {
        r = @asyncResume(frame, null);
    }
    std.io.print("entity 0 after patrol: {},{}\n", .{ world[0].x, world[0].y });
}

Coroutines: what they replace

Coroutines earn their place by deleting something. On the era's machines, a routine that paused and resumed was one of three things: a hand-rolled state machine, a callback chain, or a thread you juggled. All three put the bookkeeping in your source.

The state machine you stop writing

The state machine is the honest baseline. A patrol that walks four steps and pauses between them needs a state word, an index, and a switch that knows where to re-enter. This is era framing: 

typedef struct { int state; int i; Entity *e; } Patrol;

/* returns 1 while suspended, 0 when finished */
int patrol_step(Patrol *p)
{
    switch (p->state) {
    case 0: p->i = 0; p->state = 1;   /* fall through */
    case 1:
        if (p->i >= 4) { p->state = 3; return 0; }
        p->e->x += p->e->vx;
        p->i++;
        return 1;
    default: return 0;
    }
}

In Z98 the same routine is written in the order it happens, and the pause is a statement: 

fn patrol(e: *Entity) void {
    var i: i32 = 0;
    while (i < 4) : (i += 1) {
        e.x += e.vx;
        _ = @asyncSuspend(null);
    }
}

What was deleted: the state word, the index field, the re-entry switch, and the calling convention that told the caller whether to call again. The compiler synthesises the step machine, the frame layout, and the state word; std.async owns the scheduler and the frame pool. Against a callback chain, the win is the same: the logic reads top to bottom instead of being sliced across callbacks that pass a context pointer around. Against a thread, the win is the era's economics — a coroutine is a frame buffer, not a stack and a kernel object, and because nothing preempts, correctness does not depend on which lock you remembered to take.

A higher-level C89, not a smaller modern Zig

Now the framing sentence from the top, defended. "Higher-level C89" means Z98 raises the parts of C89 that produce the most expensive bugs — failure handling, memory lifetime, scheduling, and representation — while emitting plain C89 with no hidden runtime. An error union is a checked return code. The arena is a disciplined malloc with a single free. Coroutines are a state machine the compiler writes instead of you. The introspection builtins are sizeof grown up. Every one of them is visible in the emitted C, and none needs an unwinder, a garbage collector, a virtual machine, or a thread.

"Not a smaller modern Zig" means the missing features are not a queue of unfinished work; they are the boundary of the design. Modern Zig's headline abilities — general comptime, generics, anyerror, threads — are absent because the target machine cannot host them, and because the point was never to imitate a language that runs somewhere else. Z98 borrows Zig's syntax and its taste for explicitness; it does not borrow Zig's feature set, and it is not apologising for that.

The practical consequence is what the rest of this volume teaches. A Z98 program looks like a well-organized C89 program: structs and free functions, init functions instead of constructors, a struct of function pointers instead of a virtual table, arenas instead of ownership graphs, and error unions instead of status codes. If you write C89 today, you already know the shape. Z98 changes what the compiler checks, not what the machine does.

What that means for you

Choose Z98 when the target is the era — a 1998 machine, a C89 toolchain, a small dependency surface — and when you want the compiler to enforce the disciplines C89 leaves to you. Choose C++98 when templates, classes, or exceptions are load-bearing and the memory budget can carry them. Choose modern C or modern Zig when the target is modern; they are excellent at that, and they are not available here. Judged against the tools that did run on the target, Z98 is the one that adds safety without adding a runtime.

The chapters between the mental shifts (3 through 11) teach the rest of the syntax at the same pace: pointers, aggregates, arrays and slices, control flow, and defer. If you come from C, expect the vocabulary to look familiar and the rules to be stricter. If you come from modern Zig, expect the vocabulary to look familiar and the feature set to be the era's. Both readers end the volume writing C89-shaped programs in Z98's syntax, with the compiler checking the parts C89 leaves to a comment.

Common mistakes

The mistakes below are the ones a C or C++ programmer makes first in Z98. Each has a diagnostic or a corrected shape, and each diagnostic points at the rule that was crossed.

Reaching for malloc and free. The base language's memory story is the arena: you hand std.arena.init a buffer and let try std.arena.alloc bump within it. There is no free to match, because there is no per-object lifetime; std.arena.reset reclaims the whole arena at once. If a C library you call hands you memory, it is still yours to release through that library, but the Z98 objects you build come from the arena.

Expecting method syntax. e.update(dt) is not a method call with a different spelling in Z98; it is a member lookup, and it fails: 

error[3060]: no field or member function named 'update' in struct type

Write the free function and pass the receiver: update(&e, dt).

Expecting generics or comptime. A comptime type parameter does not parse: 

error[2000]: expected ':' but found identifier

Write one function for the concrete type, or a small concrete container as the standard library does. Where a type genuinely must be open, that is what C++98 templates are for; it is a reason to pick C++98 for that project, not a hole to paper over in Z98.

Treating try/catch as exceptions. try and catch operate on error unions, which are values. Nothing unwinds, and a catch block must produce a value of the payload type or diverge (return, break, and so on). There is no throw, no anyerror, and no @errorName; the error is a declared tag in the function's signature.

Spawning a thread for a pause. Z98 has no thread API; it has coroutines. A routine that needs to wait writes @asyncSuspend where the pause belongs and is driven by std.async, cooperative and round-robin. Reaching for threads on a 1998 machine is the expensive way to get the same single-core behaviour.

Leaving out else in a switch. Every Z98 switch needs an else prong, even when the union is fully covered: 

error[3068]: switch must have an 'else' prong

For an exhaustive switch on a tagged union, else => unreachable is the spelled-out promise that the prong can never run.
