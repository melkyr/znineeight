The Honest Comparison

You already program, so this volume does not owe you "what is a variable". It owes you a harder answer: what is Z98, and why would anyone choose it? Here is the answer this whole volume defends: Z98 is a higher-level C89, not a smaller modern Zig.

The comparison runs across five languages: C89, C++98, Z98, modern C, and modern Zig. Z98 is the subject; the other four are the world it sits in. Everything this manual says about Z98 is checked against docs/reference/Language_Spec_Z98.md and the compiler rebuilt from the committed seed. Everything it says about the other four is era framing — a summary of where those languages stood and stand, not a specification — and is marked as such where it matters.

Honest note. This chapter compares languages, and comparison is opinion. The statements about C89, C++98, modern C, and modern Zig are era framing: context, not claims this manual's tooling verifies. Only the Z98 column is checked, claim by claim, against the language reference and the compiler. When the two disagree, the Z98 column wins; when a sentence about another language ages badly, the Z98 column is still true.

The five languages at a glance

The table is the map. The rows are languages; the columns are the four questions that decide most projects: where memory comes from, how failure is reported, what you can build types out of, and what concurrency looks like.

Language Memory Failure Abstraction Concurrency
C89 malloc/free by hand return codes, errno, conventions structs, unions, enums, function pointers none in the language (OS APIs only)
C++98 new/delete, constructors and destructors exceptions: try/throw/catch classes, templates, virtual dispatch none in the standard (OS APIs only)
Z98 arena over a buffer you supply error unions: try/catch/errdefer structs, enums, unions, packed structs; no generics or classes cooperative coroutines (@async* + std.async)
modern C malloc/free error codes (no exceptions) structs, unions, enums; _Generic selection C11 <threads.h> (optional), atomics
modern Zig allocator interface passed explicitly error unions: try/catch structs, enums, unions, plus comptime generics threads (std.Thread)

Read the failure column: outside C++98, nobody in this table throws. Read the last column: only the modern languages ship a thread story at all, and Z98's story is coroutines, not threads. Read the Z98 row and it looks like C89 that traded two manual disciplines — memory and failure — for compiler-checked ones, and gained a coroutine library along the way.

What each language brings

One paragraph each. This is the era framing part: it is the author's summary of the five languages, not a set of verified claims about the four that are not Z98.

C89 — the baseline

C89 is the language Z98 emits and the language it improves on. Its virtues are the era's virtues: a small language, a small runtime, compilers almost everywhere, and output a 1998 machine runs comfortably. Its costs are also the era's: memory is malloc/free pairs you must match correctly, failure is a return code you must remember to check, and the language itself has no generics, no classes, and no exceptions. Everything is a function and a struct, and the discipline is entirely yours.

C++98 — power with a runtime bill

C++98 adds what C89 lacks: classes and virtual dispatch, templates, exceptions, namespaces, operator overloading, and the beginnings of the standard library. On a 32 MB machine those are not free — exception machinery, vtables, RTTI, and template expansions all cost memory and code size, and the era's compiler support was uneven. C++98 is the right tool when you need its abstractions and can pay for them.

Z98 — C89 with the sharp edges filed

Z98 speaks Zig's syntax (a strict subset of it) and emits C89. Its additions are the four in the next section: error unions, coroutines, the arena, and the compile-time introspection builtins. Everything else is deliberately C89-shaped: structs, enums, unions, packed structs, arrays, slices, and free functions. There are no classes to pay for at runtime and no hidden allocations; when the compiler adds something, you can read the C89 it produces.

modern C — the same model, more facilities

C99 and later made C easier without changing its model: declarations anywhere, // comments, fixed-width integer types, variadic macros. C11 added atomics and an optional threads library. Memory is still malloc/free, failure is still error codes, and there are still no classes and no exceptions.

modern Zig — the same taste, a much bigger language

Modern Zig shares Z98's taste: explicit errors, explicit allocators, no hidden control flow, no exceptions. It is also far larger. Full comptime, generics, anytype, @Type, @typeInfo, anyerror, and std.Thread are all part of it. Z98 borrows Zig's syntax, but it is not a cut-down modern Zig; the features modern Zig is known for are simply absent, on purpose.

What Z98 gives you that C89 does not

Four things. None requires a runtime the C89 output cannot carry, and each is verified on the compiler this manual ships with.

Error unions

In C89, failure is a convention. In Z98, failure is part of a function's type: error{Foo, Bar}!i32 means "an i32, or one of these errors", and the compiler holds both sides of the contract. A caller propagates with try, handles with catch |err|, and undoes partial work with errdefer. A call whose result is an error union cannot be silently dropped; the compiler rejects it. Neither is try allowed in a function that never promised to carry an error on. The old -1-and-errno shapes are not part of the language, so the compiler never sees them and cannot check them; error unions are the checked replacement.

Two absences define the design. There is no anyerror type and no @errorName builtin: an error is always a declared tag in a declared set, and the function signature is where a caller can read it. This is the first big shift, and chapter 12 is devoted to it.

Coroutines

C89 has no concurrency in the language at all. Z98 has cooperative, stackless coroutines: four builtins — @asyncInit, @asyncSuspend, @asyncResume, @asyncFrameSize — plus a scheduler and a per-task frame pool in std.async. The frame lives in a buffer you provide; the coroutine's state is type-erased to *void; a suspension happens only where the code says @asyncSuspend; the driver resumes it with @asyncResume. There is no async/await keyword and no future type, and the scheduler is ordinary library code you can read.

That shape is a promise. Because nothing preempts a running coroutine, it keeps the machine until it reaches a suspension point, and shared state never changes under it at an arbitrary instruction boundary.

The arena

There is no malloc/free pair in Z98's memory model. You give std.arena.init a byte buffer; std.arena.alloc bumps within it and returns ArenaError![*]u8, or error.OutOfMemory; std.arena.reset reclaims everything at once. Allocation is fallible and it is an error union, so the same try/catch machinery from the previous section applies — orelse is the wrong operator for it and is rejected. Typed allocation goes through an init function that casts the raw block. There is no deinit: the reset is the whole lifetime story.

The other half of the pattern is knowing when memory dies. Long-lived state and short-lived scratch work get separate arenas, so the scratch arena can be reset on a schedule without touching anything permanent. This is the second big shift, and chapter 14 carries it.

Comptime-introspection builtins

C89 gives you sizeof and offsetof. Z98 adds a family of compile-time questions about types and representation: @sizeOf, @alignOf, @offsetOf, @bitSizeOf, @bitOffsetOf, and checked conversions such as @intCast. The interesting pair is @sizeOf/@bitSizeOf, because integer types can be declared at exact widths — unsigned u1 through u64, signed i1 through i63: @sizeOf reports the C carrier the value is stored in, and @bitSizeOf reports the width you declared. A u3 occupies one byte and knows it is three bits wide.

What Z98 does not have is the general comptime system those builtins live beside in modern Zig. The answers are compile-time constants, not a metaprogramming language. The builtins are the replacement for most of what comptime is used for at this scale.

Around those four additions sits the rest of the language: optionals (?T, null, orelse), defer and errdefer, fixed-size arrays and slices with .ptr and .len, packed structs, tagged unions, and enums with explicit backing widths. All of it lowers to C89, and none of it needs a garbage collector or an unwinder.

What Z98 does not give you

The other half of honesty. These are not bugs to be worked around; they are the shape of the language. Each has a documented boundary and, usually, an idiom that covers most of the need.

Generics, templates, and comptime

There are no generics: no type parameters, no anytype, no @Type, no @typeInfo, and no comptime beyond constant folding and the specific builtins. A comptime parameter does not parse; the compiler reports error[2000]: expected ':' but found identifier. A generic function is written as one function per concrete type, and container types are written out concretely. C89 has the same hole; C++98 fills it with templates, which is one reason to reach for C++98 when templates are the point.

Classes and methods

There are no classes and no method syntax. Aggregate types cannot contain function declarations, so s.bar() is not a method call with a different spelling; it is rejected with error[3060]: no field or member function named 'bar' in struct type. The Z98 idiom is the C idiom made explicit: free functions take the struct as their first parameter, and polymorphism is a struct holding a function pointer plus the data pointer — a manual vtable.

Exceptions

There are no exceptions and no stack unwinding. The keywords try and catch are error-union operators, not exception handlers: nothing is thrown, nothing unwinds, and an error is a value that travels through return types until someone handles it. There is no throw statement (it does not parse), no anyerror to erase tags into, and no @errorName to recover their names. C++98 has exceptions; C89 does not. Z98 chooses the C89 answer and then makes it checked.

Threads and preemption

There is no thread API in the language and none in the shipped standard library, and the coroutines do not change that: they are cooperative and round-robin, resumed by a scheduler at explicit suspension points, never preempted. Nothing runs in parallel; nothing interrupts a running function at an arbitrary instruction. If a program needs real parallelism, it comes from an operating-system API reached through extern declarations — the same door C89 uses — or from another tool.

Honest note. If your project's core need is one of those four — templates or generics, classes and virtual dispatch, exceptions, or preemptive threads — Z98 is the wrong tool, and no amount of idiom will make it the right one. That is not a defect report; it is the design. Volume III's honesty chapters (planned) take each case in turn and say when C89, C++98, or assembly is the better choice.

A higher-level C89, not a smaller modern Zig

Now the framing sentence from the top, defended. "Higher-level C89" means Z98 raises the parts of C89 that produce the most expensive bugs — failure handling, memory lifetime, scheduling, and representation — while emitting plain C89 with no hidden runtime. An error union is a checked return code. The arena is a disciplined malloc with a single free. Coroutines are a state machine the compiler writes instead of you. The introspection builtins are sizeof grown up. Every one of them is visible in the emitted C, and none needs an unwinder, a garbage collector, a virtual machine, or a thread.

"Not a smaller modern Zig" means the missing features are not a queue of unfinished work; they are the boundary of the design. Modern Zig's headline abilities — general comptime, generics, anyerror, threads — are absent because a 1998 machine and a C89 toolchain cannot pay for them the way a modern target can. Z98 borrows Zig's syntax and its taste for explicitness; it does not borrow Zig's feature set. Read it as a different point in the design space, not a cut-down version of the same point.

The practical consequence is what the rest of this volume teaches. A Z98 program looks like a well-organized C89 program: structs and free functions, init functions instead of constructors, a struct of function pointers instead of a virtual table, arenas instead of ownership graphs, and error unions instead of status codes. If you write C89 today, you already know the shape. Z98 changes what the compiler checks, not what the machine does.

What that means for you

Choose Z98 when the target is the era — a 1998 machine, a C89 toolchain, a small dependency surface — and when you want the compiler to enforce the disciplines C89 leaves to you. Choose C++98 when templates, classes, or exceptions are load-bearing and the memory budget can carry them. Choose modern C or modern Zig when the target is modern; they are better at being themselves than Z98 is at imitating them. The rest of this volume assumes the first case and teaches the language on those terms.

The chapters between the mental shifts (2 through 11) teach the rest of the syntax at the same pace: types, pointers, aggregates, arrays and slices, control flow, and defer. If you come from C, expect the vocabulary to look familiar and the rules to be stricter. If you come from modern Zig, expect the vocabulary to look familiar and the features to be missing. Both readers end the volume writing C89-shaped programs in Z98's syntax, with the compiler checking the parts C89 leaves to a comment.
