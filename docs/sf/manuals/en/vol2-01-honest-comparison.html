The Honest Comparison

Z98 is checked C89: C89 with contracts in the type system. It is a language, a compiler, a target, and an output format, and the output format is C89. It exists for the 1998 machine, and it keeps that machine's cost model while moving the disciplines C89 leaves to the programmer into checks the compiler performs.

The comparison that matters is against the era's peers: C89, the baseline, and C++98, the era's heavyweight. This chapter is the map: what Z98 stops you from shipping, where it leads the era's languages, where they lead it, where they tie, and what the limits are — with the way over each.

Era framing. Statements in this chapter about era machines, era toolchains, C89, and C++98 are era context. Statements about Z98 are checked against docs/reference/Language_Spec_Z98.md and the compiler built from the committed seed, and the Z98 fragments on this page compile and run on it.

What Z98 is

C89 and C99 are ISO standards: documents that describe a language. Z98 is not a standard and is not competing to be one. Z98 is a language with its own specification, plus a compiler, plus a target (the era's 32-bit PCs), plus an output format (C89). Saying "Z98 is better than C89" would be a category error; the honest sentence is that Z98 is a compiler over C89. What it adds is not a new dialect of the standard. What it adds is checking.

C89 leaves a specific set of disciplines to the programmer: matching every allocation with a free, checking every return code, keeping every index inside its array, pairing every acquire with a release, casting with care. Those rules lived in comments and code review. Z98 moves them into the type system and the analyzer, and still emits C89. Error handling becomes an error union in the signature. Cleanup becomes defer and errdefer in the language. Buffer length travels with the buffer as a slice. Suspension becomes a coroutine. The compiler holds you to all of it, and the machine still runs plain C89.

Why not C99, then? Because the target's toolchain is C89. The 1998 machine has C89 compilers, and Z98's output is written for exactly those compilers. C99 is a standard, not something the era's machine becomes; and a program that requires C99 has left the era target behind. A project aiming at a modern machine is a different project with different tools; this manual is about the era target. For a program that must run on the era's hardware and compile with the era's compilers, the choice is between C89 as written and C89 with checks the C89 compiler cannot provide. That second thing is Z98.

The toolchain cost

The target here is a home-user machine of the era: a 32-bit PC running Windows 95 or 98, with tens of megabytes of RAM. A modern compiler — gcc, mingw, or Zig — is built for a modern machine: it expects a modern operating system and far more memory than that machine has, and its binaries do not run there. Adopting one means adopting a new machine and a new OS. That is a fine decision, but it is a different target; the software is no longer for the machine the project set out to serve.

Z98's toolchain cost is the opposite one. It emits C89, and C89 is what the compilers already on that machine accept — the era's C compilers, including the OpenWatcom path this manual uses for Win9x. There is no new runtime to install, no garbage collector, no unwinder, and no operating-system upgrade. The RAM the machine has is the RAM the program gets.

That is the whole reason the comparison in this chapter is C89 and C++98. They are the peers that ran on the target. A feature scoreboard against a language that cannot run on the target would measure the wrong thing; what matters is what the target's toolchain can build, and what the target's machine can carry.

The comparison set

Three languages, one machine. The columns are the questions that decide an era project: what builds it, where memory comes from, how failure is reported, and what the compiler checks for you.

Language Toolchain Memory Failure What the compiler checks
C89 the era's C compilers malloc/free by hand return codes, errno, conventions syntax and types only
C++98 the era's C++ compilers new/delete, constructors, destructors exceptions: try/throw/catch classes, templates, type rules
Z98 emits C89; the same era C compilers arena over a buffer you supply error unions: try/catch/errdefer errors, lifetimes, suspension, bounds, casts

Read the last column: that is the chapter. Z98 compiles to the same C89 the first row compiles to, for the same compilers, with the disciplines of the first row turned into things the compiler enforces.

What Z98 stops you from shipping

In 1998 a bug ships on a disk. There is no telemetry, no crash reporter, and no fix in an hour; the defects below are the ones a C89 codebase shipped most often. Each is a convention in C89 that becomes a check in Z98.

The error that went unchecked

In C89 a fallible function returns -1, or sets errno, or writes through an out-parameter, and the caller is trusted to notice. Forget the check and the program continues with bad data. Z98 puts the failure in the function's type — error{...}!T — so it cannot be ignored by accident: 

error[3015]: error union result is ignored; use 'try', 'catch', or assign the result

try may only appear in a function whose return type carries the error; using it in a void function is rejected before the program is built: 

error[3075]: expected type 'void', found error set
note: function cannot return an error

The C89 program ran a forgotten check until it crashed on a user's machine. The Z98 program does not build.

The index that walked off the array

In C89, map[r * w + c] is arithmetic on a pointer, and the compiler has no idea where the array ends. A bound computed from the wrong variable reads or writes whatever follows. Z98 slices carry their length, and indexing is checked. A bound the compiler can see is rejected at compile time: 

error[3062]: index 5 outside array of length 3

A bound that only exists at runtime traps under the default safety mode (-fsafe) instead of corrupting memory. The same tilemap loader that walks off the end of a C89 array stops at the edge in Z98.

The memory that leaked, dangled, or was freed twice

C89's malloc/free discipline has one failure mode per line: an early return leaks, a stale pointer dangles, a duplicate cleanup path frees twice. Z98's memory story is the arena: one buffer, bump allocation, one reset. There is no per-object free to double, and no wrong pointer to pass to it. Allocation failure is an error union, so an exhausted arena is a caught error rather than a null dereference: 

error.OutOfMemory

The arena's own limit is honest and small: memory lives until the reset, so the discipline is choosing the reset level well. That is one decision, reviewed in one place, instead of a free on every path through every function.

The pointer that was null

In C89 every pointer can be NULL, and every dereference is a bet. Z98 splits the case in the type system: *T is not nullable, and absence is ?T, which must be unwrapped explicitly with if (opt) |v| or orelse. There is no silent dereference of a maybe-null pointer, because the type does not allow one. When the analyzer cannot prove a dereference safe, it says so: 

warning[3037]: potential null pointer dereference

The cast that silently truncated

C89 converts integers and pointers implicitly, and truncation, sign change, or qualifier loss is silent. Z98 makes the dangerous conversions explicit and checks them. An implicit width mismatch at a declaration warns; a const or volatile discard is an error; a checked cast traps in the safety mode if the value does not fit: 

warning[3000]: type mismatch in variable declaration -- initialization type may not be compatible with declared type
error[3000]: cannot implicitly discard 'volatile' qualifier; use @volatileCast to remove it
panic: integer cast overflow in @intCast

Those are the failure modes that made 1998 software expensive to get right. Z98 does not make them a checklist of features: it makes them things the compiler refuses to let through.

Side by side: the same evaluator in C89 and Z98

Abstract lists are cheap, so here is the same small task written twice: a Lisp-style evaluator over a tree of expressions, with one real failure mode (division by zero). It forces every hard part of a system language — tagged data, allocation, recursion, dispatch, and error plumbing — and it shows exactly which C89 conventions become Z98 types.

C89: tag it, allocate it, plumb it, dispatch it

The C89 shape is an enum tag, a union payload, a malloc/free per node, and a status int threaded through every call. This is era framing, the pattern every C programmer of the period wrote: 

typedef enum { E_NUM, E_NEG, E_ADD, E_SUB, E_MUL, E_DIV } EKind;

typedef struct Expr {
    EKind kind;
    union {
        int num;
        struct Expr *neg;
        struct { struct Expr *l, *r; } bin;
    } u;
} Expr;

/* 0 = success, -1 = divide by zero; the result comes back through *out */
static int eval(const Expr *e, int *out)
{
    int l, r;
    switch (e->kind) {
    case E_NUM: *out = e->u.num; return 0;
    case E_NEG:
        if (eval(e->u.neg, &l) != 0) return -1;
        *out = -l; return 0;
    case E_ADD:
        if (eval(e->u.bin.l, &l) != 0) return -1;
        if (eval(e->u.bin.r, &r) != 0) return -1;
        *out = l + r; return 0;
    case E_DIV:
        if (eval(e->u.bin.l, &l) != 0) return -1;
        if (eval(e->u.bin.r, &r) != 0) return -1;
        if (r == 0) return -1;
        *out = l / r; return 0;
    default: return -1;
    }
}

The compiler cannot see the conventions. Nothing ties the tag to the union member. Nothing makes a caller check the status. Nothing pairs the malloc with a free on the error paths, and the default prong exists because the switch cannot be proven exhaustive.

Z98: one type, one switch, an error in the signature

The Z98 shape makes the tag and the payload one type, makes the switch exhaustive and payload-binding, and puts the failure in the return type: 

const Bin = struct { l: u32, r: u32 };

const Expr = union(enum) {
    num: i32,
    neg: u32,
    add: Bin,
    sub: Bin,
    mul: Bin,
    div: Bin,
};

fn eval(nodes: []Expr, i: u32) error{DivideByZero}!i32 {
    switch (nodes[@intCast(usize, i)]) {
        .num => |v| return v,
        .neg => |j| return -(try eval(nodes, j)),
        .add => |b| return (try eval(nodes, b.l)) + (try eval(nodes, b.r)),
        .sub => |b| return (try eval(nodes, b.l)) - (try eval(nodes, b.r)),
        .mul => |b| return (try eval(nodes, b.l)) * (try eval(nodes, b.r)),
        .div => |b| {
            const rhs = try eval(nodes, b.r);
            if (rhs == 0) return error.DivideByZero;
            return (try eval(nodes, b.l)) / rhs;
        },
        else => unreachable,
    }
}

The tag and the payload cannot drift apart; the switch binds the payload to a name, so b.l is a u32. The failure is written into the signature as error{DivideByZero}!i32, so try propagates it and the compiler refuses to let it be dropped. Nodes come from one arena slice instead of a malloc per node, and the index goes through a length-carrying slice. This is the convention-to-type move in one function: C89's tag discipline, status discipline, and allocation discipline are now parts of the language.

The example: lisp_eval.z98

The first runnable program is that evaluator, complete: docs/sf/manuals/src/vol2/lisp_eval.z98. It builds a node pool over an arena, constructs (2+3)*(10-4)/2, evaluates it, then evaluates 10/(10-10) and catches the error. 

const std = @import("std");

const Bin = struct { l: u32, r: u32 };

const Expr = union(enum) {
    num: i32,
    neg: u32,
    add: Bin,
    sub: Bin,
    mul: Bin,
    div: Bin,
};

const Pool = struct { nodes: []Expr, used: u32 };

fn make(pool: *Pool, e: Expr) u32 {
    const i = pool.used;
    pool.nodes[@intCast(usize, i)] = e;
    pool.used = i + 1;
    return i;
}

fn eval(nodes: []Expr, i: u32) error{DivideByZero}!i32 {
    switch (nodes[@intCast(usize, i)]) {
        .num => |v| return v,
        .neg => |j| return -(try eval(nodes, j)),
        .add => |b| return (try eval(nodes, b.l)) + (try eval(nodes, b.r)),
        .sub => |b| return (try eval(nodes, b.l)) - (try eval(nodes, b.r)),
        .mul => |b| return (try eval(nodes, b.l)) * (try eval(nodes, b.r)),
        .div => |b| {
            const rhs = try eval(nodes, b.r);
            if (rhs == 0) return error.DivideByZero;
            return (try eval(nodes, b.l)) / rhs;
        },
        else => unreachable,
    }
}

pub fn main() !void {
    var buf: [8192]u8 = undefined;
    var arena = std.arena.init(buf[0..]);
    const raw = try std.arena.alloc(&arena, @sizeOf(Expr) * 64);
    var pool = Pool{ .nodes = @ptrCast([*]Expr, raw)[0..64], .used = 0 };

    const two = make(&pool, .{ .num = 2 });
    const three = make(&pool, .{ .num = 3 });
    const ten = make(&pool, .{ .num = 10 });
    const four = make(&pool, .{ .num = 4 });

    const sum = make(&pool, .{ .add = .{ .l = two, .r = three } });
    const diff = make(&pool, .{ .sub = .{ .l = ten, .r = four } });
    const product = make(&pool, .{ .mul = .{ .l = sum, .r = diff } });
    const answer = make(&pool, .{ .div = .{ .l = product, .r = two } });

    std.io.print("eval((2+3)*(10-4)/2) = {}\n", .{ try eval(pool.nodes, answer) });

    const zero = make(&pool, .{ .sub = .{ .l = ten, .r = ten } });
    const bad = make(&pool, .{ .div = .{ .l = ten, .r = zero } });
    _ = eval(pool.nodes, bad) catch {
        std.io.print("eval(10/(10-10)) caught DivideByZero\n", .{});
        return;
    };
    std.io.print("unreachable\n", .{});
}

The first line is the successful evaluation: (2+3) is 5, (10-4) is 6, the product is 30, and 30/2 is 15. The second line is the error path: the evaluator reaches a zero divisor, returns error.DivideByZero, and the catch at the call site handles it. The program exits 0. The compile is clean: no warnings, no casts to paper over, and no free to match.

Side by side: the era's game code

An evaluator is a compiler-shaped example. The same convention-to-type moves show up in the two pieces of every era game — moving entities and loading a tilemap — and in the cleanup code that surrounded both.

The entity update loop

C89 passes a bare pointer and a separate count, and trusts the loop bound. This is era framing: 

typedef struct { int x, y, vx, vy; } Entity;

void update(Entity *e, int dt) {
    e->x += e->vx * dt;
    e->y += e->vy * dt;
    if (e->x < 0)   { e->x = 0;   e->vx = -e->vx; }
    if (e->x > 100) { e->x = 100; e->vx = -e->vx; }
    if (e->y < 0)   { e->y = 0;   e->vy = -e->vy; }
    if (e->y > 60)  { e->y = 60;  e->vy = -e->vy; }
}

void step(Entity *world, int n, int dt) {
    int i;
    for (i = 0; i < n; i++) update(&world[i], dt);
}

Z98 keeps the arithmetic and attaches the length to the data: 

const Entity = struct { x: i32, y: i32, vx: i32, vy: i32 };

fn update(e: *Entity, dt: i32) void {
    e.x += e.vx * dt;
    e.y += e.vy * dt;
    if (e.x < 0) { e.x = 0; e.vx = -e.vx; }
    if (e.x > 100) { e.x = 100; e.vx = -e.vx; }
    if (e.y < 0) { e.y = 0; e.vy = -e.vy; }
    if (e.y > 60) { e.y = 60; e.vy = -e.vy; }
}

fn step(world: []Entity, dt: i32) void {
    for (world) |_, i| {
        update(&world[i], dt);
    }
}

The win is not shorter code. The win is that world carries its own length, so there is no separate n to pass or to get wrong, and the index is checked in the default safety mode. A bounds bug that would corrupt memory in C89 stops and reports instead.

The tilemap loader

Loading a w×h grid in C89 means allocating, checking the allocation, filling with a manually computed index, checking the fill status, and freeing every path out. Length is a variable the caller keeps beside the pointer: 

static int load_map(unsigned char *map, int w, int h)
{
    int r, c;
    if (map == NULL) return -1;
    for (r = 0; r < h; r++)
        for (c = 0; c < w; c++)
            map[r * w + c] = (unsigned char)((r + c) % 4);
    return 0;
}

unsigned char *map = malloc((size_t)w * (size_t)h);
if (map == NULL) { cleanup(); return -1; }
if (load_map(map, w, h) != 0) { free(map); return -1; }
/* ... use map ... */
free(map);

In Z98 the loader returns either a slice or an error, and the slice carries its length. The allocation failure is in the type, and there is no free: 

fn loadMap(arena: *std.arena.Arena, w: usize, h: usize) ![]u8 {
    const raw = try std.arena.alloc(arena, w * h);
    const map = @ptrCast([*]u8, raw)[0..w * h];
    var r: usize = 0;
    while (r < h) : (r += 1) {
        var c: usize = 0;
        while (c < w) : (c += 1) {
            map[r * w + c] = @intCast(u8, (r + c) % 4);
        }
    }
    return map;
}

Three things are gone from the call site: the malloc result check (try replaces it), the separate width and height bookkeeping (map.len is the slice's own), and the free and its error paths (the arena reset reclaims the map). The fill still writes through a manually computed index, and @intCast makes the narrowing to u8 explicit and checked — but the failure and length plumbing that made the C89 version long is in the type system now.

The cleanup that lived on every path

C89 cleanup is a convention around a label: each resource is released in reverse order at one exit, and every early return must jump there. This is era framing: 

static int load_save(World *w)
{
    FILE *f = NULL;
    unsigned char *map = NULL;
    int rc = -1;

    f = fopen("world.dat", "rb");
    if (f == NULL) goto cleanup;
    map = malloc(w->w * w->h);
    if (map == NULL) goto cleanup;
    if (fread(map, 1, (size_t)(w->w * w->h), f) != (size_t)(w->w * w->h))
        goto cleanup;
    w->map = map;
    map = NULL;
    rc = 0;

cleanup:
    free(map);
    if (f != NULL) fclose(f);
    return rc;
}

Z98 writes the cleanup next to the thing it cleans up, and the compiler lays the exits out: 

fn loadSave(ok: bool) !void {
    defer std.io.print("save slot closed\n", .{});
    errdefer std.io.print("save slot rolled back\n", .{});
    if (!ok) return error.Corrupt;
    std.io.print("save slot loaded\n", .{});
}

defer runs at every scope exit; errdefer runs only when the scope leaves with an error. The C89 version's correctness depends on every future edit remembering the label; the Z98 version's cleanup is attached to the declaration and cannot be skipped by an early return.

The example: game_loop.z98

The second runnable program puts the pieces together: docs/sf/manuals/src/vol2/game_loop.z98. It updates two entities, loads and measures a tilemap, runs a four-step patrol coroutine, then loads a save slot on the success and error paths. 

const std = @import("std");

const Entity = struct { x: i32, y: i32, vx: i32, vy: i32 };

fn update(e: *Entity, dt: i32) void {
    e.x += e.vx * dt;
    e.y += e.vy * dt;
    if (e.x < 0) { e.x = 0; e.vx = -e.vx; }
    if (e.x > 100) { e.x = 100; e.vx = -e.vx; }
    if (e.y < 0) { e.y = 0; e.vy = -e.vy; }
    if (e.y > 60) { e.y = 60; e.vy = -e.vy; }
}

fn step(world: []Entity, dt: i32) void {
    for (world) |_, i| {
        update(&world[i], dt);
    }
}

fn loadMap(arena: *std.arena.Arena, w: usize, h: usize) ![]u8 {
    const raw = try std.arena.alloc(arena, w * h);
    const map = @ptrCast([*]u8, raw)[0..w * h];
    var r: usize = 0;
    while (r < h) : (r += 1) {
        var c: usize = 0;
        while (c < w) : (c += 1) {
            map[r * w + c] = @intCast(u8, (r + c) % 4);
        }
    }
    return map;
}

fn loadSave(ok: bool) !void {
    defer std.io.print("save slot closed\n", .{});
    errdefer std.io.print("save slot rolled back\n", .{});
    if (!ok) return error.Corrupt;
    std.io.print("save slot loaded\n", .{});
}

const MoveArgs = struct { e: *Entity };

var g_pool: [1024]u64 = undefined;
var g_frame: [256]u8 = undefined;

fn patrol(e: *Entity) void {
    var i: i32 = 0;
    while (i < 4) : (i += 1) {
        e.x += e.vx;
        _ = @asyncSuspend(null);
    }
}

pub fn main() void {
    var world = [2]Entity{
        .{ .x = 10, .y = 10, .vx = 7, .vy = -3 },
        .{ .x = 90, .y = 50, .vx = -9, .vy = 4 },
    };
    step(world[0..], 1);
    std.io.print("entity 0 after update: {},{} v={},{}\n", .{ world[0].x, world[0].y, world[0].vx, world[0].vy });
    std.io.print("entity 1 after update: {},{} v={},{}\n", .{ world[1].x, world[1].y, world[1].vx, world[1].vy });

    var buf: [8192]u8 = undefined;
    var arena = std.arena.init(buf[0..]);
    const map = loadMap(&arena, 8, 4) catch {
        std.io.print("map load failed\n", .{});
        return;
    };
    var tsum: usize = 0;
    for (map) |t| {
        tsum = tsum + @intCast(usize, t);
    }
    std.io.print("tilemap len={} checksum={}\n", .{ map.len, tsum });

    var args = MoveArgs{ .e = &world[0] };
    const ctx = std.async.contextInit(@ptrCast([*]u8, &g_pool)[0..8192]);
    const frame = @asyncInit(ctx, @ptrCast([*]u8, &g_frame), patrol, @ptrCast(*const void, &args));
    var r = @asyncResume(frame, null);
    while (r != null) {
        r = @asyncResume(frame, null);
    }
    std.io.print("entity 0 after patrol: {},{}\n", .{ world[0].x, world[0].y });

    loadSave(true) catch {};
    loadSave(false) catch {
        std.io.print("corrupt save rejected\n", .{});
    };
}

The first two lines are the stepped entities: the first moved to (17,7) and kept its velocity; the second moved to (81,54) without hitting a wall. The third line is the tilemap: a length-carrying slice whose 32 tiles sum to 48. The fourth is the coroutine: four suspensions, each advancing x by 7, so the entity ends at 45. Coroutines: what they replace

Suspension is the third convention C89 leaves to you. A routine that pauses and resumes was one of three things on the era's machines: a hand-rolled state machine, a callback chain, or a thread you juggled. All three put the bookkeeping in your source.

The state machine you stop writing

The state machine is the honest baseline. A patrol that walks four steps and pauses between them needs a state word, an index, and a switch that knows where to re-enter. This is era framing: 

typedef struct { int state; int i; Entity *e; } Patrol;

/* returns 1 while suspended, 0 when finished */
int patrol_step(Patrol *p)
{
    switch (p->state) {
    case 0: p->i = 0; p->state = 1;   /* fall through */
    case 1:
        if (p->i >= 4) { p->state = 3; return 0; }
        p->e->x += p->e->vx;
        p->i++;
        return 1;
    default: return 0;
    }
}

In Z98 the routine is written in the order it happens, and the pause is a statement: 

fn patrol(e: *Entity) void {
    var i: i32 = 0;
    while (i < 4) : (i += 1) {
        e.x += e.vx;
        _ = @asyncSuspend(null);
    }
}

What was deleted: the state word, the index field, the re-entry switch, and the calling convention that told the caller whether to call again. The compiler synthesises the step machine, the frame layout, and the state word; std.async owns the scheduler and the frame pool. Because nothing preempts, the coroutine keeps the machine until it reaches a suspension point, shared state cannot change under it, and there are no locks to buy. A coroutine costs a frame buffer, not a stack and a kernel object — which is the only version of concurrency a 16 MB machine should be asked to run.

Where C89 and C++98 take the lead

Honesty is two-sided. Z98 checks more than C89 and less than C++98, and there are places the era's languages genuinely win.

C89 leads on ubiquity and on nothing-new. Every era compiler accepts it, every era programmer reads it, and it asks for no toolchain change at all. There are decades of existing C89 code and libraries to link; Z98's output is C89, so it links with them directly. C89 also leads on total freedom: there is no checker to disagree with you, and when you know exactly what you are doing, that is a feature. And C89 is an ISO standard, with a stable document behind it.

C++98 leads wherever abstraction is worth a runtime. Templates give generic containers; classes give constructors and destructors, so cleanup runs automatically on every exit; exceptions unwind the stack to the handler; and operator overloading lets the standard library read naturally. When the memory budget carries the vtables and the exception machinery, C++98 gives leverage Z98 deliberately does not. A short era-framing sketch: 

template <typename T>
class Stack {
public:
    Stack() : data(new T[64]), count(0) {}
    ~Stack() { delete[] data; }   /* cleanup on every exit path */

    void push(const T& v) { if (count < 64) data[count++] = v; }
    bool pop(T& out) {
        if (count == 0) return false;
        out = data[--count];
        return true;
    }

private:
    T *data;
    int count;
};

The destructor is automatic, the container works for any T, and pop reports failure the C89 way, through a status and an out-parameter. The cost is a template expansion per type, a vtable-shaped object, and the exception tables the toolchain emits. Z98 makes the opposite trade: less abstraction, less runtime, more checking.

Where the three tie

The three languages are not worlds apart; they share the era's ground rules. All three produce native 32-bit code for the same machine with no interpreter and no garbage collector. All three compile with the era's toolchain, and Z98 output can be linked with hand-written C89 in the same program. And all three look the same on the page: structs and free functions, init functions, arrays with a length kept nearby, a status or an error to check. A C89 programmer can read a Z98 program on the first pass; the differences are in what the compiler verifies, not in what the machine executes.

The limits, and the way over each

The limits are real and worth stating plainly. None of them is a dead end; each has a shape era programmers already used, and the shape still works on this compiler.

Limit The way over it
No generics or templates Concrete functions per type and explicit tables; a *void plus a function pointer where the type genuinely varies; the standard library's containers are written out concretely.
No classes, no RAII A struct of function pointers is the manual vtable; init functions are the constructor; defer/errdefer and the arena are the destructor discipline.
No exceptions Error unions carry the failure in the signature; try propagates, catch handles, errdefer rolls back. The checked path replaces the unwinding one.
No threads, no preemption Coroutines and the std.async round-robin scheduler; suspension points are explicit, so no locks are needed. Real parallelism stays an OS concern.
No general comptime The introspection builtins answer the representation questions; everything else is ordinary concrete code and constant folding.

Two more limits deserve a line each, because they shape how a project is laid out. There is no package manager: third-party code is vendored into the tree, which is what the era did anyway. And the compiler enforces its rules rather strictly — an ignored error, an unhandled switch, an uninitialized variable, or control flow out of a defer body are build errors. That strictness is the product, not a defect, but it is a real adjustment for a programmer used to C89's silence.

Honest note. Every limit above is a deliberate trade against the era's machine, and every one has a way over it that stays inside the language and the toolchain. There is a way around Z98 too: when a project's core need is templates, RAII, or exceptions and the RAM can carry them, C++98 is the right tool. That is a project decision, not a verdict on this one.

Checked C89

The frame of the chapter, said once more in plain words: Z98 is not a better C standard. It is a compiler that checks what C89 leaves to discipline and emits C89 for the era's machines. Error handling, cleanup, suspension, buffer length, bounds, nullability, and conversions — the things a C89 team keeps in comments and code review — are types, statements, and analyzers in Z98. The C89 compiler downstream still sees plain C89, and the 1998 machine still runs it.

"We are a smaller language" would be the wrong summary, because the list of things Z98 gives is longer than the list it withholds. What it withholds is the abstraction machinery that needs a runtime the target cannot afford; what it gives is the checking that keeps an era-sized codebase correct without that runtime. It is C89 with contracts in the type system, and it is deliberately that.

What that means for you

If the target is the era — a 1998 machine, the era's compilers, an era-sized memory budget — Z98 is the toolchain that keeps the machine's cost model and raises the floor on what the compiler catches. If the project carries templates, RAII, and exceptions as core needs and the RAM allows, C++98 is the era-appropriate choice. If the goal is hand-written C89 with no checker in the way, C89 is right there.

Common mistakes

The mistakes below are the ones a C or C++ programmer makes first in Z98. Each has a diagnostic or a corrected shape, and each diagnostic points at the rule that was crossed.

Reaching for malloc and free. The base language's memory story is the arena: you hand std.arena.init a buffer and let try std.arena.alloc bump within it. There is no free to match; std.arena.reset reclaims the whole arena at once. If a C library you call hands you memory, that library still owns releasing it, but the Z98 objects you build come from the arena.

Treating a slice as a pointer plus a length variable. A slice ([]T) carries its own length; pass the slice and use .len. Keeping a separate length beside a raw pointer is exactly the convention Z98 removed, and it re-introduces the bug the slice was there to prevent.

Expecting method syntax. e.update(dt) is not a method call with a different spelling; it is a member lookup, and it fails: 

error[3060]: no field or member function named 'update' in struct type

Write the free function and pass the receiver: update(&e, dt).

Expecting generics or comptime. A comptime type parameter does not parse: 

error[2000]: expected ':' but found identifier

Write one function for the concrete type, or a small concrete container. The limits table above is the map; C++98 is the tool when a type must genuinely stay open.

Treating try/catch as exceptions. They operate on error unions, which are values. Nothing unwinds, and a catch block must produce a value of the payload type or diverge (return, break, and so on). There is no throw, no anyerror, and no @errorName; the error is a declared tag in the function's signature.

Spawning a thread for a pause. Z98 has no thread API; it has coroutines. A routine that needs to wait writes @asyncSuspend where the pause belongs and is driven by std.async, cooperative and round-robin. On a single-core era machine, that is the cheap and correct way to interleave work.

Leaving out else in a switch. Every Z98 switch needs an else prong, even when the union is fully covered: 

error[3068]: switch must have an 'else' prong

For an exhaustive switch on a tagged union, else => unreachable is the spelled-out promise that the prong can never run.
