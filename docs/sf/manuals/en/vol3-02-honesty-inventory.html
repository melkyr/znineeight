Honesty: What Z98 Does and Does Not Give You

This is the register-setter for Volume III. Volume II taught the language and measured it on the seed-built compiler. This volume is about the machine, the toolchain, and the limits, and its register is the tradeoff — not the apology, and not a scoreboard. This chapter is the map: what Z98 gives you, what it does not, and what you reach for when it does not.

You met the frame in Volume II, chapter 1, The Honest Comparison: Z98 is checked C89 — C89 with contracts in the type system. It emits C89 for the era's compilers, keeps the machine's cost model, and moves the disciplines C89 leaves to the programmer into checks the compiler performs. Chapter 16 measured the three absences that shape daily code — no methods, no generics, no comptime — and the patterns that replace them. This chapter is the full inventory those two pages implied: every item in the blueprint's gives/doesn't-give list, each paired with what you use instead.

Era framing. Statements on this page about the era's machines, toolchains, C89, and C++98 are era context, and where they are opinion the text says so. Statements about Z98 are checked against docs/reference/Language_Spec_Z98.md, the compiler source, and the compiler built from the committed seed; the Z98 fragments here are drawn from programs Volume II already shipped, compiled, and ran.

What you expect

If you arrive from a modern language, you arrive with a checklist. Generics. Classes and methods. Exceptions. Runtime type information. Threads. A package manager. An integrated development environment. Dynamic linking against libraries that ship as shared objects. A language without those feels smaller, and the first instinct is to read their absence as a deficiency to be weighed.

That reading measures the wrong thing. A modern toolchain was never a candidate for the target machine: it expects a modern operating system and far more memory than a 1998 PC has, and its binaries do not run there. Adopting it means adopting a new machine and a new operating system. That is a fine decision, but it is a different project, and it no longer serves the machine the project set out to serve. The comparison that decides an era project is against the peers that actually ran on the target: C89 and C++98. Volume II chapter 1 set that comparison out. This page states its inventory.

There is a second expectation to set aside, and it is subtler. A reader assumes that a compiler with a small feature list must be a compiler with a large runtime doing the hidden work. The truth is the opposite. Z98's list is short because the runtime is short: there is no allocator the language calls on its own, no unwinder, no garbage collector, no dynamic loader, no package graph. What the language withholds is the machinery that needs a runtime the target cannot afford; what it gives is the checking that keeps an era-sized codebase correct without that runtime.

What you get

Seven things, each of which replaces a C89 discipline with a construct the compiler enforces. The table is the inventory; the sections after it are the detail, and the measured evidence for each lives in the Volume II chapter or the spec clause named in the last column.

Error unions

The first big shift. A function that can fail says so in its type, and the failure cannot be dropped by accident: 

fn parse(n: i32) error{Negative}!u32 {
    if (n < 0) return error.Negative;
    return @intCast(u32, n);
}

The caller unwraps with try to propagate or catch to handle; a result that is neither is rejected at compile time. The chapter's shipped program behind Volume II chapter 12, docs/sf/manuals/src/vol2/error_unions.z98, prints 5 from the successful division and caught: DivideByZero on the error path, exercising try and catch |err|. This replaces C89's convention of a sentinel return, a global errno, or an out-parameter the caller is trusted to check.

Optionals

Absence is a type, not a convention. ?T is either a value or null, and it must be unwrapped explicitly with orelse or if (opt) |v|: 

const m = maybe(false) orelse 99;

*T is never nullable, so a dereference is never a silent bet on a null. The chapter's shipped program behind Volume II chapter 13, docs/sf/manuals/src/vol2/lookup.z98, prints sizes: ?i32=8 ?u8=8 ?*Entry=8 *Entry=4, resolves a hit with orelse hit: 1, and falls back on a miss with orelse miss: -1. This replaces the C89 pattern where every pointer can be NULL and every value carries an untyped “is this valid?” flag.

Coroutines

Suspension is a language statement. A function that contains @asyncSuspend is compiled to a step machine; @asyncInit, @asyncResume, and @asyncFrameSize drive it; std.async owns the scheduler and the per-task frame pool: 

fn worker(out: *i32) void {
    var i: i32 = 0;
    while (i < 3) : (i += 1) {
        @asyncSuspend(null);
    }
    out.* = i;
}

The shipped program docs/sf/manuals/src/vol2/builtins/async.z98 reports frame=88 and n=3 steps=4 on this compiler, and the same @async* surface is catalogued in Volume II chapter 15. This is the third mental shift, and chapter 9, Coroutines — the third big shift (planned) takes it apart. It replaces the hand-rolled state machine: a state word, an index, and a re-entry switch the compiler writes for you.

The arena

Memory comes from a buffer you supply. std.arena.init starts a cursor over it, std.arena.alloc is fallible (so exhaustion is a caught error, not a null dereference), and std.arena.reset reclaims the whole arena in one call. There is no per-object free to double and no wrong pointer to pass to one: 

var buf: [32]u8 = undefined;
var arena = std.arena.init(buf[0..]);
const p = try Point_init(&arena, 3, 4);

The measured program behind Volume II chapter 14 prints cap=32 used=0, p=3 4 used=8, used after reset=0, and catches error.OutOfMemory from an over-large request. The dual-arena pattern — one arena for the whole run, one for the phase — is measured in the same program.

Comptime-introspection builtins

The compile-time questions a C89 program answers with macros are answered by a fixed builtin catalog: introspection (@sizeOf, @alignOf, @offsetOf, @bitSizeOf), conversion (@intCast, @ptrCast, @bitCast, @as), and target folding (@isWindows): 

@sizeOf(Vec)          // 8
@alignOf(Vec)         // 4
@offsetOf(Vec, "y")   // 4
@bitSizeOf(u16)       // 16

Those four values are what this compiler folds for const Vec = struct { x: i32, y: i32 };, the same shape Volume II chapter 15 catalogued. An unknown builtin is a clean error[3000]: unsupported builtin function. This replaces the preprocessor version of the same questions, and it is the whole of Z98's compile-time surface.

Deterministic C89 emission

The compiler's output is a function of its input, not of the wall clock or the run: emitting the same program twice produces byte-identical C. That property is a gate, not a hope. Four reference programs (game of life, the Lisp interpreter, the JSON parser, and mud_server) are dumped twice each and their emitted C must be byte-identical; the Volume II compiler work held that gate unchanged through every fix. It is what lets you diff generated C between builds, debug it with gdb (chapter 15, planned), and trust that a rebuilt program is the same program. The alternative is hand-written C with no second emitter to compare against.

A self-hosting compiler

Z98's compiler is written in Z98, and it is rebuilt from a committed seed with only gcc: the seed compiles the current source, and the result compiles the source again to the same binary. On this run the two hops closed at 8216fedc…, the recorded fixed point for seed v89. The practical consequence for you is the seed model: when the compiler is changed, rebuilding is a two-hop process, and the reason the compiler can be rebuilt on the era's machine at all is that it is small enough to fit the target's memory budget. A self-hosting compiler is also the strongest single proof that the language is complete enough to write real programs in.

What you do not get

This is the other column, and it is the one a modern checklist is looking for. Every row is a fact, and every row is paired with the era alternative that takes its place — a Z98 idiom, a standard module, or another language. There are no bare absences on this page.

Generics and templates

A comptime type parameter never parses, and a plain type parameter leaves the bound name undeclared, so there is no instantiation step to reach: 

fn id(comptime T: type, x: T) T { return x; }
// error[2000]: expected ':' but found identifier

The way over is the concrete container. Where a C++ library would write List<T> once, a Z98 program writes ShapeList for shapes and a second, separate container for the next element type. This is not a workaround for a missing feature; it is the design, and the compiler's own source does it — the concrete hash maps it needs are hand-written in sf/src/util/hash.zig. When a type genuinely must stay open and the 32 MB can carry the template expansions, C++98 is the era-appropriate tool, and chapter 4 (planned) says so outright.

Classes and methods

An aggregate type has fields but no function members, so a call such as s.bar() is rejected where it appears: 

const s = S{ .x = 1 };
s.bar();
// error[3060]: no field or member function named 'bar' in struct type

The way over is two patterns from Volume II chapter 16: the receiver is an ordinary first parameter (draw(sh), never sh.draw()), and polymorphism is a struct of function pointers plus one erased *void. The interface costs one data pointer and one function pointer per operation — measured as Shape size=12 align=4 fn=4 on the 32-bit target — and calling it compiles to a call through a C function pointer, with no receiver magic and nothing to look up at run time.

Exceptions

There are no exception keywords and nothing unwinds. Failure is a value in the return type, so the cost of a failure path is the cost of a branch, not the cost of an unwinder and its tables. The way over is the error union: the same try/catch/errdefer discipline that Volume II chapter 12 measures. Where the abstraction genuinely needs stack unwinding and the memory can carry it, C++98 supplies it, and chapter 4 (planned) is where that trade is stated.

RTTI

There is no runtime type oracle: no type information travels with a value, and nothing can ask “what type is this really?” at run time. The way over is the tag you write. A tagged union carries its discriminant, a switch on it binds the payload and is exhaustive, and that is the only dispatch the program has. A C89 program of the era did the same thing with an enum field and a union, and Z98 simply folds the pair into one type. The manual vtable covers the object-style case, and its data contract — the function signature plus the erased pointer — is the whole of the type agreement.

Threads and preemption

There is no thread API, and nothing runs behind your back: a coroutine keeps the machine until it reaches a suspension point, so shared state cannot change under it and there are no locks to buy. The way over is the std.async scheduler, cooperative and round-robin, with suspension written where the pause belongs: 

@asyncSuspend(null);

On a single-core era machine that is the cheap and correct way to interleave work; a coroutine costs a frame buffer, not a stack and a kernel object. Real parallelism, where it is needed at all, stays an operating-system concern and is reached through extern declarations, not through the language.

Manual vtables, in place of dynamic dispatch

There is no language-level dynamic dispatch. What there is, is the idiom the compiler would otherwise generate for you, written by hand: 

const Shape = struct {
    draw_fn: fn (*void) void,
    data: *void,
};

Construction is an init function that stores the operation and the object's address; dispatch is an ordinary call through the field. The measured program behind Volume II chapter 16 builds two concrete shapes into three interface values and prints shapes drawn 3. The interface's contract is partly outside the type checker — the erased pointer's real type is a promise the init function keeps — which is why the init function matters more here than a constructor does in a language with classes.

anyerror, and comptime beyond the builtins

anyerror is not a type the compiler knows: 

fn f(e: anyerror) void {}
// error[20]: identifier 'anyerror' is not declared or imported in this module

Failures are declared, not erased: write error{Foo, Bar} or an anonymous !T, and the compiler tracks the set. In the same way, comptime exists only as the builtin catalog; there is no @Type to build a type at compile time and no @typeInfo to inspect one. The way over for both is the same as for generics: name the concrete thing, and use the introspection builtins for the representation questions they were built to answer.

A package manager, an IDE, and dynamic linking

These three are absences of tooling rather than of language, and each has the era's answer. Third-party code is vendored into the tree, because that is what a 1998 project shipped and because a package graph cannot resolve without a network and a runtime to fetch through. Editing is a text editor and the compiler's numbered diagnostics, because the manual's own site is hand-authored plain HTML for the same reason: no external resources and no framework to depend on. And a modern shared library is not something the target can load; Z98 emits C89, and C89 links against the era's static libraries and object files directly, which is the same seam Volume II chapter 1 describes as the language's reason for existing.

The trade

Read the two tables together and one trade appears under every row. The compiler withholds the machinery that needs a runtime, and in exchange the runtime is nothing you did not write. There is no allocator called for you, no unwinder, no garbage collector, no dynamic loader, no package graph. A call is a call. Storage is a buffer you declared. A failure is a branch. A pause is a statement. The generated C89 has no machinery in it that a 1998 programmer reading the output would not recognise.

That is what buys the two facts at the bottom of the gives table. The emission is deterministic, so the generated C can be diffed and debugged like source you wrote. And the compiler is small enough to rebuild itself on the target within the memory budget, which is why the seed model can rebuild it with nothing but gcc. A language with classes, exceptions, and a package manager is not the same size, and pretending otherwise would be the modern scoreboard this volume refuses to keep.

The trade is not free, and honesty requires naming the winner where another tool wins. C89 wins on ubiquity and on asking for nothing new; its output is already the output Z98 produces, so you can mix the two freely — that is the load-bearing fact of chapter 3 (planned). C++98 wins wherever abstraction is worth a runtime: templates, constructors and destructors, and exceptions unwind the stack for you, and when the 32 MB can carry the vtables and the unwinder, that leverage is real. Assembly wins where the C89 emission is not tight enough. Those are the subjects of chapters 3, 4, and 5, and this page is the inventory they each draw on.

Honest note. The sharpest limit is not a missing feature; it is that nothing is hidden. There is no runtime behind your back to allocate, unwind, collect, dispatch, or resolve, and that is deliberate. It means the trade is reversible at the seam: because Z98 emits C89, when a project's core need is templates, RAII, or exceptions and the memory can carry them, you can compile that part in C++98 and link it, or move the project there outright. Nothing on this page says Z98 is always right. It says what it gives, what it does not, and what to reach for instead.

The way over it

The way over each absence is an era shape that already existed, and it still works on this compiler. Stated once, compactly:

  • Need a generic container? Write the concrete one. A second element type means a second container; the repetition is real and the types stay concrete in every phase. When the type must genuinely stay open, C++98.
  • Need objects with behavior? Free functions with the receiver first, plus a manual vtable for polymorphism and init functions to establish the contract. This is the direct translation of the method table a compiler would otherwise generate.
  • Need failure to unwind through frames? An error union carries the failure in the signature, try propagates it, catch handles it, and errdefer rolls back the partial work. The checked path replaces the unwinding one.
  • Need to know a type at run time? Write the tag and switch on it. The discriminant is the type oracle.
  • Need concurrency? A coroutine suspends and resumes; the scheduler is round-robin and cooperative, so no locks are needed. Real parallelism is the OS's.
  • Need third-party code? Vendor it into the tree. Need an editor? Use a text editor and read the compiler's numbered diagnostics. Need a library? Link the era's C89 objects, because that is what your output already is.

If an item in the tables had no line here, it would be a complaint, and this chapter would have dropped it rather than list it. Every limit in the doesn't-give table carries a way over, and three of the ways over — C89, C++98, and assembly — are whole chapters with their own verdicts.

Common mistakes

The mistakes below are the ones a reader arriving with a modern checklist makes first. Each is a misreading of the inventory, not a defect in it.

Reading the list as a scoreboard. The inventory is not a verdict that Z98 is smaller or weaker; a modern toolchain was never a candidate for the target. The honest summary is the one Volume II chapter 1 gives: Z98 is not a better C standard, it is a compiler that checks what C89 leaves to discipline and emits C89 for the era's machines. The things it withholds are the abstraction machinery that needs a runtime the target cannot afford.

Reaching for a feature and expecting it to be there. A comptime type parameter does not parse, method syntax does not resolve, and anyerror is not a name the compiler knows. The measured diagnostics are: 

error[2000]: expected ':' but found identifier
error[3060]: no field or member function named 'bar' in struct type
error[20]: identifier 'anyerror' is not declared or imported in this module

Each points at the rule that was crossed, and each has the corrected shape in the section above. There is no hidden form of the feature to find.

Treating a limit as a defect to file. Every absence in this chapter is a deliberate trade against the era's machine, and the way over stays inside the language, the standard library, or the toolchain. Filing the absence of templates as a bug asks the language to become a different language with a different runtime; the epoch-appropriate answer is C++98 or the concrete container.

Assuming a convenience layer. The standard library is a set of concrete hand-written helpers, not a framework; it is the thirteen modules Volume II chapter 17 names, and the printer takes five specifiers and no width, precision, or alignment. There is no package manager to fetch a fuller one, so third-party code is vendored and reviewed like source.

Expecting storage to appear. No operation allocates behind your back. When a program needs storage it declares a buffer and hands an arena over it; when it needs an object it uses an init function and owns the storage. Reaching for an allocator that is not there is the mistake; declaring the buffer is the habit.

Spawning a thread for a pause. There is no thread API. A routine that needs to wait writes @asyncSuspend where the pause belongs and is driven by std.async. On the era's single-core machine, that is the cheap and correct interleaving, and it costs a frame buffer rather than a stack and a kernel object.
