Error Unions — the First Big Shift

Every language has a way to say "this did not work". C says it with a return value, a global variable, and a comment. Z98 says it with a type. This is the chapter where that difference stops being a slogan and becomes something you type. It is the first big shift for a C programmer, and it is the one that changes how the rest of the manual reads.

Honest note. If you come from C, your hands already know the old shapes: return -1 and set errno, or carry a status variable down the function and goto cleanup when it goes bad. Both work, and Z98 emits C89, so you can still write them. But the compiler cannot see them. Nothing forces the caller to check the -1; nothing runs the cleanup when a later step fails; the error is a convention between people, not a fact the tool can reason about. Here is the Z98 way: make the error part of the function's return type, propagate it with try, handle it with catch, and undo partial work with errdefer.

Error sets: error{...}

An error set is a named list of error tags. You declare it with the error keyword and bind it to a name with const: 

const MyErrors = error{ DivideByZero, Bad };

The spec writes the same declaration as error { Foo, Bar }; the spacing is not significant. Each tag is a distinct value, not an integer you have to keep straight. A function that can fail returns the set as part of its type, so a caller reading the signature knows exactly what can go wrong.

Error unions: !T and E!T

An error union is "a value of type T, or one of a set of errors". Write it with the error set, then a bang, then the payload type: 

fn divide(a: i32, b: i32) error{DivideByZero}!i32 {
    if (b == 0) return error.DivideByZero;
    return a / b;
}

error{DivideByZero}!i32 is a named error union: success is an i32, failure is DivideByZero. If you name the set once, the signature reads MyErrors!i32; the two forms mean the same thing. The short form !T is an anonymous error union and is what main uses: 

pub fn main() !void {
    ...
}

A plain value of type T is implicitly coerced to !T as a success, and an error literal is implicitly coerced to any error union. That is why return a / b; above needs no wrapping: an i32 becomes a successful error{DivideByZero}!i32 on the way out. The compiler represents an error union as a C struct holding the payload and an error code, so on the wire it is still plain C89.

A function returning !void (or ErrorSet!void) that falls off the end of its body implicitly returns success. That is the one exception to the usual rule that a non-void function must return a value, and it is why main in the example above needs no final return.

try: propagate it

try expr unwraps an error union. On success it yields the payload; on error it returns that error from the current function. The enclosing function must return a compatible error union, so the error travels up the call chain without a single status variable: 

const ok = try divide(10, 2);

If divide succeeds, ok is the quotient. If it fails, main returns the error immediately and the line after it never runs. try is the everyday spelling of "I cannot handle this here; pass it on".

catch |err|: handle it

catch is where the error stops. expr catch |err| fallback evaluates expr; on success the payload is yielded and the fallback is skipped; on error the tag is bound to err and the fallback is evaluated. The fallback can be an expression or a block, and the capture is optional: 

const bad = divide(1, 0) catch |err| {
    std.io.print("caught: DivideByZero\n");
    return;
};

The result type of a catch expression is the payload type of the operand, so the fallback must either produce that type or diverge. The block above diverges with return, which is why it can stand in for the i32 that divide would have produced. Inside the block, err is an ordinary value you can inspect, and the spec's own example compares it: 

const res = mightFail() catch |err| {
    if (err == error.Bad) return 0;
    return 1;
};

error.Tag: the error value itself

error.TagName is an error literal: an unqualified value of the tag, with no type name attached. You write it in a return, compare it with ==, and coerce it into any error union. The tag in return error.DivideByZero; and the tag in err == error.DivideByZero are the same value.

errdefer: undo on the error path

errdefer statement schedules code to run only when the scope exits with an error. It is the structured replacement for the goto cleanup tail: you put the undo next to the thing it undoes, and the compiler runs it when the error leaves the scope, in reverse order of declaration, and never on the success path. Braces are optional: 

fn check(a: i32, b: i32) MyError!i32 {
    errdefer std.io.print("errdefer ran\n");
    const v = try divide(a, b);
    return v;
}

If divide fails, try returns the error from check, and errdefer runs on the way out. If divide succeeds, errdefer is skipped. The same is true when the function returns the error itself: an explicit return error.Tag; is an error exit, so every errdefer in the scope runs before the error leaves the function: 

fn boom() error{Boom}!void {
    errdefer std.io.print("undo\n");
    return error.Boom;
}

Two errdefers in the same scope run innermost first, in reverse order of declaration. A dynamic error-union return is no exception: when return someErrorUnion; returns an error, the errdefer runs on the way out; when it returns success, the errdefer is skipped, just as for any other exit.

The defer/errdefer control-flow rule

A defer or errdefer body is not an ordinary block. It runs while the surrounding scope is being left, so it cannot itself redirect that exit. The compiler enforces the same rule for both, and the rule is scope-aware:

  • return anywhere in the body is rejected (error[3051]).
  • break or continue that leaves the body, targeting a loop or labeled block declared outside it, is rejected (error[3052] for break, error[3053] for continue).
  • try in the body is rejected (error[3054]): propagating an error from cleanup would replace the error already on its way out.

Control flow that stays inside the body is fine. A break or continue aimed at a loop or labeled block declared inside the body is allowed, and a continue can only target a loop.

Why orelse is not the tool

orelse looks like a natural fallback for an error union, and it is not. orelse belongs to optionals (?T): it fires when the value is null. An error union is never null; it carries an error tag, and the operation that handles a tag is catch. The compiler enforces the distinction. Asking orelse to handle an error union is rejected: 

error[3016]: orelse requires an optional operand; use 'catch' for error unions

So the rule is short: ?T takes orelse, E!T takes catch. Use the wrong one and the compiler tells you which is which.

Why there is no anyerror

Modern Zig has an anyerror type: one type that can hold any error tag. Z98 does not. anyerror is not in the token set, and naming it is a compile error, not a silently accepted type: 

error[3000]: unknown type in variable declaration

The reason is the same one that runs through the whole language: errors are declared, not erased. A function says in its signature which errors it can return, and the caller can see that list without reading the body. If you want to group tags, name a set; if you want "some error, unnamed", write the anonymous !T.

One rule you will meet early

An error union cannot be ignored. A statement whose result is an error union and is discarded is rejected, because dropping it would throw away the very thing the type exists to make visible: 

error[3015]: error union result is ignored; use 'try', 'catch', or assign the result

This is the compiler holding up its end of the bargain: if a function declares that it can fail, every call site has to say what it does about that.

The example

The whole chapter in one program. divide returns error{DivideByZero}!i32. The first call succeeds and try unwraps it; the second fails and catch reports it: 

const std = @import("std");

fn divide(a: i32, b: i32) error{DivideByZero}!i32 {
    if (b == 0) return error.DivideByZero;
    return a / b;
}

pub fn main() !void {
    const ok = try divide(10, 2);
    std.io.printInt(@intCast(i32, ok));
    std.io.print("\n");

    const bad = divide(1, 0) catch |err| {
        std.io.print("caught: DivideByZero\n");
        return;
    };
    std.io.printInt(@intCast(i32, bad));
    std.io.print("\n");
}

Build the compiler once from the committed seed, then emit and compile the program: 

bash scripts/seed/build_from_seed.sh release/seed/zig1-seed.tgz /tmp/manual_seed

That produces /tmp/manual_seed/zig1_5_clean with the standard library beside it in /tmp/manual_seed/lib/. Now translate the program to C89, build it, and run it: 

$ mkdir -p /tmp/manual_out
$ /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol2/error_unions.z98
$ cd /tmp/manual_out && sh build_target.sh linux error_unions
Building for linux...
Built: error_unions
$ ./error_unions
5
caught: DivideByZero

The first line of output is the successful division. The second is the catch block reporting the error from divide(1, 0). The program exits with status 0.
