Your First Useful Program

The last thirteen chapters taught the pieces one at a time: values and types, arithmetic, decisions, repetition, functions, structs, lists, and how to read a compiler complaint. This chapter puts the pieces together into something worth keeping: a line counter. The tool reads text and reports three numbers — the lines, the words, and the characters — the same three numbers the era's word-count utilities print. Every language feature it needs was introduced in chapters 6 through 12, plus one new spelling the chapter introduces: the character literal.

The tool lives beside the earlier examples, in docs/sf/manuals/src/vol1/wc.z98. Compile it with the compiler from chapter 4 and run it as shown below. One new idea carries the chapter: how a program reads input, instead of only writing output.

The program

const std = @import("std");

const END_OF_INPUT: u8 = 255;

const Counts = struct {
    lines: i32,
    words: i32,
    chars: i32,
};

fn isSpace(c: u8) bool {
    return c == ' ' or c == '\t' or c == '\r' or c == '\n';
}

fn countInput() Counts {
    var lines: i32 = 0;
    var words: i32 = 0;
    var chars: i32 = 0;
    var in_word: bool = false;
    var c: u8 = std.io.readByte();
    while (c != END_OF_INPUT) {
        chars = chars + 1;
        if (c == '\n') {
            lines = lines + 1;
        }
        if (isSpace(c)) {
            in_word = false;
        } else {
            if (!in_word) {
                words = words + 1;
                in_word = true;
            }
        }
        c = std.io.readByte();
    }
    return Counts{ .lines = lines, .words = words, .chars = chars };
}

pub fn main() void {
    const counts = countInput();
    std.io.print("lines: {}\n", .{counts.lines});
    std.io.print("words: {}\n", .{counts.words});
    std.io.print("chars: {}\n", .{counts.chars});
}

Read it once before the walk-through. The shape is already familiar: a counter or two, a loop that reads one byte at a time, an if that updates the counters, and a struct that carries the three totals back to main.

Where input comes from

Every program so far has only written. std.io.print sends its text to standard output, the stream the terminal shows (chapter 5). The other direction is standard input: a stream of bytes the machine feeds to the program, one byte at a time, in order. std.io.readByte() takes the next byte from that stream and answers it as a u8, the one-byte integer type from chapter 6. Each byte of text is one u8.

When the stream has no more bytes, readByte reports it with the value 255. That number did not arrive in the input; it is the reader's signal that the input is finished. The shipped readByte is a thin wrapper over the C library's character reader, whose end-of-file value is −1; stored in the u8 the function returns, it becomes 255. The program gives the signal a name — const END_OF_INPUT: u8 = 255; — so every loop that tests it says what it means.

Where does the file come in? The shell decides. The command line 

$ ./wc < sample.txt

runs wc, but before the program starts, the shell opens sample.txt and connects it to the program's standard input. The program is never told the name sample.txt; it sees a stream of bytes that happens to be the file's contents. The same tool can read another program's output through a pipe, as cat sample.txt | ./wc does. Output was always the terminal's stream; input is the same idea in the other direction.

A first read makes the idea concrete. A fragment with one read and one print: 

var c: u8 = std.io.readByte();
std.io.print("first byte is {}\n", .{c});

For the sample file used below, the first byte is the letter o, whose number is 111, so the fragment prints first byte is 111. The byte and the character are the same thing seen two ways: the machine stores characters as small numbers, and {} prints the number, exactly as in earlier chapters.

Counting the lines

The line counter is a while loop from chapter 9 with an if from chapter 8 inside it: 

var c: u8 = std.io.readByte();
while (c != END_OF_INPUT) {
    if (c == '\n') {
        lines = lines + 1;
    }
    c = std.io.readByte();
}

Three details are worth a second look. First, there are two reads. The read before the loop puts a real byte into c before the loop's first test, because a while tests before it runs the body. The read at the end of the body replaces that byte with the next one, so each pass consumes exactly one byte and the loop always moves forward. When that second read answers 255, the test fails and the loop stops.

Second, a line ends at the newline byte, and the character literal '\n' names it: one character between single quotes, using the same backslash escapes you have written inside strings. '\n' is the byte a text file writes at the end of a line, so counting those bytes counts the lines.

Third, lines is an i32 that starts at 0, the counter pattern from chapters 6 and 7. The count therefore grows by one for every newline the loop meets.

Counting the characters

The first line of the loop body is chars = chars + 1;, so every byte the tool reads is counted once. In this text one character is one byte, so that makes chars the character count. The newline at the end of every line is a character too and is included: the number describes the whole file, not only the letters you can see.

The read before the loop is not counted, because the body has not run yet; the end signal is not counted either, because the loop stops before its body would see it. Every real byte, and nothing else, is counted exactly once.

Counting the words

A word is a run of bytes that are not spaces. The tool names the separating bytes in a helper function, using chapter 10's functions, chapter 6's bool, and chapter 7's or: 

fn isSpace(c: u8) bool {
    return c == ' ' or c == '\t' or c == '\r' or c == '\n';
}

Four bytes separate words in ordinary text: the space (32), the tab (9), the carriage return (13), and the newline (10). The carriage return is the one that surprises people. Text saved by a Windows editor ends each line with two bytes, CR then LF, and a tool that forgets CR treats a byte that is not a letter as word material. Keeping it in the set costs one comparison and makes the tool read the same text the same way on both machines.

The word count itself needs one piece of memory that survives from byte to byte: in_word, a bool that remembers whether the previous byte was inside a word. The rule is short: a word begins at a byte that is not a space and was not already inside a word. 

if (isSpace(c)) {
    in_word = false;
} else {
    if (!in_word) {
        words = words + 1;
        in_word = true;
    }
}

A space ends any word that was open by clearing the flag. Anything else is word material; when the flag says no word is open, this byte is the first of a new word, so the count moves up by one and the flag is set. Counting at the first byte, rather than at the separator that follows, means a file whose last word has no newline after it still counts that word: the count happened when the word began, and no separator is needed to finish it.

Grouping the totals

Three counters travel together, which is a job for the structs of chapter 11: 

const Counts = struct {
    lines: i32,
    words: i32,
    chars: i32,
};

countInput reads the whole stream and returns one Counts value, so main stays short and the reading lives in one place: 

fn countInput() Counts {
    ...
    return Counts{ .lines = lines, .words = words, .chars = chars };
}

pub fn main() void {
    const counts = countInput();
    std.io.print("lines: {}\n", .{counts.lines});
    std.io.print("words: {}\n", .{counts.words});
    std.io.print("chars: {}\n", .{counts.chars});
}

The return type Counts is written after the parameter list, and the returned value is built with the field-by-name initialization from chapter 11. Chapter 10's rule that a value-returning function must answer on every path is satisfied because the loop can only end by falling through to the return. The three counters are local to countInput; once the function hands back the struct, they cannot be changed by anyone else, which is exactly what a report should do.

Building and running it

The commands are the ones from the last chapters, with wc in place of scores. The compiler is still at /tmp/manual_seed, built in chapter 4: 

$ mkdir -p /tmp/manual_out
$ /tmp/manual_seed/zig1_5_clean -o /tmp/manual_out docs/sf/manuals/src/vol1/wc.z98
$ cd /tmp/manual_out && sh build_target.sh linux wc
Building for linux...
Built: wc
$ cat > sample.txt <<'EOF'
one two three
four five
six
EOF
$ cat sample.txt
one two three
four five
six
$ ./wc < sample.txt
lines: 3
words: 6
chars: 28

The first two commands build the tool exactly as before. The cat command then writes a three-line sample file, and the second cat shows what went into it. The last command runs the tool with the file connected to its input.

Read the three answers against the sample. lines: 3 counts the three newline bytes, one after each line. words: 6 counts one two three four five six. chars: 28 counts every byte: 13 in one two three, plus its newline; 9 in four five, plus its newline; 3 in six, plus its newline. The pipe form reads the same bytes and prints the same answers: 

$ cat sample.txt | ./wc
lines: 3
words: 6
chars: 28

Running under Windows 98

The tool builds for Win9x exactly as hello, types, and the rest did: emit with -osw from chapter 3, then compile the emitted C with src/build_owc.bat or the emitted script's mingw target. Input redirection is a shell feature, not a Z98 feature, and the Windows 98 command prompt supports it too, so wc.exe < sample.txt reads the sample file and prints the same three lines. Common mistakes

The mistakes a first input-reading tool attracts are loop mistakes. Each one below is a loop that never ends, a tool that stops early, or a count that answers a slightly different question than the one you meant.

Forgetting to fetch the next byte. If the last line of the loop body — c = std.io.readByte(); — is deleted, c never changes. The loop tests the same byte on every pass, the counters grow on every pass, and nothing is ever printed. The rule the tool depends on is that every pass consumes exactly one byte and brings in the next; a loop with a read in its body but no second read cannot move.

Waiting for a zero byte. The end of input is not a zero byte. Zero is an ordinary byte that can appear in a file (and a condition such as c != 0 would stop early the moment one did), but the end of input is reported as 255. That makes c != 0 wrong twice over: it can stop on real data, and at the true end of the stream it is true forever, because readByte answers 255 on every call once the input is over. The end value is END_OF_INPUT; no other number means finished.

Expecting a last line with no newline to count. The counter counts newline bytes, so a file whose final line has no newline ends without one last increment. The input one\ntwo has one newline and one word that ends at the file's end, and the tool prints: 

$ ./wc < no_newline.txt
lines: 1
words: 2
chars: 7

A person looking at that file sees two lines; the tool reports the number of newline bytes, and so does the era's wc. If the last line must count, the file should end with a newline, the way text files normally do.

Leaving the carriage return out of isSpace. Text saved by a Windows editor ends each line with CR and LF. Remove c == '\r' from isSpace and the CR of a blank line becomes a word of its own. For the input a\r\n\r\nb\r\n — a word, a blank line, and a word — the tool then prints words: 3 instead of words: 2, because the blank line's CR counts as a word byte. This is the quiet kind of mistake: the program still builds, still runs, and is wrong only on files with a shape the test sample did not have.

Pointing the tool at a binary file. 255 is a legal byte, so a file that contains one stops the tool early. For an input that begins a\n and then holds byte 255 and more text, the tool prints lines: 1, words: 1, chars: 2, because byte 255 is the end signal. Text files are made of printable ASCII characters and line separators, so plain ASCII text never contains 255; a file in another encoding, or a binary file, can, and needs a different tool.

Check yourself

Answer these before moving on. The first four can be answered from the transcript and the source; the rest ask you to change the program and run it.

  1. Why does the sample's chars come to 28? Name the bytes that make up the count, line by line.
  2. Why does the program read one byte before the loop and one byte at the end of the loop body? What happens to the stream if the read at the end of the body is deleted? What would the loop's first test be examining if there were no read before the loop?
  3. What is the first byte of the sample file, as a number, and why is it 111?
  4. What does isSpace answer for '\r', and why does the word counter care about that byte at all?
  5. The tool counts a word when it meets the first non-space byte rather than when it meets the space that follows. What would a file ending in a word with no newline report if the count happened at the separator instead?
  6. Predict what the tool prints for a file whose content is exactly a\nb\nc — no newline at the end. Then make the file with printf 'a\nb\nc' > three.txt and run ./wc < three.txt. Was the prediction right?
  7. Extend the tool with a fourth counter, e_count, that counts every byte equal to 'e'. Add it to the Counts struct and print e: {} after the other three lines. What does the sample report?
  8. Change main so the three prints become one: std.io.print("{} {} {}\n", .{counts.lines, counts.words, counts.chars});. Rebuild and run. What prints, and why does the order of the tuple matter?
